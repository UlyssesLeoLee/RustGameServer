# 1. 前言

## 1.1 目的

本文档处理两类此前登记但未展开/未决议的空白：

1. **部署区域方针**：RGS-REQ-001§9.6已登记TBD-007（附件D ISS-007）——"单区域或多区域、是否需要跨境同步"待决议，本文档给出正式决议（ARC-034）
2. **数据分析管线**：RGS-REQ-008定义的可观测性（指标/日志/追踪）**目的是运维故障定位**（NFR-OP-001〜005），与**面向策划/运营的用户行为分析**（留存、付费转化、任务完成率等产品决策指标）是不同性质的读取模式与受众，此前从未被区分设计，容易被误用同一套基础设施（本文档新增ARC-035澄清边界）

## 1.2 判定原则（先声明）

- 本文档**不是**"新增多区域部署"的实现指南，而是**决议**当前应采用单区域还是多区域——决议结果见ARC-034，**结论是单区域优先**，理由见§8.1
- 数据分析管线**不重复采集**：复用既有事件基础设施（ARC-010）与Outbox机制产生的事件流作为数据源，**不要求**业务服务为分析目的新增专属埋点采集路径

## 1.3 关联文档

| 文档 | 关系 |
|---|---|
| RGS-REQ-001 | §9.6 NFR-EN-001、TBD-007；附件D ISS-007待决议对象 |
| RGS-REQ-008 | 既有可观测性范围声明与本文档ARC-035的边界区分对象 |
| RGS-REQ-010 | 零信任NetworkPolicy等安全边界，多区域场景下需联动评审（若未来触发） |
| RGS-BAS-007 | 备份恢复RTO既有标准，本文档§5容灾范围与其衔接 |

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 单区域（Single-Region） | 全部生产集群部署于同一云/数据中心区域 |
| 容灾（Disaster Recovery, DR） | 区域级故障（如整个数据中心不可用）时的业务连续性保证机制 |
| 数据分析管线（Analytics Pipeline） | 面向产品/运营决策的用户行为数据处理链路，区别于面向运维故障定位的可观测性 |

# 3. 背景与课题

| 课题编号 | 课题 |
|---|---|
| P-INF-001 | TBD-007（部署区域方针）自基准文档制定起长期未决议，导致集群拓扑与NFR-EN-005时刻同步设计缺少确定的前提条件 |

# 5. 功能需求：部署拓扑与容灾

| 编号 | 需求 |
|---|---|
| FR-INF-001 | 当前生产部署**必须**采用单区域拓扑（ARC-034决议），**不得**在OLU预算回正（附件D§5.3回收计划完成）前引入跨区域常驻基础设施 |
| FR-INF-002 | 单区域内**必须**采用多可用区（Multi-AZ，若云环境提供该能力）部署以应对单可用区级故障，**不构成**跨区域容灾，但**应当**是单区域拓扑下的最低容错要求 |
| FR-INF-003 | 数据库备份**必须**遵循RGS-BAS-007既定的备份恢复RTO标准，备份介质**必须**存储于与生产环境物理隔离的位置（即使单区域部署，备份存储也**不得**与生产数据同可用区/同磁盘阵列） |
| FR-INF-004 | 触发多区域评估的条件**必须**被明确列出（而非模糊的"未来需要时再说"），至少包含：①CCU规模超过既定阈值（具体值TBD-INF-001）②监管要求数据本地化③OLU预算经§5.3回收后有明确盈余可支撑新增运维面 |
| FR-INF-005 | 若未来条件触发多区域评估，**必须**先完成ARC-014既定的判定基准评审与ARC-026 OLU预算核算（同既有中间件导入纪律），**不得**绕过既定治理流程直接实施 |

# 6. 功能需求：数据分析管线

| 编号 | 需求 |
|---|---|
| FR-INF-010 | 数据分析管线**必须**复用既有ARC-010事件基础设施与Outbox机制产生的事件流作为数据源，**不得**要求业务服务为分析目的新增专属埋点采集代码路径 |
| FR-INF-011 | 分析管线的数据消费**必须**与可观测性（RGS-REQ-008）的数据消费物理隔离（不同的读取端点/不同的存储实例），**不得**让分析类查询（大范围扫描、聚合计算）与运维故障定位所需的低延迟查询共享同一存储实例，避免相互干扰 |
| FR-INF-012 | 分析管线**必须**提供运营/策划可自助访问的查询界面（复用开源BI工具，如既有RGS-BAS-004提及的Grafana生态或同类OSS方案，具体选型见TBD-INF-002），**不得**要求每次分析需求都由工程团队编写专属查询代码 |
| FR-INF-013 | 分析管线的数据**必须**允许滞后于实时事件流（同RGS-REQ-017 ARC-031"派生视图可容忍滞后"的同类思想），**不得**以牺牲主链路性能为代价换取分析数据的实时性 |
| FR-INF-014 | 分析管线**不得**成为个人隐私数据的额外泄露面：涉及玩家个人可识别信息的字段**必须**在进入分析管线前脱敏（复用RGS-BAS-004既有脱敏实现） |

# 8. 架构设计方针 ARC-034／ARC-035

## 8.1 ARC-034：部署区域方针——单区域优先（决议TBD-007/ISS-007）

| 项目 | 内容 |
|---|---|
| **决定** | 当前生产部署**采用单区域拓扑**（含Multi-AZ容错）。多区域部署**推迟**至FR-INF-004列出的触发条件之一满足，且经ARC-014/ARC-026既定治理流程评审通过后再实施 |
| **理由** | ①附件D§5.2台账显示当前OLU占用已超支-22，§5.3回收计划完成后余额也仅+2，几乎无冗余——多区域部署（跨区域数据同步、跨区域故障切换演练、双倍基础设施运维）的运维负荷远超当前预算承受能力，若强行引入将重演RSK-002②当前需求文档体系（NFR-PE-002等）尚未有确凿的、要求多区域低延迟接入的业务论证（如面向全球分布用户的强延迟敏感场景）③CON-002既定"避免依赖商业SaaS托管方案降低自建运维复杂度"的精神，同样适用于"避免过早引入自建运维复杂度更高的多区域架构"这一决定 |
| **对TBD-007的处置** | 本决定即为TBD-007的正式决议，ISS-007状态更新为"决议完毕" |
| **与ARC-014的关系** | 触发多区域评估时，须先满足ARC-014既定的判定基准评审（避免重复P-006"提前引入分布式中间件"的历史教训） |

## 8.2 ARC-035：数据分析管线与运维可观测性的读写分离

| 项目 | 内容 |
|---|---|
| **决定** | 数据分析管线**复用**既有事件基础设施作为数据源，但**物理隔离**其存储与查询端点，与运维可观测性（RGS-REQ-008，面向故障定位）**不共享**同一存储实例 |
| **理由** | 两者的查询模式截然不同（可观测性=低延迟、聚焦近期时间窗口；分析=大范围扫描、聚合计算、允许滞后），若共享存储实例，分析类查询的资源消耗会干扰故障定位所需的低延迟保证，这正是ARC-031"派生视图与权威数据源分离"思想在数据消费侧的又一次应用 |
| **与ARC-018的关系** | 分析管线的组件**依附**既有可观测性基础设施与事件基础设施运行，不新建独立限界上下文 |
