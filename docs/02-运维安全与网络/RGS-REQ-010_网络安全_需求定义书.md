# 1. 前言

## 1.1 目的

RGS-REQ-001第9章已定义单点级安全需求（NFR-SE-001服务器权威〜NFR-SE-012个人信息保护），但**尚未**系统性定义：①如何抵御边界外的网络层攻击（DDoS、扫描、暴力破解）②服务间是否应默认互信还是默认拒绝（零信任）③密钥/证书如何轮换而不产生人工操作窗口④依赖库/镜像的供应链完整性如何保证⑤安全事件发生后如何响应。本文档补齐这一"网络与基础设施纵深防御"层面，与既有NFR-SE-*系列共同构成完整的安全需求集。

## 1.2 适用范围

| 层面 | 说明 |
|---|---|
| 边界防护 | 公网到网关/API网关之间的攻击面（DDoS、恶意扫描、协议滥用） |
| 内部零信任网络 | 集群内服务间通信的默认信任模型（复用并推广RGS-BAS-002§5.3、RGS-BAS-003§4.4已用于个案的NetworkPolicy思路，本文档将其**升级为全局强制原则**） |
| 密钥与证书管理 | mTLS证书、数据库凭证、第三方API密钥的生成、分发、轮换、吊销 |
| 供应链安全 | 依赖库漏洞、容器镜像来源可信度、构建产物完整性 |
| 安全事件响应 | 检测到入侵/异常后的处置流程骨架（具体SOP细节属RGS-OPS-001） |

**不适用范围**：客户端侧反作弊具体实现（属X-004既有排除项）、具体渗透测试报告内容（属安全评审记录，非本文档）。

## 1.3 关联文档

| 文档编号 | 文档名 | 与本文档的关系 |
|---|---|---|
| RGS-REQ-001 | 需求定义书 | 本文档延展NFR-SE-001〜012、CON-001（OSI许可）、CON-002（不依赖付费SaaS） |
| RGS-BAS-002§5.3／RGS-BAS-003§4.4 | 既有NetworkPolicy个案设计 | 本文档ARC-022将其原则**推广为全局默认**，不改变两处既有具体设计 |
| RGS-REQ-007／BAS-003 | 运维与GM后台管控 | GM后台自身的接入安全（mTLS、RBAC）已在RGS-BAS-003设计，本文档补充其所处网络边界的防护 |
| RGS-BAS-006 | 网络安全 基本设计书 | 本文档的基本设计展开（本次同步制定） |

# 2. 术语约定

沿用RGS-REQ-002术语表。本文档新增：

| 术语 | 定义 |
|---|---|
| 零信任（Zero Trust） | "默认拒绝，显式允许"的网络信任模型：任意两个组件间的通信必须被显式声明为允许才可达，而非默认集群内网络互通 |
| 纵深防御（Defense in Depth） | 多层独立的安全控制叠加，使单一控制失效不直接导致整体失陷 |
| 供应链安全（Supply Chain Security） | 对依赖库、构建工具链、容器镜像来源的完整性与可信度的保证 |
| SBOM（Software Bill of Materials） | 软件物料清单，列出构建产物包含的全部依赖组件及版本 |
| 密钥轮换（Secret Rotation） | 定期或触发式地更换密钥/证书/凭证，缩短一旦泄露的可利用窗口 |

# 3. 背景与课题

| 编号 | 课题 |
|---|---|
| P-SEC-001 | 若集群内服务间网络默认互通（K8s默认行为），一旦任意一个Pod被攻破（如通过某依赖库漏洞），攻击者可横向移动访问全部其他服务，包括数据库，与RGS-BAS-002/003已针对个案设计的NetworkPolicy思路不一致（个案设计若不推广为默认原则，新增服务容易遗漏） |
| P-SEC-002 | 若密钥/证书轮换依赖人工操作，轮换往往被无限期推迟（"能用就不动"），一旦密钥泄露，暴露窗口可能长达数月 |
| P-SEC-003 | 依赖库供应链攻击（恶意包、被劫持的维护者账号）是现实存在的攻击面，若无自动化检查，一次`cargo`依赖更新可能引入恶意代码而不被察觉 |
| P-SEC-004 | 若无预先定义的安全事件响应流程，真正发生入侵时team会在"该联系谁、该先做什么"上浪费宝贵的响应时间，扩大损失 |
| P-SEC-005 | 游戏服务器是DDoS攻击的高频目标（尤其QUIC/UDP路径），若无边界防护，NFR-AV-*系列可用性目标可被外部攻击轻易击穿，与工程侧的可用性设计投入不成比例地失效 |

# 4. 业务需求

| ID | 需求 | 优先级 |
|---|---|---|
| BR-SEC-001 | 系统须能抵御常见的网络层攻击（DDoS、扫描），使NFR-AV-*系列可用性目标不因外部攻击而失效 | 高 |
| BR-SEC-002 | 单点组件被攻破**不得**导致攻击者可直接横向访问核心业务数据库 | 高 |
| BR-SEC-003 | 密钥泄露的可利用窗口须被主动控制在可接受范围内，而非依赖"永不泄露"的假设 | 高 |
| BR-SEC-004 | 安全事件发生时，团队须有预先定义、可执行的响应流程 | 中 |

# 5. 功能需求

## 5.1 边界防护

| ID | 需求 |
|---|---|
| FR-SEC-001 | 公网入口（网关QUIC端口、API网关HTTPS端口）**必须**部署DDoS防护（L3/L4层），具体实现（云服务商防护/自建）依ARC-014判定基准评审 |
| FR-SEC-002 | API网关（HTTPS路径）**必须**部署Web应用防火墙（WAF）或等价的应用层攻击过滤能力，覆盖常见注入/异常请求模式 |
| FR-SEC-003 | 边界防护**不得**替代NFR-SE-006既有的应用层输入校验，两者是不同层级的纵深防御，**必须**同时具备 |

## 5.2 内部零信任网络

| ID | 需求 |
|---|---|
| FR-SEC-010 | 集群内**全部**服务间通信**必须**默认拒绝，仅显式声明的依赖关系可通信（复用并推广RGS-BAS-002§5.3、RGS-BAS-003§4.4已用于个案的NetworkPolicy机制，升级为**全局默认**——新增任意服务时NetworkPolicy的"默认拒绝"须由标准化脚手架自动生成，而非事后补充） |
| FR-SEC-011 | 服务间通信**必须**保持既有mTLS（NFR-SE-003），零信任网络策略与mTLS是**互补**关系（网络层"谁能连谁"与传输层"连接双方身份互证"），两者缺一不可 |
| FR-SEC-012 | 数据库访问**必须**仅限其所属限界上下文的服务可达（同RGS-BAS-002§5.3既有约束，本条将其确认为全局强制原则而非个案） |

## 5.3 密钥与证书管理

| ID | 需求 |
|---|---|
| FR-SEC-020 | mTLS证书**必须**支持自动轮换，**不得**依赖人工定期更换（复用RGS-BAS-001§7.3既有"证书由K8s证书管理机制自动轮换"决定，本文档确认并扩展至全部密钥类别） |
| FR-SEC-021 | 数据库凭证、第三方API密钥**必须**存储于K8s Secret或等价的密钥管理机制，**不得**硬编码于代码/镜像/配置文件（复用既有NFR-SE-009），且**应当**支持定期轮换 |
| FR-SEC-022 | 密钥轮换**不得**要求服务重启/停机（同插件热插拔RGS-REQ-009"tick边界原子切换"的同类思路：新旧密钥并存的过渡窗口） |

## 5.4 供应链安全

| ID | 需求 |
|---|---|
| FR-SEC-030 | 依赖库漏洞扫描**必须**纳入CI（复用既有NFR-SE-011），扫描范围覆盖直接与传递依赖 |
| FR-SEC-031 | 容器镜像构建**必须**产出SBOM，且**应当**验证基础镜像来源可信（如仅使用官方/内部审核过的基础镜像） |
| FR-SEC-032 | 生产环境部署的镜像**必须**可追溯至具体的构建流水线执行记录与源码提交（构建溯源，Build Provenance），**不得**允许未经CI构建的镜像直接部署至生产环境 |

## 5.5 安全事件响应

| ID | 需求 |
|---|---|
| FR-SEC-040 | 系统**必须**具备安全相关的可观测性埋点（异常登录模式、异常API调用频率、异常权限提升尝试），复用RGS-BAS-004埋点体系，作为入侵检测的数据来源 |
| FR-SEC-041 | 检测到高置信度的安全事件**必须**通过既有告警推送通道（RGS-BAS-003§6）触发告警，响应流程骨架见RGS-BAS-006，具体人工SOP属RGS-OPS-001 |
| FR-SEC-042 | 安全事件的处置**必须**产生审计记录（复用RGS-BAS-003§7审计设计），用于事后复盘 |

## 5.6 认证后滥用与崩溃防护（本次新增，补齐"防攻击防崩溃"完整闭环）

> **背景**：§5.1〜§5.5覆盖了网络边界（DDoS/WAF）、集群内部（零信任）、密钥、供应链、事件响应五个维度，但均以"抵御未授权/外部攻击者"为出发点。本节补齐两类此前从未系统定义的攻击面：①**已通过认证的合法连接**发送畸形/病态数据导致进程崩溃（区别于网络层DDoS，无法被边界防护拦截，因为流量本身"合法"地完成了握手）②**已认证账号**利用游戏内正常API发起高频/高代价操作，造成单节点过载（区别于IP级DDoS，因为请求来自单一已登录账号而非海量匿名连接）。此前散落在RGS-BAS-001（panic监督恢复）、RGS-BAS-005（插件panic隔离）、RGS-BAS-008（FFI panic捕获）的实践都只解决"崩溃后如何恢复"，从未有需求明确"输入解析本身不得引发崩溃"这一更早、更根本的防线；同时`NFR-SEC-008`（多层限流标准）此前已被RGS-BAS-019/RGS-BAS-023/RGS-REQ-026三处文档以"既有"名义引用，但从未在本文档实际定义，是一处断裂的引用，本节一并补齐。

| ID | 需求 |
|---|---|
| FR-SEC-050 | 全部**面向未信任网络输入**的反序列化/解析路径（客户端QUIC消息、API网关HTTP请求体）**必须**基于`Result`返回错误而非依赖可能触发panic的操作（如数组越界索引、整数溢出未检查运算、对`Option`/`Result`的裸`unwrap`/`expect`），解析失败**必须**作为一条可预期的错误路径处理（丢弃该请求/断开该连接），**不得**导致所在Tokio task/进程崩溃。**不适用**于内部可信数据（如自身数据库读出的记录，其格式由自身写入路径保证，非本条约束对象——本条**仅**针对跨越信任边界的输入） |
| FR-SEC-051 | 系统**必须**具备**多层速率限制**：①单连接级（复用ARC-013既有背压设置点）②**账号级**（同一`player_id`跨连接/跨请求类型的累计频率，防止已登录账号短时间内对同一/不同API发起海量请求）③IP级（复用§5.1边界防护，防匿名/批量注册账号发起的分布式滥用）。三层**独立**生效，**不得**以其中一层替代另一层——单连接限流防不住"多连接同账号"，账号级限流防不住"单连接内海量不同账号"（如网关代理场景），IP级限流防不住"单IP多账号"，三者组合才是完整覆盖 |
| FR-SEC-052 | 游戏内可由玩家触发、且会消耗服务器计算/存储资源的操作（如物品创建、场景实体生成、好友/公会成员增加等）**必须**有服务器侧强制配额上限，配额校验**必须**在既有服务器权威路径内完成（复用ARC-005单一写入者原则），**不得**依赖客户端自行遵守配额——即便是"设计上不应超过某数量"的正常玩法，服务器**仍须**做硬性上限校验，防止漏洞/篡改客户端导致资源无界增长压垮服务器（区别于RGS-REQ-028反作弊体系针对的"作弊获得不公平优势"，本条针对的是"合法接口被滥用导致过载"，二者信号来源不同但可复用同一套服务器权威校验基础设施） |
| FR-SEC-053 | 网关QUIC端口**必须**启用协议既有的地址验证机制（Address Validation / Retry，QUIC协议标准能力），在完成握手前**不得**为未验证来源地址的连接分配可观测的服务器资源（防止UDP反射/放大攻击将本系统作为攻击跳板，或消耗网关资源处理大量伪造源地址的握手请求） |
| FR-SEC-054 | 场景Actor的崩溃重启**必须**复用既有崩溃循环退避机制（RGS-BAS-010 G-013既定的指数退避），本条**不新增**机制，仅确认该机制同样适用于"由恶意构造输入触发的持续性崩溃"这一场景（而不仅是"随机偶发故障"场景），是FR-SEC-050的最后一道纵深防线：即便FR-SEC-050的解析安全设计百密一疏，退避机制也能防止单一恶意输入造成持续性的崩溃循环资源浪费 |

# 6. 非功能需求

| ID | 类别 | 内容 | 目标值/判定基准 |
|---|---|---|---|
| NFR-SEC-001 | 可用性（安全维度） | DDoS防护生效后，正常玩家流量的可用性影响 | 误杀率<0.1%（依边界防护方案实测校准） |
| NFR-SEC-002 | 密钥轮换周期 | mTLS证书、数据库凭证、第三方API密钥的最长轮换周期 | 证书≤90天，数据库凭证≤180天，第三方API密钥依供应商能力尽量缩短，初始值详细设计确定 |
| NFR-SEC-003 | 漏洞响应 | 复用既有NFR-SE-011（High以上14天内应对），本文档补充：Critical级别须<72小时应对 | CI持续检查+响应时限追踪 |
| NFR-SEC-004 | 零信任覆盖率 | 集群内服务间NetworkPolicy覆盖率 | 100%（新服务由脚手架强制生成，不存在"裸奔"服务，验收见AC-SEC-002） |
| NFR-SEC-005 | 事件响应时间 | 高置信度安全事件从检测到触发告警的时延 | 复用RGS-REQ-007 NFR-OPS-002同等量级（p99<30秒） |
| NFR-SEC-006 | 崩溃安全（解析路径） | 未信任输入解析路径（FR-SEC-050）在模糊测试（Fuzzing）下的panic发生率 | 0（任何一例由模糊测试发现的panic均视为需修复的缺陷，纳入CI持续回归而非一次性验收） |
| NFR-SEC-007 | 账号级限流触发后的正常玩家影响 | 账号级速率限制（FR-SEC-051）生效阈值下，正常游玩行为触发限流的比例 | <0.1%（阈值须显著高于正常玩法的最大合理请求频率，依PH-4实测数据校准，同NFR-SEC-001误杀率同类判定精神） |
| NFR-SEC-008 | **多层速率限制标准**（此前被RGS-BAS-019/RGS-BAS-023/RGS-REQ-026三处文档引用为"既有"但从未实际定义，本次补齐定义，处置断裂引用） | FR-SEC-051三层限流的具体判定基准 | 连接级：复用RGS-BAS-001§7.2.1既有背压参数（可配置，初始值详细设计给出）；账号级：滑动窗口计数，具体阈值TBD-SEC-003确定；IP级：复用§5.1边界防护既有DDoS/WAF方案的内建限流能力，不重复实现 |
| NFR-SEC-009 | 资源配额校验开销 | FR-SEC-052服务器侧配额校验对既有请求处理路径的额外时延 | 配额校验**必须**是O(1)或O(log n)复杂度的简单计数比较（如"当前数量+1 ≤ 上限"），**不得**引入需要遍历/聚合计算的校验逻辑，确保配额校验本身不成为新的性能瓶颈 |

# 7. 架构设计方针 ARC-022

本节为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接RGS-REQ-009新增的ARC-021。**决定事项**，变更须经ADR与审批。

## 7.1 ARC-022：零信任内部网络与纵深防御体系（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | 集群内网络策略**必须**采用"默认拒绝，显式允许"的零信任模型，作为**全局强制原则**（而非仅在RGS-BAS-002/003个别场景实施）；该原则**必须**通过标准化脚手架（RGS-BAS-002§4）自动生成基线NetworkPolicy落地，新增任意服务**不得**以"暂缓补充网络策略"为由跳过 |
| **理由** | RGS-BAS-002§5.3、RGS-BAS-003§4.4已分别针对"新挂载App"与"运行时受限控制通道"两个场景实施了默认拒绝的NetworkPolicy，证明该模式技术可行且必要。若不将其确立为全局原则，后续新增服务/新增路径容易因"个案未覆盖"而遗漏，形成横向移动的攻击面 |
| **与既有mTLS的关系** | 零信任网络策略解决"谁能连谁"（网络层可达性），mTLS（NFR-SE-003既有决定）解决"连接双方是否可信"（传输层身份互证）。两者是正交的纵深防御层，**不得**以一层替代另一层 |
| **供应链纵深防御** | 依赖漏洞扫描（既有NFR-SE-011）与本文档新增的SBOM/构建溯源（FR-SEC-031/032）共同构成供应链维度的纵深防御，理由同插件体系ARC-021已识别的"不受信代码执行"风险——供应链攻击是另一条注入不受信代码的路径，需要独立的防线 |
| **否决方案** | "仅在网关/API网关做边界防护，集群内网络保持互通以简化运维"——一旦边界被突破或内部凭证泄露，互通网络会让攻击者获得远超预期的横向移动能力，与NFR-OP-010运维负荷上限之间的权衡不能以牺牲纵深防御为代价，已否决 |
| **适用范围** | 本系统全部集群内组件，含RGS-REQ-006挂载的新限界上下文、RGS-REQ-009的插件体系宿主服务 |

# 8. 验收标准

| ID | 验收标准 |
|---|---|
| AC-SEC-001 | 模拟DDoS流量注入试验，验证正常玩家连接的可用性影响满足NFR-SEC-001 |
| AC-SEC-002 | 对集群内全部服务做NetworkPolicy覆盖率审计，确认100%覆盖（NFR-SEC-004），不存在默认允许全部流量的服务 |

| AC-SEC-004 | CI流水线对已知漏洞依赖（人为注入的测试用例）能正确拦截，且Critical级别触发的响应时限符合NFR-SEC-003 |
| AC-SEC-005 | 安全事件模拟演练（如异常权限提升尝试）触发告警的时延满足NFR-SEC-005 |
| AC-SEC-006 | 对全部未信任输入解析路径运行模糊测试（Fuzzing）套件，持续N小时（具体值详细设计确定）无panic产生（FR-SEC-050、NFR-SEC-006） |
| AC-SEC-007 | 模拟同一账号短时间内对同一API发起海量请求，验证账号级限流生效且不影响其他账号的正常请求（FR-SEC-051） |
| AC-SEC-008 | 模拟绕过客户端直接调用服务端接口批量创建游戏对象（物品/实体），验证服务器侧配额上限生效且返回明确拒绝而非无界接受（FR-SEC-052） |
