# 1. 前言

## 1.1 目的与范围边界

RGS-REQ-019定义的支付对账（FR-SUP-010〜015）以"支付服务商侧记录"为对账权威来源，但未区分**平台内购**（App Store／Google Play，玩家在平台侧完成支付，平台侧持有交易凭证/收据，游戏服务器须主动向平台校验收据合法性）与**直连支付**（游戏内接入第三方支付网关，服务器直接持有交易回调）这两种截然不同的支付路径。本文档补齐平台内购特有的收据校验环节。

同时，RGS-REQ-016（大厅、社交通信与运营活动）在其§1.1范围声明中明确"玩家在完成鉴权后进入大厅"，但**鉴权成功之后、进入大厅之前**——玩家如何选择要进入哪一个游戏世界/大区/服务器——从未被设计。若游戏采用多服/分区运营模式（常见于MMO品类），选服与后续的合服/分服运维流程是必需能力。

## 1.2 判定原则（先声明，避免与既有模块混淆）

- 平台内购收据校验**不改变**RGS-REQ-019已确立的"支付对账最终裁定源"原则（ARC-033），只是为"支付服务商"这一角色在平台内购场景下补充"如何向平台验证收据"的具体机制
- 选服/合服**不新建**独立限界上下文，复用既有玩家（PL）/运维（AD）限界上下文；合服/分服的执行流程**复用**ARC-018既定的挂载/退场判定原则（服区的新增与下线本质上是"新Atomic App接入/退场"的同类问题）

## 1.3 关联文档

| 文档 | 关系 |
|---|---|
| RGS-REQ-019 | ARC-033支付对账最终裁定源原则，本文档为平台内购场景的具体化 |

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 收据（Receipt） | 平台（App Store/Google Play）为一笔内购交易签发的、可被服务器验证真伪的凭证 |
| 逻辑服（Realm/Server） | 玩家数据相互隔离的独立游戏世界实例，多个逻辑服可能共享底层基础设施 |
| 合服 | 将两个或以上逻辑服的玩家数据合并至同一逻辑服的运维操作 |

# 3. 背景与课题

| 课题编号 | 课题 |
|---|---|
| P-PLT-001 | 若不做平台侧收据校验、仅信任客户端上报"支付成功"，攻击者可伪造支付成功请求骗取内购权益 |
| P-PLT-002 | 平台侧退款/撤销通知（如Apple的App Store Server Notifications）若未接入，玩家通过平台申请退款后，游戏内权益不会被追回，形成"退款后仍保留权益"的漏洞 |
| P-PLT-003 | 多服运营模式下，选服环节缺失会导致玩家无法determinate地进入预期的游戏世界，新玩家分流、老玩家回归指定服等运营诉求无法实现 |
| P-PLT-004 | 合服操作若无标准流程，容易在数据合并阶段产生同名角色冲突、货币/道具重复或丢失等严重事故 |

# 5. 功能需求：平台内购收据校验

| 编号 | 需求 |
|---|---|
| FR-PLT-001 | 客户端完成平台内购后，**必须**将收据提交至服务器，服务器**必须**向对应平台（App Store／Google Play）的官方验证接口校验收据合法性，**不得**仅凭客户端上报的"购买成功"状态发放权益 |
| FR-PLT-002 | 收据校验成功后的权益发放**必须**复用既有FR-EC-003确定请求路径，且**必须**以收据的唯一交易标识作为幂等键，**不得**对同一笔交易重复发放 |
| FR-PLT-003 | 系统**必须**接入平台侧的退款/撤销异步通知（如App Store Server Notifications／Google Play RTDN），收到退款通知后**必须**触发既有权益的追回或标记流程（具体追回方式因权益类型而异，留待TBD-PLT-001评审） |
| FR-PLT-004 | 收据校验失败（签名无效/已被使用/环境不匹配沙盒与生产）**必须**被拒绝并留痕（复用RGS-BAS-003§7审计设计），作为支付欺诈排查依据 |
| FR-PLT-005 | 平台内购与RGS-REQ-019既有的直连支付对账**必须**共享同一套`PaymentOrder`数据模型（复用RGS-BAS-016§3.1既有结构），**不得**为平台内购单独建一套支付记录体系 |

# 6. 功能需求：服务器列表与选服

| 编号 | 需求 |
|---|---|
| FR-PLT-010 | 系统**必须**支持向客户端返回可选逻辑服列表，列表**应当**包含服务器状态（正常/爆满/维护中）供玩家参考 |
| FR-PLT-011 | 新账号首次选服后，**应当**将该服记为其"主服"，后续登录**必须**默认路由至主服，**不得**要求玩家每次登录都重新选服 |
| FR-PLT-012 | 若采用多服架构，账号数据**必须**按逻辑服隔离（不同逻辑服的同一账号可有独立的角色/进度），选服**必须**在鉴权成功后、进入大厅前完成（FR-GW-002既有鉴权流程之后新增的路由环节） |
| FR-PLT-013 | 服务器状态（正常/爆满/维护中）**必须**由GM后台运维配置驱动（复用既有RGS-BAS-003维护模式传播机制），**不得**硬编码 |

# 7. 功能需求：合服与分服

| 编号 | 需求 |
|---|---|
| FR-PLT-020 | 合服操作**必须**复用ARC-018既定的挂载/退场判定原则：被合并服的下线视为"退场"流程，目标服的数据合并视为一次性数据迁移作业，**不得**绕过既有变更管理流程直接执行 |
| FR-PLT-021 | 合服时的数据冲突（如同名角色、重复的唯一性道具）**必须**有明确的解决规则（如角色改名、道具数量累加），规则**必须**在合服前与运营团队评审确定并配置化，**不得**由执行人员临时决定 |
| FR-PLT-022 | 合服操作**必须**支持在维护窗口内以只读演练模式先行验证（同RGS-BAS-007既定的数据库迁移Expand-Contract纪律的同类应用），确认无异常后再执行正式合并 |
| FR-PLT-023 | 合服/分服过程**必须**留痕（复用RGS-BAS-003§7审计设计），过程中**不得**产生玩家资产的丢失或重复 |

# 9. 架构设计方针 ARC-038

## 9.1 ARC-038：平台收据的权威来源与服区边界的原子迁移（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | ①平台内购的权威事实来源是**平台官方验证接口的返回结果**，不是客户端声明，也不是游戏服务器自行推断——这是RGS-REQ-019 ARC-033"支付对账以服务商侧记录为最终裁定源"原则在平台内购场景下的具体化②合服/分服**必须**复用ARC-018挂载/退场原则处理，且**必须**先经只读演练验证，**不得**跳过演练直接执行正式合并 |
| **理由** | ①与其他支付/发放场景一致的"权威来源不由自身推断"原则，是防止支付欺诈的结构性保证②合服涉及不可逆的数据合并操作，历史上是游戏行业事故高发环节（同名角色冲突、道具复制/丢失），演练验证是把该风险从"生产环境试错"前移至"演练环境验证"的标准做法 |
| **与ARC-018的关系** | 选服/合服/分服组件**依附**既有PL/AD限界上下文运行，**不新建**独立限界上下文；合服/分服流程**复用**ARC-018既定的变更管理纪律，而非新建一套独立的服区管理流程 |

# 10. 验收标准

| 编号 | 内容 |
|---|---|
| AC-PLT-001 | 伪造收据拒绝测试：提交未经平台签发的伪造收据，验证权益不被发放 |
| AC-PLT-002 | 收据幂等测试：同一收据交易标识重复提交，验证不重复发放 |
| AC-PLT-003 | 退款追回测试：模拟平台退款通知，验证对应权益被追回或标记 |
| AC-PLT-004 | 合服演练验证：在演练环境执行合服流程，验证数据冲突规则生效且资产总量前后一致 |
