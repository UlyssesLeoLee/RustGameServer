## 1. 前言

负责人指示"核心游戏逻辑应该考虑速度和断线重传，主要使用KCP协议，其他周边功能根据性质使用TCP/UDP"，后续补充指示"前项纠错等防止丢包的技术也要在KCP需求文档中体现，如果现在有新技术出现，也要用更新的设计"。

本文档将该指示拆解为两个独立问题处理：

1. **是否应将核心传输协议由QUIC整体改为KCP** —— 详见§4，结论为**否**，理由是KCP与QUIC同属"可靠传输之上再谈实时性"的工程谱系，而ARC-003已经用QUIC的双路径能力（可靠Stream＋不可靠Datagram）解决了KCP试图解决的问题，整体改用KCP会重新引入ARC-003已规避的"重传导致状态陈旧"问题。
2. **是否应采纳KCP技术谱系中的"前向纠错（FEC）防丢包"技术** —— 详见§5、§9，结论为**是**，作为ARC-003不可靠Datagram路径的增强层，新增ARC-047。

周边功能（登录、商店、GM运营、可观测性等）的协议选型并非本次指示的空白点——RGS-REQ-001 §5.2已逐项定义（IF-001〜IF-008），本文档§7仅作现状汇总确认，不引入新决定。

## 2. 术语约定

| 术语 | 定义 |
|---|---|
| ARQ（Automatic Repeat reQuest） | 基于确认与重传的可靠传输机制，KCP与QUIC Stream均属此类 |
| FEC（Forward Error Correction，前向纠错） | 发送端附加冗余数据，接收端无需重传即可恢复部分丢失数据的技术 |
| 块式Reed-Solomon FEC | KCP默认FEC实现方式：按固定块大小分组编码，解码延迟随块大小增长 |
| Datagram路径 | ARC-003定义的QUIC不可靠子路径（RFC 9221），用于高频状态同步 |
| Stream路径 | ARC-003定义的QUIC可靠子路径，用于必达事件 |

## 3. 背景与课题

- RGS-REQ-001 §10.4 ARC-003已裁定核心传输采用QUIC，并明确拒绝"整体TCP+TLS1.3"方案，理由是可靠路径上的重传会延迟后续状态、用陈旧数据加剧NFR-PE-004（输入→ACK p99<100ms）的达成难度。
- 附件D ISS-006/REQ-001 TBD-006登记的问题是"QUIC发送节奏・拥塞控制的调整方针"，长期"未着手"，未细分"丢包恢复"与"拥塞节奏"两个子问题。
- 负责人指示要求评估KCP协议及"更新的防丢包技术"，本文档需要在**不反转ARC-003**的前提下回应该指示。

## 4. 判定：为什么不是"整体改用KCP协议"

ARC-003（REQ-001 §10.4）原文的拒绝理由是：

> 可靠路径上的重传会延迟后续状态的送达，导致用陈旧数据覆盖新数据，加剧NFR-PE-004（输入→ACK的p99<100ms）的达成难度。

KCP本质上是**用户态实现的ARQ协议**——通过更激进的重传/ACK策略换取比原生TCP更低的延迟，但其核心机制仍是"丢包→重传→等待"。若将核心传输整体替换为KCP：

1. 高频状态同步一旦运行在KCP单一可靠连接之上，某个数据包的重传等待会阻塞该连接后续所有数据的送达（队头阻塞），这正是ARC-003原文所拒绝的"重传延迟后续状态"问题，只是从TCP搬到了KCP，并未消除。
2. KCP默认不区分"必达事件"与"可丢弃即覆盖的高频状态"，需要应用层自行在单一连接上模拟ARC-003已经用QUIC双路径原生解决的区分，属于重新发明已有能力。
3. ARC-003的QUIC方案已同时具备：Stream路径的可靠传输（不弱于KCP的ARQ能力）与Datagram路径的不可靠传输（KCP不具备的原生能力）。整体改用KCP在能力上是**子集替换超集**。

**结论**：整体改用KCP协议对本项目属于技术倒退，不予采纳。ARC-003保持不变。

负责人指示中的"防丢包/纠错技术"诉求，转化为在ARC-003既有Datagram不可靠路径之上**新增FEC编解码层**（§9 ARC-047），而非替换传输协议本身。

## 5. 功能需求：核心传输防丢包强化（FEC）

| ID | 需求 |
|---|---|
| FR-NET-001 | 高频状态同步（IF-001-1，QUIC Datagram路径）**必须**新增FEC编解码层，用于在不触发重传的前提下恢复部分丢失的Datagram；FEC解码失败时**必须**静默丢弃并等待下一帧覆盖，**不得**触发任何形式的重传或阻塞后续帧 |
| FR-NET-002 | FEC实现**不得**采用KCP默认的块式Reed-Solomon方案（解码延迟随块大小增长）；**必须**采用解码延迟与块大小无关（或近似常数）的设计，例如逐包异或校验（XOR parity）等轻量方案 |
| FR-NET-003 | FEC冗余开销**必须**落在既有NFR-PE-006带宽预算内，且**应当**根据实测丢包率动态调整冗余率（丢包率低时降低冗余，减少带宽浪费） |
| FR-NET-004 | FEC具体编解码库/实现方式待定（TBD-NET-001）。**不得**在未经ARC-014中间件导入判定的前提下默认采用`libkcp`或任何第三方crate（含`fastnet`，见§11 TBD-NET-001） |

## 6. 功能需求：可靠事件路径与断线重连（现状确认，非新设计）

| ID | 需求 |
|---|---|
| FR-NET-005 | 断线重连**继续**沿用FR-GW-005（重连・重绑定）与`session_epoch`机制，不因本文档而变更；现状已满足NFR-PE-007（重连恢复p99<3s） |
| FR-NET-006 | 必达事件（IF-001-2）**继续**通过QUIC Stream路径传输，不变更为KCP连接；QUIC多路Stream原生避免跨Stream队头阻塞，技术上优于单一KCP-ARQ连接上模拟多优先级事件 |

## 9. 架构设计方针 ARC-047：QUIC Datagram路径FEC编解码层

| 项目 | 内容 |
|---|---|
| 方针 | 在ARC-003既有QUIC不可靠Datagram路径之上新增FEC编解码层，用于在不引入重传的前提下恢复部分丢失数据包 |
| 判定基准（附件D§3开头三条件判定基准，非ARC-014中间件导入判定——ARC-014另见FR-NET-004） | ①当时确有具体可辩护的替代方案（整体改用KCP协议；KCP默认块式Reed-Solomon FEC）②采纳会实质改变架构（若整体改用KCP将反转ARC-003的传输协议选择）③否决理由并非"需求就是这么要求的"，而是可论证的解码延迟/NFR-PE-004带宽预算论证。三条件同时成立，**本方针须制定正式ADR**（见附件D§3 ADR-0047），不适用"决策显然"简化路径 |
| 否决方案1 | 整体改用KCP协议替代QUIC。否决理由：KCP本质ARQ，会重新引入ARC-003已规避的"重传延迟后续状态"问题，详见§4 |
| 否决方案2 | 直接复用KCP默认的块式Reed-Solomon FEC。否决理由：解码延迟随块大小增长，在50ms tick预算下不可控，违反NFR-NET-001的设计意图（详见FR-NET-002） |
| 候选实现 | ①自研单包级XOR异或校验FEC（无第三方依赖，解码延迟与块大小无关）②评估`fastnet` crate（Rust，2025-11-29创建，最新0.3.1版本2026-02-12发布，总下载量618，单一维护者Filipe Freitas，MIT许可，早期0.1.0〜0.1.5为"MIT OR Apache-2.0"，仓库github.com/filipe-freitas-dev/fastnet；crates.io自述"Ultra-low latency encrypted networking for real-time games. TLS 1.3 + ChaCha20-Poly1305 with ~15µs RTT"，**未提及**FEC/BBR/增量压缩等能力，此类描述若来自其他渠道**须视为未经crates.io权威信息验证的自我宣称，不得作为采纳依据**）。两者均须经ARC-014判定，`fastnet`额外须满足RSK-NET-001的成熟度复核 |
| 不变更范围 | ARC-003可靠Stream路径**不变更**；不引入ARQ式重传逻辑；不反转ARC-003的QUIC传输协议选择 |
