# 1. 前言

## 1.1 目的

RGS-REQ-001 NFR-AV-008 与 NFR-PE-002/019 既有容量目标（10万CCU）下，单服 / 少量服的"日常运维"覆盖了大部分运营场景。但**当业务跨越 T1 → T2 → T3 容量级别**（RGS-REQ-025 §5），或**当某服进入运营末期**（玩家流失、合服窗口、版本下线），**或当运营需要新开服承载大版本首发流量**时，**整条"服务器从无到有再到消亡"的端到端流程**是当前语料库的明显缺口：

| 阶段 | 现状 | 缺口 |
|---|---|---|
| 开新服 | BAS-022 §3.3 一句话引用 ARC-018 | **无运营 SOP**——资源评估、容量门禁、路由登记、灰度开放、玩家通知、演练剧本均无设计 |
| 扩缩容 | BAS-017 / BAS-022 既有 HPA 设计 | 既有覆盖节点级自动扩缩，但**不覆盖**"整服水平扩缩"（如把单服拆为 2 服部署形态） |
| 分服 | RGS-REQ-023 §7 FR-PLT-020~023 简述为"合服的逆向" | **误将分服等同于合服逆向**——分服是数据归属重写 + 玩家分流 + 跨服关系保持，与合服的"数据合并"在操作语义上完全不同 |
| 合服 | BAS-020 §4 五步流程较完整 | 既有设计较完整，**本文档对其作纵向延伸**（接续退场与归档，不重复 BAS-020 §4 既有内容） |
| 退场 | ARC-018 退场原则 | **将退场等同于删除**——未设计"退场后归档"的数据保留路径，玩家历史数据 / 客服查询 / 监管取证均无支撑 |
| 归档 | 无 | **完全空白**——RGS-REQ-005 附件 D「问题风险管理表」明确保留"退场后数据如何处理"为后续补强项 |

本文档补齐这一整条 6 阶段生命周期，作为面向**运营 + SRE + DBA + 合规**多方协作的统一视图。

## 1.2 核心设计约束（贯穿全文档）

- **本文档不重新设计挂载 / 退场判定**——ARC-018 既有挂载/退场原则是技术底座，本文档**复用**为"新分片接入"与"分片下线"的技术判定
- **本文档不重新设计容量分级**——ARC-040 既有 T0~T3 四级与触发门禁是容量维度决策，本文档**承接**为"何时需要开新服 / 何时可以合服"的输入
- **本文档不重新设计选服路由**——RGS-BAS-020 §3 既有 `RealmDirectoryService` / `RealmRouter` 负责玩家侧路由，本文档仅定义**路由表内容如何随生命周期变化**
- **本文档不重新设计 Saga**——跨阶段涉及的多 DB 写入仍**复用** RGS-ADR-0015 Saga 适用边界与单一调解者原则，不引入新事务范式
- **本文档不重新设计 GM 控制平面**——阶段变更的审批、审计、留痕**全部经由**既有 `AdminService`（ARC-019），不新建独立的 LCM 控制台
- **本文档不强制要求任何阶段都实施**——T0 单服场景下，扩缩容 / 分服 / 合服 / 退场 / 归档的**实施触发**与 OLU 预算挂钩，**未触发不实施**（同 ARC-014「未证明不引入复杂性」精神）

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 逻辑服（Realm） | 玩家可选/可被路由的独立游戏世界单位，复用 RGS-REQ-023 FR-PLT-010 既定概念 |
| 物理节点（Node） | 承载场景 Actor / 网关 / 业务服务的 Kubernetes Pod 或裸金属实例，**一个逻辑服可跨多个物理节点** |
| 数据库分片（DB Shard） | 数据库层按 `realm_id` 切分后的独立实例；T2 起按 `realm_id` 物理隔离，T0/T1 单实例按 `realm_id` 逻辑隔离 |
| 全生命周期（Full Lifecycle） | 一个逻辑服从无（未创建）到有（已开放）到消亡（已退场 + 已归档）的完整过程 |
| 阶段变更（Phase Transition） | 生命周期中任一阶段的进入 / 退出事件；每个阶段变更**必须**经演练验证与审计留痕 |
| 演练模式（Drift / Drill Mode） | 复用 RGS-REQ-023 FR-PLT-022 既定概念——以生产数据快照在演练环境执行完整流程，验证无异常后方可正式执行 |
| 跨服迁移（Cross-Realm Migration） | 玩家数据从一个 `realm_id` 归属迁移到另一个 `realm_id` 归属，分服 / 合服 / 退场的核心操作 |
| 退场（Retire） | 逻辑服停止承接新玩家流量并下线运行时节点，但数据仍保留 |
| 归档（Archive） | 退场后，将该服数据从生产 DB 迁至冷存储 / 离线存储，仅供客服查询 / 监管取证访问 |
| 灰度开放（Staged Open） | 新服创建后，先对白名单 / 邀请码玩家开放，观察无异常后再全量开放的运营动作 |
| 演练剧本（Drill Playbook） | 每个阶段变更的端到端可执行步骤清单（输入 / 步骤 / 预期 / 回滚），**强制要求**每类变更在演练环境通过后方可正式执行 |

# 3. 背景与课题

| 课题编号 | 课题 |
|---|---|
| P-LCM-001 | RGS-REQ-023 §7 + BAS-020 §4 + BAS-022 §3.3 三处散落定义了"开新服 / 合服 / 分服 / 退场"的局部语义，但**没有任何一份文档把它们视为一个统一的端到端生命周期**——读者需要自行在 3~4 份文档间交叉引用拼出全貌，且语义上"分服 = 合服逆向"的简化说法掩盖了分服与合服在数据归属重写方向、玩家分流策略、跨服关系保持三类问题上的本质差异 |
| P-LCM-002 | "开新服"作为运营事件，目前语料库给出的最近表述是 BAS-022 §3.3「新增分片走 ARC-018 挂载」——但 ARC-018 是面向架构师的技术判定清单，**不**是面向运营/SRE 的执行 SOP。运营在拿到这份文档后**仍不知道**开新服前要做什么资源评估、何时走容量门禁、怎么登记到 `RealmDirectoryService`、怎么灰度开放、玩家通知怎么发、演练剧本怎么写 |
| P-LCM-003 | "退场"被等同于"删除"——但真实运营场景中，退场后必须保留数据：①客服工单需要查询历史玩家（支付争议、违规申诉、外挂封禁依据）；②监管合规（GDPR、数据安全法、个人信息保护法）要求保留期内的玩家数据可被查询 / 导出 / 删除；③合服回溯（合服后发现错误需要回退，或被合并服玩家申诉要求恢复独立服）。当前语料库对归档路径**完全空白** |
| P-LCM-004 | "分服"在 RGS-REQ-023 §7 中被描述为"合服的逆向"，但合服是 N→1（多服并入一服），分服是 1→N（一服拆为多服）：①合服的难点是数据冲突解决（同名角色、重复唯一道具），分服的难点是**玩家分流**（按什么规则决定谁去哪个新服，玩家是否有选择权）；②合服后玩家自然归属目标服，分服后玩家**主动或被动地**被分配到某个新服，可能造成社交关系断裂（好友、工会、聊天频道）；③合服是数据**合并**（去重 + 累加），分服是数据**复制 + 删除**（每个玩家只属于一个新服）。**直接套用合服流程会出错** |
| P-LCM-005 | 阶段变更的端到端不变量（"任何阶段变更都不能丢资产"）目前散落在 FR-PLT-023 等多处，**未**作为统一约束明确——一旦某阶段变更（如分服）漏掉"邮箱绑定数据""第三方支付凭证""未结算抽奖""未领取邮件附件"等边缘数据，资产丢失将无审计可查 |
| P-LCM-006 | 每个阶段变更的演练要求不一致：合服有 RGS-REQ-023 FR-PLT-022 明确要求"演练模式验证"，开新服 / 分服 / 退场 / 归档**均无**强制演练要求——这是阶段间风险水平不一致的体现（合服最容易出错故有演练要求），但**不**意味着开新服 / 分服 / 退场可以无演练 |
| P-LCM-007 | 阶段变更的 OLU 预算（运维负荷）目前**未**纳入 ARC-026 核算——开新服 / 合服 / 分服 / 退场均涉及多团队协作（架构 / SRE / DBA / 运营 / 法务），属于高负荷运维面，与 RGS-REQ-005 附件 D ISS-065「PendingReceiptVerification 定时重试任务为新增常态运维面，OLU 运维负荷未核算」同类问题，**必须**在本文档明确纳入 OLU 预算门禁 |

# 4. 业务需求

| ID | 业务需求 |
|---|---|
| BR-LCM-001 | 开新服须有标准化的端到端流程——从资源评估、容量门禁、路由登记、灰度开放到玩家通知的每一步**均**有可执行 SOP 与演练剧本 |
| BR-LCM-002 | 任意容量级别（T0~T3，ARC-040 既有）下的服务器扩缩容须可执行——不因规模增长而失去扩缩容能力 |
| BR-LCM-003 | 分服须能在一服玩家无感知或最小感知下完成拆分，**不**丢失玩家资产、**不**强制破坏跨服社交关系（好友 / 工会 / 聊天记录可按既定策略保留或重路由） |
| BR-LCM-004 | 合服须有标准化流程——同 RGS-REQ-023 FR-PLT-020~023 既有约束，**不**由执行人员临时决定冲突规则 |
| BR-LCM-005 | 退场后**不得**简单删除数据——玩家历史数据须在保留期内可被客服查询、监管取证、合服回溯 |
| BR-LCM-006 | 任意阶段变更**不得**丢失或重复任何玩家资产——跨阶段端到端不变量 |
| BR-LCM-007 | 任意阶段变更**必须**经演练验证后方可正式执行——与既有 FR-PLT-022 演练要求同构，覆盖全部 6 阶段 |
| BR-LCM-008 | 阶段变更涉及的多 DB 写入须满足最终一致性——复用 RGS-ADR-0015 Saga 适用边界，不引入新事务范式 |

阶段定义：

| 阶段 | 含义 | 进入触发 | 退出触发 |
|---|---|---|---|
| `NotYet` | 逻辑服尚未创建 | （无） | 资源评估通过 + ARC-018 挂载清单通过 + 容量门禁未拒绝 |
| `Active` | 逻辑服已开放、承接玩家流量 | `NotYet → Active` 完成 | 决定进入 `Scaling` / `Splitting` / `Merging` / `Retired` 任一阶段 |
| `Scaling` | 节点级或整服级扩缩容 | 容量监控 / 运营计划 | 扩容 / 缩容执行完毕，状态回到 `Active` |
| `Splitting` | 一服拆为多服 | 容量持续超阈值 / 运营决策 | 分服完成，新服进入 `Active`，旧服进入 `Retired` |
| `Merging` | 多服并入一服 | 玩家流失 / 运营决策 | 合服完成，被合并服进入 `Retired`，目标服仍在 `Active` |
| `Retired` | 停止承接新流量、运行时节点下线、数据保留 | `Active → Retired` 决定 | 数据归档完成（§11），状态进入 `Archived`（不视为生命周期终态，仍可被查询） |

## 5.2 端到端不变量

| 编号 | 不变量 |
|---|---|
| FR-LCM-001 | **资产不丢不重**：任意阶段变更**不得**导致任何玩家资产的丢失或重复——`account_id` 在任意时刻**仅**归属于一个 `realm_id`（迁移窗口除外，且迁移窗口的事务保证见 FR-LCM-005） |
| FR-LCM-002 | **跨阶段可审计**：任意阶段变更**必须**在 `admin_db.operation_audit`（既有，复用 RGS-BAS-003 §7）留下**完整**审计记录（操作者 / 时间 / 阶段 / 演练 / 正式执行快照 / 前后状态 / 影响账号数 / 异常处理） |
| FR-LCM-003 | **跨阶段可演练**：任意阶段变更**必须**先在演练环境以生产数据快照执行完整流程，**通过后方可**正式执行——同 RGS-REQ-023 FR-PLT-022 |
| FR-LCM-004 | **跨阶段门禁一致**：任意阶段变更**必须**经既有 `AdminService`（ARC-019）统一入口，**不得**绕过 RBAC、审计、限流等横切关注点——同 RGS-BAS-031 §2.2 责任矩阵 |
| FR-LCM-005 | **跨 DB 写入最终一致**：跨 DB 阶段变更（如分服时 player_db / economy_db / social_db 同时改写）**必须**复用 RGS-ADR-0015 Saga 模式，由单一调解者（ClusterOpsService，ARC-051）编排，**不得**为阶段变更引入新事务范式 |
| FR-LCM-006 | **跨阶段对玩家透明或最小告知**：阶段变更对玩家**应当**透明（不告知）或最小告知（仅在无法避免时告知，如合服前 7 天公告 + 邮件 + 游戏内横幅）——**不得**在玩家无感知时擅自转移其资产归属 |

# 6. 功能需求：开新服 New Realm

## 6.1 触发条件

| 编号 | 需求 |
|---|---|
| FR-LCM-010 | 开新服**应当**由以下三类触发之一驱动：①**容量门禁触发**（既有服的 CCU 持续超阈值达 N 天，TBD-LCM-001）；②**运营计划触发**（大版本首发 / 活动分服 / 渠道分服，**须**经运营计划登记，复用 RGS-BAS-003 §10 运维工单）；③**架构决策触发**（如 T2→T3 多区域拓展，**须**经 ARC-014/026 评审）——**不得**由单人临时决策开新服 |
| FR-LCM-011 | 容量门禁触发的开新服**必须**先经 BAS-022 §3.2 跨分片能力清单评估，确认新服作为新分片**不**引入未评估的跨分片能力——同 RGS-REQ-025 FR-CAP-011 |

## 6.2 资源评估与挂载

| 编号 | 需求 |
|---|---|
| FR-LCM-020 | 开新服**必须**先完成资源评估并出具评估报告，**至少**包含：①目标 `realm_id` 与命名规范（与既有命名空间不冲突）；②DB 实例（player_db / economy_db / social_db 按 `realm_id` 物理或逻辑隔离）；③运行时节点池（场景 Actor 节点数、网关副本数）；④网络资源（VPC / 子网 / NetworkPolicy / Ingress / 网关配额）；⑤容量预算（T0/T1/T2 各级预留余量，复用 RGS-BAS-022 §4.1） |
| FR-LCM-021 | 开新服**必须**复用 ARC-018 挂载清单（既有，RGS-BAS-002 §4）执行技术性挂载——DB 迁移、Helm Release、NetworkPolicy、可观测性埋点等，**不得**为开新服发明独立于 ARC-018 的挂载流程 |
| FR-LCM-022 | 开新服**应当**采用"渐进式挂载"：先以最小配置（1~2 节点 / 最小 DB）就位，通过健康检查 + 预热探针验证可用性，再逐步扩容到目标配置——**不得**一步到位全量开通，避免"上线即故障" |

## 6.3 路由登记与灰度开放

| 编号 | 需求 |
|---|---|
| FR-LCM-030 | 开新服**必须**在 `RealmDirectoryService`（RGS-BAS-020 §3 既有）登记新服元数据：状态（**初始** `hidden`）、`realm_id`、显示名、所属区域、开放时间、维护窗口——`hidden` 状态**不**对普通玩家可见，仅白名单可见 |
| FR-LCM-031 | 开新服**应当**采用**灰度开放**：①**白名单阶段**（邀请码 / 内部账号 / 压测账号）观察 N 天无异常 → ②**渠道灰度阶段**（指定渠道或注册时间窗口）观察 N 天 → ③**全量开放**。每阶段切换**必须**经 ARC-019 GM 控制平面操作，留痕 |
| FR-LCM-032 | 灰度开放期间**必须**保留快速回滚能力——若新服出现严重故障，可秒级切回 `hidden` 状态，**不**对玩家造成已生效的资产影响（新服**仅**接收灰度玩家，未对其既有资产产生跨服变更） |
| FR-LCM-033 | 开新服**应当**同步完成玩家通知链路：①开服前 N 天游戏内公告 + 邮件预告；②开服当日游戏内横幅；③开服后 N 天内的"新服专属活动"——通知内容**不得**误导玩家（不承诺无兑现的奖励，不夸大新服优势） |

# 8. 功能需求：分服 Split

| 编号 | 需求 |
|---|---|
| FR-LCM-050 | 分服**不得**被视为"合服的逆向"——分服是 1→N 的数据归属重写 + 玩家分流 + 跨服关系保持，与合服的 N→1 数据合并在操作语义上**本质不同**；本文档为分服**单独**设计流程，**不**与合服共用步骤模板 |
| FR-LCM-051 | 分服**必须**先确定**玩家分流策略**并写入 `SplitPlan`，策略至少三类：①**强制分流**（按 hash 分配，玩家无选择权）；②**自选分流**（玩家在分流窗口期内选择去新服 A 或新服 B，超期未选则按默认规则分配）；③**混合分流**（核心玩家自选 + 普通玩家强制）——具体策略由运营/产品决策，**不**由执行人员临时决定 |
| FR-LCM-052 | 分服**必须**保持**跨服关系**（好友 / 工会 / 聊天记录）的可恢复性——**至少**支持：①**跨服好友**（好友关系在分服后保留为跨服好友，可跨服聊天 / 跨服组队）；②**工会整体迁移**（若工会成员全部被分到同一新服，工会整体迁入；若分散到多服，工会按既定策略拆分或保留为跨服工会）；③**私聊记录按玩家归属迁移**（不与跨服关系混同） |
| FR-LCM-053 | 分服**必须**复用 FR-LCM-005 Saga 模式编排跨 DB 写入：player_db 改写 `realm_id`、social_db 同步好友/工会归属、economy_db 同步邮件/未结算交易——**单一调解者**（ClusterOpsService）按预定步骤推进，**任一失败按反向步骤补偿** |
| FR-LCM-054 | 分服**必须**复用 §6.3 灰度开放流程——新服从 `hidden` → 灰度 → 全量，旧服同步进入 `Retired` 流程（§10）；**不得**一步切换全量玩家 |
| FR-LCM-055 | 分服**必须**先在演练环境以生产数据快照执行完整流程，**通过后方可**正式执行——同 FR-LCM-003 端到端不变量，且分服**特别**要求验证：①资产不丢不重（FR-LCM-001）；②玩家分流与策略一致；③跨服关系正确保持或拆分；④Saga 补偿在分服中途崩溃场景下能回退至分服前状态 |

# 9. 功能需求：合服 Merge

| 编号 | 需求 |
|---|---|
| FR-LCM-060 | 合服**复用** RGS-REQ-023 §7 + RGS-BAS-020 §4 既有五步流程，**不**在本文档重复定义；本文档仅在以下三处作**纵向延伸**：①§10 退场（合服后被合并服进入 `Retired`）；②§11 归档（合服数据回溯需要退场服归档数据支持）；③本节 FR-LCM-061~064 新增 4 条端到端约束 |
| FR-LCM-061 | 合服**必须**先冻结被合并服的所有进行中事务（玩家间交易、未结算抽奖、未领取邮件附件、跨服工会申请等）——同 ARC-001 既有「场景为单位、数据连续排布无需加锁」原则的应用延伸，**不得**在事务进行中直接合服 |
| FR-LCM-062 | 合服**必须**在 `MergeConflictRuleSet`（RGS-BAS-020 §4.1 既有）中至少明确：①同名角色处理规则；②重复唯一性道具处理规则；③货币累加规则（**仅**累加，**不**允许重置 / 清零）；④**扩展**：⑤未结算抽奖处理规则；⑥未领取邮件附件处理规则；⑦冻结中跨服工会申请处理规则——本文档**新增**⑤⑥⑦三类边缘数据冲突的处理**强制要求** |
| FR-LCM-063 | 合服**必须**留痕（FR-LCM-002）+ 演练（FR-LCM-003）+ 跨 DB Saga（FR-LCM-005）——同既有 FR-PLT-023 + FR-PLT-022 + 本文档 FR-LCM-005 |
| FR-LCM-064 | 合服**必须**支持回退——若合服后短期内发现严重错误（资产错乱、玩家大规模投诉），可按 Saga 反向步骤回退至合服前状态；回退窗口期（典型 7~30 天，具体 TBD-LCM-002）内 `realm_id` 变更的逆操作仍可执行，超出窗口期则进入退场服归档（§11）查询通道，**不**回退到在线服 |

# 10. 功能需求：退场 Retire

| 编号 | 需求 |
|---|---|
| FR-LCM-070 | 退场**不得**等同于"删除"——退场是"停止承接新玩家流量 + 下线运行时节点 + 数据保留"的复合操作，**与删除的差异**在数据保留通道（§11 归档） |
| FR-LCM-071 | 退场**必须**先进入**只读维护模式**——`RealtimeServerSupervisor` 停止接收新玩家会话、停止场景创建、停止新交易撮合；既有玩家**应当**在退场公告后被引导迁出（合服 / 自然流失 / 主动转服），超期未迁出的玩家进入"数据保留态"（仍可查询历史，但不再登录游戏） |
| FR-LCM-072 | 退场**必须**保留**全部玩家数据**——账号身份、角色数据、好友/工会关系、邮件、未结算交易、支付凭证、运营审计——**不得**在退场时清空任何字段（FR-LCM-001 端到端不变量） |
| FR-LCM-073 | 退场**应当**支持**退场后查询通道**——客服系统（既有 RGS-REQ-019）须能在退场服上查询玩家历史数据（支付争议、违规申诉、合服回溯）；查询通道**仅限**客服 / SRE / 法务角色按 RBAC 访问，**不得**对玩家开放 |
| FR-LCM-074 | 退场**必须**在 `RealmDirectoryService`（RGS-BAS-020 §3 既有）将服状态置为 `retired`，**不再**对玩家选服列表可见——但**仍**对客服 / 监管角色可见（用于查询通道） |
| FR-LCM-075 | 退场**应当**支持"二次激活"——若退场后短期内（如 30 天）发现退场决策错误，可按"反向退场"流程重新上线（数据仍在 DB，恢复运行时节点 + 路由登记即可）；超期后激活须经架构评审（与开新服同等评审），避免对既有玩家造成"我玩了几年的服没了"的体验 |

# 11. 功能需求：归档 Archive

| 编号 | 需求 |
|---|---|
| FR-LCM-080 | 归档**应当**在退场后 N 天（TBD-LCM-003，建议 30~90 天）启动——给"二次激活"窗口期 + 退场后短期内的高频客服查询期；归档启动**不得**阻塞退场流程本身 |
| FR-LCM-081 | 归档**必须**保留**全部玩家数据**——同 FR-LCM-072 不丢不重；归档**不**等于"数据删除"，**不**等于"匿名化"，仅等于"从生产 DB 迁至冷存储 / 离线存储" |
| FR-LCM-082 | 归档**应当**采用**分级存储**：①**热归档**（近 N 年数据，仍在关系型 DB 冷备实例，可在线查询但无写入）；②**冷归档**（超 N 年数据，转储至对象存储 / 归档库，查询时按需还原）——具体分级阈值 TBD-LCM-004 |
| FR-LCM-083 | 归档**必须**保留**完整审计链**——从开新服到退场到归档的每一步阶段变更、每次运营操作、每条客服查询（即便归档后客服查询仍可发生），**全部**在 `admin_db.operation_audit` 留痕（既有，复用 RGS-BAS-003 §7） |
| FR-LCM-084 | 归档**必须**支持**合规删除**——若某玩家在退场服上的数据满足 GDPR / 个人信息保护法"被遗忘权"等合规删除条件（即便服已退场 + 已归档），仍须能从冷归档中**定位并删除**该玩家数据，**不得**以"已归档"为由拒绝——同 NFR-SE-010「仅追加」约束的例外处理，例外**仅**适用于合规删除场景，由 `AdminService` 高危操作分支执行并双重审计 |
| FR-LCM-085 | 归档**应当**支持**跨服合并回溯**——若两个已归档退场服曾被合服，合服前的资产归属记录须可被还原（避免合服后"找不到玩家原归属服"导致客服投诉无据可查） |

# 13. 架构设计方针 ARC-038 扩展

## 13.1 ARC-038 扩展：服务器全生命周期治理（LCM 延伸）

| 项目 | 内容 |
|---|---|
| **决定** | 服务器的**完整生命周期**（开新服 → 扩缩容 → 分服 → 合服 → 退场 → 归档）**必须**作为统一的端到端治理对象，**不**分散在开新服 / 合服 / 退场各自的局部设计中处理；**所有**阶段变更**必须**经 ClusterOpsService（ARC-051）作为单一调解者编排，**复用** ARC-018 挂载/退场判定原则、ARC-019 GM 控制平面、ARC-040 横向分片架构、ARC-026 OLU 预算核算 |
| **理由** | ①开新服 / 合服 / 分服 / 退场 / 归档作为单一生命周期的不同阶段，**共享**端到端不变量（资产不丢不重、可审计、可演练、跨 DB 一致、玩家最小告知）；**分开设计**会导致端到端不变量在阶段间出现裂缝（FR-LCM-001/002/003/005 跨阶段适用）②ClusterOpsService（ARC-051）已是 Feature 编排的单一调解者，阶段变更作为 Feature 类型扩展（`bounded_context` / `plugin` / `patch` / `config` 四类既定 + 新增 `realm_lifecycle` 一类）走 PFAU 编排，**不**为生命周期管理另设调解者③ARC-018 挂载/退场原则是技术底座，阶段变更**复用**而非"另起一套"——避免阶段间出现与既有治理框架冲突的设计 |
| **与 ARC-038 既有内容的关系** | 既有 ARC-038 决定①（平台内购权威来源）+ 决定②（合服复用 ARC-018 + 演练）保持不变，**新增**决定③「服务器生命周期作为统一治理对象」 |
| **Feature 类型扩展** | 在 RGS-BAS-031 §1.1 既有四类 Feature（`bounded_context` / `plugin` / `patch` / `config`）基础上**新增** `realm_lifecycle` 类型——开新服 / 分服 / 合服 / 退场 / 归档作为 `realm_lifecycle` Feature 的具体子类，由 ClusterOpsService PFAU 编排执行 |

# 14. 验收标准

| 编号 | 验收标准 |
|---|---|
| AC-LCM-001 | **开新服端到端验证**：模拟完整开新服流程（资源评估 → 挂载 → 路由登记 → 灰度开放 → 全量开放），验证每一步可执行、可审计、可演练，演练通过后方可正式执行 |
| AC-LCM-002 | **合服不丢不重**：模拟两个服 A+B 合服至 A，验证合服前后两服玩家资产总量 100% 一致，`MergeConflictRuleSet` 规则全部按既定执行，无任何资产丢失或重复 |
| AC-LCM-003 | **分服后两服独立可玩**：模拟一个服拆为 A+B，验证两服各自独立可登录、玩家分流与 `SplitPlan` 策略一致、跨服关系（好友/工会）按既定规则保留或拆分 |
| AC-LCM-004 | **退场后查询通道可用**：模拟一个服退场，验证客服系统能按 RBAC 在退场服上查询玩家历史数据，玩家侧**不**可登录该服 |
| AC-LCM-005 | **归档后合规删除可行**：模拟一个服退场后归档，验证收到 GDPR / 个人信息保护法"被遗忘权"请求时能从冷归档定位并删除该玩家数据，同时保留审计链 |
| AC-LCM-006 | **跨阶段不变量覆盖**：验证任意阶段变更的 `admin_db.operation_audit` 留痕完整，无"无法解释的状态变更"；任意阶段变更均经演练验证后正式执行 |
| AC-LCM-007 | **阶段变更 OLU 核算**：开新服 / 分服 / 合服 / 退场 / 归档的 OLU 预算纳入 ARC-026 核算，未核算视为未批准 |
| AC-LCM-008 | **二次激活可行**：模拟退场后 30 天内"反向退场"重新激活，验证数据完整、运行时节点可恢复、路由登记可重新生效 |
| AC-LCM-009 | **合服回退窗口内可回退**：模拟合服后 7 天内发现严重错误，按 Saga 反向步骤回退至合服前状态，验证资产 100% 还原 |
| AC-LCM-010 | **跨服合并回溯**：模拟两个已归档退场服曾被合服，验证合服前资产归属记录可被还原，无"找不到玩家原归属服" |

| RSK-LCM-002 | 分服时玩家分流不均匀（hash 分配偏差 / 自选分流集中）可能导致某新服过载、某新服过冷——缓解：①演练阶段**必须**验证分流结果在 ±20% 内；②分服后 N 天内**应当**保留玩家自选切换新服的"冷静期"通道（已分配玩家可在 N 天内主动切到另一新服，TBD-LCM-005） | 演练层面缓解 |
| RSK-LCM-003 | 跨服迁移数据损坏（DB 写入中途部分成功导致 `realm_id` 归属错乱）若未及时发现，可能在玩家尝试登录 / 支付 / 跨服交互时显现，造成玩家资产损失——缓解：①Saga 反向步骤兜底；②分服 / 合服后 N 天内**必须**对受影响玩家跑资产一致性校验脚本（自动比对迁移前快照与迁移后实际归属，**任何**不一致立即告警） | Saga + 一致性校验双重缓解 |
| RSK-LCM-004 | 退场后若二次激活失败（节点恢复失败 / 路由登记冲突 / DB 实例不可用），玩家可能"无法找回"——缓解：①二次激活窗口期内**必须**保证 DB 实例可恢复（不退场即释放 DB 资源）；②二次激活流程**必须**经架构评审，不允许"自动激活" | 流程层面缓解 |
| RSK-LCM-005 | 归档后冷存储数据若因存储介质损坏 / 备份失效丢失，客服查询 / 监管取证 / 合服回溯将无据可查——缓解：归档**必须**采用多副本 + 异地备份（具体存储选型 TBD-LCM-006），多副本**至少**满足 N+2 冗余 | 存储层面缓解 |
| RSK-LCM-006 | 阶段变更涉及多团队协作（架构 / SRE / DBA / 运营 / 法务）的 OLU 负荷若未充分核算，可能在高密度阶段变更期间（如大版本首发前同时开新服 + 退场旧服 + 归档历史服）击穿 SRE 上限——缓解：阶段变更 OLU **必须**纳入 ARC-026 预算核算（NFR-LCM-007），高密度期间**必须**串行调度避免并发 OLU 击穿 | OLU 预算门禁缓解 |
