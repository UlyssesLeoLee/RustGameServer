# 1. 前言

## 1.1 目的

RGS-REQ-001已定义最小限度的运营API（FR-AD-001封禁、FR-AD-002补偿、FR-AD-003维护模式、FR-AD-004异常行为检测、FR-AD-005审计日志），由§IF-007规定运营工具通过HTTPS/RBAC调用`AdminService`。随着运营团队规模扩大与游戏上线，运营方需要一个**独立的GM后台系统**（以下称"GM后台"，本系统之外的既有或另行开发的管理界面）来日常化地完成：账号/玩家管控、服务器状态查看、配置热更新触发、故障告警接收等工作。

本文档的目的：

1. **补全**FR-AD-001〜005之外，GM后台日常运营所需但既有需求集尚未覆盖的功能缺口（如踢人/禁言、在线状态查询、告警推送、场景级只读监控）。
2. **明确**"GM后台"作为**本系统外部系统**接入的边界与安全模型——它与RGS-REQ-006"新功能挂载"讨论的"新限界上下文（系统内部组件）"不同，GM后台不运行在本系统的Kubernetes集群内，仅通过既定API边界与本系统互通。
3. **定义**"运维功能"中，本文档负责的范围（面向GM后台暴露的、系统内建的运维API与观测数据）与RGS-OPS-001（已制定，见 RGS-OPS-001；以手册演练证据确认目标，面向SRE的具体运维手顺书）负责的范围（人工操作步骤、值班流程）之间的分工。

## 1.2 适用范围

| 范畴 | 说明 |
|---|---|
| GM后台互通 | GM后台如何鉴权接入本系统、如何调用管控API、如何接收本系统主动推送的事件/告警 |
| GM后台控制服务器 | GM后台可对本系统下达的操作指令目录：账号/会话级、场景/运行时级、配置级、发布/维护级 |
| 运维功能（系统侧） | 本系统需内建、供GM后台或运维人员使用的监控数据聚合、审计查询、健康视图等能力 |
| **不适用范围** | GM后台自身的UI/UX设计（X-006既有排除项的延伸）；K8s集群层面的直接操作权限（见§7 ARC-019，明确排除）；SRE的人工值班/故障处理SOP文档（属RGS-OPS-001） |

# 2. 术语约定

沿用RGS-REQ-002术语表及RGS-REQ-006§2新增术语。本文档新增：

| 术语 | 定义 |
|---|---|
| GM后台 | 本系统之外、供运营/GM（Game Master）人员使用的管理系统，通过本系统暴露的运营API与本系统互通。GM后台本身**不在**本系统Kubernetes集群的信任边界内 |
| 控制平面（Control Plane，本文档语境） | 本系统内负责接收并执行GM后台管控指令的组件集合：`AdminService`（业务层）与运行时受限控制通道（见ARC-019） |
| GM指令 | GM后台向本系统发起的、会改变系统状态或返回运营视角数据的操作请求，统称"指令"，区别于玩家侧的游戏操作 |
| 爆炸半径（Blast Radius） | 一次误操作/权限滥用可能影响的系统范围，本文档用作安全边界设计的判定尺度（见ARC-019） |

# 3. 背景与课题

| 编号 | 课题 |
|---|---|
| P-OPS-001 | 既有FR-AD-001〜005仅覆盖封禁、补偿、维护模式、异常检测、审计五项，缺少GM日常最高频使用的"踢人/强制下线/禁言"与"在线状态/场景负载查询" |
| P-OPS-002 | 若GM后台为求"方便"而直接被授予K8s API权限或数据库直连权限，一次误操作（如误删Deployment、误改数据）的爆炸半径将波及整个集群，且脱离本系统既有的审计（NFR-SE-010）与幂等（ARC-009）保护 |
| P-OPS-003 | 若GM后台的控制指令直接下发至运行时场景Actor的tick循环路径，会破坏ARC-013"背压设置位置"与"死锁防止"的既有边界，重演P-005（缺乏测定手段的优化会致方向错误）同类"未受控路径影响核心循环"的问题 |
| P-OPS-004 | 若系统故障/告警只能靠GM后台人员主动查询才能发现，而非系统主动推送，会延长MTTR（平均故障恢复时间），与ARC-017"可观测性自PH-1起必须具备"的精神相悖 |
| P-OPS-005 | 若维护模式（FR-AD-003）的传播机制未明确定义到网关/运行时/业务服务各层，可能出现"GM后台点了维护开关，但玩家仍能匹配到新场景"的不一致 |

| ID | 需求 | 优先级 |
|---|---|---|
| BR-OPS-001 | 运营/GM人员须能通过GM后台，在不依赖工程团队人工介入的前提下完成日常账号管控（封禁、踢人、禁言）与补偿发放 | 高 |

| BR-OPS-003 | 任何GM/运维操作都必须可追溯到具体操作者、具体时间、具体操作内容，满足合规审计要求 | 高 |
| BR-OPS-004 | GM后台的管控能力不得成为攻击者/误操作破坏系统可用性或数据一致性的捷径 | 高 |

# 5. 功能需求

## 5.1 GM后台互通

| ID | 需求 |
|---|---|
| FR-GM-001 | GM后台**必须**通过既有IF-007运营API通道（HTTPS＋RBAC，NFR-SE-005）接入本系统，**不得**开辟额外的、绕过RBAC与审计的接入路径 |
| FR-GM-002 | GM后台的身份鉴别**必须**基于操作者级别的凭证（而非仅系统级API Key），使得§5.3（FR-OPS-003）审计日志可精确到操作者个人 |
| FR-GM-003 | 本系统**必须**提供只读查询API集合，供GM后台展示：在线人数、在线玩家列表（分页/筛选）、场景负载概览、维护模式当前状态、最近告警列表 |
| FR-GM-004 | 本系统**应当**提供事件推送通道（Webhook或消息订阅），将关键告警（NFR-OPS-*阈值触发）、审计高危操作、维护模式变更**主动**推送至GM后台，减少GM后台被动轮询 |
| FR-GM-005 | 推送通道的事件**必须**携带`event_id`保证幂等，GM后台侧重复接收不产生重复处理（同ARC-009 Effectively Once精神） |

## 5.2 GM后台控制服务器（扩展既有FR-AD-001〜005）

判定原则：以下指令默认扩展既有`AdminService`（admin限界上下文），除非指令本身需要独立的高吞吐/低延迟存储或独立扩缩容策略，才按RGS-REQ-006 ARC-018走新限界上下文挂载流程（本版判定：均不需要，全部纳入`AdminService`扩展，§5.2.4额外说明例外情形）。

### 5.2.1 账号/会话级控制

| ID | 需求 | 对应/扩展 |
|---|---|---|
| FR-GM-010 | GM后台**必须**能对指定玩家账号执行封禁/解封 | 复用FR-AD-001 |
| FR-GM-011 | GM后台**必须**能对指定在线会话执行强制踢下线（KickSession），指令须能到达该玩家所在的运行时节点并使其会话失效 | 新增 |
| FR-GM-012 | GM后台**应当**能对指定玩家/公会频道执行禁言（MuteChat），带可选到期时间 | 新增（依赖PH-6社交功能） |
| FR-GM-013 | GM后台**必须**能批量发放补偿 | 复用FR-AD-002 |

### 5.2.2 场景/运行时级控制（只读为主，写操作须谨慎）

| ID | 需求 |
|---|---|
| FR-GM-020 | GM后台**必须**能查询场景级运行指标（当前实体数、tick耗时、mailbox积压等，取自既有可观测性数据，ARC-017），用于判断是否需要人工介入 |
| FR-GM-021 | GM后台**可以**对判定为异常（如死锁、tick严重超时）的单个场景发起"强制重启该场景"指令，但该指令**必须**先进入待确认状态，由具备"高危操作"角色的操作者二次确认后才执行（同§6非功能需求的高危操作二次确认原则） |
| FR-GM-021的例外声明 | FR-GM-021涉及运行时进程内部状态操作，**不得**通过修改数据库或直接kill Pod实现，**必须**通过运行时暴露的受限控制通道（见ARC-019）以命令方式请求运行时自身安全终止并重建该场景，遵循FR-RT-009既有的检查点恢复机制 |

### 5.2.3 配置/发布级控制

| ID | 需求 |
|---|---|
| FR-GM-030 | GM后台**必须**能触发数值表热更新（对应既有ARC-016"数值表・配置的热更新"），指令须携带目标版本号，执行结果（成功/一致性检查未通过）须回传GM后台 |
| FR-GM-031 | GM后台**必须**能查询/切换维护模式（复用FR-AD-003），维护模式变更须按§7 ARC-019定义的传播路径生效至网关、API网关、运行时排空流程（具体传播时序见RGS-BAS-003§5） |
| FR-GM-032 | GM后台**不得**被授予直接触发K8s滚动更新/扩缩容/Pod重启的权限。此类操作**只能**"发起请求"（记录一条待处理的运维请求工单），由SRE或既有CI/CD流水线执行（见§7 ARC-019否决方案） |

### 5.2.4 异常检测与风控联动

| ID | 需求 |
|---|---|
| FR-GM-040 | 本系统**必须**继续按FR-AD-004对异常行为（移动速度/输入频度等）进行检测，检测结果**应当**可被GM后台查询，作为FR-GM-010封禁决策的辅助依据 |

# 7. 架构设计方针 ARC-019

本节为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接RGS-REQ-006新增的ARC-018。**决定事项**，变更须经ADR与审批。

## 7.1 ARC-019：GM后台控制平面的统一入口与爆炸半径限制（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | GM后台对本系统的一切管控操作，**必须且只能**经由既有`AdminService`（IF-007运营API）这一**统一入口**下达；涉及运行时进程内部状态的操作，**必须**经运行时新增的**受限控制通道**（与业务tick循环解耦的独立gRPC端点，仅`AdminService`可调用，不对GM后台/客户端/网关直接开放）二次转发；**GM后台不得在任何情况下持有K8s API凭证、数据库直连凭证，或运行时受限控制通道的直接调用权限** |
| **理由** | 延续ARC-007"运行时不直接暴露给外部权威调用者"、ARC-013"背压设置位置"与ARC-009"幂等/审计"的既有精神。若GM后台可以绕过统一入口直接操作基础设施，任何单点的凭证泄露或误操作都会产生无法追溯、无法限流、无法审计的全集群级爆炸半径 |
| **控制平面组件** | ①`AdminService`（业务层网关，RBAC+审计+限流，既有组件的能力扩展）②运行时受限控制通道（新增，见RGS-BAS-003§4，仅处理KickSession/MuteChat/场景重启请求/场景级只读指标查询，异步处理不阻塞tick） |
| **K8s层操作的例外处理** | 扩缩容/滚动更新/Pod重启等K8s层面操作，**不得**开放给GM后台直接触发。GM后台**只能**产生一条"运维请求工单"，由SRE人工审批或既有CI/CD流水线（同RGS-REQ-006 ARC-018既有CI/CD路径）代为执行。本系统**不**因GM后台的存在而新增GM后台可直接调用的K8s Operator/API Server权限 |
| **否决方案1** | "为提升GM后台响应速度，允许其直接调用K8s API做扩缩容"——一次误操作（如错误的副本数、错误的命名空间）可能导致大范围服务不可用，与NFR-AV-*系列可用性目标冲突，已否决 |
| **否决方案2** | "运行时受限控制通道向GM后台直接开放"——会在运行时Pod上新增一个未经统一RBAC/审计/限流保护的入口，破坏ARC-013"全部边界须设置同时执行数上限・队列上限・超时・速率限制・熔断器"的既定要求，已否决 |
| **适用范围** | 全部GM后台发起的管控操作。系统内部（运行时↔业务服务、业务服务↔业务服务）既有的gRPC调用路径不受本条影响，继续遵循ARC-007/ARC-009/ARC-013 |
