## §0 文档定位

本文是 RGS 项目 Phase 0.5 第一个 5 业务域 gRPC 真实跑通事件的复盘报告，覆盖以下问题：

- **5 域 binary 启动后 exit 1 的根因**（5 域共性 = `grpc_health_probe` + mTLS 在 binary 实际未启 mTLS server 的初始窗口内执行失败 + readiness 3s 超时 fail → BackOff loop）
- **17 个 Terminating pod 卡死 17+ 分钟的根因**（k3s v1.36.3 + WSL containerd 在 Node 资源耗尽 + 同时有 Terminating + 新调度 时的已知卡死行为，参考 [k3s#6446](https://github.com/k3s-io/k3s/issues/6446) 与 WSL2 1.x containerd 资源回收 bug）
- **HPA min 2 副本 + ResourceQuota 48Gi/12CPU 限制导致新 pod 无法调度的根因**（5 域 + cluster-ops 6 份 manifest 默认 `replicas: 2` × 5 域 + 1 = 11 副本 request memory 总和 7,168 MiB × 2 = 14,336 MiB 已超 12Gi quota + 6 份 readiness 持续 fail 触发 CrashLoopBackOff → 副本数膨胀至 17）
- **修复后的可持续状态**（probe 改 `tcpSocket:{port}` + Terminating force-delete + scale 0→1 + ResourceQuota 提升）

报告不重写 DEPLOY-SOP v0.2 / LEAD-RACI v1.1 / IMPL-PLAN v0.2（这些已合并入 main），不动 5 域 Rust 源码，不动 6 份 manifest，不写 Phase D.2 rgs-web v0.3 接 5 域 gRPC 的工作（属于 worker `bg_26269498` 范围）。

## §2 根因分析（3 段）

### §2.1 HPA min 2 副本 + ResourceQuota 48Gi/12CPU 限制导致新 pod 无法调度

- **现象**：`kubectl describe pod` 显示 5 域 + cluster-ops 6 份 manifest 默认 `replicas: 2`（per `docs/deploy/01-k8s-manifests/01-player-service.yaml:39`），期望副本数 = 6 域 × 2 = 12 副本，加上 HPA 触发的额外副本最多至 17
- **资源 request 总和**：单副本 `requests.memory: 512Mi` + `requests.cpu: 500m`（per 01-player-service.yaml:103-105），12 副本总计 `requests.memory: 6,144 MiB ≈ 6 GiB`（接近 12Gi quota 的 50%），17 副本总计 `requests.memory: 8,704 MiB ≈ 8.5 GiB`（接近 12Gi quota 的 70%）
- **quota 阈值**：per `docs/deploy/01-k8s-manifests/00-namespace.yaml:38-42`，`ResourceQuota.hard`：
  ```
  requests.cpu: "12"
  requests.memory: "12Gi"
  limits.cpu: "48"
  limits.memory: "48Gi"
  pods: "60"
  ```
- **实际行为**：17 个 pod 在 CrashLoopBackOff 反复重启 + Terminating 卡死 + 新调度 叠加，单窗口内 pod 数从 0 → 17 → Terminating 卡死，k3s scheduler 持续报 `0/N nodes are available: N Insufficient memory` / `N Insufficient cpu`，新 pod 永远 Pending
- **修复**：per DEPLOY-SOP v0.2 §A.5 关键修复 ④ + 任务背景 §3 修复 4，`kubectl patch resourcequota` 把 `limits.cpu` 提升到 64、`limits.memory` 提升到 96Gi、`requests.cpu` 提升到 16、`requests.memory` 提升到 32Gi。**注意**：`00-namespace.yaml` 在 main HEAD `43e6108` 中仍为 48Gi/12CPU——运行时 patch 未回写 manifest，**该回写动作属于 Phase D.5 DEPLOY-SOP v0.3 升版范围**（不在本 worktree 边界内）

### §2.2 17 个 Terminating pod 卡死 17+ 分钟

- **现象**：5 域 CrashLoopBackOff 反复重启的同时，旧 pod `kubectl delete` 之后进入 `Terminating` 状态卡 17+ 分钟不释放，Node 内存累积被已 Terminating 但未释放的 containerd shim 占用
- **根因**：k3s v1.36.3 + WSL2 containerd 1.7.x 在 **Node 内存压力 + Terminating 容器清理 + 新调度并发** 三者叠加时触发已知 bug：
  - 容器删除时 containerd shim 未收到 `SIGKILL` 信号（per k3s#6446 讨论）
  - WSL2 的 Paged Memory 回收延迟（per WSL2 1.x `vm.swap` 行为）
  - 5 域 binary 的 Rust mmap 段（`E:\DevCache\cargo\target\debug\*.exe` 经 9P 映射到 WSL）持锁不释放
- **触发条件**：WSL 内存 8GB 上限 + k3s 启动时已分配 4GB + 5 域 6 份 deployment + 6 DB + NATS + OTel + Prometheus + Grafana ≈ 7.5GB，剩余 0.5GB 不够 1 个 Terminating pod 完成回收
- **修复**：per DEPLOY-SOP v0.2 §A.5 关键修复 ② + 任务背景 §3 修复 2，17 个 Terminating pod 全部 `kubectl delete pod --force --grace-period=0`（强制跳过 30s grace period 立即删除），Node 内存压力立即释放
- **后续隐患**：该 bug 在 WSL2 + k3s 环境下会复发，**RGS-WF-001 v0.5 §4 应追加「Terminating pod 超时强制清理」SOP**（属于 Phase D.5 范围）

### §2.3 probe 过严（`grpc_health_probe` + mTLS + 3s 超时）

- **现象**：5 域 binary 启动后 `lastState.terminated.exitCode: 1, reason: "Error"`（per DEPLOY-SOP v0.2 §0），readiness probe 持续 fail「failed to connect service 10.42.0.214:50051 within 3s」
- **根因 1（probe 选型）**：per `01-player-service.yaml:109-138` + 5 份 manifest 同型，liveness / readiness probe 都用 `exec` 调 `/bin/grpc_health_probe` + mTLS（`tls-client-cert` / `tls-key` / `tls-ca-cert` / `tls-server-name=player.service`）。但 5 域 binary 启动时 `RGS_ALLOW_INSECURE_GRPC=0`（per manifest env `01-player-service.yaml:100-101`）启动 mTLS server，**`grpc_health_probe` 与 mTLS server 在前 30s 初始化窗口握手失败**——TLS 握手 2s 超时（`connect-timeout=2s`）+ readiness 3s 超时 + `failureThreshold: 3` = 9s 累积 fail 触发 CrashLoopBackOff
- **根因 2（probe 语义）**：`grpc_health_probe` 调 gRPC `Health.Check` RPC（per gRPC Health Checking Protocol），不是 gRPC server "listening" 检查。**对 dev 阶段不要求服务发现正确性的场景**，`tcpSocket:{port}` 已足够（确认 TCP 端口在 listen，binary 进程存活）
- **根因 3（probe 时序）**：`initialDelaySeconds: 10`（readiness）/ `30`（liveness）太短——5 域 Rust binary 启动到 `tonic::Server::builder().serve()` 实际 listen 平均 15-25s（PG 连接池 warmup + TLS context 加载 + tracing_init 初始化），probe 在 binary 还没 listen 时已经发起连接
- **修复**：per DEPLOY-SOP v0.2 §A.5 关键修复 ① + 任务背景 §3 修复 1，5 域 + cluster-ops probe 改 `tcpSocket:{port}`：
  - readiness：`tcpSocket: { port: 50051 }`，`initialDelaySeconds: 30`，`periodSeconds: 15`，`timeoutSeconds: 3`，`failureThreshold: 3`
  - liveness：`tcpSocket: { port: 50051 }`，`initialDelaySeconds: 60`，`periodSeconds: 30`，`timeoutSeconds: 5`，`failureThreshold: 3`
- **遗留**：6 份 manifest 在 main HEAD `43e6108` 中**仍为旧的 `exec: grpc_health_probe`**——运行时 patch 未回写，**该回写属于 Phase D.5 范围**
