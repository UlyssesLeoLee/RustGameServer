> 本文档是**编码实施前的最后一道关卡**——所有"🟠 重要"及以上的问题**必须**在第一行代码提交前解决或明确"接受风险，**带条件进入实施**"。

## Q-005　NATS JetStream 故障时业务路径如何降级？

| 字段 | 内容 |
|---|---|
| **状态** | ☐ Open |
| **优先级** | 🟠 重要 |
| **背景** | NATS 是事件总线的事实中心（CEM ARC-051 / RGS-TS-001 §3.6），但若 NATS 集群全停：①已发但未消费的事件丢失 ②新事件无消费者 ③ Outbox 堆积 ④ retry 死循环 |
| **假设** | 三段降级：①NATS 全停 → Producer 退回 DB-side Outbox 暂存，Consumer 端暂停消费（业务路径用强一致回退到同步 RPC）②NATS 部分节点停 → 自动重试 + 临时单节点 + 告警 ③NATS 健康但积压 → 限流 Producer + 扩容 Consumer |
| **验证** | Chaos Mesh 注入 NATS pod-kill 演练；降级到同步 RPC 的延迟影响实测；Outbox 暂存的容量上限 |
| **阻塞** | ARC-040 容量规划的 NATS 容量子项；RGS-REQ-001 NFR-AV-* 验收 |
| **负责人** | 架构师 + SRE |
| **截止** | PH-4 前（首次 NATS 上线前） |

## Q-007　100k CCU 网络带宽预算是多少？

| 字段 | 内容 |
|---|---|
| **状态** | ☐ Open |
| **优先级** | 🟠 重要 |
| **背景** | 100k 玩家 × 状态更新频率 = 总带宽。NFR-PE-* 仅给了延迟目标，没给带宽预算。若按"每玩家 1Hz 状态包 × 200B" = 20MB/s = 160Mbps——单 AZ 可承受，但跨 AZ 复制后是 3 倍 |
| **假设** | 100k CCU × 平均 2Hz 状态同步 × 200B 压缩后 = 40MB/s = 320Mbps 单向；预留 50% 余量 = 480Mbps；建议 ingress ≥ 1Gbps，AZ 间 ≥ 2Gbps |
| **验证** | k6 脚本实测 + OTel 网络埋点；RGS-TS-001 §3.11.1 主机规格需重审 |
| **阻塞** | RGS-OPS-001 §1.1 硬件最低要求表；多 AZ 部署规划 |
| **负责人** | SRE Lead |
| **截止** | PH-3 前 |

| 字段 | 内容 |
|---|---|
| **状态** | ☐ Open |
| **优先级** | 🟡 应当 |
| **背景** | FR-PFAU-021 默认 120 秒。multi-AZ 部署下，跨 AZ 节点确认可能有 50-200ms 延迟 × 22 节点 + NATS 序列化 + 跨 AZ 网络——批量确认时间可能超 120 秒 |

| **阻塞** | 多 AZ 部署上线 |
| **负责人** | SRE Lead |
| **截止** | PH-5 前（多 AZ 上线前） |
