# 1. 前言

## 1.1 目的

系统当前已有19个领域文档、约40+功能场景，每个限界上下文的请求处理链条中，鉴权（FR-GW-002）、限流（NFR-SEC-008）、输入校验、脱敏（RGS-BAS-004§5）、审计留痕（RGS-BAS-003§7）、错误响应格式等**横切关注点**此前均由各服务**各自实现**，从未有一份文档将其收口为**标准化的前处理/后处理管道**。这带来两个后果：①新服务接入时容易遗漏某项既有要求（如忘记脱敏）②既有服务之间对同一横切关注点的实现细节可能存在不必要的差异（如错误响应格式不统一，增加客户端处理成本）。本文档将既有分散能力**整合**为一条标准化管道，**不新增**新的横切能力，而是**收口既有能力的接入方式**。

## 1.2 判定原则（先声明，避免误解）

- 本文档**不新增**任何前文未定义的横切关注点，鉴权/限流/脱敏/审计等能力**全部**复用既有需求（RGS-REQ-001/007/008/010等）已定义的内容，本文档的价值在于**标准化接入方式**，而非发明新能力
- "前处理"（业务逻辑执行前）与"后处理"（业务逻辑执行后）是**管道阶段**的划分，**不是**新的组件类型，实现上体现为既有服务框架的中间件/拦截器链（如Rust `tower`生态的Service/Layer模式，或等价机制），**不要求**新建独立的网关层来承载这些逻辑（网关层的鉴权/限流已有ARC-003/既定网关设计，本文档聚焦网关之后、业务逻辑之前/之后的服务内管道）
- 标准化**必须**通过ARC-018既定挂载脚手架落地——新服务生成时**自动**获得标准管道骨架，**不得**要求每个服务的开发者手动拼接横切关注点代码

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 前处理（Pre-processing） | 业务逻辑执行前，对请求做的统一处理：鉴权、限流、输入校验/反序列化、幂等键提取、追踪上下文传播 |
| 后处理（Post-processing） | 业务逻辑执行后，对响应/结果做的统一处理：序列化、脱敏、错误规范化、埋点上报、审计留痕 |
| 管道（Pipeline） | 前处理阶段＋业务逻辑＋后处理阶段构成的请求处理全链条，各阶段以**有序、可插拔**的方式组合 |
| 旁路（Bypass） | 请求处理绕过标准管道中某个阶段直接到达业务逻辑或直接返回响应的路径，本文档原则上禁止 |

# 3. 背景与课题

| 课题编号 | 课题 |
|---|---|
| P-PPL-001 | 各限界上下文各自实现鉴权/限流/脱敏/审计，新服务接入时容易遗漏，此前只能靠代码评审人工发现，缺少结构性保证 |
| P-PPL-002 | 错误响应格式此前未统一规范，不同服务的错误码/错误体结构可能不一致，增加客户端（含RGS-REQ-012三引擎SDK）的错误处理复杂度 |
| P-PPL-003 | 输入校验若在各服务业务逻辑内部分散实现，容易出现"校验规则写了但漏了某个字段"这类疏忽，缺少统一的、结构化的校验声明方式 |
| P-PPL-004 | 埋点/脱敏虽有既定规范（RGS-BAS-004），但"如何确保每个新服务都正确接入"从未有强制机制，目前依赖开发者主动遵循文档 |

# 5. 功能需求：前处理阶段

| 编号 | 需求 |
|---|---|
| FR-PPL-001 | 标准管道的前处理阶段**必须**按固定顺序执行以下步骤：①追踪上下文提取/生成（复用RGS-BAS-004既定`trace_id`规范）②鉴权（复用既有FR-GW-002令牌验证）③限流（复用既有NFR-SEC-008多层限流标准）④输入反序列化与结构化校验⑤幂等键提取（若该请求属确定请求路径，复用FR-EC-003既定幂等语义） |
| FR-PPL-002 | 输入结构化校验**必须**以**声明式规则**定义（如基于既有IDL/Schema定义附加校验注解，而非在业务函数体内手写`if`校验），校验失败**必须**在到达业务逻辑前拒绝，返回统一错误格式（FR-PPL-011），**不得**让非法输入进入业务逻辑内部才被发现 |
| FR-PPL-003 | 前处理阶段的任一步骤失败**必须**短路（不再执行后续步骤与业务逻辑），并直接进入后处理阶段生成对应的标准错误响应，**不得**部分执行 |
| FR-PPL-004 | 前处理阶段的执行**不得**引入超出既有ARC-006/007既定边界的新同步依赖（如前处理阶段**不得**新增对其他限界上下文数据库的直接查询） |

# 6. 功能需求：后处理阶段

| 编号 | 需求 |
|---|---|
| FR-PPL-010 | 标准管道的后处理阶段**必须**按固定顺序执行以下步骤：①业务逻辑结果/异常规范化②响应序列化③日志/埋点脱敏（复用既有RGS-BAS-004§5脱敏规则）④黄金指标埋点上报（复用既有RGS-BAS-004§3指标目录）⑤审计留痕（若该请求属需审计类操作，复用既有RGS-BAS-003§7审计设计） |
| FR-PPL-011 | 错误响应**必须**遵循统一的结构化格式（错误码、错误类别、面向人类的描述、面向客户端程序判断的机器可读字段），**不得**由各服务自行定义互不兼容的错误体结构。既有服务的错误响应格式若与本规范不一致，**应当**在后续迭代中逐步收敛（不要求一次性推倒重来） |
| FR-PPL-012 | 后处理阶段的脱敏**必须**在日志/埋点数据**离开服务进程前**完成，**不得**假设下游（日志聚合/指标存储）会代为脱敏——这是RGS-BAS-004"脱敏优先于清洗"既定精神在管道设计上的强制体现 |
| FR-PPL-013 | 审计留痕的触发**必须**基于请求的**操作性质**（是否属高危/需审计类，复用既有RGS-BAS-003§8高危操作判定）而非由各服务自行决定是否留痕，避免因遗漏判断导致该留痕的操作未被记录 |

# 7. 功能需求：标准化与脚手架集成

| 编号 | 需求 |
|---|---|
| FR-PPL-020 | 标准前处理/后处理管道**必须**并入ARC-018既定挂载脚手架（RGS-BAS-002），新服务生成时**自动**包含管道骨架代码，开发者**仅需**为业务逻辑填空，**不得**要求开发者从零搭建横切关注点处理代码 |
| FR-PPL-021 | 管道**必须**支持按服务/按方法粒度的**有限度定制**（如某些只读查询方法可跳过幂等键提取），定制**必须**是显式声明（如方法级注解/配置），**不得**是默认行为，且**不得**允许定制掉过鉴权/限流/脱敏/审计这几项安全与合规相关阶段（FR-PPL-022的旁路禁止范围） |
| FR-PPL-022 | 鉴权、限流、脱敏、审计四项阶段**禁止**任何形式的旁路——**不存在**"某服务因特殊原因跳过鉴权"这类例外，若确有场景需要不同的鉴权/限流策略，**必须**通过配置不同的策略参数实现，而非绕过该阶段本身 |
| FR-PPL-023 | 既有服务（挂载脚手架落地前已存在的服务）**应当**逐步迁移至标准管道，迁移**不要求**一次性完成，但新增服务**必须**自诞生起即使用标准管道，**不得**允许新服务继续手工拼接横切关注点代码 |

# 8. 非功能需求

| 编号 | 分类 | 项目 | 目标 |
|---|---|---|---|
| NFR-PPL-001 | 性能 | 管道自身开销 | 前处理+后处理阶段合计耗时占请求总耗时的比例**不得**超过既定阈值（具体值详细设计确定，须计入既有NFR-PE-002等tick/延迟预算） |
| NFR-PPL-002 | 一致性 | 错误响应格式 | 抽查全部服务的错误响应，符合FR-PPL-011统一格式的比例作为迁移进度指标（既有服务允许渐进迁移，新服务须100%符合） |
| NFR-PPL-003 | 不可旁路性 | 鉴权/限流/脱敏/审计四项 | 静态分析/代码评审确认不存在绕过这四项阶段的代码路径 |
| NFR-PPL-004 | 可扩展性 | 新增前/后处理步骤 | 新增一个管道步骤**不得**要求修改已接入服务的业务逻辑代码，仅需在管道配置中插入新步骤 |

# 9. 架构设计方针 ARC-041

## 9.1 ARC-041：前后处理管道的标准化与旁路禁止原则（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | ①全部服务的请求处理**必须**遵循标准化的前处理→业务逻辑→后处理管道结构，管道各阶段的顺序**固定**，**不得**由各服务自行决定执行顺序②鉴权、限流、脱敏、审计四项阶段**不存在**旁路——这是本文档最核心的强制性约束③标准管道**必须**并入ARC-018挂载脚手架，作为新服务的默认骨架，而非可选项 |
| **理由** | ①固定顺序是可推理性的基础——若各服务可自由决定"先鉴权还是先限流"，会让横切关注点的行为变得难以统一验证②旁路是安全与合规问题的常见根源：一旦允许"这个服务特殊，可以跳过鉴权"的先例，后续会不断出现类似的临时例外请求，最终侵蚀整个系统的一致性保证（同RGS-BAS-011§7A.5闸门变更管控"不得以放宽支持新功能为由绕过"的同类精神）③并入脚手架是让"正确的事情成为默认的事情"，而非依赖开发者记住并主动遵循一份文档 |
| **与ARC-018的关系** | 本文档**扩展**而非替代ARC-018既定的挂载脚手架内容，标准管道是脚手架生成物的**新增标准组成部分** |
| **与ARC-041和ARC-039/ARC-040的关系** | 后处理阶段的埋点上报数据是RGS-BAS-021拓扑可视化画布的数据来源之一（方法级颗粒度追踪Span）；管道自身的开销纳入RGS-REQ-025弹性容量规划的tick/延迟预算考量范围，不额外豁免 |

# 10. 验收标准
