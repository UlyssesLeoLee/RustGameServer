# 1. 前言

## 1.1 目的

本系统已通过ARC-018（RGS-REQ-006）确立「独立DB+独立部署单元+gRPC/事件+脚手架+可观测性」的新功能挂载五要素，通过ARC-021（RGS-REQ-009）确立「拒绝动态链接库，仅以编译期特性开关+沙箱脚本实现热插拔」的两条合规路径，通过ARC-042（RGS-REQ-027）确立「集群清单+依赖图+幂等编排+断点续跑」的集群级部署编排原则，通过ARC-019（RGS-REQ-007）确立「GM后台统一入口+爆炸半径限制」的运维控制面。四块已有方针各自独立、互不重复，但**没有以「功能（Feature）」为操作单元的统一定义**，导致以下三类问题在生产运营中反复出现：

1. **升级粒度混乱**：业务方提出"上线一个新活动"时，工程方需要先判定这是"新限界上下文"（走ARC-018，重）、"新插件"（走ARC-021，轻）、"既有功能的补丁"（无明确流程）、还是"集群级配置变更"（无明确流程）。判定本身依赖个人经验，没有工具辅助，没有可视化呈现
2. **事件流不可观测**：现有事件机制是各App自治发布到事件总线，**没有中心事件管理**——管理员无法在一个统一视图中看到"今天哪些事件被发出、被谁消费、消费延迟多少、是否有死信、是否能重放"
3. **原子性不可视**：插件热插拔（ARC-021）与集群部署（ARC-042）虽各自保证"插件级／集群级"原子性，但**管理员无法在单一界面看到"一个功能从版本A升级到版本B，跨多少节点、跨多少依赖、何时全部生效、何时可回滚"**。一次失败的回滚在多节点间可能只回滚了一半

本文档的目的：

1. 引入**功能（Feature）**作为统一的操作单元，将ARC-018（限界上下文）、ARC-021（插件）、ARC-042（集群部署条目）、ARC-016（数值表配置）四种"可独立变更的产物"统一收束为同一棵功能树
2. 定义**中心事件管理（CEM, Central Event Management）**——一个独立于各App的集群级事件治理面，含事件注册表、Schema目录、订阅关系、消费者健康、死信队列、可重放历史
3. 定义**每功能原子升级（PFAU, Per-Feature Atomic Upgrade）**——以单个功能为粒度，支持版本声明、灰度生效、跨节点一致性确认、原子回滚；保证一个功能的"上线"或"回滚"在管理员看来是一个不可分割的、有开始时间与完成时间的操作
4. 定义**集群运营控制台（COC UI）**——管理员可见的Web控制台，集中展示功能矩阵、版本矩阵、事件流、依赖图、灰度进度、原子回滚面板，且与既有GM后台共用RBAC与统一入口（不另开凭证体系）
5. 给出**API契约**与**DB侧存储过程／函数**的协同约束——前者保证集群级操作以声明式API接入既有gRPC控制面（ARC-019精神），后者保证DB侧自治事务（如事件Outbox分发、功能开关生效、版本快照）不会破坏ARC-005权威边界与ARC-009幂等保证

## 1.4 判定原则（先声明，避免与既有模块混淆）

- **不替代**ARC-018／021／042的既有流程，而是**为它们提供统一操作单元、统一可视面、统一事件治理面**
- **不新建**独立限界上下文存放"功能元数据"——按ARC-008精神复用既有`admin_db`（与FR-OPS-001既有健康视图聚合API同库），不新增DBaaS
- **不绕过**ARC-019的AdminService统一入口——COC UI对系统的写操作**必须**经由AdminService，**不得**直接调用运行时受限控制通道或K8s API
- **不绕过**RGS-ADR-0020的"拒绝动态链接库"——PFAU的"补丁型Feature"上线时仍只能走编译期特性开关或沙箱脚本，**不得**上传新动态库
- **不要求**改造既有各App的事件生产代码——CEM在事件总线上挂"探针/订阅器"即可聚合，**不得**强制各App改造Publisher SDK

# 2. 术语约定

沿用RGS-REQ-002术语表及RGS-REQ-006／RGS-REQ-009／RGS-REQ-027既有术语。本文档新增：

| 术语 | 定义 |
|---|---|
| **功能（Feature）** | 本系统内可独立声明版本、独立灰度生效、独立回滚的最小操作单元；可为新限界上下文、插件、补丁、配置条目四种形态之一 |
| **功能版本（Feature Version）** | 单个Feature的语义化版本号（`major.minor.patch`+`build_meta`），由COC UI集中登记 |
| **功能矩阵（Feature Matrix）** | 全集群当前生效的Feature×版本×节点 三维表，是COC UI的"首页"视图 |
| **集群运营中心（Cluster Operations Center, COC）** | 本文档定义的管理员可见Web控制台，集中呈现功能矩阵／事件流／依赖图／灰度进度／原子回滚面板；**作为GM后台的新增页面**（不复用VIZ的无限画布页面，但可复用其渲染能力） |
| **集群运营中心服务（ClusterOpsService）** | COC UI对应的后端聚合与编排服务，gRPC接入既有控制面；归AD限界上下文扩展，不新建限界上下文（ARC-039同精神） |
| **中心事件管理（Central Event Management, CEM）** | 跨App的事件治理面，由事件注册表／Schema目录／订阅关系图／消费者健康视图／死信队列／可重放历史六部分构成 |
| **事件注册表（Event Registry）** | 集群级声明式登记，列出全部已注册的`event_type`与其所属Feature、Schema版本、Producer集合、partition_key规则 |
| **每功能原子升级（Per-Feature Atomic Upgrade, PFAU）** | 以单个Feature为粒度，提供"声明→灰度→确认→完成"四步升级与"回滚→确认→完成"三步回滚的不可分割操作；保证任一时刻要么全集群全部生效新版本、要么全集群全部回旧版本，无中间态 |
| **灰度批次（Canary Batch）** | PFAU在灰度阶段将目标节点集合拆分为多个批次，每批次满足"上一批次全部确认成功+全部健康检查通过+既定观察期已过"才推进下一批次 |
| **跨节点一致性确认（Cross-Node Confirm）** | PFAU完成态的前置条件——所有目标节点对"目标版本已生效"达成一致确认；任何节点超时未确认或确认失败则PFAU暂停等待人工介入 |
| **功能开关（Feature Flag, FF）** | 编译期特性开关插件的运行时开关（沿用ARC-021 §7.1 ①路径），COC UI通过此开关plug/unplug，**不得**上传新代码 |
| **沙箱脚本（Sandbox Script）** | 沙箱化脚本插件（沿用ARC-021 §7.1 ②路径），COC UI可热加载/热替换脚本版本，**不得**绕过Rhai沙箱的权限模型 |
| **补丁型Feature（Patch Feature）** | 文档新增的Feature形态：既有限界上下文的非破坏性补丁（如匹配算法v2、新增可选API方法）；走PFAU的"补丁通道"灰度上线，不触发ARC-018的挂载五要素 |
| **DB侧协同对象（DB-Side Coordinated Object）** | DB侧存储过程／触发器／物化视图的统称，本文档对其约定"能／不能做什么"，防止破坏ARC-005权威边界 |

# 3. 背景与课题

| 编号 | 课题 |
|---|---|
| P-COC-001 | ARC-018（重挂载）／ARC-021（轻热插拔）／ARC-042（集群部署）三套流程**没有共同的操作单元**。业务方提出"上线X功能"时，工程方需要逐项判定走哪条流程，无工具辅助，依赖个人经验 |
| P-COC-002 | 既有事件机制是各App自治发布到事件总线，**没有中心注册表**。当事件类型超过百种后（新事件族持续增加），管理员无法在一个视图中看到"哪些事件被谁生产、被谁消费、消费延迟多少、死信率多少" |
| P-COC-003 | 既有事件**没有可重放历史**——若一次发布后下游业务出现异常，需要"重放一次发布事件"以复现时，无既有机制支持 |
| P-COC-004 | 既有插件热插拔（ARC-021）的"已启用↔已禁用"切换在多节点间通过tick边界原子切换（NFR-PLG-003 p99<5秒），但**没有"功能从版本A升级到版本B"的统一操作面**——管理员需要在GM后台与CI/CD两套工具间切换 |
| P-COC-005 | ARC-042的"回滚"是按依赖图逆序的**集群级**回滚（HELM rollback所有App），但**没有"按Feature粒度的回滚"**——若只想回滚"春节活动插件v1.2→v1.1"而不影响其他功能，既有无对应操作 |
| P-COC-006 | 既有GM后台（RGS-REQ-007）的管控指令以"账号／会话／场景"为对象，**没有"功能版本"为对象的管控指令** |
| P-COC-007 | 既有VIZ画布（RGS-REQ-024）是**只读**拓扑呈现，**不含写操作**——plug/unplug、灰度推进、回滚面板都不在其范围 |
| P-COC-008 | 既有各App的事件Publisher SDK分散在各App中，**没有集群级事件注册表**——Schema变更没有审计，事件重命名没有强约束 |
| P-COC-009 | 既有DB侧自治事务（Outbox分发、触发器、物化视图刷新）由各App在其DB内自治，**没有集群级协同视图**——一次Outbox积压只能在该App的DB内排查，无法在COC UI统一看到"全集群Outbox积压矩阵" |
| P-COC-010 | 既有RGS-REQ-007 NFR-OPS-004明确"GM后台不得在任何路径下获得K8s API凭证或数据库直连凭证"，COC UI必须沿用此约束，**不得**为追求"管理便利"而开新凭证体系 |

| ID | 需求 |

| FR-CEM-001 | 系统**必须**提供集群级事件注册表，登记每个`event_type`的：所属Feature ID、Schema版本、Producer集合（App×版本）、partition_key规则、retention天数。注册表**不得**手动编辑——必须经`AdminService.RegisterEvent`API声明，由COC UI或CI自动登记 |
| FR-CEM-002 | 任一App的事件Publisher在生产事件时**必须**校验其`event_type`已注册；未注册的事件类型**必须**在生产端被拒绝（fail-fast），并写入审计日志（不允许"先生产后补登记"的灰色地带） |
| FR-CEM-003 | 事件Schema变更**必须**经`AdminService.UpdateEventSchema`API声明，**必须**标注`schema_version`自增；旧版本Schema的事件**必须**按ARC-015的Expand-Contract原则在retention窗口内仍可被消费 |

## 5.2 Schema目录

# 6. 功能需求：每功能原子升级（PFAU）

## 6.1 Feature的四种形态与统一抽象

| ID | 需求 |
|---|---|
| FR-PFAU-001 | 系统**必须**支持Feature的四种形态：①**限界上下文型**（对应ARC-018重挂载，1 Feature=1 新App挂载）②**插件型**（对应ARC-021轻热插拔，1 Feature=1 插件实例）③**补丁型**（本文档新增，1 Feature=1 既有App的非破坏性补丁，如匹配算法v2、新增可选API方法）④**配置型**（对应ARC-016，1 Feature=1 数表条目或配置中心条目） |
| FR-PFAU-002 | 任意Feature的元数据**必须**统一存于`feature_registry`表（同`admin_db`），字段至少包含：`feature_id`（稳定不变）、`feature_type`（四选一）、`current_version`、`target_version`、`depends_on`（Feature级依赖，对应ARC-042的`depends_on`）、`status`（pending/in_progress/active/rolling_back/rolled_back/deprecated） |
| FR-PFAU-003 | 任意Feature的版本声明**必须**是语义化版本（`major.minor.patch`+可选`build_meta`），且**必须**在`feature_version_history`表追加不可变记录（**不得**覆盖或删除历史） |

## 6.2 升级与回滚流程

| ID | 需求 |
|---|---|
| FR-PFAU-010 | Feature升级**必须**遵循"声明→灰度→确认→完成"四步状态机，任何步骤失败**必须**暂停并等待人工介入（COC UI提供"重试／跳过／回滚"三选一人工操作，**不得**自动推进） |
| FR-PFAU-011 | Feature回滚**必须**遵循"回滚→确认→完成"三步状态机，回滚目标版本**必须**为`feature_version_history`中已存在的`active`状态版本，**不得**回滚到从未生效的版本 |
| FR-PFAU-012 | 灰度阶段**必须**支持多批次拆分（默认5批次，每批20%节点，可调），批次间**必须**等待"上一批次全部确认成功+既定观察期已过"才推进，**不得**跳过批次 |

## 6.3 跨节点一致性确认

| ID | 需求 |
|---|---|
| FR-PFAU-020 | 任一Feature的"完成"前置条件**必须**是"全集群目标节点对目标版本已生效达成一致确认"，确认机制为：①运行时通过既有健康检查端点声明"我已加载目标版本"②控制面（ClusterOpsService）收集所有节点声明，缺失或超时未声明的节点**必须**阻止状态机推进 |
| FR-PFAU-021 | 确认超时阈值**必须**可配置（默认120秒，PH-7前根据实测调整），超时后PFAU暂停，控制面写入"待人工处理"队列 |
| FR-PFAU-022 | 任意节点在升级过程中失联（K8s Pod异常退出／节点失联）**必须**触发自动回滚至上一稳定版本（**不得**等人工介入后才回滚，与NFR-AV-007同等量级的自动回滚） |

## 6.4 灰度策略

| ID | 需求 |
|---|---|
| FR-PFAU-030 | 灰度策略**必须**支持：①按节点百分比（默认20%递增）②按节点标签（如`region=cn-east-1`）③按Feature级依赖顺序（先升级被依赖的Feature）三种模式，可叠加 |
| FR-PFAU-031 | 灰度批次**必须**可由COC UI动态调整（如"第2批从20%扩到40%"），**不得**要求重新提交版本声明 |
| FR-PFAU-032 | 灰度阶段**必须**实时展示"每批次成功率／错误率／p99延迟"指标，**不得**仅展示"进行中"状态（沿用ARC-017可观测性要求） |

## 6.5 补丁型Feature的特殊约束

| ID | 需求 |
|---|---|
| FR-PFAU-040 | 补丁型Feature**必须**遵守ARC-015 Expand-Contract——补丁只可新增API方法／新增可选字段，**不得**修改既有API语义、**不得**删除既有字段、**不得**改变既有事件的Schema语义（仅可新增`schema_version`） |
| FR-PFAU-041 | 补丁型Feature上线**必须**经自动化测试门禁（既有回归测试+金丝雀测试），门禁失败**不得**进入灰度阶段（**不得**让COC UI成为绕过测试的入口） |
| FR-PFAU-042 | 补丁型Feature回滚**必须**不要求旧版本二进制存在——回滚指"关闭新特性开关（FF off）"，**不得**触发K8s镜像回退（与"插件型Feature回滚"的语义不同，须在COC UI明确区分） |

## 6.6 集群级一致性

| ID | 需求 |
|---|---|
| FR-PFAU-050 | 任意Feature升级／回滚**必须**与依赖它的其他Feature保持版本兼容——若升级Feature A会导致Feature B不兼容，控制面**必须**自动拒绝Feature A的"完成"步骤并提示"需先升级Feature B" |
| FR-PFAU-051 | 任意Feature升级／回滚**必须**在COC UI留下完整审计记录（操作者／时间／目标版本／灰度进度／确认节点列表／结果），保留期与NFR-OPS-005一致（3年） |

# 8. 功能需求：API契约与DB侧协同约束

## 8.1 集群运营API契约

| ID | 需求 |
|---|---|
| FR-API-001 | ClusterOpsService**必须**以gRPC对外暴露（与既有业务服务同栈），**不得**新增REST/HTTP endpoint（避免API风格碎片化） |
| FR-API-002 | 全部集群运营API**必须**是**声明式**API——调用方提交"目标状态"，由ClusterOpsService负责将实际状态推向目标状态，**不得**命令式API（"执行这个步骤"）以减少调用方与服务端版本耦合 |
| FR-API-003 | 全部集群运营API**必须**携带`request_id`（幂等键，同ARC-009），重复提交相同`request_id`**不得**产生副作用 |
| FR-API-004 | 全部集群运营API的gRPC方法**必须**是流式（`Bidi streaming`或`Server streaming`），用于返回灰度进度等长周期状态（**不得**用Unary调用+客户端轮询） |
| FR-API-005 | 全部集群运营API**必须**经既有AdminService转发（沿用ARC-019），**不得**让COC UI或第三方直接调用ClusterOpsService |

## 8.2 DB侧存储过程／函数约束

| ID | 需求 |
|---|---|
| FR-DB-001 | DB侧存储过程／函数**仅允许**承担三类职责：①事件Outbox轮询分发（每App自治）②功能开关（FF）应用（每Feature在所属App的DB中有一行FF表）③Feature版本快照（`feature_version_history`表追加记录的DB trigger）。**不得**承担业务逻辑——业务逻辑必须在App代码中（沿用RGS-ADR-0022业务逻辑不入库） |
| FR-DB-002 | DB侧存储过程／函数**不得**跨限界上下文直接访问其他DB（同ARC-008），跨库协同**必须**经既有gRPC/事件机制 |
| FR-DB-003 | DB侧存储过程／函数**不得**绕过ARC-009幂等保证——任何"按时间窗口批量更新"的操作**必须**幂等（基于`feature_id`+`version`+`applied_at`三列唯一约束） |
| FR-DB-004 | DB侧存储过程／函数**不得**持有长事务——单次执行**必须**在5秒内完成（超时则由COC UI"DB协同对象健康"页面告警，**不得**静默重试） |

## 8.3 事件总线契约

| ID | 需求 |
|---|---|
| FR-API-010 | 事件总线**必须**为CEM提供"事件注册变更"事件（`coc.event_registry_changed`），CEM订阅此事件**必须**实时更新事件注册表，**不得**要求CEM轮询（避免延迟与资源浪费） |
| FR-API-011 | 事件总线**必须**为COC UI提供"Feature状态变更"事件（`coc.feature_state_changed`），订阅此事件的应用**应当**能实时更新本地缓存（沿用ARC-009 Eventually Consistent精神） |
| FR-API-012 | 事件总线**不得**因CEM的订阅而显著增加生产路径延迟——CEM的订阅**必须**走"只读镜像"链路（消费事件总线的只读副本，**不得**与生产App竞争consumer线程） |

| NFR-COC-009 | 兼容性 | 既有GM后台 | COC UI作为新增顶级页面**不得**改变既有GM后台的页面布局、RBAC、入口；既有功能测试**不得**因COC UI新增而回归失败 |
| NFR-COC-010 | 可回滚性 | COC UI自身上线后发现问题 | 可在30分钟内通过Helm回滚至上一版本（沿用NFR-AV-007同等量级），回滚**不得**影响PFAU进行中实例的可见性（实例元数据持久化于`admin_db`，COC UI仅是视图层） |

# 11. 架构设计方针 ARC-051

本节为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接RGS-REQ-009新增的ARC-021（中间历经ARC-030〜050的领域方针）。**决定事项**，变更须经ADR与审批。

## 11.1 ARC-051：集群运营中心、中心事件管理与每功能原子升级（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | ①引入"功能（Feature）"作为集群级操作的统一单元，覆盖ARC-018（限界上下文）、ARC-021（插件）、本文档新增的"补丁型"、ARC-016（配置）四种形态②建立"中心事件管理（CEM）"集群级事件治理面，含事件注册表、Schema目录、订阅关系、消费者健康、死队列、可重放历史六部分③建立"每功能原子升级（PFAU）"操作模型，以"声明→灰度→确认→完成"四步状态机保证Feature从版本A到版本B的升级是跨节点一致的、原子性的、可回滚的④提供"集群运营控制台（COC UI）"作为管理员可见的统一操作面，作为GM后台的新增顶级页面，沿用既有RBAC与AdminService统一入口，不另开凭证体系⑤API契约采用声明式+流式gRPC，DB侧存储过程／函数被严格限制在Outbox分发、FF应用、版本快照三类协同职责 |
| **理由** | ARC-018／021／042／019四块已有方针各自独立、互不重复，但**没有以"功能（Feature）"为操作单元的统一定义**。当系统演进到22+个域、上百种事件族、ARC-021插件机制上线后，管理员需要一个统一视图与统一操作面，否则会出现"升级粒度混乱／事件流不可观测／原子性不可视"三类反复出现的问题。本方针将既有四块按"Feature"收束为同一棵树，新增"补丁型"Feature补足既有App非破坏性升级的流程缺口，定义CEM解决"事件无中心治理面"的问题，定义PFAU解决"升级原子性不可视"的问题 |
| **Feature的四种形态** | ①**限界上下文型**：对应ARC-018重挂载，Feature的`target_version`即新App的Helm chart version；②**插件型**：对应ARC-021轻热插拔，Feature的`target_version`即插件版本号（编译期开关插件）或脚本版本号（沙箱脚本插件）；③**补丁型**（本文档新增）：既有App的非破坏性补丁，Feature的`target_version`即补丁二进制版本号（不走ARC-018挂载五要素，走FF off/on语义回滚）；④**配置型**：对应ARC-016，Feature的`target_version`即数表条目版本号 |
| **CEM的范围** | 事件注册表、Schema目录、订阅关系、消费者健康、死信、可重放历史六部分。**不**包括各App的业务事件内容定义（各App自治，**不**强制统一Publisher SDK），CEM在事件总线上挂"探针/订阅器"聚合即可 |
| **PFAU的原子性边界** | "原子"指"全集群目标节点对目标版本已生效达成一致确认"——**不**指"全部节点同时切换"（物理上不可能）。任一节点超时未确认或确认失败则PFAU暂停，由人工决定重试／跳过／回滚 |
| **COC UI的边界** | ①**仅作为GM后台新增页面**（顶级页面），沿用既有RBAC、AdminService统一入口、审计通路；②**复用**VIZ域的无限画布渲染能力（FR-COC-003），**不**单独开发前端；③**写操作全部经AdminService**（FR-COC-020），**不**直接调用运行时或K8s API |
| **API契约** | 声明式（FR-API-002）+ 流式gRPC（FR-API-004）+ `request_id`幂等键（FR-API-003）+ 全部经AdminService转发（FR-API-005） |
| **DB侧约束** | 仅Outbox分发、FF应用、版本快照三类协同职责（FR-DB-001）；不跨库（FR-DB-002）；幂等（FR-DB-003）；不长事务（FR-DB-004） |
| **否决方案1** | "为简化COC UI实现，让COC UI直接调用K8s API做部署"——破坏NFR-OPS-004（GM后台不得持有K8s凭证），爆炸半径不可控，已否决 |
| **否决方案2** | "CEM在每个App的DB中建独立Schema目录表"——破坏ARC-008（独立DB原则），增加跨库同步成本，已否决 |
| **否决方案3** | "PFAU的'补丁型Feature'允许上传新动态库"——破坏RGS-ADR-0020（拒绝动态链接库加载），已否决 |
| **适用范围** | 全部Feature的升级／回滚／热插拔操作；全部事件族的中心治理；COC UI的全部读写操作。**不**覆盖各App内部业务事件的具体业务语义（属各App自治） |

# 12. 验收标准

| ID | 验收标准 |
|---|---|
| AC-COC-001 | 功能矩阵首页能在2秒内呈现全集群当前生效的Feature×版本×节点三维表，且数据与各App实际声明版本一致（无缓存漂移） |

| AC-COC-003 | 模拟一次"补丁型Feature"上线，验证：①未经自动化测试门禁的补丁无法进入灰度阶段②回滚操作仅关闭FF开关，**不**触发K8s镜像回退 |
| AC-COC-004 | 事件流视图能展示当前活跃事件族列表，每条附"Producer数／Consumer Group数／p99延迟／死信率"四指标，且指标数据来自既有可观测性基础设施（**不**为CEM新增采集SDK） |

| AC-COC-006 | 渗透测试验证：COC UI的写操作全部经AdminService转发，**不**存在任何直接调用K8s API、数据库直连或运行时受限控制通道的路径（沿用NFR-OPS-004） |

| AC-COC-009 | COC UI本身可在30分钟内通过Helm回滚至上一版本（沿用NFR-AV-007），回滚后PFAU进行中实例的可见性不丢失（实例元数据持久化于`admin_db`） |
