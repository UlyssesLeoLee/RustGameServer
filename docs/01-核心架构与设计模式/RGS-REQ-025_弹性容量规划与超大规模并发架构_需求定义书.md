# 1. 前言

## 1.1 目的

RGS-REQ-001既定的容量目标止步于10万CCU（NFR-PE-002/019的验证基准），且RSK-006已明确标注"其现实性存疑，待PH-4实测数据外推验证"。此前的架构讨论从未系统性回答：**从5万日活并发的初期规模，成长至千万级并发时，架构该如何分阶段演进，而不是推倒重来**。本文档补齐这一空白，核心不是承诺"千万并发在今天就能跑起来"，而是**在架构层面预留演进路径**——今天的设计决定不因未来10倍、100倍的增长而需要推倒重来。

## 1.2 判定原则（先声明，避免误解）

- 本文档**不要求**在当前阶段（PH-1〜PH-6）就构建千万级并发的完整基础设施——这既不现实也违反ARC-014"未证明不引入复杂性"的既定判定基准。本文档要求的是**架构决策不排除未来演进的可能性**，即"预留"而非"预建"
- 容量的跨级增长**主要**依靠**横向分片**（多个独立的服务器分组，见§6），**不是**依靠单个分片内部无限堆叠资源——单集群/单分片的垂直扩容有物理上限（同ARC-001"场景为Actor单位"已确立的单线程顺序执行模型，不可能通过加机器突破单场景的tick预算约束）
- 插件热插拔（RGS-REQ-009/ARC-021既有能力）**不因**容量级别提升而失效或降级为需要停机——这是本文档对"架构灵活应对"的具体化要求之一，而非事后补丁

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 容量级别（Capacity Tier） | 按并发规模划分的架构演进阶段，见§5.1，每级对应不同的基础设施拓扑复杂度 |
| 横向分片（Horizontal Shard） | 一组相互独立、各自完整的服务器部署单元（复用RGS-REQ-023"逻辑服"概念，但强调其作为容量扩展手段的架构属性），分片间玩家数据不互通 |
| 弹性预留（Elastic Reservation） | 在常态负载之上预先保留的容量余量，用于吸收突发流量在自动扩容生效前的窗口期 |
| 预测性预热（Predictive Pre-warming） | 基于已知事件（活动上线、版本更新）提前扩容，区别于被动响应负载变化的自动扩缩容 |

# 3. 背景与课题

| 课题编号 | 课题 |
|---|---|
| P-CAP-001 | 现有容量目标（10万CCU）与"千万级并发"之间存在两个数量级的差距，缺少中间演进阶段的架构规划，容易在业务增长压力下被迫仓促重构 |
| P-CAP-002 | 单个ECS场景Actor的tick处理是单线程顺序执行（ARC-001既定），物理上无法通过增加单机资源无限扩容，容量突破必须依靠分片，但分片带来的"玩家分布在哪个分片""分片如何扩缩"从未设计 |
| P-CAP-003 | 突发流量（如版本更新后的回流高峰、活动开启瞬时涌入）若完全依赖被动HPA自动扩容，15分钟量级的扩容窗口期（NFR-PE-019既定）内的容量缺口会直接影响玩家体验，需要预留与预测性手段配合 |
| P-CAP-004 | 插件热插拔（ARC-021）此前的设计与验证均在既有10万CCU量级下考虑，未明确其在更大规模、更多分片下的行为——例如跨分片的插件状态同步是否会成为新瓶颈 |

# 5. 功能需求：容量分级模型

| 编号 | 需求 |
|---|---|
| FR-CAP-001 | 系统**必须**定义明确的容量级别模型，**至少**包含以下四级：**T0**（初期规模，日活并发约5万，对应约当前RGS-REQ-001既定的1,000〜10,000 CCU负载试验量级）、**T1**（既有NFR-PE-002/019验证目标，10万CCU，单区域单/少量分片）、**T2**（百万级并发，多分片常态化，需分片路由与跨分片治理）、**T3**（千万级并发，多分片+可能的多区域，需重新评估ARC-034单区域方针） |
| FR-CAP-002 | 每个容量级别**必须**明确其对应的架构复杂度增量（如T1→T2新增分片路由组件，T2→T3可能触发RGS-REQ-020 FR-INF-004多区域评估门禁），**不得**跳级实施——每级演进**必须**经ARC-014/026同等评审后方可进入下一级基础设施建设，防止提前引入不必要的复杂度（同ARC-014"未证明不引入复杂性"精神在容量维度的应用） |
| FR-CAP-003 | 容量级别之间的**触发条件**（何时评估从T_n升级至T_n+1）**必须**明确且可监控（如CCU持续超过当前级别目标值的80%达N天），**不得**是模糊的"业务需要时再说" |

# 6. 功能需求：横向分片架构

| 编号 | 需求 |
|---|---|
| FR-CAP-010 | T2级别起，系统**必须**支持横向分片：多个相互独立的部署单元（复用RGS-REQ-023"逻辑服"概念），各分片拥有独立的运行时节点池、独立的数据库实例，分片间**不共享**玩家实时状态 | 
| FR-CAP-011 | 分片间**允许**共享的能力**必须**明确列出边界（如：全局排行榜可能需要跨分片聚合，复用RGS-REQ-017 ARC-031派生视图思想；账号身份系统FR-IDN系列可能需要跨分片唯一，复用RGS-REQ-021既有设计），**不得**假设"分片天然完全隔离"而忽略这类跨分片诉求，也**不得**为追求跨分片一致性而重新引入分片存在的意义之矛盾（分片的意义正是避免单点无限扩容） |
| FR-CAP-012 | 分片的新增/下线**必须**复用ARC-018既定挂载/退场判定原则与RGS-REQ-023§7合服/分服演练流程，**不得**为分片扩容单独发明一套流程 |
| FR-CAP-013 | 分片路由（玩家如何被分配到某个分片）**必须**复用RGS-REQ-023 FR-PLT-010〜013既定的选服路由设计，**不得**重复建设 |

# 7. 功能需求：快速扩容与预留设计

| 编号 | 需求 |
|---|---|
| FR-CAP-020 | 每个容量级别**必须**在其目标负载之上预留明确的弹性余量（如目标CCU的20%，具体值TBD-CAP-001），该余量**必须**是**已就绪可承接流量**的容量，而非仅是"可以临时申请"的理论上限——弹性预留的意义正是覆盖HPA扩容生效前的窗口期（NFR-PE-019既定15分钟量级） |
| FR-CAP-021 | 系统**必须**支持**预测性预热**：对已知的流量突增事件（版本更新公告、活动开启时间），**应当**支持在事件发生前按计划提前扩容，**不得**仅依赖被动HPA响应已发生的负载变化 |
| FR-CAP-022 | 无状态的业务服务组件（Rust微服务，PL/EC/MT/GD等）**必须**保持水平扩容的**无状态设计**（复用既有ARC-005/006原则的自然结果），扩容**不得**要求业务服务代码变更，仅需增加副本数（复用既有HPA机制，RGS-BAS-002§2.2.2） |
| FR-CAP-023 | 有状态的场景运行时节点（ECS场景Actor）扩容**必须**以"新增场景实例分布到新节点"的方式实现（复用既有ARC-001场景为单位的既定设计），**不得**尝试将单个场景的模拟拆分到多机（违反ARC-001"数据连续排布，无需加锁"的核心理由） |
| FR-CAP-024 | 数据库层面的扩容（读多写少场景）**必须**优先通过既有只读副本（复用RGS-BAS-007既定标准）与分区（RGS-BAS-007§4）吸收，**仅**当单分片内单库确已成为瓶颈时才考虑该分片内的进一步拆分，遵循"先用足既有手段，再引入新复杂度"的ARC-014精神 |

# 8. 功能需求：插件热插拔在高并发下的适用性

| 编号 | 需求 |
|---|---|
| FR-CAP-030 | 插件热插拔（既有ARC-021）**必须**在全部容量级别（T0〜T3）下保持可用，**不得**因规模增长而降级为需要停机维护窗口才能操作 |
| FR-CAP-031 | 分片架构下（T2+），插件的启用/禁用/回滚**必须**支持**按分片粒度**独立操作（如某活动插件仅在部分分片开放测试），**不得**强制要求全部分片同步生效，复用既有RGS-BAS-005插件注册表设计并扩展分片维度字段 |
| FR-CAP-032 | 插件状态的跨节点同步机制（既有RGS-BAS-005§5）**必须**在分片规模扩大后仍满足既有同步时延目标，若既有机制在T2+规模下不再满足，**必须**先修订该同步机制而非默认其自然适用——这是**明确的验证要求**而非假设 |

# 10. 架构设计方针 ARC-040

## 10.1 ARC-040：容量分级与横向分片的弹性预留原则（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | ①容量增长**必须**按T0〜T3四级分阶段演进，每级演进须经ARC-014/026评审，**不得**跳级实施②千万级并发的达成手段**必须**是**横向分片**（多个独立部署单元），**不是**单分片内无限垂直扩容——这是由ARC-001"场景为Actor单位、单线程顺序执行"这一既有架构事实决定的物理约束，而非可选的设计偏好③各容量级别**必须**预留可承接流量的弹性余量，**不得**仅依赖事后被动扩容④插件热插拔能力**不得**因容量级别提升而降级 |
| **理由** | ①分阶段演进是ARC-014"未证明不引入复杂性"精神在容量维度的直接应用——今天不该为不存在的千万并发预建整套多区域多分片基础设施，但也不该因为"当前用不到"就在架构决策上排除演进可能性，二者的平衡点是"预留而非预建"②横向分片是ARC-001既有决定的必然推论：既然单场景不可拆分到多机，容量突破只能靠"更多独立的场景/分片"而非"让单场景跑得更快"，这不是本文档新提出的判断，而是既有架构的逻辑延伸③被动扩容存在窗口期（NFR-PE-019的15分钟量级），突发流量若无预留余量吸收，窗口期内的体验损失是确定会发生的，不是概率性风险 |
| **与ARC-018的关系** | 分片本质上是"多个独立部署单元"，其新增/下线**复用**ARC-018既定挂载/退场判定原则，**不新建**独立的分片管理流程 |
| **与ARC-034的关系** | T3级别可能触发RGS-REQ-020 FR-INF-004多区域评估门禁——本文档**不**提前批准多区域，触发时仍须走该既定评审流程 |
