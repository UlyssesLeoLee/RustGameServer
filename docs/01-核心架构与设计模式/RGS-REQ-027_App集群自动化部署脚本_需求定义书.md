# 1. 前言

## 1.1 目的

系统当前已有22个以上域文档，每个域对应一个Atomic App，其接入遵循ARC-018（RGS-REQ-006）与RGS-BAS-002定义的**挂载脚手架**（独立DB、gRPC、Helm chart、网关/事件注册、可观测性接入、检查清单）。该脚手架解决的是"**单个** App如何正确接入既有集群"的问题，但从未有文档回答"如何从零**构建整个集群**"——例如：新开一个地区/环境（RGS-BAS-017拓扑设计下的新Multi-AZ环境）、灾备重建、复刻一套开发/预发环境。当前唯一的做法是运维人员人工按记忆顺序、逐个App执行既有脚手架步骤，存在三个具体风险：①遗漏依赖顺序（例如在网关/事件总线尚未就绪前误启动业务域App，导致注册失败或数据丢失）②遗漏某个App（清单式人工核对不可靠）③无法可重复地复现同一集群状态（用于灾备演练或多套环境对齐）。本文档定义**集群级部署编排自动化**的需求，其价值在于**编排已有的、逐App的挂载步骤**，而非发明新的部署机制。

## 1.2 判定原则（先声明，避免误解）

- 本文档**不替代**ARC-018的挂载脚手架，也**不新增**新的部署工具链；编排脚本调用的每一步骤，其实现仍是既有的GitOps/Helm Release流程（RGS-BAS-002已声明"复用既有GitOps/Helm Release流程，不新建独立部署工具链"），本文档的编排层只负责**排序、依赖判定、状态跟踪、失败处理**，不重新实现Helm/CI/CD本身
- "集群"在本文档中指"一整套完整跑起来的Atomic App集合"（可以是生产环境、单个开发/预发环境，或灾备重建目标），不是单指RGS-BAS-022的容量分档概念，但会引用该分档决定初始规模
- 本文档定位为**运维自动化工具**需求，不改变任何既有域的业务功能需求或数据模型

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 集群清单（Cluster Manifest） | 声明式文件，列出目标集群应包含的全部Atomic App及其目标版本、目标环境参数 |
| 依赖图（Dependency Graph） | App之间的先后依赖关系有向无环图（DAG），决定编排执行顺序 |
| 编排运行（Orchestration Run） | 一次集群清单的执行实例，具有唯一run_id，包含每个App挂载步骤的执行状态 |
| 基础设施层App（Foundation App） | 被其他App依赖、必须最先就绪的App（如网关、事件总线、配置中心、可观测性基座） |
| 业务域App（Domain App） | 依赖基础设施层App的具体业务域Atomic App（如TRD交易、SUP工单等） |

# 3. 背景与课题

## 3.1 现状

- ARC-018挂载脚手架（RGS-BAS-002）：定义单个App如何接入，未定义多App集合的执行顺序与整体状态跟踪
- RGS-BAS-017：定义了单区域Multi-AZ拓扑，但未定义"如何把这个拓扑内的全部App从零启动起来"
- RGS-BAS-022：定义了T0-T3容量分档，决定"每个App该配多少资源"，但未定义"按什么顺序把这些App部署出来"

## 3.2 课题

- **CH-DEP-01**：22+ App人工排序部署，顺序错误会导致部分App启动失败或以不一致状态运行（例如业务域App早于事件总线就绪导致订阅丢失）
- **CH-DEP-02**：新环境（开发/预发/灾备）复刻集群时，无可重复、可审计的执行记录，只能凭经验重做
- **CH-DEP-03**：部分执行失败（如第15个App失败）后，缺少"从失败点续跑"而非"全部重来"的机制
- **CH-DEP-04**：新增域App时，若未同步更新集群清单/依赖图，会导致该App在集群级部署时被遗漏——这是ARC-018脚手架检查清单未覆盖的盲区

# 4. 业务需求

| ID | 业务需求 |
|---|---|
| BR-DEP-001 | 提供一份可版本控制的集群清单，声明式列出目标集群应包含的全部Atomic App及目标版本 |
| BR-DEP-002 | 提供依赖图定义机制，保证基础设施层App先于依赖它的业务域App就绪 |
| BR-DEP-003 | 编排执行必须可重复（幂等）、可审计、支持从失败点续跑 |
| BR-DEP-004 | 支持面向不同环境（开发/预发/生产/灾备重建）复用同一套编排逻辑，仅参数化差异部分 |
| BR-DEP-005 | 新增域App时，ARC-018挂载脚手架检查清单必须包含"登记进集群清单与依赖图"这一步骤，防止遗漏 |

# 5. 功能需求：依赖图与编排

- **FR-DEP-001**：系统须提供集群清单文件格式（如YAML），字段至少包含：`app_id`（对应域简称，如GW/EVT/TRD/SUP）、`target_version`、`depends_on`（数组，引用其他`app_id`）、`scaffold_ref`（指向该App的ARC-018挂载脚手架产物，如Helm chart路径）
- **FR-DEP-002**：系统须根据`depends_on`字段构建依赖图，并校验其为有向无环图（DAG）；若检测到环依赖，编排运行须在执行前失败并报告环路径，不得静默忽略
- **FR-DEP-003**：编排执行须按依赖图的拓扑排序执行，同一层级（无相互依赖）的App允许并行部署以缩短总时长
- **FR-DEP-004**：系统须预置基础设施层App清单（网关、事件总线、配置中心/ARC-016、可观测性基座、密钥管理），依赖图校验须保证所有业务域App的`depends_on`直接或间接包含必要的基础设施层App，否则视为清单不合法
- **FR-DEP-005**：每次编排运行须生成唯一`run_id`，并记录目标集群标识（环境名）、清单版本、开始/结束时间

# 6. 功能需求：幂等性与断点续跑

- **FR-DEP-006**：单个App的部署步骤（调用既有Helm Release流程）须为幂等操作——对已处于目标状态的App重复执行不产生副作用（复用Helm的声明式特性，编排层不得引入自定义的非幂等步骤）
- **FR-DEP-007**：编排运行须持久化每个App在本次`run_id`下的执行状态（待执行/执行中/成功/失败/跳过），失败时须保留已成功App的状态，不回滚已成功部分（除非用户显式触发整体回滚，见FR-DEP-011）
- **FR-DEP-008**：编排运行支持"续跑"模式：给定一个已存在但未完成的`run_id`，仅重新执行状态为"待执行"或"失败"的App，跳过已成功的App
- **FR-DEP-009**：编排运行须对每个App的部署步骤设置超时与最大重试次数（复用既有CI/CD平台的重试机制，不新增编排层自己的重试引擎），超过重试次数后该App标记为失败，编排暂停并等待人工介入（不得自动继续部署依赖于失败App的下游App）

# 7. 功能需求：环境与容量分档

- **FR-DEP-010**：集群清单须支持按环境（开发/预发/生产/灾备）分别声明参数覆盖（如副本数、资源配额），且须显式引用RGS-BAS-022定义的T0-T3容量分档，不得在编排层重新发明容量数值来源
- **NFR-DEP-004**（容量分档参见§9）：不同环境使用同一份基础清单+环境专属参数覆盖文件，禁止为每个环境维护完全独立、易失步的清单副本

# 8. 功能需求：Dry-run/回滚/审计

- **FR-DEP-011**：系统须提供dry-run模式：仅输出将要执行的依赖图拓扑排序结果与各步骤的目标状态差异（diff），不实际触发任何部署动作
- **FR-DEP-012**：系统须提供整体回滚：对某次`run_id`中已成功部署的App，按依赖图的**逆拓扑序**（先回滚下游业务域App，再回滚基础设施层App）依次回滚到部署前版本，回滚过程本身也须记录审计日志
- **FR-DEP-013**：每次编排运行的完整执行记录（清单版本、依赖图、每步开始/结束时间、执行者、结果）须写入既有审计留痕机制（复用RGS-BAS-003§7审计设计，不新建独立审计存储）

# 10. 架构设计方针 ARC-042

**ARC-042：集群级部署编排的幂等性与依赖有序原则**

集群级部署编排是ARC-018挂载脚手架之上的**编排层**，遵循：
1. **编排层不重新实现部署机制**：所有实际部署动作仍通过既有GitOps/Helm Release流程执行，编排层只负责调用顺序、状态跟踪与失败处理
2. **依赖优先于并行**：必须先构建并校验依赖图（DAG），拓扑排序结果决定执行顺序；同层级允许并行，跨层级严禁并行
3. **幂等是硬约束**：任何编排层新增的步骤，若无法保证幂等，不得纳入编排范围，只能作为人工介入的手动步骤单独记录
4. **失败不静默、不自动扩散**：单个App失败必须暂停其下游依赖的部署，不得"跳过失败继续往下部署"，避免在缺失依赖的情况下把下游App置于不一致状态
5. **回滚遵循逆依赖序**：回滚顺序与部署顺序相反，防止先移除仍被依赖的基础设施层App

具体设计详见 RGS-BAS-024。

# 11. 验收标准

| ID | 验收标准 |
|---|---|
| AC-DEP-001 | 给定一份包含循环依赖的清单，编排系统在执行前报错并给出环路径，不发起任何部署动作 |
| AC-DEP-002 | 对同一清单重复执行编排（在无变更情况下），第二次执行不对任何App产生实际变更（幂等性验证） |
| AC-DEP-003 | 模拟第N个App部署失败，验证：下游依赖它的App均未被部署；使用续跑模式可从失败点继续，不重新执行已成功的前N-1个App |
| AC-DEP-004 | dry-run模式输出的拓扑顺序与diff与实际执行顺序一致，且dry-run不产生任何实际部署副作用 |
| AC-DEP-005 | 触发整体回滚后，验证回滚顺序为逆拓扑序，且回滚记录完整写入审计留痕机制 |

# 12. 风险与未决事项

- **TBD-DEP-001**：编排层的具体实现载体（Rust CLI工具 / 现有CI平台的Pipeline-as-Code / 两者结合）尚未选型，将在RGS-BAS-024中给出建议方案，最终选型待技术评审
- **TBD-DEP-002**：依赖图的"层级并行"上限（同时并行部署多少个同层App）未定义具体数值，需结合CI/CD平台并发配额与目标环境资源上限确定
- **RSK-DEP-001**：若集群清单与ARC-018挂载脚手架检查清单之间缺少强制联动（如CI检查），新增域App时清单登记步骤仍可能被人工遗漏，需在CI层面（复用既有`scripts/check-docs-consistency.sh`同类机制）增加校验
- **RSK-DEP-002**：灾备重建场景下，若基础设施层App本身依赖的外部状态（如数据库快照恢复）耗时远超业务域App部署，编排的"总时长"目标可能被基础设施恢复过程主导，需在NFR-DEP-003基准测算时单独考虑
