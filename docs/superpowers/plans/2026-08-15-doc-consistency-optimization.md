# Plan: 文档体系综合优化补充（跨REQ/BAS/DET各级文档一致性收尾）

## Context

本仓库文档体系遵循IPA共通フレーム的分阶段结构：需求定义书（RGS-REQ-001〜005）→ 基本设计书（RGS-BAS-001）→ 详细设计书（RGS-DET-001）。三阶段文档在本会话中先后完成，但在完成后审查发现若干**已被本文档体系自身规则要求、但尚未执行**的收尾事项——不是新的架构决定，而是文档集对自己已作出的承诺的执行。

**Spec（本计划的约束权威）**：不存在独立的规格书文件；约束权威是文档集自身已声明的治理规则，具体为：
- `docs/README.md` §3 文档管理规则（尤其规则4"未登记TBD不得遗留"、规则7"基本设计书与详细设计书矛盾时以基本设计书为准"）
- `docs/RGS-REQ-002_附件A_术语表.md` §7 表述规则与开篇"新术语的追加必须通过本附件的修订进行"
- `docs/RGS-REQ-005_附件D_问题风险管理表.md` §4.3 OSS许可盘点运维规则（LC-002/LC-004）
- `docs/RGS-BAS-001_基本设计书.md` §1.1 文档间优先级（详细设计不得变更基本设计的架构决定/逻辑数据模型，但ISS已决议的补充例外）
- ISS-012（`RGS-REQ-005`）：明确记载"需在RGS-BAS-001下次修订版（1.3）中补充至§5.4 ER图"——即本计划Task 3是**执行一项已经批准的决议**，不是新提案

## Global Constraints

- **只做补充/订正，不做架构变更**：任何编辑都不得改变已确定的架构决定（ARC-nnn）、已确定的字段设计、已确定的时序图。允许新增指针、新增术语条目、新增此前已获批准的ER实体（ISS-012）、修正已识别的措辞不一致。
- **每个任务必须更新对应文档的"修订历史"表**，并在受影响的情况下同步版本号（版本号规则：仅审批完毕的版本持有主版本号，评审中的版本记为`0.x`；已持有主版本号`1.x`的文档，追加性小修订按次版本号递增，如`1.2→1.3`，这是本文档集既有的既成模式，非新规则）。
- **不得引入新的未注册`【TBD-nnn】`**。若编辑中出现任何尚未决定的事项，必须已有对应ISS编号（复用既有的），不得凭空新增未登记的悬而未决事项。
- **不得在需求定义书/术语表中使用具体产品名**（RGS-REQ-002§7"需求定义书使用角色名，不使用产品名"），但RGS-REQ-005的OSS许可盘点表本身就是记录具体产品名的地方，不受此限。
- **无自动化测试**：本计划的"验证"手段是文档一致性核对——每个任务的验收标准写在该任务小节内，实现者必须在报告中逐条给出核对结果（如"grep确认全文再无残留旧写法"），这是文档项目里"测试"的等价物。
- 全部改动均在当前分支（`docs/basic-design-document`，非main/master）进行，改动内容全部可通过git历史回滚，无需额外worktree隔离。

## 执行顺序与依赖
