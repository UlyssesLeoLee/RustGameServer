### P0-02：`audit_log` 未按月分区（per RGS-BAS-007 §4 既定标准）

**问题描述**：
- `crates/admin-service/migrations/0001_init.sql:23-32` `audit_log` 表无 `PARTITION BY RANGE`
- RGS-BAS-007 §4 明确：`audit_log` 应按月范围分区（3 年 36 个分区滚动保留）
- RGS-REQ-001 §NFR-SE-010 双层审计要求 3 年保留期

**影响**：
- 3 年后单表 1.8 亿行（按 5M/月估算）
- 索引膨胀，查询性能劣化
- 备份/恢复成本线性增长
- GDPR 审计通路性能下降，影响合规检查

**修复建议**（PH-2 实施）：
```sql
-- 新建分区表 + 数据迁移（per Expand-Contract）
-- 1. 创建新分区表 audit_log_partitioned
CREATE TABLE audit_log_partitioned (LIKE audit_log INCLUDING ALL)
    PARTITION BY RANGE (created_at);

-- 2. 创建初始当月 + 下月分区
DO $$
DECLARE
    current_month_start TIMESTAMPTZ := date_trunc('month', now());
    next_month_start TIMESTAMPTZ := date_trunc('month', now()) + INTERVAL '1 month';
    month_after_start TIMESTAMPTZ := date_trunc('month', now()) + INTERVAL '2 month';
    current_partition TEXT := 'audit_log_y' || to_char(current_month_start, 'YYYYMM');
    next_partition TEXT := 'audit_log_y' || to_char(next_month_start, 'YYYYMM');
BEGIN
    EXECUTE format('CREATE TABLE IF NOT EXISTS %I PARTITION OF audit_log_partitioned FOR VALUES FROM (%L) TO (%L)', current_partition, current_month_start, next_month_start);
    EXECUTE format('CREATE TABLE IF NOT EXISTS %I PARTITION OF audit_log_partitioned FOR VALUES FROM (%L) TO (%L)', next_partition, next_month_start, month_after_start);
END $$;

-- 3. 数据迁移：双写期 + 后台 batch copy
INSERT INTO audit_log_partitioned SELECT * FROM audit_log WHERE created_at < now();
-- 应用层切换写入目标表

-- 4. Contract：rename + drop 旧表
BEGIN;
ALTER TABLE audit_log RENAME TO audit_log_legacy;
ALTER TABLE audit_log_partitioned RENAME TO audit_log;
-- 保留 audit_log_legacy 30 天后 DROP
COMMIT;

-- 5. 实施分区滚动 cron job（per 14-§5）
```

**推荐阶段**：**PH-2 实施 + PH-4 负载试验验证**（高优先级）

### P0-03：`outbox` × 6 域未按周/月分区（per RGS-BAS-007 §4）

**问题描述**：
- 6 域 `outbox` 表（player / economy / match / social / admin / cluster_ops）均无分区
- RGS-BAS-007 §4：outbox 类高频写表应按周/月范围分区（已发布短期归档后清理）
- 6 域合计：6 × 千万/日 × 365 ≈ 数十亿/年

**影响**：
- `idx_outbox_pending` / `idx_outbox_in_flight` 索引膨胀
- `status='sent'` 历史数据无法快速清理
- worker 拉取 pending 性能劣化

**修复建议**（PH-2 实施）：
- 按 `created_at` 月度范围分区（per 域吞吐量调整）
- 已发布（`status='sent'`）的记录通过 DETACH 旧分区 + 归档清理
- 实施 cron job：每月 1 号建下下月分区 + 清理 90 天前分区

**模板 DDL**（6 域共用）：
```sql
-- per 13-Outbox 跨域模板
CREATE TABLE IF NOT EXISTS outbox (
    ... -- 同模板
) PARTITION BY RANGE (created_at);

-- 初始分区
DO $$
DECLARE
    current_month_start TIMESTAMPTZ := date_trunc('month', now());
    next_month_start TIMESTAMPTZ := date_trunc('month', now()) + INTERVAL '1 month';
    current_partition TEXT := 'outbox_y' || to_char(current_month_start, 'YYYYMM');
    next_partition TEXT := 'outbox_y' || to_char(next_month_start, 'YYYYMM');
BEGIN
    EXECUTE format('CREATE TABLE IF NOT EXISTS %I PARTITION OF outbox FOR VALUES FROM (%L) TO (%L)', current_partition, current_month_start, next_month_start);
    EXECUTE format('CREATE TABLE IF NOT EXISTS %I PARTITION OF outbox FOR VALUES FROM (%L) TO (%L)', next_partition, next_month_start, date_trunc('month', now()) + INTERVAL '2 month');
END $$;
```

**推荐阶段**：**PH-2 实施**（6 域同步；用独立 migration 0006_outbox_partitioned 模式）

### P1-03：`decks.like_count` 冗余字段（应拆 `deck_likes` 表）

**问题描述**：
- `crates/player-service/migrations/0005_decks.sql:63-64` `like_count` 存点赞数
- 每次点赞需 `UPDATE decks SET like_count = like_count + 1 WHERE deck_id = ?` → 行级锁 + 热点行写竞争
- 1 个 deck 被 1000 个用户同时点赞 → 串行化

**影响**：
- 热门 deck 性能瓶颈
- OCC 模式下 `WHERE version = ?` + retry 增加

**修复建议**（PH-2 实施）：
```sql
-- 新建 deck_likes 表
CREATE TABLE IF NOT EXISTS deck_likes (
    deck_id UUID NOT NULL, -- 弱引用 decks.deck_id
    player_id UUID NOT NULL, -- 跨域弱引用 players.id
    liked_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (deck_id, player_id)
);
CREATE INDEX IF NOT EXISTS idx_deck_likes_player ON deck_likes (player_id);
CREATE INDEX IF NOT EXISTS idx_deck_likes_deck_count ON deck_likes (deck_id);

-- 删除 decks.like_count 字段（Expand-Contract）
-- 1. 双写期：应用层写 deck_likes + 保留 decks.like_count
-- 2. 切换：查询走 `SELECT COUNT(*) FROM deck_likes WHERE deck_id = ?`（用 idx_deck_likes_deck_count）
-- 3. Contract：DROP COLUMN decks.like_count
```

**推荐阶段**：**PH-2 实施**

### P1-10：`merge_conflict_rule_set_v2.locked_at` 缺修改防护触发器

**问题描述**：
- `crates/cluster-ops/migrations/0020_lcm_tables.sql:128-137` `locked_at` 非空时**应用层**禁 UPDATE/DELETE
- 没有 DB 层强保证
- 应用层 bug 或直接 SQL 都能绕过

**修复建议**（per ARC-023 极窄允许边界）：
```sql
-- BEFORE UPDATE/DELETE 触发器（属"单表数据完整性 + 不产生跨表副作用"，符合 ARC-023）
CREATE OR REPLACE FUNCTION merge_conflict_rule_set_v2_locked_no_modify()
RETURNS TRIGGER AS $$
BEGIN
    IF OLD.locked_at IS NOT NULL THEN
        RAISE EXCEPTION 'merge_conflict_rule_set_v2 is locked at %, modifications not allowed (per FR-LCM-062)', OLD.locked_at;
    END IF;
    RETURN OLD;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_merge_conflict_locked_no_update ON merge_conflict_rule_set_v2;
CREATE TRIGGER trg_merge_conflict_locked_no_update
    BEFORE UPDATE OR DELETE ON merge_conflict_rule_set_v2
    FOR EACH ROW EXECUTE FUNCTION merge_conflict_rule_set_v2_locked_no_modify();
```

**注意**：触发器**不**做"修改"操作本身（仅抛异常），属 ARC-023 极窄允许范围。

**推荐阶段**：**PH-2 评审 + ADR 登记**

- 滚动清理：每月 1 号建下下月分区 + 清理 3 个月前分区

**推荐阶段**：**PH-2 评审 + PH-4 验证**

### P1-16：`audit_log.actor_id` 同库弱引用（见 P1-05 #2）

### P1-17：玩家删除时 `moves` 删除破坏回放完整性

**问题描述**：
- `moves.player_id` 跨域弱引用（match_db ← player_db）
- 玩家 GDPR 删除时，应用层需 `DELETE FROM moves WHERE player_id = ?`（per [15-§6](#6-gdpr-合规per-nfr-se-010-双层审计)）
- 但 moves 是 replay 完整性的一部分——删除后 `replays.object_key` 指向的 replay 数据"残缺"

**影响**：
- 合规删除 vs 业务数据完整性冲突
- 玩家 A 删除后，玩家 B 查看与 A 的对局 replay 看不到 A 的 moves

**修复建议**（PH-2 评审）：
- **选项 A（推荐）**：moves 删除时同步 anonymization（`UPDATE moves SET player_id = 'ANONYMIZED_<hash>'`）而非 DELETE
- **选项 B**：replay 数据存对象存储，删除玩家时仅元数据 anonymization，不动对象存储
- **选项 C**：保留 moves 但加 `is_anonymized BOOLEAN` 标志，查询时显示匿名

**推荐阶段**：**PH-2 评审 + GDPR Lead 拍板**
