# 1. 前言

## 1.1 目的

本文档展开RGS-REQ-001 BR-009（玩家间交易）、FR-EC-008（交易的原子成立）、FR-WF-002（交易工作流）、ST-004（交易状态机：`Draft → Offered → Accepted → Settled／Cancelled、Expired`）为可实现的功能需求集。这些编号自基准文档制定起即已存在，但从未被展开——RGS-REQ-016在其§3背景课题中已指出这一点，但该文档明确将交易排除在其范围之外（其展开对象为BR-007/008，不含BR-009）。

## 1.2 判定原则（先声明）

- 交易**不新建**独立限界上下文：交易的挂单/撮合/成交结算依附既有玩家经济上下文（EC）运行，遵循ARC-018挂载判定原则
- 交易成交的最终价值转移**必须**复用既有FR-EC-003确定请求路径，**不得**新设发放/扣款旁路（与RGS-REQ-017 FR-GSM-013同类原则的又一次应用）
- 交易**不是**拍卖行／全服市场（那是更大范围的产品决策，超出本文档范围）：本文档定义的是点对点（双方对等）交易，若未来需要拍卖行/市场，属新的业务需求，须另行提案

## 1.3 关联文档

| 文档 | 关系 |
|---|---|
| RGS-REQ-001 | 展开BR-009／FR-EC-008／FR-WF-002／ST-004；复用ARC-005（Single-Writer）、ARC-006（ACK边界）、ARC-011（Saga边界） |
| RGS-REQ-016 | 大厅/社交文档明确排除交易范围，本文档补齐该空白 |
| RGS-REQ-017 | 复用同类"确定请求路径唯一化"原则（FR-GSM-013） |
| RGS-BAS-007 | 复用数据库设计标准（分区/归档，用于交易历史记录） |

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 挂单（Offer） | 交易发起方声明"以物品/货币A换取物品/货币B"的意向，尚未被对方确认 |
| 撮合 | 挂单与另一方响应之间的匹配过程（本系统为**双方主动协商式**，非自动撮合市场） |
| 原子成立 | 交易双方的物品/货币转移在同一事务边界内**同时成立或同时不成立**，不产生"甲方已扣，乙方未收到"的中间态 |

# 3. 背景与课题

| 课题编号 | 课题 |
|---|---|
| P-TRD-001 | 交易涉及双方各自的物品/货币变更，若不在同一事务边界内完成，网络中断/节点故障可能导致"单方受损"（甲方物品已转出，乙方对价未到账），這正是ARC-006确定请求路径与ARC-011 Saga边界所要解决的一类问题，但从未被具体应用到"交易"这一场景 |
| P-TRD-002 | 若无挂单超时/撤销机制，物品可能被"挂起"锁定却无法找回，影响玩家对自有资产的可用性 |
| P-TRD-003 | 交易天然是欺诈高发场景（如诱导线下支付后不发货、利用未同步的价格差进行套利），若无基本的防护设计，玩家投诉将直接涌向GM人工处理，增加RGS-REQ-007既有工单负荷 |

# 4. 业务需求

| 业务需求 | 业务需求名 | 描述 | 优先级 |
|---|---|---|---|
| BR-TRD-001 | 玩家可发起点对点交易 | 双方可协商交换物品/货币，交易结果具有原子性保证 | 高 |
| BR-TRD-002 | 交易不产生资产损失风险 | 无论网络状况如何，交易结果只有"双方成功"或"双方不变"两种终态 | 高 |
| BR-TRD-003 | 玩家可自助管理挂单 | 挂单可撤销、有明确的过期时间，不产生资产永久锁定 | 中 |

# 5. 功能需求：挂单与撮合

| 编号 | 需求 |
|---|---|
| FR-TRD-001 | 交易发起方**必须**能创建挂单，声明己方提供的物品/货币与期望获得的物品/货币，挂单**必须**指定目标玩家（点对点，非公开市场） |
| FR-TRD-002 | 挂单创建时，己方提供的物品/货币**必须**被冻结（不可用于其他操作，如出售/丢弃），冻结**必须**是显式状态标记，**不得**通过临时扣除实现（避免与背包其他并发操作产生竞态） |
| FR-TRD-003 | 挂单**必须**有明确的过期时间（默认可配置，如24小时），过期后**必须**自动解冻并转为`Expired`终态，**不得**要求任一方手动操作才能解冻 |
| FR-TRD-004 | 挂单发起方**必须**能在对方响应前主动撤销挂单，撤销**必须**立即解冻 |
| FR-TRD-005 | 交易对方响应挂单**必须**经过明确的"接受"操作（对应ST-004`Offered → Accepted`），**不得**默认接受或自动成交 |
| FR-TRD-006 | 系统**应当**对交易目标玩家的可见性做限制（如仅好友或同队伍可发起交易，具体范围留待TBD-TRD-001评审），防止陌生人骚扰式挂单 |

# 6. 功能需求：交易执行与防欺诈

| 编号 | 需求 |
|---|---|
| FR-TRD-010 | 交易双方均接受后，**必须**触发原子成立流程：双方的物品/货币变更**必须**在同一事务边界内完成（复用ARC-011 Saga边界，同RGS-REQ-001 FR-EC-008既定原则），**不得**出现单方已扣、对方未到账的中间态 |
| FR-TRD-011 | 交易的价值转移**必须**复用既有FR-EC-003确定请求路径，**不得**新设发放/扣款旁路 |
| FR-TRD-012 | 交易成立**必须**具备幂等性：客户端因网络重试重复提交同一笔"接受"操作，**不得**导致重复扣款/重复发货 |
| FR-TRD-013 | 交易过程中**不得**存在"一方已确认、允许中途反悔"的窗口——`Accepted`状态**必须**是不可逆的单向迁移，直到`Settled`（同ST-004状态机既定纪律，RGS-REQ-001第8章） |
| FR-TRD-014 | 交易双方的物品/货币快照（挂单声明的内容）**必须**在`Accepted`时刻锁定，**不得**在双方确认之间被任一方通过其他并发操作变更挂单内容（防止"临时调包"式欺诈） |
| FR-TRD-015 | 全部交易记录（含已成立、已撤销、已过期）**必须**留存审计日志（复用RGS-BAS-003§7审计设计的同类存储原则），保留期与既有审计日志一致，供玩家投诉时GM查证 |
| FR-TRD-016 | 交易记录**必须**支持按分区归档（复用RGS-BAS-007§4既定标准），避免历史交易数据无限增长影响主表性能 |
| FR-TRD-017 | 系统**应当**提供交易手续费机制（可配置比例，默认0，是否启用为运营决策），手续费的扣除**必须**在同一原子事务内完成，**不得**产生"手续费扣了但交易未成立"的情形 |
| FR-TRD-018 | GM后台**必须**能查询指定玩家的交易历史（复用RGS-BAS-003§3.4只读查询模式），作为处理交易欺诈投诉的信息来源，**不得**要求单独开发查询工具 |

# 8. 架构设计方针 ARC-032

## 8.1 ARC-032：交易的原子成立与欺诈防护边界（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | 交易**必须**建模为ARC-011既定Saga边界内的一个具体工作流实例（对应ST-004状态机），价值转移**必须**复用FR-EC-003确定请求路径。挂单内容在`Accepted`时刻**锁定**（快照隔离），防止确认窗口内的并发调包 |
| **理由** | 交易的本质是"双方各自单向操作组合成一个需要原子性的复合操作"，这正是Saga模式要解决的问题类型（同RGS-REQ-001既有的商店购买FR-EC-007/工作流FR-WF-001同类模式）。若不复用既有基础设施而另起炉灶，会重复建设幂等/补偿逻辑 |
| **与ARC-018的关系** | 交易的挂单/撮合/结算组件**依附**既有EC限界上下文，**不新建**独立限界上下文、独立数据库或独立部署单元 |
| **例外范围** | 本决定**不覆盖**拍卖行/全服市场这类"多对多撮合"场景——若未来引入，须重新评审是否需要独立的撮合引擎组件（可能触发新的ARC决定） |

# 9. 验收标准

| 编号 | 内容 |
|---|---|
| AC-TRD-001 | 交易原子成立的故障注入试验：交易成立过程中节点故障重启后，结果与不中断时一致，无单方受损（FR-TRD-010） |
| AC-TRD-002 | 挂单超时自动解冻验证：过期挂单在无人操作情况下自动转为`Expired`并解冻资产 |
| AC-TRD-003 | 幂等性验证：重复提交同一笔接受操作不产生重复扣款/发货 |
| AC-TRD-004 | GM后台交易历史查询可用性验证，支持按玩家ID检索 |
