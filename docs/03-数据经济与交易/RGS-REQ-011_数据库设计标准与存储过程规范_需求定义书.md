# 1. 前言

## 1.1 目的与本文档在文档体系中的位置

RGS-REQ-001已在DR-001〜015定义数据相关的架构级原则（OCC、Outbox、幂等等），RGS-BAS-001§5给出了5个限界上下文的**逻辑**ER设计。物理DDL（数据类型、索引、约束、分区、DDL）的归宿是各限界上下文对应的分域RGS-DTL章节：RGS-DTL-001§2.1／§3.1、RGS-DTL-015§2、RGS-DTL-016§2、RGS-DTL-025§2与RGS-DTL-026§2；新增限界上下文沿用同一分域模式。

但截至目前，**尚未定义**编写分域RGS-DTL物理DDL章节时应遵循的**通用标准**——若每个限界上下文的物理设计各自摸索命名习惯、索引策略、迁移方式，会产生标准不一致、DBA审查成本高、跨库运维工具无法复用等问题。本文档的目的：

1. 定义全系统统一的数据库物理设计标准（命名、索引、分区、迁移流程、备份恢复），作为各分域RGS-DTL物理DDL章节编写与评审的依据。
2. 对"是否使用存储过程/触发器承载业务逻辑"这一常见但本项目尚未明确表态的问题给出**架构级判定**（ARC-023），并给出其**允许的极窄使用范围**（若有）。

## 1.2 适用范围

| 范畴 | 说明 |
|---|---|
| 数据库物理设计标准 | 命名规范、索引与分区策略、迁移（migration）流程、备份恢复标准、连接池标准 |
| 存储过程/触发器使用边界 | 是否允许、允许范围、评审流程 |
| **不适用范围** | 各限界上下文的具体物理DDL（属对应分域RGS-DTL物理DDL章节，本文档是其编写前提而非替代） |

| 文档编号 | 文档名 | 与本文档的关系 |
|---|---|---|

# 2. 术语约定

沿用RGS-REQ-002术语表。本文档新增：

| 术语 | 定义 |
|---|---|
| 存储过程（Stored Procedure） | 存储并执行于数据库服务器内部的过程化代码（含PostgreSQL的函数/触发器/规则） |
| 迁移（Migration） | 对数据库schema的版本化、可重放、可回滚的结构变更操作 |
| 分区（Partitioning） | 将大表按某种策略（时间、哈希等）切分为多个物理子表以提升查询与维护性能的技术 |

# 3. 背景与课题

| 编号 | 课题 |
|---|---|
| P-DBS-001 | 若业务逻辑分散写入存储过程与Rust服务两处，会破坏CON-003"服务端主语言为Rust，业务服务用Rust编写"的既定约束，且存储过程的版本管理、代码评审、测试覆盖率通常弱于应用层代码，与ARC-015"版本演进"的既有规范难以对齐 |
| P-DBS-002 | 若各限界上下文自行命名表/列/索引，DBA与运维工具（备份脚本、监控查询）需要为每个库单独适配，运维负荷随限界上下文数量线性增长，与NFR-OP-010上限冲突 |
| P-DBS-003 | 若审计日志（`OPERATION_AUDIT`）、Outbox等高写入频率表缺少分区策略，随运营时间推移会出现查询性能劣化，且缺乏可预期的容量规划依据 |
| P-DBS-004 | 若迁移脚本无统一规范（幂等性、回滚能力），CI流水线（复用RGS-BAS-002§4.2既有骨架）中的"migrations校验"阶段无法有效把关 |

# 4. 业务需求

| ID | 需求 | 优先级 |
|---|---|---|
| BR-DBS-001 | 各限界上下文的分域RGS-DTL物理DDL章节编写须有统一可依据的标准，减少评审分歧与返工 | 高 |

# 5. 功能需求

## 5.1 命名与结构标准

| ID | 需求 |
|---|---|
| FR-DBS-001 | 数据库/表/列命名**必须**统一采用`snake_case`，且与RGS-BAS-004§4.3既有的API/日志字段命名（同一概念同一名称）保持一致，**不得**在物理层引入与逻辑设计（RGS-BAS-001§5）不同的字段拼写 |
| FR-DBS-002 | 每个限界上下文**必须**对应一个独立`database`（或经容量评审的独立`schema`，复用RGS-BAS-001§5.1、RGS-BAS-002§6.2既有判定原则），本文档不改变该既有决定 |
| FR-DBS-003 | 承载永久事实且可能并发更新的表**必须**遵循RGS-BAS-001§5.8既有的通用表结构范式（主键、`version`乐观锁列、`updated_at`） |

## 5.2 索引与分区标准

| ID | 需求 |
|---|---|
| FR-DBS-010 | 高频查询路径（对应各gRPC方法的请求字段，见RGS-BAS-001§6字段级API设计）**必须**建立与查询模式匹配的索引，索引设计须在对应分域RGS-DTL物理DDL章节中逐表说明其对应的查询场景（**不得**无理由建索引，避免写放大） |
| FR-DBS-011 | 高写入频率、随时间增长的表（审计日志`OPERATION_AUDIT`、`outbox`系列表、行为日志）**必须**采用时间范围分区，分区策略须与既定保留期（RGS-REQ-001既有保留期表：审计日志3年、行为日志400天）对齐，支持按分区批量清理（DROP PARTITION）而非逐行DELETE |

## 5.3 迁移流程标准

| ID | 需求 |
|---|---|
| FR-DBS-020 | 全部结构变更**必须**通过版本化迁移脚本执行，**不得**手工直接对生产数据库执行DDL |
| FR-DBS-021 | 迁移脚本**必须**幂等（可重复执行不产生副作用）且**应当**提供对应的回滚脚本，复用RGS-BAS-002§4.2既有CI"migrations校验"阶段的"向前迁移+回滚"演练要求 |
| FR-DBS-022 | 破坏性变更（删除列/表、修改列类型）**必须**遵循ARC-015既有Expand-Contract两阶段流程，**不得**在同一次迁移中"新增+删除"合并执行 |

## 5.4 备份与恢复标准

| ID | 需求 |
|---|---|
| FR-DBS-030 | 全部限界上下文数据库**必须**遵循RGS-REQ-001既有NFR-AV-004/005（RTO 30分钟、RPO=0同步复制），本文档不改变该目标，仅在RGS-BAS-007中给出实现层面的标准化脚本/流程 |
| FR-DBS-031 | 备份**必须**定期演练恢复（而非仅执行备份不验证可恢复性），演练结果记入运维记录 |

## 5.5 存储过程使用边界

| ID | 需求 |
|---|---|
| FR-DBS-040 | 业务逻辑（订单/交易/道具/货币计算等）**必须**在Rust服务层实现，**不得**使用存储过程/触发器承载，遵循§7 ARC-023决定 |
| FR-DBS-041 | 数据库内部**可以**使用极窄范围的过程化机制（见ARC-023允许范围），但**必须**逐项经架构评审并记录ADR，**不得**默认自由使用 |

# 7. 架构设计方针 ARC-023

本节为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接RGS-REQ-010新增的ARC-022。**决定事项**，变更须经ADR与审批。

## 7.1 ARC-023：业务逻辑不入库——存储过程的极窄允许边界（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | 本系统**不使用**存储过程/触发器承载任何业务逻辑（订单计算、道具/货币变更、状态机迁移判定等）。数据库**仅**承担数据持久化、约束校验（`CHECK`/`UNIQUE`/外键）、索引与分区等结构性职责。**唯一允许的例外**：与单表数据完整性直接相关、且不产生跨表业务副作用的**极简约束触发器**（如`updated_at`自动刷新），且须逐项经架构评审并记录ADR |
| **理由** | 延续CON-003"服务端主语言为Rust，业务服务用Rust编写"的既定约束。存储过程分散业务逻辑至两套技术栈（Rust代码+SQL过程化代码），会削弱代码评审、单元测试、版本管理（ARC-015 Expand-Contract）、可观测性埋点（RGS-BAS-004）等已围绕Rust服务建立的整套工程实践的覆盖率——存储过程内部的逻辑无法产生trace span，无法被RGS-BAS-004统一的埋点SDK覆盖，形成可观测性盲区 |
| **与ARC-009的关系** | ARC-009要求的OCC（乐观并发控制）与幂等性通过Rust服务层的"读取version→业务处理→带version条件更新"模式实现，**不**通过数据库存储过程封装该流程——保持该模式在Rust代码中可读、可测试、可埋点 |
| **与ARC-021插件体系的关系** | 若某"数据库内自动化"的诉求源于希望绕过Rust部署周期实现某种"热生效"，正确路径是RGS-REQ-009插件体系（沙箱脚本或特性开关），而非在数据库内实现过程化逻辑——两者都是"不通过传统部署周期即可生效的行为"，但插件体系有明确的沙箱边界、审计、回滚设计，数据库存储过程没有 |
| **例外的评审要求** | 极简约束触发器的例外申请须按RGS-DTL-007§5的统一登记表，在对应分域RGS-DTL的DDL章节中登记：触发器名称、所在表、具体逻辑（须为一行以内的赋值级操作）、评审人、ADR编号 |
| **否决方案** | "为提升性能，将高频路径的道具扣减逻辑写成存储过程直接在数据库内完成"——性能收益应优先通过索引优化、连接池调优、读写分离等标准手段获取（依ARC-014"默认替代方案优先"的同类精神），而非以牺牲整个工程实践体系的一致性为代价，已否决 |
| **适用范围** | 全部限界上下文数据库。RGS-REQ-009插件体系的沙箱脚本**不属于**存储过程（运行于应用进程内的沙箱引擎，而非数据库内部），不受本条约束，但受ARC-021约束 |
