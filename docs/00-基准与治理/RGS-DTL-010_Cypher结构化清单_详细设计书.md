## 1. 前言

RustGameServer 项目在 2026-10-04 通过 Cypher 结构化清单系统的全量部署，为所有 511 个 Rust 源文件生成了机械派生的代码结构清单。该系统作为 RGS-BAS-009 §4 治理闭环的 CI 机械校验框架的关键组成部分，通过以下方式增强代码治理：

1. **结构验证**：机械派生，代码变更时自动更新，杜绝手写清单与实现的漂移
2. **依赖追溯**：记录模块、类型、函数、常量之间的调用关系和跨文件依赖
3. **一致性保障**：通过两个独立验证器（不共享生成器代码）交叉核验每个清单的完整性

本设计书遵循 RGS-BAS-001 既有记述规则（§1.4 强度用语、图示规则）。

## 2. 系统概述

### 2.1 功能定位

Cypher 结构化清单系统是 RGS 项目的**代码结构静态分析框架**，旨在：

- **生成阶段**：从 Rust 源代码自动派生每文件的结构化清单（节点与关系），编码为 Cypher 查询注释
- **验证阶段**：通过六项验证规则和两个独立跨检工具（cross-checker）确保清单与代码的一致性
- **治理阶段**：将清单作为代码结构的机械记录，支持后续的架构分析、依赖追踪、以及治理策略的落地

### 2.2 部署范围

| 指标 | 数值 |
|---|---|
| 已部署 Rust 文件数 | 511 |
| 清单项目数（节点） | 4,000+ 个声明（函数、类型、模块、常量） |
| 依赖关系数（边） | 1,000+ 个函数调用，4,000+ 个跨文件引用 |
| 验证通过率 | 100% (511/511 文件通过全部 6 项规则) |
| 验证覆盖率 | 1,004/1,004 CALLS 验证，4,013/4,013 跨文件声明目标确认 |

### 2.3 关键特性

1. **完全机械派生**：无手写注解，每次生成都从源代码重新解析
2. **代码透明**：清单以注释形式嵌入，不影响编译或文档生成（cargo doc 忽略注释）
3. **版本控制友好**：idempotent 再生成，只修改清单实际变更的文件
4. **验证独立性**：生成器、验证器 A、验证器 B 使用独立的解析逻辑，互相不依赖

## 3. Cypher 清单的核心语义

### 3.1 数据模型概览

每个 `.rs` 文件的 Cypher 清单编码以下内容：

```
┌─────────────────────────────────────────┐
│ File: src/example.rs                    │
├─────────────────────────────────────────┤
│ NODES                                   │
│  • File {path, lines, crate, ...}       │
│  • Module {name, fqn, kind, ...}        │
│  • Class {name, fqn, kind, ...}         │
│  • Function {name, fqn, kind, ...}      │
│  • Variable {name, fqn, kind, ...}      │
├─────────────────────────────────────────┤
│ RELATIONSHIPS                           │
│  • CONTAINS: 文件/模块持有项            │
│  • HAS_METHOD: trait/impl 持有方法      │
│  • CALLS: 函数调用（工作区内）          │
│  • USES: 使用常量/构造类型/导入         │
└─────────────────────────────────────────┘
```

### 3.2 节点类型与属性

| 节点类型 | 何时生成 | 关键属性 | 用途 |
|---|---|---|---|
| `File` | 每个 .rs 文件 | `path`, `crate`, `module_path`, `lines`, `kind` | 文件身份与大小追踪 |
| `Module` | 每个 `mod` 声明 + 每个 crate root | `fqn`, `kind` (crate/file/inline/external_crate), `visibility` | 模块化结构，可见性 |
| `Class` | `struct`, `enum`, `trait`, `union`, `type`, `impl` 目标 | `fqn`, `kind`, `visibility`, `line`, `implements` | 类型定义与 trait 实现追踪 |
| `Function` | `fn` 声明、`macro_rules!`、测试函数 | `fqn`, `kind` (fn/method/trait_method/test/macro), `signature`, `visibility`, `attributes`, `line` | 函数粒度的控制流分析 |
| `Variable` | `const` 和 `static` | `fqn`, `kind` (const/static), `visibility`, `value_type` | 常量与静态变量追踪 |

每个节点均包含 `name` 和 `type` 字段；`fqn` (fully-qualified name) 作为跨文件链接的身份。

### 3.3 关系类型

| 关系 | 何时生成 | 应用场景 |
|---|---|---|
| `CONTAINS` | 文件/模块结构上持有项；`impl` 持有关联常量 | 从容器遍历内容，发现模块化边界 |
| `HAS_METHOD` | `trait` 或 `impl` 体声明方法 | trait 方法表，impl 的具体实现追踪 |
| `CALLS` | 函数体内调用工作区内的函数 | 函数调用图，循环检测，调用链追踪 |
| `USES` | 函数读常量、构造类型、导入/再导出符号 | 依赖分析，符号可见性验证 |

### 3.4 清单格式示例

```cypher
// ==== BEGIN CYPHER HEADER (generated by tools/cypher-header-gen; do not edit) ====
// ```cypher
// CREATE
//   (n1:File {name: "outbox.rs", type: "file", path: "crates/shared/src/outbox.rs", lines: 663}),
//   (n5:Class {name: "OutboxEntry", type: "class", fqn: "shared_platform::outbox::OutboxEntry", kind: "struct", visibility: "pub"}),
//   (n11:Function {name: "process", type: "function", fqn: "shared_platform::outbox::OutboxEntry::process", kind: "method", signature: "fn(&mut self, ...)", visibility: "pub", line: 42}),
//   ...
// MERGE (x3:Module {name: "sqlx", type: "module"}) ON CREATE SET x3.kind = "external_crate", x3.fqn = "sqlx";
// CREATE
//   (n1)-[:CONTAINS]->(n5),
//   (n5)-[:HAS_METHOD]->(n11),
//   (n11)-[:CALLS {via: "execute()"}]->(x7)
// ```
// ==== END CYPHER HEADER ====
```

## 4. 代码结构数据模型

### 4.1 数据建模原则

1. **粒度平衡**：记录函数、类型、模块，不涉及语句级细节（避免过度膨胀）
2. **跨文件追踪**：`fqn` 统一身份，支持多文件场景下的 MERGE 操作
3. **属性限制**：
   - 超长签名截断至 220 字符（避免清单膨胀）
   - 属性列表上限 6 名（external imports 上限 12）
4. **机械一致**：所有值都从源代码解析，无推测或默认值

### 4.2 跨文件依赖表示

对于工作区外的符号，清单使用 `MERGE` 语句创建或引用外部节点：

```cypher
MERGE (x3:Module {name: "sqlx", type: "module"}) 
ON CREATE SET x3.kind = "external_crate", x3.fqn = "sqlx", x3.imports = ["FromRow", "Pool", ...]
```

这允许加载所有 511 个文件的清单到一个统一的图中，而不产生重复节点。

### 4.3 可见性与访问控制建模

| 可见性 | 示例 | Cypher 表示 |
|---|---|---|
| pub | `pub fn foo()` | `visibility: "pub"` |
| pub(crate) | `pub(crate) fn bar()` | `visibility: "pub(crate)"` |
| 私有 | `fn baz()` | `visibility: "private"` |
| pub(super) | `pub(super) fn qux()` | `visibility: "pub(super)"` |

可见性用于验证跨模块调用的合法性。

## 5. 生成器设计（cypher_header.py）

### 5.1 生成流程

```
[ALL .rs FILES]
       ↓
[BASELINE HASH: code without header]
       ↓
[PARSE EACH FILE]
  • Extract: mod, struct, enum, trait, impl, fn, const, static
  • Link: CONTAINS, HAS_METHOD, CALLS, USES
  • Resolve: FQN 对每个符号，本工作区 vs 外部 crate
       ↓
[DERIVE CYPHER MANIFEST]
  • emit CREATE for nodes owned by this file
  • emit MERGE for external crates & workspace cross-refs
  • apply signature truncation, attribute capping
       ↓
[PREPEND TO FILE]
  • wrap as comment block (// ... //)
  • preserve line endings (CRLF/LF)
  • bytes after header = original file (verified by baseline)
       ↓
[IDEMPOTENT RE-RUN]
  • strip existing header if present
  • re-derive from code
  • write only if manifest changed
  • report: N files changed, M files unchanged
```

### 5.2 关键设计决策

| 决策 | 理由 | 实现 |
|---|---|---|
| **机械派生，无手写** | 杜绝版本漂移 | 每次生成都从源重新解析 |
| **注释形式** | 不影响编译 | `//` prefix，`cargo doc` 忽略 |
| **Idempotent 再生成** | 版本控制友好 | 存在的 header 先剥离，baseline hash 对比 |
| **行结尾保留** | 支持混合 CRLF/LF 仓库 | 检测原文件行结尾，生成 header 时采用相同格式 |
| **符号解析限制** | 避免假设 | 仅生成代码中真实存在的符号，unresolvable 目标计数但不猜测 |

### 5.3 规则 1-4：生成器自我约束

1. **Nothing is invented**（不发明符号）
   - CALLS 边仅在 callee 在工作区索引或文件内真实存在时才生成
   - 无法解析的调用点被计数与报告，从不猜测

2. **Code never touched**（代码完整性）
   - Header 作为字节前缀添加
   - Header 后的文件体与生成前字节一致
   - Baseline hash 验证

3. **Regeneration is idempotent**（再生成幂等性）
   - 每次生成前剥离现有 header
   - `line` 属性保持稳定
   - 两次连续运行不改变任何文件

4. **Line ending preserved**（行结尾保留）
   - 检测原文件的 CRLF 或 LF
   - Header 采用相同格式
   - 不强制统一格式

## 6. 验证框架

### 6.1 双层验证架构

Cypher 清单通过两个**代码完全独立**的验证器交叉检查，降低单一解析器偏差的风险：

```
生成器 (cypher_header.py)
    ↓
验证器 A (verify_headers.py) ← 独立解析，6 项规则
    ↓
验证器 B (cross_check_calls.py) ← 独立解析，CALLS 边逐一确认
    ↓
报告
```

### 6.2 六项验证规则（verify_headers.py）

#### 规则 1：FIDELITY（保真度）
- **检查内容**：Header 后的文件字节 hash 与 baseline hash 一致
- **失败原因**：生成器无意中修改了代码
- **恢复方案**：重新生成清单

#### 规则 2：COVERAGE（覆盖度）
- **检查内容**：源代码中的每个声明（mod, struct, fn, const 等）都有对应的 node
- **失败原因**：生成器遗漏了某个声明
- **恢复方案**：更新生成器的解析逻辑

#### 规则 3：VOCABULARY（词汇一致）
- **检查内容**：仅使用 5 个 node labels (`File`, `Module`, `Class`, `Function`, `Variable`) 和 4 个 relationship types (`CONTAINS`, `HAS_METHOD`, `CALLS`, `USES`)
- **失败原因**：生成器引入了未授权的节点或关系类型
- **恢复方案**：检查生成器是否误新增了 label/relationship

#### 规则 4：REFERENTIAL（引用完整性）
- **检查内容**：每条边的两个端点都是已声明的节点；`CALLS` 的目标必须是 `Function` 节点
- **失败原因**：清单含有悬空引用或类型不匹配的边
- **恢复方案**：清单脏了，需要重新生成

#### 规则 5：EXECUTABLE（可执行性）
- **检查内容**：Cypher 语法有效（括号平衡、语句完整、无重复变量）
- **失败原因**：生成器生成了语法错误的 Cypher
- **恢复方案**：生成器 bug，需要修复

#### 规则 6：COMMENTED（注释完整）
- **检查内容**：每行 header 都以 `//` 开头（防止误写的裸 `CREATE` 出现在 .rs 文件顶部）
- **失败原因**：生成器生成了非注释行
- **恢复方案**：生成器 bug，需要修复

### 6.3 CALLS 跨检（cross_check_calls.py）

逆向验证：对清单中的每个 `CALLS` 边，检查代码中是否真的调用了：

1. **定位函数体**：使用朴素的行号范围法（故意避免精细的 AST 遍历，以独立于生成器）
2. **查找调用**：在函数体内搜索调用目标的 FQN
3. **验证外部目标**：对于跨文件 CALLS，确认目标文件真的声明了该符号
4. **报告不可追踪**：若定位失败，报告而不计为验证通过

### 6.4 验证流程与集成

| 阶段 | 工具 | 输出 | 决策 |
|---|---|---|---|
| **Baseline** | verify_headers.py --write-baseline | .baseline.json | 建立代码指纹 |
| **生成** | cypher_header.py | 511 个 .rs 文件 + header | 产生清单 |
| **验证 A** | verify_headers.py --baseline .baseline.json | 6 项规则报告 | 逻辑验证 |
| **验证 B** | cross_check_calls.py | CALLS 边逐一确认 | 语义验证 |
| **决议** | 两个验证器全部通过 | ✓ 清单可信 | 提交/发布 |

## 7. 与 CI 机械校验框架的集成

### 7.1 治理闭环中的位置

RGS-BAS-009 §4 CI 机械校验框架包含多个验证维度：

```
┌─ 业务治理 (§5.1)
│  ├─ 永久事实标注校验
│  ├─ API 权限校验
│  └─ DB 访问路由校验
│
├─ 代码结构验证 ← RGS-DTL-010 (本文档)
│  ├─ Cypher 清单生成与验证
│  ├─ 依赖一致性检查
│  └─ 跨文件符号解析
│
└─ 文档一致性 (RGS-BAS-002 §4.2)
   ├─ ARC 序列连续性
   ├─ 需求可追溯性
   └─ 设计文档版本同步
```

### 7.2 日志事件定义

Cypher 系统的 CI 机械校验事件（新增至 RGS-BAS-009 §4.1 表格）：

| 事件名 | 触发条件 | 频率 | 采样 | 成本 |
|---|---|---|---|---|
| `gov.ci.cypher_generation_started` | 清单生成任务启动 | 每 push | release 必出 | ~200B |
| `gov.ci.cypher_generation_completed` | 生成完成（N 文件变更，M 文件不变） | 每 push | release 必出 | ~300B |
| `gov.ci.cypher_verification_passed` | 6 项验证规则 + CALLS 跨检全部通过 | 每 push | release 必出 | ~250B |
| `gov.ci.cypher_verification_failed` | 任一验证规则失败 | 偶发 | release 必出 (error!) | ~400B |
| `gov.ci.cypher_coverage_summary` | 覆盖统计：N 个节点，M 个边，K 个外部引用 | 每 push | release 必出 | ~350B |

### 7.3 与 GitHub Actions 集成

Cypher 系统作为 CI/CD pipeline 的一部分（建议位置）：

```
GitHub Push
    ↓
[doc-consistency.yml]  (existing)
  ├─ ARC 序列核验
  ├─ 需求可追溯性
  └─ ...
    ↓
[code-structure-validation.yml]  (建议新增)
  ├─ python verify_headers.py --baseline .baseline.json

    ↓

```

## 9. 已知限制与未来扩展

### 9.1 当前设计的限制（有意设计，非遗漏）

1. **方法调用属性不完整**
   - 当前：`self.repo.append()` 不归类为方法调用
   - 原因：需要类型推断，会产生假设
   - 未来：可考虑扩展至 resolved type 的方法调用

2. **常量初始化器不扫描**
   - 当前：const/static 初始化中的调用不记录
   - 原因：本工作区的常量初始化多为字面量或编译期常量
   - 未来：可扩展支持复杂初始化逻辑

3. **超长签名截断**
   - 当前：>220 字符的签名截断为 220 + `…`
   - 原因：避免清单膨胀
   - 未来：支持可配置的截断阈值

4. **宏展开不跟踪**
   - 当前：宏（如 `tonic::include_proto!`）生成的项目无法追踪
   - 原因：需要宏展开，超出范围
   - 未来：可考虑与编译器集成的方案
