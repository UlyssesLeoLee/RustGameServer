## 1. 本附件的定位与等级选择的思路

本附件记录需求定义书第9章各项非功能需求的**等级选择及其依据**。等级的含义如下。

| 等级 | 一般含义 |
|---|---|
| Lv.0 | 无要求・不考虑 |
| Lv.1 | 最低限度。在一定程度上容许停止・丢失 |
| Lv.2 | 相当于一般业务系统水平 |
| Lv.3 | **本系统的基准**。24×365运行，社会影响有限 |
| Lv.4 | 高可用・高安全。影响范围较广 |
| Lv.5 | 相当于社会基础设施水平。要求极高 |

### 1.1 将基准等级定为Lv.3的依据

| 观点 | 判断 |
|---|---|
| 业务影响 | 商用服务，停止将直接造成收益损失与信誉下降 |
| 用户规模 | 同时在线100,000（ASM-004）。故障影响用户数量众多 |
| 运维体制 | SRE 1〜2人（ASM-001）。Lv.4以上的全面适用在体制上无法成立 |
| 社会影响 | 不直接涉及生命・金融・行政。Lv.5属过度 |

**结论**：基准定为Lv.3，**仅对与货币・资产丢失直接相关的项目上调至Lv.4**。会增加运维负荷的项目不超过Lv.3。这种非对称设定是本系统的非功能方针。

### 1.2 上调至Lv.4的项目及理由

| 项目 | 需求编号 | 上调理由 |
|---|---|---|
| RPO（永久事实） | NFR-AV-005 | 道具・货币的丢失是不可恢复的信誉损害，损害游戏根基 |
| 分布式追踪 | NFR-OP-001 | 异步・多段构成下，若无trace贯通，故障一次排查无法成立 |
| 关联ID的传播 | NFR-OP-002 | 同上 |
| API・Schema版本管理 | NFR-OP-006 | 24×365运行下无停机更新的前提条件 |
| 服务器权威 | NFR-SE-001 | 采纳客户端申告值将直接导致经济系统崩溃 |
| 通信加密（外部） | NFR-SE-002 | 涉及认证信息与付费信息 |
| 输入校验 | NFR-SE-006 | 同上 |
| 审计日志 | NFR-SE-010 | 货币增减的不可否认性是运营层面的必要需求 |
| 许可约束 | NFR-EN-003 | 项目的根本目的（G-005），不可妥协 |

### 1.3 保持在Lv.2的项目及理由

| 项目 | 需求编号 | 维持理由 |
|---|---|---|
| RPO（实时状态） | NFR-AV-006 | HP・位置丢失可通过重连容忍。若在此处要求高水平，将挤压tick预算（与NFR-PE-002冲突） |
| 新建构建 | NFR-MI-001 | 不存在从既有系统的迁移 |
| 支持语言・地区 | NFR-EN-004 | 服务端与地区无关即可满足 |

## 7A. 领域扩展NFR系列的等级归属（本次新增，处置ISS-076）

> **背景**：§1.1既定"基准定为Lv.3，仅资产/货币相关项目上调Lv.4"这一非对称方针，自身适用范围**未随**RGS-REQ-014（NEURO）起13个域新增的NFR-<域>-*系列同步声明——本节补齐，全部新增NFR系列**默认继承Lv.3基准**，仅逐一核对是否存在§1.1同类"资产/货币直接相关"的上调理由。

| NFR系列 | 归属域 | 等级 | 理由 |
|---|---|---|---|
| NFR-NEURO-001〜010 | NEURO | Lv.3 | 智能层建议不直接持有资产判定权（ARC-030确定性闸门），不满足上调条件 |
| NFR-GSM-001〜006 | GSM | Lv.3 | 排行榜/任务/举报均非资产直接相关 |
| NFR-TRD-001〜004 | TRD | **Lv.4**（部分） | 玩家间交易涉及道具/货币转移，同§1.2既有"货币・资产丢失直接相关"上调理由，与NFR-AV-005同一非对称方针 |
| NFR-SUP-001〜004 | SUP | **Lv.4**（支付对账相关项） | 支付对账/掉单补偿直接关联货币权益，同上 |
| NFR-INF-001〜006 | INF | Lv.3 | 容灾/分析管线为基础设施横切能力，非资产直接相关 |
| NFR-IDN-001〜004 | IDN | Lv.3 | 身份联合/合规规则非资产直接相关 |
| NFR-OPT-001〜004 | OPT | Lv.3 | 推送/兑换码——兑换码核销涉及奖励发放，但核销幂等性已由既有FR-EC-003确定请求路径保证（同ARC-005/006既有Lv.3机制），不单独上调 |
| NFR-PLT-001〜004 | PLT | **Lv.4**（收据校验相关项） | 平台内购收据校验直接关联真实货币交易，同NFR-SE-006既有上调理由 |
| NFR-VIZ-001〜005 | VIZ | Lv.3 | 拓扑可视化为只读运维工具，非资产相关 |
| NFR-CAP-001〜005 | CAP | Lv.3 | 容量分级为横切架构方针，非资产相关 |
| NFR-PPL-001〜004 | PPL | Lv.3 | 请求处理管道标准化为横切基础设施 |
| NFR-DEP-001〜004 | DEP | Lv.3 | 集群部署编排为运维自动化工具 |
| NFR-ANT-001〜004 | ANT | Lv.3 | 反作弊检测/案件治理不直接持有资产判定权（处置权收口至AdminService人工审核，ARC-043） |
| NFR-SEC-006〜009 | SEC | Lv.3 | 认证后滥用与崩溃防护属边界防护范畴，与既有NFR-SEC-001〜005同一等级 |

> **判定方法**：凡NFR描述的失败场景会直接导致"货币/道具的丢失或伪造"（同§1.2既有判定标准），上调Lv.4；其余默认Lv.3。本表所列"部分"上调的域（TRD/SUP/PLT），具体是该域NFR系列中哪几项适用Lv.4，留待各自BAS文档详细设计阶段结合具体NFR描述逐项标注，本表只确认**该域存在Lv.4候选项**，不代表整个NFR系列区间统一为Lv.4。

## 8. 等级设定总结

| 大项目 | Lv.4项目数 | Lv.3项目数 | Lv.2项目数 | 总结 |
|---|---|---|---|---|
| 可用性 | 1 | 8 | 1 | 仅资产保全采用最高水平。稼动率与体制相称 |
| 性能・扩展性 | 0 | 18 | 1 | 全部项目以可实测数值定义 |
| 运维・维护性 | 3 | 7 | 0 | 优先保障可观测性与版本管理。运维负荷设定上限 |
| 迁移性 | 0 | 4 | 1 | 确保可替换性，应对许可风险 |
| 安全性 | 4 | 8 | 0 | 服务器权威与审计采用最高水平 |
| 系统环境 | 1 | 3 | 1 | 许可方面不妥协 |
| **合计** | **9** | **48** | **4** | — |

**方针总结**：*资产・信誉・可追溯性采用Lv.4，会增加运维负荷的项目不超过Lv.3。*
