# 1. 前言

## 1.1 目的

RGS-REV-001的核心结论是：新增的七组领域文档**整体游离于基准文档所建立的治理闭环之外**。基准文档（RGS-REQ-001／004／005）建立的闭环是：

```
需求ID体系 → 可追溯性矩阵（防遗漏/防过度实现）
           → 阶段计划（PP-004：未达标不得进入下一阶段）
           → 试验体系（TL/VF/FT）
           → 验收标准（第15章：全项必须）
           → TBD/风险/ADR登记（附件D）
```

这个闭环之所以有效，是因为它**封闭**：每个需求都必须落在某个子系统、某个阶段、某个试验、某个验收标准之内，否则会被机械检出。新文档发明平行ID体系后，闭环被打开——新需求既不被聚合、也不被排期、也不被验证、也不阻断上线。

本文档的目的是**重新闭合该环路**，而非追加新的业务功能。

# 2. 术语约定

沿用RGS-REQ-002术语表。本文档新增：

| 术语 | 定义 |
|---|---|
| 治理闭环（Governance Loop） | 需求ID→可追溯性→阶段→试验→验收→未决登记的封闭控制结构。"封闭"指任何需求都必须落在该结构内，否则可被机械检出 |
| 基准文档／领域文档 | 基准文档＝RGS-REQ-001（及其附件）；领域文档＝RGS-REQ-006〜013等按主题划分的卫星需求文档 |
| 域内ID／主编号 | 域内ID＝领域文档中使用的带域名段的ID（如`TBD-SEC-001`）；主编号＝基准文档ID体系中的连续编号（如`TBD-020`）。二者经登记表一一映射 |
| 运维负荷单位（Ops Load Unit, OLU） | 用于量化常态运维负荷的相对单位。定义见ARC-026，用途是把NFR-OP-010这一定性上限转换为可分配、可核算的定量预算 |
| 合成谬误（Fallacy of Composition） | 各部分分别满足某约束，不蕴含整体满足该约束。F-008即此类问题 |

# 4. 架构设计方针 ARC-025・ARC-026

本章为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接RGS-REQ-012新增的ARC-024。**决定事项**，变更须经ADR与审批。

## 4.1 ARC-025：治理闭环的重新闭合（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | 领域文档**必须**通过以下四项机制接入基准文档的治理闭环，缺一即视为未完成基准化：①**两级ID体系**（域内ID＋主编号映射，§4.1.1）②**三层文档位阶**（§4.1.2）③**两层验收结构**（§4.1.3）④**架构方针的统一登记**（§4.1.4） |
| **理由** | 基准文档的治理闭环之所以有效，依赖于其**封闭性**——任何游离于体系外的需求都能被机械检出。领域文档扩充时打开了这个封闭性，使TR-001〜004、AC-016、AC-018、PP-004等一系列既有控制点对新需求全部失效。重新闭合的代价（本文档＋两份附件的修订）远小于放任不闭合的代价（新需求在整个项目周期内不被追踪、不被验证、不阻断上线） |
| **为何不采用全量重命名** | 将约200个域内ID重命名为主编号形式，将破坏领域文档之间已核对完成的交叉引用，且重命名过程本身是高风险的机械操作；而两级映射在保留领域文档可读性的同时，使聚合与门禁功能完全恢复。**用登记表换重命名**是更低风险的等效解 |
| **否决方案1** | "维持现状，待各领域文档进入实现阶段时再补登记"——与RGS-REQ-006 ARC-018、RGS-REQ-008 ARC-020已两次否决的"事后补齐规范"模式同构，其否决理由（事后补齐的实际执行率偏低）在此同样适用 |
| **否决方案2** | "放弃基准文档的封闭ID体系，各领域文档自治"——将使附件C可追溯性矩阵、附件B非功能等级评定、第15章上线门禁三套机制同时失去统一作用面，等于以放弃治理换取编写便利 |
| **适用范围** | 全部领域文档（RGS-REQ-006〜013及今后新增者）及其配套基本设计书 |

## 4.2 ARC-026：运维负荷预算（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | NFR-OP-010（常态运维需在SRE 2人以内成立）由"事后检查的目标值"转为**事前分配的预算**。任何新增常态运维面（新中间件、新定期作业、新审计流程、新发布通道等）**必须**先在**运维负荷预算台账**中申领额度；台账余额不足时**不得**新增该运维面，须先通过自动化或废止既有项**回收**额度 |
| **理由** | ARC-014的判定基准是**逐项**的（"该中间件是否值得引入"），NFR-OP-010是**总量**的（"合计是否仍在2人以内"）。逐项判定全部通过不蕴含总量约束成立——这是合成谬误。RGS-REV-001 F-008已实证：七组文档各自声明遵守NFR-OP-010，合计新增9个常态运维面，而无任何机制核算总量。既有风险表中RSK-002（运维负荷超出SRE体制）的发生概率已评为**高**，本次扩充在未核算的情况下直接推高该风险 |
| **NFR-OP-010的特殊性再确认** | RGS-REQ-001第9章已声明NFR-OP-010"不是应达成的目标，而是**不得超越的上限**……**本项目对其他全部方案选择起制约作用**"。ARC-026是该声明的执行机制——此前该条只有宣示，没有执行手段 |
| **预算单位** | 引入运维负荷单位（OLU），定义与初始分配见RGS-BAS-009§3。OLU为**相对单位**，其绝对校准依PH-4起SRE值班件数与应对时长的实测数据（附件D RSK-002既有的征兆检测方法）迭代修正 |
| **与ARC-014的关系** | ARC-014回答"**该不该**引入"（技术必要性），ARC-026回答"**养不养得起**"（运维总量）。二者**均须通过**方可引入，任一不通过即否决。ARC-014通过而ARC-026不通过时，正确的应对是**先回收额度再引入**，而非放宽NFR-OP-010 |
| **否决方案1** | "以增加SRE人手化解总量压力"——直接违反ASM-001（团队规模前提）与NFR-OP-010，且ASM-001崩溃将触发第11章阶段计划的全面重评估，代价远大于约束新增运维面 |
| **否决方案2** | "仅做定性评审，不引入量化台账"——定性评审在逐项场景下与ARC-014重复，无法回答总量问题；而总量问题恰恰是F-008的实质 |
| **适用范围** | 全部会产生常态运维负荷的新增项，含中间件、定期作业、审计流程、发布通道、值班响应类要求 |

# 5. 横切需求

本章处置RGS-REV-001检出的四项横断设计问题。这些需求**跨越多个领域文档的边界**，不归属任何单一领域文档，故集中于本章。

## 5.1 插件与永久事实权威边界（处置F-009）

| ID | 需求 |
|---|---|
| FR-GOV-001 | 插件（RGS-REQ-009所定义者）的沙箱白名单API中，凡产生**永久事实**（DR-002：道具获取・消耗、货币增减、购买、交易、升级、成就解锁）的操作，**必须**复用经济服务既有的幂等确定请求路径（FR-EC-003／`CommitTransaction`），**不得**新设任何旁路 |
| FR-GOV-002 | 插件**不得**被授予绕过以下既有保证的能力：`session_epoch`（ARC-005 Single-Writer）、`request_id`幂等键（ARC-009）、`expected_version`乐观并发控制（DR-007／008）、ACK须在持久化之后（ARC-006） |
| FR-GOV-003 | 插件**不得**被授予对任何业务数据库的直接连接能力（沿用ARC-007"运行时不直接访问业务数据库"的既有边界，明示其对插件同样适用） |
| FR-GOV-004 | 沙箱白名单API的注册**必须**经架构评审，评审**必须**逐项确认FR-GOV-001〜003的遵守情况，评审记录纳入插件的Mount Record同类留痕 |

> **设计意图**：插件机制的价值在于"绕过部署周期"，而非"绕过一致性保证"。二者必须被明确区分——前者是ARC-021的目的，后者是ARC-021**未曾授权**、且与ARC-005／006／007／009直接冲突的行为。本节使该区分成为明文约束而非依赖实现者的自觉。

## 5.2 个人数据删除与审计不可变性的并存（处置F-010）

| ID | 需求 |
|---|---|
| FR-GOV-010 | 个人数据删除请求的执行方式**必须**为**去标识化（pseudonymization）**而非物理删除审计记录：将审计记录（`admin_db.operation_audit`等仅追加表）中指向自然人的标识（`target_player_id`等）替换为不可逆的替代标识，**保留**操作事实、操作者、时间序列 |
| FR-GOV-011 | 承载自然人可识别信息的业务数据（账号邮箱／手机号等，非`player_id`本身）**必须**支持物理删除或不可逆哈希化，其归属表须在RGS-DBS-001中逐表标注"含个人可识别信息"标记 |
| FR-GOV-012 | 删除请求的执行**必须**跨全部限界上下文数据库（`player_db`／`economy_db`／`match_db`／`social_db`／`admin_db`及今后挂载的新库）编排完成，编排**必须**幂等且可重入（同ARC-009），部分失败时**不得**留下"部分已删除"的不确定状态而无记录 |
| FR-GOV-013 | 删除请求的受理与执行结果本身**必须**产生审计记录（该记录不含被删除的个人信息），用于向监管证明请求已被处理 |
| FR-GOV-014 | 新挂载的限界上下文（RGS-REQ-006 ARC-018）**必须**在其Mount Record中声明是否持有个人数据及其删除方式，未声明者**不得**完成挂载 |

> **设计意图**：NFR-SE-010（审计不得删除）保护的是**不可否认性**——"谁在何时做了什么"这一事实不可被抹除；删除权保护的是**与自然人的关联**。去标识化恰好切开这两者：事实与时间序列保留，自然人关联移除，两条要求同时成立而非二选一。
>
> **未决**：本方针的法律充分性依赖于最终适用法规，须与ISS-004（适用个人信息保护法规的确定）联动确认，登记为ISS-012。

### 5.2.1 数据可携带权（导出）（本次新增，补齐"删除权"之外的对称权利）

> **背景**：§5.2已完整设计"被遗忘权"（删除），但多数隐私法规（如GDPR）同时要求**数据可携带权（Right to Data Portability）**——数据主体有权以结构化、常用、机器可读的格式取得其个人数据副本。此前从未有需求覆盖这一方向，是删除权的对称缺口。本节复用§5.2已确立的跨库编排能力（FR-GOV-012），**不新建**独立的跨库查询机制。

| ID | 需求 |
|---|---|
| FR-GOV-015 | 系统**必须**提供个人数据导出请求的受理入口（复用既有客服工单渠道，RGS-REQ-019 FR-SUP-001，导出请求作为工单的一个既定类型，**不新建**独立提交入口） |
| FR-GOV-016 | 导出请求的执行**必须**复用§5.2 FR-GOV-012既定的跨限界上下文编排机制（同一套编排框架，动作从"删除"变为"聚合读取"），**不得**为导出单独建一套跨库查询流程；导出范围**必须**与删除范围同源（同一份"个人数据归属表清单"，RGS-DBS-001已有的"含个人可识别信息"标记，见FR-GOV-011），保证两项权利覆盖的数据集合一致，不出现"能删但导不出"或"能导出但删不干净"的不一致 |
| FR-GOV-017 | 导出产物**必须**为结构化、机器可读格式（如JSON），**不得**要求数据主体解析专有二进制格式；导出产物本身**不得**持久化存储于系统中超过既定时限（如生成后48小时内失效链接/自动删除该导出文件），避免导出产物本身成为新的个人数据泄露面 |

> **与删除权的关系**：导出与删除共用同一份"个人数据归属表清单"与同一套跨库编排框架，是**同一机制的两种动作模式**（读取聚合 vs 去标识化/物理删除），而非两套独立设计——这是ARC-014"未证明不引入复杂性"精神在合规需求上的应用：能复用就不重新发明。

## 5.3 运行时可变配置的单一分发通道（处置F-011、F-014）

| ID | 需求 |
|---|---|
| FR-GOV-020 | "无需重启即可生效、在tick边界原子切换"的运行时可变配置，全系统**必须**采用**单一分发通道**。ARC-016（数值表热更新）既有的版本化产物分发与tick边界原子切换机制为该唯一通道 |
| FR-GOV-021 | RGS-REQ-009的特性开关插件状态**应当**复用FR-GOV-020所定义的既有通道分发；`PLUGIN_REGISTRY`表**应当**退化为该配置的**权威来源与审计载体**，而非各节点独立轮询的运行时数据源 |
| FR-GOV-022 | 若因技术原因确需保留独立的轮询通道，其数据库负荷**必须**纳入ARC-014既有的轮询型分发器同款判定基准（"分发器的DB负荷超过整体的10%"），并在PH-4负载试验中实测；未实测**不得**进入生产环境 |

## 5.4 经济类插件的单点判定（处置F-012）

| ID | 需求 |
|---|---|
| FR-GOV-030 | 插件**必须**在注册时声明其是否为**经济类插件**（其生效与否影响道具／货币／奖励数值者） |
| FR-GOV-031 | **经济类插件的生效判定必须由经济服务（EC）单点执行**。各运行时节点本地持有的插件状态**仅可**用于表现层（如向客户端提示"活动进行中"），**不得**作为道具／货币计算的判定依据 |
| FR-GOV-032 | 非经济类插件（表现、玩法规则、非结算性玩法）**可以**接受NFR-PLG-003所允许的跨节点最终一致窗口 |
| FR-GOV-033 | 插件注册时的经济类判定**必须**经架构评审确认，误判为非经济类的影响须在评审中评估 |

> **设计意图**：RGS-BAS-005原将跨节点一致性责任下放给"插件自身的业务逻辑"，并援引ARC-009幂等性作为手段。但幂等性解决的是"同一操作重复执行"，**不解决**"不同节点对同一时刻的活动是否生效判断不同"——后者是判定权分散问题。若某活动为奖励倍率类，窗口期内玩家可反复重连择优落到已生效节点套利。将判定权收归EC单点，是与ARC-005（Single-Writer）同构的解法：**有争议的判定必须有唯一的判定者**。
