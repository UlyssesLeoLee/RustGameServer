## Q3. 036 SPEC §A.3 "5+1" 对账是怎么做的?为什么是 5+1 不是 3+2?

**答**:**5+1 = 源 DTL v1.4.2 §3 末 5 项已知缺口 + 1 项 SPEC 自身元缺口**,与源 DTL 1:1 对账。

**源 DTL v1.4.2 §3 末 5 项** (per v1.4.2 hotfix commit `2c81361`):
1. gRPC 方法名与父 BAS-001 §6.3.1 PlayerService 现有方法名对账
2. 与 REQ-001 §FR-PL-004 / FR-PL-005 / FR-PL-006 三条业务规则对账
3. `session_epoch` 必填规则的具体强制落点(中间件 / 拦截层)
4. `PlayerRegistered` 事件的字段组成(待与 FR-PL-001 对账)
5. 错误枚举(DDD Review 阶段从零设计)

**RGS-SPEC-DTL-036 v0.2 §A.3** 逐项对应这 5 项,并**显式声明**每项都是 DDD Review 阶段必查项:
- 第 1 项:仅引用源 DTL §3 占位名 + 父 BAS 现行方法名(回溯事实陈述),"具体 proto 路径 / crate 路径 / 中间件层由 DDD Review 阶段决定,本 SPEC 不预设"
- 第 2 项:仅引用 FR-PL-004/005/006 业务规则编号(回溯事实陈述)
- 第 3 项:"本版本不预设实现文件路径"
- 第 4 项:"本版本不预设具体字段名"
- 第 5 项:"本版本不预设具体枚举值"
- 第 6 项(自身元缺口):审批栏 DDD Review 必查

**为什么不是 3+2**?早期我写过一次"3 项核心 + 2 项补充"的 3+2 写法,自审 5 发现这与源 DTL v1.4.2 §3 末 5 项结构对不齐,review 阶段读者对照会困惑。修正为 5+1 后与源 DTL 1:1 对账,可读性与可对账性同时提升。

**为什么 036 特殊**:036 是当天**唯一**有 hotfix 链的 DTL(v1.4 + v1.4.1 + v1.4.2 三次升版),且 v1.4.1 hotfix 撤回了"per BAS-001 v1.1 接口目录升版前的形态"伪造出处 + v1.4.2 hotfix 撤回了 v1.4.1 已知缺口清单后 3 项自相矛盾项——这是当日 review 反馈的重点对象,§A.3 必须详列。其他 25 份 SPEC 的 §A.3 是通用模板("无新缺口继承"或"配套父 BAS 升版即可")。

**证据**:
- `git show 2c81361 -- 'docs/01-核心架构与设计模式/RGS-DTL-036_Player域_详细设计书.md'` 显示源 DTL v1.4.2 §3 末 5 项清单
- RGS-SPEC-DTL-036 v0.2 §A.3 119-132 行:`### A.3 已知缺口 / 待 DDD Review 必查项` 标题 + 6 条 numbered list
