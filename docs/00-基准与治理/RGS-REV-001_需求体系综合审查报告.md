# 1. 审查的目的与方法

## 1.1 背景

RGS-REQ-001／RGS-BAS-001（基准文档，2026-08-15）确立了本系统的需求与架构基准（ARC-001〜017）。此后于2026-08-16一次性扩充了七组领域文档（RGS-REQ-006〜012／RGS-BAS-002〜008，新增ARC-018〜024），文档总数由6份增至22份。

各份新文档**在其自身范围内**均已完成自审，交叉引用与编号归属已核对。但**单份文档的自洽不等于体系的自洽**——本次审查的目的正是检出那些"只有把全部文档摆在一起才看得见"的问题。

## 1.2 审查方法

| 视角 | 检查内容 |
|---|---|
| **治理闭环视角** | 基准文档（RGS-REQ-001／004／005）建立了一套闭环控制机制：需求→可追溯性矩阵→试验→验收标准→TBD/风险/ADR登记。检查新文档是否落在该闭环之内 |
| **规则遵从视角** | 检查新文档是否遵守基准文档明文规定的规则（ID体系§1.5.3、TBD登记§1.5.4、附件C运维规则、README文档管理规则） |
| **横断冲突视角** | 检查新增架构方针（ARC-018〜024）之间、及其与既有方针（ARC-001〜017）之间是否存在语义冲突或职责重叠 |
| **累积效应视角** | 检查各文档**单独**满足约束、但**合计**是否突破系统级上限（尤其NFR-OP-010运维负荷上限） |
| **数值可实现性视角** | 检查新增非功能需求的目标值在既有架构约束下是否物理可达 |

## 1.3 严重度定义

| 严重度 | 判定基准 |
|---|---|
| **重大（Critical）** | 违反基准文档明文规则，或导致既有治理机制失效，或构成安全／一致性漏洞。**基准化前必须解决** |
| **中（Major）** | 存在实质性设计缺陷或不可实现的目标值，但不阻碍基准化。**须于对应阶段开始前解决** |
| **轻（Minor）** | 改善建议，不解决亦不影响正确性 |

# 2. 审查结论摘要

## 2.1 总体判定

**结论：新增七组文档在领域内容上质量可接受，但在体系治理层面存在系统性缺陷，当前状态下不具备基准化条件。**

具体而言：新文档**整体游离于基准文档所建立的治理闭环之外**——它们发明了平行的ID体系、未登记TBD与风险、未纳入可追溯性矩阵、未挂接阶段计划与验收门禁。这不是七个独立的疏漏，而是**一个共同的根因**：扩充文档时按"新增独立领域文档"的模式推进，而未同步维护基准文档所定义的全局控制结构。

此外，横断审查检出四项**仅在体系层面可见**的实质性设计问题（F-008〜F-011），其中F-009（插件可绕过经济权威边界）与F-010（删除权与仅追加审计日志冲突）具有实质风险。

# 3. 重大问题（Critical）

## F-001 【重大】ID体系分叉，基准文档的封闭ID体系被架空

| 项目 | 内容 |
|---|---|
| **现象** | RGS-REQ-006〜012新增了约200个需求ID，全部采用基准文档未定义的编号形式：`FR-MNT-*`／`FR-GM-*`／`FR-OPS-*`／`FR-LOG-*`／`FR-PLG-*`／`FR-SEC-*`／`FR-DBS-*`／`FR-SDK-*`、`NFR-MNT-*`〜`NFR-SDK-*`、`TBD-MNT-*`〜`TBD-SDK-*`、`RSK-MNT-*`〜`RSK-SDK-*`、`AC-MNT-*`〜`AC-SDK-*`、`P-MNT-*`〜`P-SEC-*` |
| **违反的规则** | RGS-REQ-001§1.5.3规定`FR-<SS>-nnn`中的`<SS>`为**§5.1所定义的11个子系统符号**（GW／RT／SY／PL／EC／MT／GD／EV／WF／OB／AD）；`NFR-<区分>-nnn`中的`<区分>`为**第9章所定义的6个区分**（AV／PE／OP／MI／SE／EN）；`TBD-nnn`／`RSK-nnn`／`AC-nnn`均为**无域名段的连续编号** |
| **体系层面的后果** | ①附件C可追溯性矩阵按子系统与NFR区分聚合，新ID无法被机械聚合，TR-001〜TR-004四项保证全部无法对新需求生效②AC-016（全部TBD已解决）、AC-018（不存在未挂接试验的◎需求）的判定范围不含新需求，验收门禁形同虚设③IPA非功能要求グレード的等级评定（附件B）以6个区分为单位，新增的7个NFR区分无等级归属 |
| **根因** | 扩充时将各领域视为独立文档，未意识到基准文档的ID体系是**封闭的**（即新增ID类别须经基准文档修订而非各文档自行定义） |
| **处置方针** | **不采用全量重命名**（约200个ID的重命名将破坏文档间已核对的交叉引用，且引入新的错误风险）。改为由ARC-025建立**两级ID体系**：域内ID（`FR-<域>-nnn`）保留可读性，同时在ID登记表中声明其**归属子系统／归属NFR区分**，使可追溯性矩阵仍可按既有维度聚合。对参与治理闭环的TBD／RSK／AC，**追加分配主编号**（TBD-009〜、RSK-012〜、AC-019〜）并记录映射 |
| **对应处置** | RGS-REQ-013 ARC-025、附件C／附件D修订 |

## F-002 【重大】17项TBD未登记至附件D，违反明文规则

| 项目 | 内容 |
|---|---|
| **现象** | RGS-REQ-006〜012正文中记载了17项未决事项（TBD-MNT-001／002、TBD-OPS-001〜003、TBD-LOG-001〜004、TBD-PLG-001／002、TBD-SEC-001／002、TBD-DBS-001／002、TBD-SDK-001／002），均未登记至附件D问题管理表 |
| **违反的规则** | ①RGS-REQ-001§1.5.4："未确定事项以`【TBD-nnn】`记载，并**必须**同时登记至附件D问题管理表"②附件D§1.2表下方规则："**不得**遗留未登记的TBD"③README§3规则4：同上 |
| **体系层面的后果** | AC-016（"全部TBD已解决，或已正式决议为「范围外」"）以附件D登记内容为判定依据。未登记的TBD既不会被追踪，也不会阻断上线判定——**未决事项被静默丢失**，这正是该规则要防止的情况 |
| **处置方针** | 全部17项登记至附件D**新设的§1.3（领域文档问题一览）**，分配主编号TBD-009〜TBD-025并各配一条ISS编号（ISS-012〜028），补充期限与负责人（原文档已记载期限的沿用，未记载的补充）。新设独立小节而非扩充§1.2，是为在既有表结构不变的前提下增加"域内ID"列，实现两级ID映射 |
| **对应处置** | 附件D（RGS-REQ-005）§1.3新设 |

## F-003 【重大】9项风险未登记至附件D，且未做概率／影响度评估

| 项目 | 内容 |
|---|---|
| **现象** | RGS-REQ-006〜012识别了9项风险（RSK-MNT-001、RSK-OPS-001、RSK-LOG-001、RSK-PLG-001、RSK-SEC-001／002、RSK-DBS-001、RSK-SDK-001／002），均仅在各文档§9以"持续跟踪，纳入附件D问题风险管理表"的措辞提及，实际未登记 |
| **体系层面的后果** | ①附件D§2.1定义了发生概率（高／中／低）与影响度（大／中／小）的评估基准，新风险未经评估，无法与既有RSK-001〜011一同排序②各风险的预防措施／发生时对策／征兆检测方法／负责人四栏均缺失——**风险被识别但未被管理** |
| **处置方针** | 全部9项登记至附件D**新设的§2.3（领域文档风险一览）**，分配主编号RSK-012〜RSK-020，并按§2.1基准完成评估、补齐四栏。同时更新RSK-002（运维负荷超出SRE体制）——该风险经F-008的量化核算已由"潜在"转为**已确认超支**，须追加ARC-026作为预防措施 |
| **对应处置** | 附件D§2.3新设、§2.2 RSK-002更新 |

## F-004 【重大】ARC-018〜024缺少对应ADR，与自身条文矛盾

| 项目 | 内容 |
|---|---|
| **现象** | 新增的7条架构方针（ARC-018〜024）各自条文均写有"**决定事项**，变更须经ADR与审批"，但附件D§3"决定事项一览（ADR化对象）"仍仅列ADR-0001〜0016（对应ARC-001〜017），未为新方针分配ADR编号 |
| **体系层面的后果** | ①附件D§3声明"需求定义书第10章的架构设计方针，须作为以下ADR分别记录"——新方针位于卫星文档而非第10章，形式上不受该条覆盖，构成规则空隙②AC-017（"不存在未经ARC-014判定基准而导入的中间件（全部具备对应ADR）"）无法对新方针涉及的中间件（沙箱脚本引擎、DDoS/WAF、Secrets管理、SBOM工具链）生效 |
| **处置方针** | 附件D§3扩展至ADR-0025，覆盖ARC-018〜026（含本次新增的ARC-025／026），并明确"架构设计方针"的定义涵盖卫星需求文档中新增的ARC-nnn |
| **对应处置** | 附件D§3修订、ARC-025 |

## F-005 【重大】可追溯性矩阵失效，且其自身断言已过时

| 项目 | 内容 |
|---|---|
| **现象** | ①附件C§4末尾明文断言："**确认结果**：全部架构方针（ARC-001〜017）均挂接课题或非功能需求之一，不存在无依据的方案（满足TR-004）"——ARC-018〜024出现后，该断言已不成立②新增的业务需求（BR-MNT／BR-OPS／BR-LOG／BR-PLG／BR-SEC／BR-DBS／BR-SDK，共约22项）未纳入§2业务需求→功能需求表③新增课题（P-MNT-*／P-OPS-*／P-LOG-*／P-PLG-*／P-SEC-*／P-DBS-*／P-SDK-*，共约30项）未纳入§4课题→架构方针表 |
| **违反的规则** | 附件C§1运维规则："需求的追加・变更时，须同时更新本附件。**本附件未同步更新的需求变更不得批准**" |
| **体系层面的后果** | 按该规则的字面含义，**RGS-REQ-006〜012当前状态下均不得批准**。这不是形式问题——TR-001（防止需求遗漏）、TR-003（防止过度实现）两项保证对新需求完全未生效 |

| **对应处置** | 附件C（RGS-REQ-004）修订 |

## F-006 【重大】新增验收标准游离于上线门禁之外

| 项目 | 内容 |
|---|---|
| **现象** | RGS-REQ-001§15声明"以下全部条件成立时，本系统达到商用上线水准。判定为**全项必须**"，其后为封闭的AC-001〜AC-018。新文档定义的AC-MNT-001〜004、AC-OPS-001〜005、AC-LOG-001〜005、AC-PLG-001〜004、AC-SEC-001〜005、AC-DBS-001〜004、AC-SDK-001〜004（共31项）位于该封闭集合之外 |

| **对应处置** | ARC-025、附件C§8、RGS-REQ-001§15追加AC-019（本次以修订提案形式记载，正式修订须走需求变更流程） |

## F-007 【重大】新增工作未挂接阶段计划，实际不可排期

| 项目 | 内容 |
|---|---|
| **现象** | ①RGS-REQ-001第11章的阶段计划（PH-1〜PH-8）与完成判定基准表未包含新文档定义的任何工作②§11.3"各阶段的中间件导入状况"表未包含新文档涉及的中间件：沙箱脚本引擎（ARC-021）、DDoS防护／WAF（ARC-022）、Secrets管理中间件（TBD-SEC-002）、SBOM／构建溯源工具链（ARC-022） |
| **违反的规则** | PP-004："各阶段须定义**完成判定基准**，未达标**不得**进入下一阶段"——未挂接阶段的工作既无完成判定基准，也不阻断阶段推进 |
| **体系层面的后果** | 七组文档定义了大量必须实现的功能（脚手架、GM控制平面、埋点SDK、插件体系、零信任网络、客户端SDK），但**没有任何一个阶段对其负责**。实际后果是这些工作会被无限期推迟至"有空再做" |
| **处置方针** | RGS-REQ-013§6给出阶段映射表，将新增工作分配至PH-1〜PH-8并给出完成判定基准；§11.3中间件表的扩展作为需求变更提案记载 |
| **对应处置** | RGS-REQ-013§6 |

## F-008 【重大・涌现】运维负荷累积未受控，NFR-OP-010上限存在突破风险

| 项目 | 内容 |
|---|---|
| **现象** | 七组新文档**各自**都声明遵守ARC-014（中间件导入判定基准）与NFR-OP-010（运维负荷上限）。但**无任何文档负责核算其合计值** |
| **新增的常态运维面（逐项）** | ①插件注册表的生命周期运维与沙箱引擎版本管理（ARC-021）②密钥／证书轮换的执行与验证（ARC-022 FR-SEC-020〜022）③依赖漏洞响应（Critical 72小时／High 14天）与SBOM归档（ARC-022）④NetworkPolicy覆盖率的定期审计（BAS-006§4.2）⑤GM控制平面与运维工单的处理（ARC-019）⑥三引擎SDK的发布与三份适配层的版本同步（ARC-024）⑦分区滚动创建／归档／清理（BAS-007§4）⑧埋点规范的CI检查维护与采样率调参（ARC-020）⑨脚手架基座（Helm chart／CI流水线）的演进维护（ARC-018） |
| **为何单份文档看不见** | ARC-014的判定基准是**逐项**判定（"某中间件是否该引入"），NFR-OP-010是**总量**约束（"常态运维需在SRE 2人以内成立"）。逐项判定全部通过，不蕴含总量约束成立——这是典型的合成谬误，只有横断审查可见 |
| **佐证** | 附件D RSK-002（"中间件运维负荷超出SRE体制"）的发生概率评估为**高**、影响度**大**，是既有风险表中概率最高的一项。本次扩充在未核算的情况下新增了9个运维面，直接推高该风险 |
| **处置方针** | 新设ARC-026（运维负荷预算）：将NFR-OP-010由"事后检查的目标"转为**事前分配的预算**，建立运维负荷预算台账，任何新增运维面须先在台账中申领额度；额度不足时**不得**新增，须先通过自动化回收既有额度 |
| **对应处置** | RGS-REQ-013 ARC-026、RGS-BAS-009§3、附件D RSK-002更新 |

## F-009 【重大・涌现】插件沙箱可构成绕过经济权威边界的路径

| 项目 | 内容 |
|---|---|
| **现象** | RGS-BAS-005§5（沙箱脚本插件设计）在"白名单API"栏举例："由宿主显式注册可供脚本调用的函数集合（如"读取当前活动配置"、"**发放声明范围内的道具**"）" |

## F-010 【重大・涌现】个人数据删除请求与仅追加审计日志存在制度性冲突，且无归属文档

| 项目 | 内容 |
|---|---|
| **现象** | 基准文档存在两条方向相反的要求：①NFR-SE-010（等级Lv.4）："运营操作・货币增减・封禁以仅追加方式记录，**不得**删除"，保留期3年②NFR-SE-012＋ISS-004／TBD-004："适用个人信息保护法规的确定……影响存储位置・保留期限・**删除请求的应对方式**" |
| **问题** | 若适用法规包含删除权（被遗忘权）类条款，则玩家的删除请求要求删除其个人数据，而审计日志中含`target_player_id`且不得删除——两条要求直接冲突。此外，删除请求需跨`player_db`／`economy_db`／`match_db`／`social_db`／`admin_db`五个库编排执行，**当前无任何文档定义该编排**：RGS-REQ-011／BAS-007定义了保留期与分区清理，但那是"按时间批量过期"，与"按个人精确删除"是不同的机制 |
| **为何本次审查才显现** | 新增的RGS-REQ-011（数据库设计标准）首次系统性处理保留期与清理机制，使"按个人删除"的缺口与"仅追加审计"的冲突同时进入视野；此前二者分散于NFR条目中未被并置 |
| **处置方针** | ①RGS-REQ-013§5.2确立方针：个人数据删除采用**去标识化（pseudonymization）而非物理删除审计记录**——将审计记录中的`target_player_id`替换为不可逆的替代标识，保留操作事实与时间序列（满足不可否认性），移除与自然人的关联（满足删除权）。该做法使两条要求同时成立②定义跨库删除编排的归属与顺序③登记为ISS-012，与ISS-004（法规确定）联动，法规裁定后确认方案充分性 |
| **对应处置** | RGS-REQ-013§5.2、RGS-BAS-009§5、附件D ISS-012 |

# 4. 中等问题（Major）

## F-011 【中・涌现】存在两套并行的"tick边界热配置"机制，构成重复建设

| 项目 | 内容 |

| **现象** | ARC-016（数值表热更新，既有）与ARC-021①（编译期特性开关插件，新增）在机制本质上是同一件事：**在tick边界原子切换的、无需重启即可生效的运行时可变配置**。但二者的分发通道不同——ARC-016采用"带版本号的表集合一次性加载"，RGS-BAS-005§4采用"从`PLUGIN_REGISTRY`表轮询拉取" |

## F-012 【中・涌现】插件跨节点生效窗口对经济类插件构成套利面

| 项目 | 内容 |
|---|---|
| **现象** | RGS-BAS-005§7承认存在跨节点不一致窗口（NFR-PLG-003允许p99<5秒），并将一致性责任下放："对一致性要求更高的插件（如涉及道具/货币的活动），**必须**在插件的业务逻辑内部增加符合ARC-009的幂等与状态检查" |
| **问题** | 幂等性解决的是"同一操作重复执行"，**不解决**"不同节点对同一时刻的活动是否生效判断不同"。若某活动为奖励倍率类，窗口期内玩家可通过反复重连择优落到已生效节点——这是**判定权分散**问题而非幂等问题，下放给各插件自行处理，等于要求每个活动策划独立解决一个分布式一致性问题 |
| **处置方针** | 确立分类原则：**经济类插件（影响道具／货币／奖励数值）的生效与否，必须由经济服务（EC）单点判定**，各节点本地的插件状态仅用于表现层（如UI提示活动进行中）；非经济类插件（表现、玩法规则）方可接受最终一致窗口 |
| **对应处置** | RGS-REQ-013§5.4、RGS-BAS-005§7修订提案 |

## F-013 【中】NFR-MNT-004的回滚时限在K8s部署模型下不可达

| 项目 | 内容 |
|---|---|
| **现象** | RGS-REQ-006 NFR-MNT-004当前值："回滚（含灰度权重回退与镜像版本回退）耗时p99<3秒完成切换，参照NFR-PE-007重连恢复时间的同等量级判定" |
| **问题** | 该值将两类性质不同的操作合并计时：①灰度权重回退——修改网关／API网关路由权重，秒级可达②**镜像版本回退**——须经K8s调度、镜像拉取（如节点无缓存）、容器启动、`readinessProbe`通过，**物理上不可能在3秒内完成**。3秒的取值源自NFR-PE-007（重连恢复p99<3秒），但重连恢复与Pod重建是完全不同量级的操作，该类比不成立 |
| **处置方针** | 拆分为两项独立目标：①流量回退（网关权重置零）p99<10秒②版本回滚（镜像回退至上一版本并就绪）与NFR-AV-007滚动更新同等量级，具体值依PH-4实测确定。同时说明紧急止血以①为准，②为完整回滚 |
| **对应处置** | RGS-REQ-006 NFR-MNT-004修订（本次执行） |

## F-018 【轻】GM后台作为外部系统的网络层来源约束未定义

| 项目 | 内容 |
|---|---|
| **现象** | RGS-BAS-006§4 NetworkPolicy基线明确覆盖"集群内全部服务间通信"，而GM后台位于集群外（RGS-REQ-007§2术语定义：GM后台"不在本系统Kubernetes集群的信任边界内"）。其接入的防护当前仅有传输层（TLS＋mTLS）与应用层（RBAC） |

| **处置方针** | 作为建议记载，具体方案与TBD-SEC-001（边界防护选型）合并处理 |
