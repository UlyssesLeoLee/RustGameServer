# 1. 前言

## 1.1 目的

RGS-REQ-012／RGS-BAS-008已定义客户端SDK的协议版本协商时序（FR-SDK-004，"N-1版本接受"策略），但该机制的作用仅是**在握手阶段判定客户端版本是否可被接受、并在不可接受时报错**——它从未回答"客户端如何获得可被接受的新版本"这个前置问题。全语料库检索（`docs/`）确认：不存在任何关于资源清单、补丁生成、完整性校验、灰度发布、分发承载层的设计。这是一个真实且基础性的缺口——没有定义好的资源分发路径，"发布新版本"这件事本身就没有可执行的落地方式，FR-SDK-004的版本拒绝逻辑也就沦为"拒绝了但没告诉客户端去哪里更新"的半截设计。本文档补齐这一整条链路：客户端如何知道有新版本、如何以最小代价获取变化的部分、如何确认下载内容未被篡改或损坏、新版本如何先对部分玩家生效再全量铺开、以及分发承载层本身应当默认基于自由开源、可自托管的方案而非假设某个付费CDN厂商。

## 1.2 核心设计约束（贯穿全文档，先声明以免读者产生误解）

- 本文档**不**重新设计协议版本协商——FR-SDK-004（RGS-BAS-008§8）已定义"客户端版本过旧时握手被拒绝并提示需升级"的行为，本文档**复用**该机制作为强制更新的判定入口，只在其基础上补充"客户端被拒绝后应当如何自动进入更新流程"这一后续动作
- 本文档**不**新建独立的认证/会话体系——未登录客户端（如首次下载游戏、或版本过旧被拒绝后需要更新）的资源下载视为**匿名静态文件获取**，不要求任何会话上下文；已登录客户端在会话中获取热更资源（如下载一个新皮肤资源包）**复用既有会话上下文**（RGS-BAS-001/003既定鉴权与限流），本文档不为热更新单独发明一套身份体系
- 本文档**不**假设任何付费CDN厂商（Cloudflare／Fastly／CloudFront等）为默认设计路径——依CON-001／CON-002（RGS-REQ-001§10附件约束"核心组件不得依赖付费SaaS或闭源组件"），分发承载层的默认方案**必须**是自由开源、可自托管的（对象存储＋自托管反向代理/缓存层，或点对点补丁分发），商业CDN**仅**作为可插拔的**可选后端**存在于抽象之后，与RGS-REQ-010 TBD-SEC-001对DDoS防护/WAF选型"是否属于基础设施层而非核心组件，需专项讨论"的处理方式同构——本文档不在此处下最终结论，只保证**默认路径**不假设付费依赖
- 本文档**不**重复发明差量算法——若RGS-BAS-010已有可复用的差分模式（Delta Compression＋Self-Healing Baseline，§3.8，当前用于客户端同步/排行榜等场景），本文档复用其"差分快照＋自愈基线"的设计精神，仅将其应用场景扩展至资源包补丁生成，不视为独立的新增算法模式
- 本文档**不**新建独立的部署/编排体系——分发后端服务（清单服务、灰度控制）依附既有Kubernetes/Helm部署骨架（RGS-BAS-002），灰度发布的"按比例放量"复用既有GM控制平面（ARC-019）作为控制入口与紧急下线（kill-switch）手段，不新建独立的运维控制台

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 资源清单（Manifest） | 描述某一版本客户端资源包构成（文件列表、各文件校验值、文件版本号）的结构化元数据 |
| 增量补丁（Delta Patch） | 仅包含新旧两个版本间发生变化部分的差分文件包，用于避免全量重新下载 |
| 完整性校验（Integrity Verification） | 对下载内容计算校验值并与清单声明值比对，用于拒绝损坏或被篡改的下载 |
| 灰度发布（Staged Rollout） | 新版本先对一部分玩家群体开放，观察无异常后再逐步扩大至全量的发布方式 |
| 强制更新闸门（Forced-Update Gating） | 复用FR-SDK-004版本协商机制，服务端拒绝低于最低受支持版本的客户端连接的行为 |
| 分发后端（Distribution Backend） | 承载资源文件实际下载流量的基础设施，本文档将其抽象为可插拔接口，默认实现为自托管方案 |

# 3. 背景与课题

## 3.1 现状

- RGS-REQ-012／RGS-BAS-008：定义了协议版本协商（FR-SDK-004），仅解决"是否接受某版本客户端连接"，未定义客户端获取新版本资源的路径
- RGS-BAS-010§3.8：已有"Delta Compression＋Self-Healing Baseline"模式用于客户端同步场景的差分快照，尚未被应用于资源包补丁场景，属于未被复用的既有能力
- RGS-BAS-022（弹性容量规划）：未包含面向新版本发布的灰度/分批放量设计（本文档检索确认该文档不含相关模式），灰度发布需在本文档内定义
- RGS-REQ-010 TBD-SEC-001：为CDN/WAF选型问题保留了"付费云服务与不依赖付费SaaS原则边界"的专项讨论空位，本文档面对同类"是否采用付费CDN"问题时采取同构处理方式（默认自托管，付费方案作为后续可选评审项，不在本文档下结论）

## 3.2 课题

- **CH-CDN-01**：客户端完全没有定义好的"我当前是什么版本、最新是什么版本、之间差异是什么"的查询路径，发布新版本时只能依赖发布方自行约定的临时机制
- **CH-CDN-02**：若每次更新都要求客户端全量重新下载资源包，在资源体积随内容增长而增大的情况下，玩家更新体验与带宽成本会同步恶化
- **CH-CDN-03**：下载内容若在传输中损坏或被篡改而未经校验直接应用，可能导致客户端运行时崩溃甚至被用于分发恶意内容
- **CH-CDN-04**：新版本客户端若直接全量放量，一旦存在未被测试覆盖的缺陷，会同时影响全部玩家而非可控范围，缺乏"先小范围验证"的中间地带
- **CH-CDN-05**：FR-SDK-004已定义"版本过旧则拒绝连接"，但客户端被拒绝后应当如何自动进入更新流程，从未被定义——版本协商与资源分发之间存在断层
- **CH-CDN-06**：若默认设计路径隐式假设某个付费CDN厂商，将与CON-001／CON-002（不依赖付费SaaS/闭源组件）产生直接冲突，且限制了自托管部署场景（如私有服务器/单机联机社区）的可用性

# 4. 业务需求

| ID | 业务需求 |
|---|---|
| BR-CDN-001 | 客户端须能查询自身版本与最新可用版本之间的差异，而非依赖发布方临时约定 |
| BR-CDN-002 | 版本更新须支持仅下载变化部分，而非强制全量重新下载 |
| BR-CDN-003 | 下载内容在应用前须经完整性校验，损坏或被篡改的下载必须被拒绝 |
| BR-CDN-004 | 新版本须支持先对部分玩家生效、观察无异常后再全量铺开，且发现问题时可快速下线 |
| BR-CDN-005 | 版本过旧的客户端被服务端拒绝连接后，须有明确路径引导其进入更新流程 |
| BR-CDN-006 | 资源分发承载层的默认设计方案须自由开源、可自托管，不依赖付费SaaS，商业方案仅作为后续可选项 |

# 5. 功能需求：版本清单与差异发现

- **FR-CDN-001**：系统**必须**提供**资源清单（Manifest）**，描述当前已发布的资源版本构成：文件列表、每个文件的版本号与完整性校验值（§6落地）、资源包总版本号。清单**必须**可被客户端匿名查询（未登录场景，§1.2既定原则），**不得**要求客户端先建立会话
- **FR-CDN-002**：客户端**必须**能够通过对比自身当前清单版本与服务端最新清单版本，得出**差异文件列表**（哪些文件发生变化、哪些未变），而非依赖客户端自行猜测或强制拉取全量清单比对
- **FR-CDN-003**：清单**必须**记录每次版本变更的摘要信息（变更说明、发布时间、是否为强制更新），供客户端在更新前向玩家展示，**不得**仅提供不透明的版本号
- **FR-CDN-004**：清单查询与差异计算**必须**是无状态、可水平扩展的只读操作，复用既有Kubernetes/Helm部署骨架（RGS-BAS-002）进行部署与扩缩容，**不得**因清单服务成为发布环节的单点瓶颈

# 6. 功能需求：增量补丁与完整性校验

- **FR-CDN-010**：对于客户端已持有旧版本资源文件的场景，系统**应当**优先提供**增量补丁（Delta Patch）**而非要求全量重新下载该文件，增量补丁的生成**复用**RGS-BAS-010§3.8既定的"Delta Compression＋Self-Healing Baseline"差分设计精神（差分快照＋损坏时自愈回退全量基线），**不得**为资源包场景重新发明一套独立的差分算法体系
- **FR-CDN-011**：当客户端本地资源状态无法确定（如本地文件缺失、损坏，或差分链路过长导致增量成本已超过全量下载）时，系统**必须**回退为提供该文件的**完整基线版本**下载，即FR-CDN-010所述"自愈基线"路径，**不得**在无法确定本地状态时仍强行应用增量补丁
- **FR-CDN-012**：清单**必须**为每个文件（无论以增量补丁或完整基线形式下载）声明**完整性校验值**（如内容哈希），客户端在应用任何下载内容（覆盖本地文件）**之前必须**校验实际下载内容与清单声明值一致，**不得**跳过校验直接应用，校验失败的下载**必须**被拒绝并可重试，**不得**静默使用可能损坏或被篡改的内容
- **FR-CDN-013**：清单本身的来源**必须**可验证（如清单文件自身亦附带签名或由可信信道分发），**不得**仅校验各资源文件而对清单本身的真实性不做任何保证——否则完整性校验可被"篡改清单声明值"绕过

# 7. 功能需求：灰度发布与强制更新

- **FR-CDN-020**：新版本资源/客户端构建的发布**必须**支持**灰度发布（Staged Rollout）**：先对可配置比例/范围的玩家群体生效，观察无异常后再逐步扩大至全量，**不得**要求每次发布都只能是"全量立即生效"这一种路径
- **FR-CDN-021**：灰度发布的放量控制（灰度比例调整、暂停、全量、紧急下线回滚到上一版本）**必须**通过既有GM控制平面（`AdminService`，ARC-019统一入口）操作，**不得**新建独立的发布控制台——发布控制本质上是一种高危运维操作，理应与既有高危操作二次确认、审计留痕机制（RGS-BAS-003§7〜8）保持一致
- **FR-CDN-022**：灰度发布判定客户端是否属于"已放量范围"的逻辑**必须**是确定性且可复现的（如按玩家ID哈希分桶），**不得**采用不可复现的随机判定，以保证同一玩家在同一灰度批次内的行为可预期、便于问题复现与排查
- **FR-CDN-023**：客户端在协议版本协商中被服务端判定为版本过旧而拒绝连接（复用RGS-BAS-008§8既有FR-SDK-004时序，`result_code=协议版本过旧`）后，**必须**能够依据该拒绝结果自动查询FR-CDN-001清单获取可更新的最低受支持版本及其下载路径，**不得**仅将错误提示丢给玩家而不提供任何后续路径
- **FR-CDN-024**：系统**必须**支持声明某次版本发布为**强制更新**（FR-CDN-003清单摘要信息的一部分），强制更新客户端**必须**在更新完成前**不得**继续使用已被判定为不再受支持的旧版本进行游戏内操作——该判定的执行点复用FR-SDK-004既有版本协商闸门，**不得**另建一套独立的强制更新执行机制

# 9. 架构设计方针 ARC-045

**ARC-045：分发后端可插拔抽象与自托管默认原则**

客户端资源分发的**承载层**（实际存放并对外提供资源文件下载的基础设施）**必须**通过一层可插拔的后端抽象接入系统，该抽象遵循以下原则：

1. **默认实现自由开源、可自托管**：默认分发后端**必须**基于自由开源、无需付费的方案（如自托管对象存储＋反向代理/缓存层，或基于点对点技术的补丁分发），满足CON-001／CON-002对核心组件许可与SaaS依赖的既定约束
2. **商业CDN是可选后端，而非默认假设**：若运营方后续评估认为引入商业CDN对特定场景（如跨地域大规模分发的边际成本）具有正当理由，**可以**将其作为抽象接口下的一个可选实现接入，但**不得**成为系统设计上默认假设、无法脱离的依赖——该决策与其评审边界，比照RGS-REQ-010 TBD-SEC-001对DDoS防护/WAF付费云服务的处理方式（是否属于基础设施层而非核心组件，需专项讨论），不在本文档内下最终结论
3. **抽象接口与清单/校验逻辑解耦**：资源清单的生成、差异计算、完整性校验（§5〜6）**不得**依赖特定分发后端的专有能力，任何符合"可通过URL获取文件字节流"这一最小契约的后端实现都应当可以接入，避免后端选型绑架上层设计
4. **不新建独立部署单元**：分发后端抽象层本身的控制面（清单服务、灰度控制）依附既有限界上下文与Kubernetes/Helm部署骨架（RGS-BAS-002），仅数据面（实际文件存储/传输）可根据所选后端实现独立于业务集群之外运行（如独立的对象存储实例），这与ARC-018挂载原则中"横切能力扩展"的简化判定路径一致，不视为新建限界上下文

具体设计详见 RGS-BAS-027。

# 10. 验收标准

# 11. 风险与未决事项

- **TBD-CDN-001**：增量补丁生成所采用的具体差分算法库选型（在RGS-BAS-010§3.8既定"差分快照＋自愈基线"设计精神约束下，具体采用哪个开源库/算法实现）留待详细设计阶段确定，须满足CON-001 OSI认可许可要求
- **TBD-CDN-002**：默认自托管分发后端的具体软件选型（对象存储实现、反向代理/缓存层软件、是否引入点对点分发作为补充手段）留待详细设计阶段结合PH-4实测的带宽/成本基线确定，须满足CON-001／CON-002
- **TBD-CDN-003**：NFR-CDN-005增量补丁体积缩减率的具体基准数值，及灰度发布默认放量梯度（如"5%→25%→100%"具体分几档、每档观察时长）留待PH-4实测数据确定，不在本文档给出跨版本通用数值
- **RSK-CDN-001**：若商业CDN在后续评审（ARC-045原则2）中被引入作为可选后端，需与CON-002条款的适用边界做出明确澄清并记录ADR，处理方式同RGS-REQ-010 RSK-SEC-002对TBD-SEC-001的处置
- **RSK-CDN-002**：自托管分发后端若未预先规划容量弹性，在版本发布高峰期（大量玩家同时拉取新版本）可能面临带宽/存储瓶颈，需结合RGS-BAS-022既有弹性容量规划原则评估是否需要预留发布高峰期的弹性扩容策略，本文档不重新设计容量规划机制
