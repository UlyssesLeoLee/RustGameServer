# 1. 前言

## 1.1 目的

RGS-REQ-030 已定义"客户端如何发现差异（Manifest）+ 如何获取变化部分（Delta Patch）+ 校验下载内容（Integrity）+ 控制发布节奏（Staged Rollout）"，BR-CDN-002 明确承诺"版本更新须支持仅下载变化部分，而非强制全量重新下载"。但**这一承诺在传输层是不完整的**：

- 单个资源文件可能达到 GB 量级（4K 材质包、剧情过场视频、初始安装包内的核心资源）
- 移动网络（4G/5G/切 Wi-Fi）、弱网、家庭 NAT 抖动、企业代理超时——任何一项都足以让单次 TCP/QUIC 连接在文件传输途中断开
- 客户端进程被玩家切换后台后被系统回收（移动平台常态）、玩家主动取消后再恢复、断点续传是"明天打开应用继续昨天没下完的 1.2GB 补丁"的基本可玩性前提

RGS-REQ-030 §6 与 RGS-BAS-027 整章仅处理"如何知道要下什么"和"如何校验下到的内容"，**从未**处理"下载中断后怎么办"。一旦文件在传输途中断开，客户端只能从头重传——增量补丁节省的 80%~95% 体积被一次中断归零，BR-CDN-002 的承诺等同于"理论存在，实践落空"。

本文档补齐这条断链：

1. 给出 HTTP Range 协议在分发后端的契约性要求（**所有** `DistributionBackend` 实现**必须**支持 Range 请求，无论自托管对象存储还是商业 CDN）
2. 定义客户端断点状态机（NotStarted / Downloading / Paused / Resuming / Completed / Failed / Canceled）与本地断点记录的持久化格式
3. 与既有 FR-CDN-012 完整性校验、FR-CDN-013 清单签名、FR-CDN-020 灰度发布、NFR-CDN-002 校验不可跳过的协同边界
4. 与 RGS-REQ-030-ADD1 CDN 边缘策略的衔接：边缘节点对 Range 请求的缓存键与回源策略

## 1.2 核心设计约束（贯穿全文档）

- **本文档不重新设计差分补丁**——增量补丁（Delta Patch）由 RGS-REQ-030 §6 既定，断点续传与增量补丁**正交**：增量补丁决定"下哪些字节"，断点续传决定"如何把这一批字节下完"
- **本文档不绕过完整性校验**——断点续传引入"分块到达"的中间态，**不得**成为绕过 FR-CDN-012 校验的入口（NFR-CDN-002 仍是硬约束）
- **本文档不重新定义分发后端选型**——HTTP Range 是 HTTP/1.1（RFC 7233）通用协议，自托管对象存储（MinIO 等）与商业 CDN 均原生支持，**不**为本场景引入新的分发后端
- **本文档不要求服务端对断点信息有状态**——服务端仅响应标准 HTTP Range 请求，断点信息完全在客户端维护，避免在分发后端（典型为无状态对象存储）引入持久化层
- **本文档不假设断点续传是分片/补丁下载独有**——它适用于所有"任意 HTTP GET 文件字节流"的场景，包括全量基线、差分包、玩家间点对点补丁

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 断点续传（Resumable Download） | 客户端在文件下载中断后，能从中断位置继续传输而无需从头开始的能力 |
| HTTP Range 请求 | HTTP/1.1 RFC 7233 定义的部分内容请求，客户端通过 `Range: bytes=START-END` 请求资源的一个字节区间 |
| 部分内容响应（206 Partial Content） | 服务端对合法 Range 请求的响应，状态码 206，包含 `Content-Range: bytes START-END/TOTAL` 头 |
| 范围不可满足（416 Range Not Satisfiable） | 客户端 Range 越界（如超出文件总大小）时的响应，状态码 416 |
| 实体标签（ETag） | HTTP 缓存与一致性标识，资源内容变更时 ETag 同步变化，Range 请求通过 `If-Range` 头携带 ETag 验证源文件未变 |
| 断点记录（Download Resume Token） | 客户端本地持久化的下载进度信息：文件标识、源 URL、已下载字节区间、未完成区间、ETag、临时文件路径 |
| 并发分片下载（Parallel Chunked Download） | 客户端将单个文件拆为多个不相交字节区间并发 Range 请求，最后拼装的下载方式 |
| 预分配文件（Sparse File） | 客户端在开始下载前先按总大小预分配磁盘空间并写零，下载过程中按区间 seek 写入，避免下载到一半磁盘不足 |

# 3. 背景与课题

| 课题编号 | 课题 |
|---|---|
| P-CDN-201 | 现有 RGS-REQ-030 / RGS-BAS-027 全文搜索 "断点"、"resume"、"Range"、"partial" 均无匹配——文件级下载中断的恢复机制在语料库层面完全空白 |
| P-CDN-202 | GB 级资源在弱网/移动网络下"一次下完"是不现实的工程假设；MMO 客户端实际部署中，主包外的增量补丁、版本大更新的材质资源包、DLC 内容包，单文件 500MB~2GB 并不罕见；断点续传不是优化项而是基本可玩性 |
| P-CDN-203 | 即便差分补丁只下变化部分（典型 80%~95% 体积缩减），剩余的 5%~20% 在弱网下一次传完的概率仍可能低于 50%，等于把"几乎全量下完"的任务变成"几乎全量下 + 重传一次"——增量收益被中断成本吞掉 |
| P-CDN-204 | 客户端断点信息若放在远端（"续传服务器"）会引入新的状态层，违反 RGS-BAS-027 §6.1 既有 `DistributionBackend` 极简契约（put/get_url/exists）；正确做法是断点信息放客户端本地，服务端仅响应标准 HTTP Range |
| P-CDN-205 | 客户端进程被系统回收（移动平台常态）后重新启动时，必须能从本地断点记录恢复，不能让玩家"再下一次完整文件"作为标准体验 |
| P-CDN-206 | 断点续传与 RGS-REQ-030-ADD1 边缘缓存的协同：边缘节点对 Range 请求的缓存键、Range 请求能否命中边缘缓存、回源策略如何避免被 Range 切片击穿——是必须明确设计的衔接点，不是天然自洽 |

# 4. 业务需求

| ID | 业务需求 |
|---|---|
| BR-CDN-201 | 客户端须能在文件下载过程中断后从中断位置继续传输，**不**强制要求从头重新下载 |
| BR-CDN-202 | 客户端须能在进程被回收（移动平台常态）或玩家主动退出后再次启动时，恢复未完成的下载 |
| BR-CDN-203 | 断点续传**不得**绕过完整性校验——分块到达的字节仍须在应用前完成与清单声明值一致的校验 |
| BR-CDN-204 | 任意符合 RGS-BAS-027 §6.1 契约的分发后端（自托管对象存储、商业 CDN）**必须**支持 HTTP Range 请求——Range 支持是后端契约的一部分，**不**是可选项 |
| BR-CDN-205 | 玩家在更新过程中须能手动暂停与恢复，暂停期间不消耗服务端带宽，恢复后从暂停位置继续 |
| BR-CDN-206 | 资源分发承载层**不得**因引入断点续传而新增持久化状态——断点信息由客户端维护，服务端保持无状态 |

# 5. 功能需求：HTTP Range 协议契约

| 编号 | 需求 |
|---|---|
| FR-CDN-040 | `DistributionBackend`（RGS-BAS-027 §6.1 既有契约）**必须**支持 HTTP/1.1 RFC 7233 定义的 Range 请求：①响应合法的 `Range: bytes=START-END` 请求返回 `206 Partial Content` 与 `Content-Range: bytes START-END/TOTAL`②响应 `Range: bytes=START-`（开区间到末尾）返回 206 + 实际区间③响应 `Range: bytes=-N`（最后 N 字节）返回 206 + 实际区间④响应越界 Range 返回 `416 Range Not Satisfiable` 与 `Content-Range: bytes */TOTAL`⑤对不支持 Range 的资源响应 `Accept-Ranges: none` 且仍能返回 200 全量 |
| FR-CDN-041 | 资源文件**必须**对外暴露**稳定的 ETag**（资源内容变更时同步变更），用于 Range 请求携带 `If-Range` 头验证源文件未变——若源文件在客户端下载过程中发生变更（理论上不应对活跃资源发生，但灰度回滚等场景会触发），服务端**必须**返回 `200 OK`（全量）而非 `206 Partial Content`，强制客户端丢弃已下字节并重传 |
| FR-CDN-042 | 服务端**必须**支持 HEAD 请求返回资源元数据（`Content-Length`、`Accept-Ranges`、`ETag`、`Last-Modified`），客户端在发起 Range 请求前**应当**先 HEAD 探测以确认文件总大小与 ETag，避免基于陈旧清单的错误断点 |
| FR-CDN-043 | 资源 URL 路径**不得**随 Range 请求变化（即**不**为不同字节区间生成不同 URL），断点续传**不得**要求服务端按区间分片存储——同一 URL 服务多 Range 请求是契约的硬要求，避免对 CDN 配置产生复杂依赖 |
| FR-CDN-044 | Range 响应的 `Content-Length` 头**必须**等于实际返回的字节数（`END - START + 1`），与 `Content-Range` 头声明的区间长度一致——客户端按此计算下载进度，**不得**出现"Content-Length 与实际字节流长度不一致"导致进度错乱的情形 |
| FR-CDN-045 | 服务端**不得**为支持 Range 而要求对资源做特殊预处理（如预切片、专用压缩）——Range 支持应基于文件原始字节流的随机访问能力，**不得**为 Range 协议改变资源文件本身的存储格式 |

# 6. 功能需求：客户端断点状态机与本地记录

## 6.1 状态机定义

| 编号 | 需求 |
|---|---|
| FR-CDN-050 | 客户端**必须**实现以下下载状态机：`NotStarted`（未开始）→ `Probing`（HEAD 探测元数据）→ `Downloading`（下载中，可细分为单流 / 并发分片子状态）→ `Completed`（完成）/ `Paused`（玩家手动暂停）/ `Failed`（网络/校验失败等不可恢复错误）/ `Canceled`（玩家主动取消） |
| FR-CDN-051 | `Paused` 与 `Failed` **必须**支持 `Resume` 操作回到 `Downloading`；`Canceled` 状态**不得**自动恢复（区别于"暂停"——取消是终态意图），玩家再次下载相同资源时从 `NotStarted` 重新开始 |
| FR-CDN-052 | 状态转移**必须**遵守：①`NotStarted → Probing → Downloading` 是唯一正常入口；②`Downloading → Paused` 仅在玩家主动暂停时发生；③`Downloading → Failed` 发生在重试耗尽或不可恢复错误；④`Failed → Resume → Downloading` 必须从断点记录的下一字节开始；⑤任何状态→`Completed` 仅在**完整文件**（含所有分片）均通过 FR-CDN-012 完整性校验后发生 |
| FR-CDN-053 | 客户端**应当**实现"幂等重试"语义：相同 `(file_path, source_url, etag)` 组合的 `Downloading → Failed → Resume` 序列**不得**在服务端留下中间状态（服务端本就无状态——无 Range 会话、无"任务"概念） |

## 6.2 断点记录（Download Resume Token）持久化

| 编号 | 需求 |
|---|---|
| FR-CDN-060 | 断点记录**必须**在客户端**本地**持久化（**不**上传服务端），其字段至少包含：`file_path`（资源相对路径，唯一标识）、`source_url`（来源 URL）、`etag`（HEAD 探测得到的 ETag）、`total_size`（文件总字节数）、`chunk_manifest`（已下载/未下载区间列表，按并发分片情况记录多段）、`temp_file_path`（下载中临时文件路径）、`last_updated_at`（最后更新时间，用于断点过期判定）、`checksum_algorithm`（FR-CDN-012 完整性校验算法标识） |
| FR-CDN-061 | 断点记录**必须**在每次成功接收完一个 Range 响应、落盘并通过该段字节的初步校验后**原子地**更新（write-ahead），**不得**采用"接收完整个文件才写一次断点记录"的方式——后者在最后一次写入前进程被回收等于没记录 |
| FR-CDN-062 | 断点记录**不得**存放在资源文件本身（避免被误删或被应用流程覆盖），**应当**存放在 SDK 私有目录（如 `~/.rgs-sdk/downloads/`），**应当**在文件 `Completed` 应用后**自动**清理对应记录（避免无限增长） |
| FR-CDN-063 | 断点记录的 `last_updated_at` 超过 **N 天未更新**（具体值 TBD-CDN-201，建议默认 7 天）视为过期——过期断点**不得**自动恢复，须从 `NotStarted` 重新开始；过期阈值**不得**长于资源更新周期（避免玩家拿到"几乎全下完但断点已废"的体验） |
| FR-CDN-064 | 客户端 SDK **不得**在断点记录中存放任何 PII（玩家 ID、设备指纹、IP 等），断点信息**仅**与文件标识与下载状态绑定——理由：断点记录可能因应用崩溃转储、备份工具捕获、SD 卡借出等场景外泄，**不**让本地断点记录成为 PII 载体 |

# 7. 功能需求：与完整性校验、灰度、限流的协同

| 编号 | 需求 |
|---|---|
| FR-CDN-070 | 断点续传**不得**绕过 RGS-REQ-030 FR-CDN-012 完整性校验：①客户端在每个 Range 响应接收完成后**应当**立即对**已落盘**的字节段计算校验值（与清单声明的整文件 hash 在末尾比对，而非按段单独校验——避免分块 hash 暴露给攻击面），但**应当**在 Range 接收过程中维护"已下字节数"与"待下字节数"的中间状态；②整文件**仅**在 `Completed` 时一次性与清单声明值比对，比对通过方可应用；③任何 Range 响应在落盘后**应当**可重读（预分配文件 + seek 写入是典型实现） |
| FR-CDN-071 | 断点续传**不得**绕过 RGS-REQ-030 FR-CDN-013 清单签名校验：恢复下载前**必须**先重新拉取最新 Manifest 并校验签名，校验通过后方可使用既有断点记录中的 ETag——避免"清单已变更但客户端仍按旧清单的 ETag 续传，导致下到与新清单不匹配的内容" |
| FR-CDN-072 | 断点续传**不得**绕过 RGS-REQ-030 FR-CDN-020 灰度发布判定：恢复下载前**必须**重新查询灰度状态，确认本次下载对应的资源版本**仍然**对该玩家处于"已放量"范围——若玩家因灰度回滚被切回旧版本，断点续传**必须**从旧版本对应的资源 URL 重新开始（而非从新版本 URL 续传） |
| FR-CDN-073 | 断点续传**不得**绕过既有 NFR-CDN 类限流规则：Range 请求与全量 GET 请求**共享**同一限流配额（按 IP / 按 player_id / 按 device_id），**不得**因为"Range 单次小"就规避限流——避免攻击者通过发大量小 Range 请求击穿带宽预算 |
| FR-CDN-074 | `If-Range` 头**必须**使用 ETag（**不**用 `Last-Modified`）——ETag 是强一致性标识，`Last-Modified` 仅秒级精度且受时钟漂移影响，与 ARC-045-4（强制更新用客户端版本号判定不用日期，避免时钟漂移）一脉相承 |

# 8. 功能需求：并发分片下载与暂停恢复

| 编号 | 需求 |
|---|---|
| FR-CDN-080 | 客户端**应当**支持**并发分片下载**（Parallel Chunked Download）：将单文件按固定粒度（如 4MB / 8MB，具体 TBD-CDN-202）切为多个不相交的字节区间，分别发起 Range 请求并发下载，最后在本地拼装——目的是充分利用 HTTP/2 / HTTP/3 多路复用与多连接带宽，对 GB 级文件显著降低端到端下载耗时 |
| FR-CDN-081 | 并发分片数**应当**可配置（典型 4~16 路），**不得**硬编码在 SDK 中——移动平台弱网下应主动收敛到 2~4 路，桌面平台强网下可放宽到 8~16 路，配置项作为 SDK 调参，**不**作为玩家可见选项 |
| FR-CDN-082 | 并发分片下载**必须**在断点续传场景下可恢复：恢复时**应当**仅重试未完成的分片（依据 FR-CDN-060 `chunk_manifest` 中未完成区间列表），已完成的分片**不得**重新下载 |
| FR-CDN-083 | 玩家手动暂停（`Paused` 状态）**必须**立即停止所有进行中的分片请求（取消未完成的 Range 请求或忽略响应），**不得**在暂停期间继续占用服务端带宽 |
| FR-CDN-084 | 客户端在开始并发下载前**应当**预分配文件空间（FR-CDN-046 定义的 Sparse File），下载期间按区间 seek 写入——避免"下载到 80% 时磁盘不足"导致已下字节作废 |

# 9. 非功能需求

|---|---|---|
| NFR-CDN-110 | 断点续传恢复后**必须**在 RGS-REQ-030 NFR-CDN-001 既有 p99 < 500ms 清单查询时延目标内完成"恢复可行性判断"（HEAD 探测 + 清单签名校验 + 灰度状态查询）——即从客户端发出恢复请求到首个 Range 字节到达的时延 | 同 NFR-CDN-001 |

| NFR-CDN-112 | 断点续传**不得**让总下载时间相比"无中断的连续下载"恶化超过 X%（X 建议 ≤ 20%，含分片顺序拼装、磁盘 seek、签名重校验的开销） | TBD-CDN-203 |

# 10. 架构设计方针 ARC-045 扩展

## 10.1 ARC-045 扩展：分发后端契约的可恢复性维度

| 项目 | 内容 |
|---|---|
| **决定** | ①**所有** `DistributionBackend` 实现**必须**支持 HTTP/1.1 RFC 7233 定义的 Range 请求（FR-CDN-040），Range 支持是后端契约的硬要求，**不**是可选项②断点信息**完全由客户端维护**，服务端保持无状态（FR-CDN-060/062），**不**新增"续传服务器"或"下载任务表"等持久化层③Range 协议**不得**改变资源文件本身的存储格式（FR-CDN-045），仅依赖文件原始字节流的随机访问能力 |
| **理由** | ①HTTP Range 是 HTTP/1.1 通用协议，自托管对象存储（MinIO 等）与商业 CDN 均原生支持，将其纳入后端契约**不**引入新组件、不增加许可审查负担，符合 ARC-014 "未证明不引入复杂性" 精神②服务端无状态与 RGS-BAS-027 §6.1 既有 `DistributionBackend` 极简契约（put/get_url/exists）一脉相承，若引入服务端状态会破坏后端抽象、增大自托管与商业 CDN 之间的差异、阻塞 ARC-045-1 既定"自托管与商业均须经审批门禁"的统一管理③不改变存储格式是 Range 协议的标准要求，亦避免"为支持断点续传而改变资源文件组织方式"的复杂化倾向 |
| **与 ARC-045 既有原则的关系** | 本扩展**不修改** ARC-045 既有 4 条原则，仅**新增**第 5 条"可恢复性维度"——即"任何符合 ARC-045 接口契约的后端实现必须额外满足 Range 支持" |
| **与 CON-001/002 的关系** | Range 支持是 HTTP 标准协议，**不**引入新组件或新许可依赖；CON-001/002 既定约束**不受影响** |

# 11. 验收标准

| 编号 | 验收标准 |
|---|---|
| AC-CDN-110 | 模拟客户端在单文件下载 60% 进度时强制断开网络，恢复后验证**从 60% 位置继续**而非从 0 重传（FR-CDN-040/050/051） |
| AC-CDN-111 | 模拟客户端进程在下载 80% 时被系统回收（kill -9 等价），重启后验证**自动恢复**至 80% 位置续传（FR-CDN-051/060/062） |
| AC-CDN-112 | 模拟源文件 ETag 在下载中途变更（如运营紧急回滚），验证客户端**正确收到 200 OK 全量响应**（而非错误的 206），并从头重传（FR-CDN-041/074） |
| AC-CDN-113 | 模拟玩家在 30% 进度时主动暂停，5 分钟后恢复，验证**从 30% 续传**且暂停期间无任何 Range 请求打到服务端（FR-CDN-083） |
| AC-CDN-114 | 模拟 GB 级文件（≥ 1GB）并发 8 路分片下载，在 30% 进度暂停，验证**仅重试未完成的 70%**，已完成分片**未**重新下载（FR-CDN-080/082） |
| AC-CDN-115 | 模拟灰度回滚（玩家从新版本切回旧版本），验证断点续传**从旧版本 URL 重新开始**而非从新版本 URL 续传（FR-CDN-072） |
| AC-CDN-116 | 注入篡改的 Range 响应（中间人攻击场景），验证客户端**整文件校验失败**并丢弃已下字节、触发全量重传，**不**通过"分块单独校验"绕过（FR-CDN-070） |
| AC-CDN-117 | 后端选型评估清单新增"HTTP Range 支持"门禁项；任何候选后端（自托管或商业）**未**通过该门禁的**不得**进入生产（FR-CDN-040/045、NFR-CDN-114） |
| AC-CDN-118 | 客户端 SDK 占用的断点记录本地存储验证 LRU 清理策略生效，存储不超配置上限（NFR-CDN-113） |

| RSK-CDN-201 | 移动平台系统对后台进程的资源回收可能晚于断点记录的最后一次更新（理论上 ≤ 数秒），若玩家在断点记录尚未 flush 前回收进程，可能丢失最近数秒的下载进度——缓解：客户端在每个 Range 响应接收完成时立即 flush 断点记录（FR-CDN-061 原子写），**不**采用"批量写"或"延迟写" | 设计层面缓解 |
| RSK-CDN-202 | 源文件 ETag 在客户端下载过程中变更（FR-CDN-041 / AC-CDN-112）理论上不应对活跃资源发生，但灰度回滚、紧急下架等场景会触发——若 ETag 变更但客户端未携带 `If-Range`，可能误判为合法续传而下到陈旧内容——缓解：服务端**必须**对每个资源 URL 启用强 ETag（内容哈希），且客户端在每次 Range 请求携带 `If-Range: <etag>` 头（FR-CDN-041/074） | 协议层面缓解 |
| RSK-CDN-203 | 商业 CDN 对 Range 请求的缓存策略可能与边缘节点不兼容（某些 CDN 对同一 URL 的不同 Range 请求不复用缓存，导致边缘命中率下降）——缓解：选型评估时（FR-CDN-040 / NFR-CDN-114）**必须**实测 Range 命中行为，CDN 候选**未**通过该实测的**不得**启用 | 选型评估门禁缓解 |
| RSK-CDN-204 | 客户端断点信息若被恶意第三方获取（应用备份、SD 卡借出等场景），可能推断出玩家正在更新的资源版本——缓解：断点信息**不**含 PII（FR-CDN-064），仅含文件标识与下载状态，且建议 SDK 默认对断点记录文件做轻量加密（具体算法 TBD） | 设计层面缓解 |
