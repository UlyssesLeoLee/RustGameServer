# 1. 前言

## 1.1 目的

RGS-REQ-001 IF-001／IF-002已定义客户端⇔服务器的协议字段（QUIC消息、HTTPS接口），RGS-BAS-001§6.2已给出字段级设计。但协议规范本身**不足以**让三个技术栈迥异的引擎（Bevy=Rust ECS、Unity=C#、Unreal Engine=C++）团队高效、一致地实现客户端侧逻辑——尤其是ARC-002"客户端预测＋服务器和解"这类**有状态、有算法细节**（输入缓冲、和解回滚、插值）的逻辑，若三个引擎团队各自实现，极易出现行为不一致（如UE客户端的预测算法与Unity客户端不同，导致同一网络条件下体验/判定结果不同），且升级协议版本时三处代码需要同步修改，与NFR-OP-006"允许混合版本运行"的既定目标产生额外的实现负担。

本文档的目的：定义一套**跨引擎共享核心逻辑、仅在接入层做引擎适配**的SDK需求，将X-001"本系统提供参考SDK"的既定声明落实为可执行的需求集。

## 1.2 适用范围

| 范畴 | 说明 |
|---|---|
| 协议编解码层 | IF-001 QUIC消息（Datagram/Stream）、IF-002 HTTPS接口的序列化/反序列化 |
| 客户端预测与和解 | ARC-002"客户端预测＋服务器和解"的算法实现（输入缓冲、序号管理、差异检测、重新应用） |
| 连接管理 | QUIC连接建立/重连、心跳、协议版本协商（NFR-OP-006 N-1兼容） |
| 引擎适配层 | Bevy（原生Rust crate）、Unity（C#绑定）、Unreal Engine（C++绑定）三种适配方式 |
| **不适用范围** | 游戏玩法逻辑、UI/UX、美术资源渲染（均属X-001/X-002既有排除范围，由外部客户端团队负责） |

## 1.3 关联文档

| 文档编号 | 文档名 | 与本文档的关系 |
|---|---|---|
| RGS-REQ-001 | 需求定义书 | 本文档延展X-001、IF-001、IF-002、ARC-002、ARC-003、ARC-004、NFR-OP-006 |
| RGS-BAS-001§6.2 | 基本设计书 QUIC消息字段设计 | SDK的编解码层直接实现该字段设计，本文档不重复定义字段本身 |
| RGS-IFS-001（待制定，PH-1） | 外部接口规格书 | 字节级线路格式（量化精度、位打包）是SDK编解码层的直接依据，SDK不得与其相悖 |
| RGS-BAS-008 | 客户端引擎适配层与SDK 基本设计书 | 本文档的基本设计展开（本次同步制定） |

# 2. 术语约定

沿用RGS-REQ-002术语表。本文档新增：

| 术语 | 定义 |
|---|---|
| 核心SDK（Core SDK） | 与引擎无关的、纯Rust实现的协议编解码/连接管理/预测和解逻辑库，本文档语境下即`rgs-client-core` |
| 引擎适配层（Engine Adapter） | 将核心SDK的能力以各引擎习惯的方式（Bevy插件/Unity C#包/UE插件模块）暴露给该引擎项目使用的薄封装层 |
| FFI（Foreign Function Interface） | 跨语言调用边界，本文档特指Rust核心SDK通过C ABI被C#/C++调用的机制 |
| 参考SDK（Reference SDK） | 复用RGS-REQ-001 X-001既有措辞，指本文档定义的核心SDK+三引擎适配层的整体产出物 |

# 3. 背景与课题

| 编号 | 课题 |
|---|---|
| P-SDK-001 | 若ARC-002客户端预测/和解算法在三个引擎中各自用C#/C++/Rust重复实现，算法细节漂移会导致相同网络条件下三个引擎的客户端表现不一致，且每次协议或算法调整需要三处同步修改，与NFR-OP-006混合版本运行的复杂度雪上加霜 |
| P-SDK-002 | 若字节级线路格式（量化精度、位打包，RGS-IFS-001待定）由三个引擎团队各自解读实现，极易出现编解码不一致（如浮点量化精度理解偏差），产生难以定位的"偶发同步错位"故障 |
| P-SDK-003 | 若客户端SDK版本与服务器协议版本脱节缺乏显式协商机制，滚动更新期间（ARC-015 Expand-Contract）新旧客户端可能各自以为自己在讲同一种协议 |
| P-SDK-004 | Unity/UE的C#/C++运行时若直接通过裸FFI调用Rust核心SDK而无边界安全设计（内存生命周期、异常传播），容易引入跨语言边界的内存安全问题或崩溃，与整个系统"以Rust内存安全为核心信任基础"的定位（CON-003）不符——虽然客户端在系统信任边界之外，但一个不稳定的官方SDK会损害客户端团队对本系统的信任与采用意愿 |

# 4. 业务需求

| ID | 需求 | 优先级 |
|---|---|---|
| BR-SDK-001 | 使用Bevy／Unity／Unreal Engine的客户端团队均须能通过官方提供的SDK快速接入本系统协议，无需从零解析字节级协议 | 高 |

| BR-SDK-003 | 协议演进（新增字段、版本升级）须能通过更新SDK版本平滑传递给三引擎客户端，不要求三个引擎团队各自重新解读协议 | 中 |

# 5. 功能需求

## 5.1 核心SDK（协议与算法层）

| ID | 需求 |
|---|---|
| FR-SDK-001 | 核心SDK**必须**实现IF-001全部消息类型（`PlayerInputMessage`／`StateDeltaSnapshot`／`InputAck`／`SessionHandshake`／`ItemGrantNotice`／`SceneTransitionCommand`等，RGS-BAS-001§6.2既定字段）的编解码，字节级格式**必须**与RGS-IFS-001（制定后）保持唯一权威来源一致 |
| FR-SDK-002 | 核心SDK**必须**实现ARC-002客户端侧算法：输入序号管理与本地立即应用、基于`InputAck`的已确认基线推进、差异检测与重新应用（和解） |
| FR-SDK-003 | 核心SDK**必须**实现QUIC双路径（不可靠Datagram／可靠Stream）的连接管理，包括ARC-003既定的回退路径（TCP/WebTransport，FR-GW-008） |
| FR-SDK-004 | 核心SDK**必须**支持协议版本协商：连接建立时交换`protocol_version`，服务器按NFR-OP-006既定策略在一定期限内接受N-1版本，核心SDK须能正确处理"服务器返回版本不匹配"的场景并向调用方（引擎适配层）暴露明确的错误 |
| FR-SDK-005 | 核心SDK**必须**为纯逻辑库，**不得**依赖任何特定渲染引擎的API/生命周期钩子（保证可被三引擎复用，落实ARC-024） |

## 5.2 引擎适配层

| ID | 需求 |
|---|---|
| FR-SDK-010 | Bevy适配层**必须**以原生Rust crate（`rgs-client-bevy`）形式提供，直接依赖核心SDK（同语言，无FFI边界），并以Bevy插件（`Plugin` trait）形式集成，暴露符合Bevy ECS习惯的System/Resource/Event接口 |
| FR-SDK-011 | Unity适配层**必须**以C#包（含预编译的核心SDK动态库+C#绑定代码）形式提供，暴露符合C#/Unity习惯的异步API（`async`/`Task`）与`MonoBehaviour`友好的生命周期钩子 |
| FR-SDK-012 | Unreal Engine适配层**必须**以UE插件模块形式提供，暴露符合UE习惯的`UObject`/`Actor Component`接口，支持Blueprint可调用的关键API（连接、发送输入、订阅快照更新） |
| FR-SDK-013 | 三引擎适配层**必须**共享同一份核心SDK的编译产物/源码，**不得**各自重新实现FR-SDK-001〜004的协议或算法逻辑（对应ARC-024核心决定） |

## 5.3 跨语言边界安全（落实P-SDK-004）

| ID | 需求 |
|---|---|
| FR-SDK-020 | FFI边界（供Unity/UE调用的C ABI）**必须**对全部导出函数做参数校验与panic捕获，**不得**允许Rust侧panic穿透至C#/C++调用方导致宿主进程崩溃 |
| FR-SDK-021 | FFI边界的内存生命周期（谁分配、谁释放）**必须**有明确约定并在API文档中显式声明，**不得**产生悬垂指针/双重释放风险 |

# 6. 非功能需求

| ID | 类别 | 内容 | 目标值/判定基准 |
|---|---|---|---|
| NFR-SDK-001 | 一致性 | 三引擎适配层在相同录制的网络轨迹（延迟/丢包序列）下重放，预测/和解结果须逐字段一致 | 回归测试用例覆盖，PH-2起纳入CI |

| NFR-SDK-005 | 接入成本 | 客户端团队从零开始集成SDK到完成登录/移动同步的时间 | ≤2个工作日（提供示例工程/文档情况下） |

# 7. 架构设计方针 ARC-024

本节为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接RGS-REQ-011新增的ARC-023。**决定事项**，变更须经ADR与审批。

## 7.1 ARC-024：核心逻辑单一实现，多引擎薄适配层（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | 协议编解码与ARC-002客户端预测/和解算法**只能**以一份Rust实现（核心SDK）存在，Bevy/Unity/UE三个引擎的适配层**必须**是对该核心SDK的**薄封装**（Bevy原生依赖；Unity/UE经FFI调用同一份编译产物），**不得**在任意引擎侧重新实现协议或算法逻辑 |
| **理由** | 延续本系统"权威逻辑只有一份实现"的一贯精神（同ARC-005 Single-Writer、ARC-020"命名规范由脚手架强制生成而非人工重复实现"的同类思路）。预测/和解算法涉及大量边界条件（乱序、丢包、快速重连），重复实现极易产生行为漂移，而这类漂移在纯客户端侧难以被服务器发现（服务器只关心和解后的最终结果），因此必须从"不可能重复实现出漂移"的路径上解决，而非依赖三个引擎团队各自谨慎 |
| **FFI边界的信任处理** | Unity/UE通过FFI调用核心SDK，跨越了Rust内存安全边界，此边界**必须**被视为需要额外防护的接口（同ARC-021"沙箱脚本仅能访问白名单API"的同类思路：任何跨越语言/信任边界的调用都需要显式的边界防护，而非隐式信任调用方正确使用），落实FR-SDK-020/021 |
| **否决方案** | "只提供协议文档，由三个引擎团队各自实现客户端逻辑"——是当前实质状态（X-001既有边界下的默认结果），已被P-SDK-001/002证明会导致行为漂移与协议解读偏差，不再作为唯一选项，改为**同时**提供官方SDK（客户端团队仍可自行实现，官方SDK是推荐而非强制，因X-001既定的"客户端本体外部团队负责"边界不因本文档而改变） |
| **适用范围** | 协议编解码与ARC-002算法逻辑。三引擎的渲染表现、输入采集、UI层逻辑不受本决定约束，由各引擎团队自行实现，SDK仅暴露标准化的数据接口（如"当前预测位置"）供其消费 |
