# 1. 前言

## 1.1 目的与范围边界（先声明以防误解）

RGS-REQ-001已在BR-007（社交・公会）、BR-008（商店购买）、BR-009（玩家间交易）与对应的FR-GD-001〜003、FR-EC-007〜008、FR-WF-001中，给出这些能力**存在**的一行摘要级声明，但均未展开为可实现的功能需求集。同时，RGS-REQ-001完全未提及**大厅（Lobby）**这一概念——玩家在进入具体场景（战斗/社交场景）之前所处的、进行社交/编队/活动入口选择的过渡性空间。

本文档的目的：将这四个方向（大厅、社交通信、内购付费、运营活动）从"存在但未展开"或"完全缺失"的状态，补齐为可实现的功能需求集，同时**严格遵守**RGS-REQ-001既有的系统范围边界：

| 边界 | 本文档遵守方式 |
|---|---|
| X-001（客户端本体不属本系统） | 本文档定义的是**服务端**需要提供的能力（数据模型、API、同步机制、状态管理），不定义UI/UX/美术表现，这些由客户端团队依本文档的服务端契约自行设计实现 |
| X-002（美术资源・关卡・数值策划内容不属本系统） | 运营活动（§8）定义的是活动的**承载机制**（如何配置、如何生效、如何与经济系统交互），不定义具体某个活动的策划内容（奖励数值、玩法规则的具体设计） |
| CON-003（服务端主语言为Rust） | 本文档全部服务端能力均为既有限界上下文（EC/GD/PL）的功能扩展或FR-PLG插件机制的应用，不引入新技术栈 |

# 2. 术语约定

沿用RGS-REQ-002术语表。本文档新增：

| 术语 | 定义 |
|---|---|
| 大厅（Lobby） | 玩家在进入具体游戏场景（战斗/副本等实时模拟场景）之前所处的过渡性空间，承载社交展示、队伍编成、活动入口选择等非战斗职能 |
| 频道（Channel） | 聊天消息的路由范围，本系统定义世界／公会／队伍／私聊四类频道 |
| 私聊（Whisper／Direct Message） | 点对点的频道类型，仅发送者与接收者可见 |
| 商品目录（Product Catalog） | 可购买内容的服务端权威定义（商品ID、价格、内容、上下架状态），区别于客户端展示的商品陈列（后者属X-001范围） |
| 权益发放（Entitlement Grant） | 购买成功后将商品对应的道具/货币/权限实际写入玩家账户的动作，复用既有FR-EC-003确定请求路径 |
| 运营活动（Live-Ops Event） | 具有明确起止时间、面向全体或分群玩家生效的临时性玩法/奖励规则，本系统中以RGS-REQ-009插件形式承载 |

# 3. 背景与课题

| 编号 | 课题 |
|---|---|
| P-LBY-001 | 缺少大厅这一过渡空间的设计，玩家在完成鉴权（§4.1.2）后直接进入具体场景，无法进行编队/查看好友在线状态等场景外社交行为，与"大规模多人在线游戏"（ASM-002）的常见产品形态不符 |
| P-LBY-002 | FR-GD-002"聊天：频道・私聊・禁言"仅一行摘要，未定义频道的路由规则、私聊的点对点投递机制、禁言与既有GM控制平面（RGS-REQ-007 FR-GM-012）的关系 |
| P-LBY-003 | FR-EC-007"购买处理：商店购买的受理・发货"未定义商品目录的数据模型与凭证校验流程，购买功能实质不可实现 |
| P-LBY-004 | 运营活动若无与经济系统交互的领域特定契约（如"活动奖励如何確定发放、如何避免重复领取"），即便RGS-REQ-009插件机制就绪，活动策划仍缺少可依据的接口规范 |

# 5. 功能需求：大厅

| ID | 需求 |
|---|---|
| FR-LBY-001 | 大厅**必须**是玩家鉴权成功后、进入具体场景前的默认状态，玩家可在大厅与在场景中之间转移（复用FR-RT-008既有场景间转移机制，大厅本身视为一种特殊"场景"） |
| FR-LBY-002 | 大厅**必须**支持查询好友/公会成员的在线状态与当前所在场景类型（复用FR-PL-006既有在线状态管理），**不得**暴露其他玩家的精确游戏内位置等隐私信息 |
| FR-LBY-003 | 大厅**必须**支持队伍编成：创建队伍、邀请、接受/拒绝、队伍解散，队伍状态**必须**在成员从大厅进入具体场景后保持关联（供后续匹配/组队进入同一场景实例使用） |
| FR-LBY-004 | 大厅**必须**展示当前生效的运营活动入口列表（复用§8既定的活动状态查询能力），**不得**展示已过期或未生效的活动 |
| FR-LBY-005 | 大厅内的社交同步（在线状态变化、队伍成员变化）**必须**复用ARC-002既定的差分快照机制，**不得**引入独立的同步算法（同ARC-024"核心逻辑单一实现"的同类精神——避免大厅另建一套同步机制与战斗场景的同步机制分道扬镳） |

# 6. 功能需求：社交通信

## 6.1 频道与路由

| ID | 需求 |
|---|---|
| FR-LBY-010 | 系统**必须**支持四类频道：世界（全服可见，可能分区/分片以控制单频道消息量）、公会（限公会成员）、队伍（限当前队伍成员）、私聊（点对点） |
| FR-LBY-011 | 私聊消息**必须**点对点投递，**不得**经由需要全频道成员都能访问的公共通道中转（即便实现上复用同一消息基础设施，私聊消息的可见范围**必须**在路由层面强制为仅两方，不依赖客户端自觉过滤） |
| FR-LBY-012 | 频道消息的传输**必须**复用IF-001既定的可靠通道（QUIC Stream，`ChatMessage`消息类型，RGS-BAS-001§6.2.2已定义字段），**不得**使用不可靠通道（聊天消息丢失不可接受，区别于位置类高频状态） |

## 6.2 禁言与治理联动

| ID | 需求 |
|---|---|
| FR-LBY-020 | 禁言**必须**复用RGS-REQ-007既有的`AdminService.MuteChat`方法（RGS-BAS-003§3.1），**不得**在社交子系统内另建独立的禁言机制——这是ARC-019"统一入口"原则在社交领域的应用：GM对聊天的管控与其他管控操作共享同一审计/RBAC/二次确认体系 |
| FR-LBY-021 | 禁言状态**必须**在消息发送时校验（服务器权威，同NFR-SE-001既定"不得采纳客户端申告值"精神的延伸——**不得**依赖客户端自行隐藏被禁言者的消息发送入口作为唯一防线） |
| FR-LBY-022 | 系统**应当**提供轻量级的自动化滥用检测（如短时间内重复消息、已知违禁词模式），检测结果**可以**作为RGS-REQ-014智能层（若已批准，ARC-027）的分析输入之一，但检测本身的基础规则**不得**依赖智能层才能运行（智能层不可用时，基础滥用检测**必须**仍然可用，同NFR-NEURO-001隔离性原则） |

# 7. 功能需求：内购与付费

## 7.1 商品目录

| ID | 需求 |
|---|---|
| FR-LBY-030 | 系统**必须**维护服务端权威的商品目录：商品ID、对应的道具/货币/权益内容、价格、上下架时间窗口、购买限制（如每日限购次数） |

## 7.2 购买与权益发放

| ID | 需求 |
|---|---|
| FR-LBY-040 | 购买流程**必须**复用既有FR-WF-001购买工作流（外部支付连携Saga）与IF-006支付渠道接口，**不得**新建独立的支付处理路径 |

| FR-LBY-042 | 支付成功但发货失败（或反之）的场景**必须**由既有Saga补偿机制处理（复用VF-006既定验证项），**不得**产生"已扣款未发货"或"已发货未扣款"的终态不一致 |

# 10. 架构设计方针 ARC-029

本节为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接RGS-REQ-015新增的ARC-028。**决定事项**，变更须经ADR与审批。

## 10.1 ARC-029：大厅作为特殊场景，社交/活动能力全部复用既有基础设施（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | 大厅**不是**新的子系统或新的技术形态，而是**运行时（RT）既有场景概念的一个特殊实例**——复用ARC-001场景Actor模型、ARC-002同步机制、FR-RT-008场景间转移机制。社交通信（频道/私聊/禁言）复用既有GD限界上下文与ARC-019 GM控制平面。内购复用既有EC限界上下文、FR-WF-001 Saga与ARC-009幂等机制。运营活动复用RGS-REQ-009插件体系与RGS-REQ-013经济边界约束。**本文档不引入任何新的子系统、新的一致性机制或新的技术栈** |
| **理由** | RGS-REV-001审查已确立的原则——"避免重复建设"（F-011两套并行热配置机制的教训）——同样适用于此处：大厅/社交/内购/活动这四个方向，若各自发明独立的同步机制、独立的一致性保证、独立的活动管理方式，会产生大量与既有ARC-001〜028平行的"影子架构"，运维负荷（ARC-026）与认知负担同步失控。本文档存在的意义正是**防止**这种重复建设——把这四个此前缺乏规范的方向，明确锚定到既有基础设施上 |
| **对判定"是否需要新机制"的态度** | 若详细设计阶段发现大厅/社交/内购/活动确有既有机制无法满足的诉求（如世界频道消息量级远超既有事件基础设施吞吐能力），**必须**依ARC-014判定基准提出证据后走ADR流程新增，**不得**在本文档或详细设计中静默引入 |
| **否决方案** | "大厅作为独立于战斗场景的新服务，用独立技术栈实现以追求开发速度"——直接违反CON-003与ARC-001既定的Actor模型，且制造新的限界上下文而不经RGS-REQ-006 ARC-018挂载评审，已否决 |
| **适用范围** | 本文档全部功能需求（§5〜§8） |
