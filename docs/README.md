# 文档体系

本目录管理RustGameServer项目的正式交付文档。文档编号规则为`RGS-<类别>-<序号>`。

文档体系遵循日本IPA（独立行政法人情报处理推进机构）的《要件定義書》标准框架（共通フレーム／非機能要求グレード），正文以中文撰写；框架层级的专有名词在首次出现处保留日文原名并附中文译名，因其为对日本标准的引用。

> **目录物理分类说明（2026-08-16起）**：本次按主题将全部文档物理归类至`docs/`下的8个编号子目录，便于查找。**文档编号（`RGS-REQ-nnn`／`RGS-BAS-nnn`）本身不变**——ARC-025治理框架的两级ID体系、附件C可追溯性矩阵、附件D问题风险管理表、全部ADR记录均以编号而非文件路径为引用基准，物理移动不影响任何编号引用的有效性。各文档内部彼此的交叉引用一律使用编号（如"RGS-REQ-006"），不使用文件相对路径，故移动不产生死链。唯一含跨文档文件路径链接的是本README，路径已同步更新。

## 3. 文档管理规则

1. 全部文档在本仓库的`docs/`目录下由Git管理，按§1的8个主题子目录物理分类存放；子目录归属仅为便于查找，**不改变**文档编号、位阶或治理关系。
2. 版本号为`主版本.次版本`，仅**审批完毕**的版本持有主版本号。评审中的版本记为`0.x`。
3. 需求的变更必须记入**修订历史**，并明确标注受影响的需求ID。
4. 未决事项以`【TBD-nnn】`（或领域文档的域内ID`TBD-<域>-nnn`）记载于正文，并同时登记至附件D问题管理表（§1.2或§1.3）。正文中不得遗留未登记的TBD。
5. 本编与附件记述矛盾时，**以本编为准**。
6. **文档位阶与冲突裁决**（依ARC-025 GOV-DOC-001〜004，处置RGS-REV-001 F-016）。本规则原仅定义RGS-REQ-001与RGS-BAS-001两份文档的优先级，文档体系扩至51份后按下表扩展：

   | 层 | 文档 | 位阶 |
   |---|---|---|
   | 第1层 | RGS-REQ-001（及附件A〜D） | **最高** |
   | 第2层 | 领域需求定义书（RGS-REQ-006〜027，不含附件） | 中 |
   | 第3层 | 基本设计书（RGS-BAS-001〜024） | 最低 |

   - **跨层冲突**：以上层为准。基本设计书不得在设计阶段变更需求层的决定；如确需变更，须先修订对应的需求文档并走ADR流程。
   - **同层冲突**（如两份领域需求定义书之间）：以**约束更强者**为准——安全性（NFR-SE系）与数据一致性（DR系）类要求 ＞ 可用性类要求 ＞ 效率／便利性类要求。裁决结果**必须**记录ADR。
   - **新增架构方针的约束**：领域文档新增的ARC-nnn与基准文档ARC-001〜017同位阶，但**不得**与基准文档既有ARC冲突；若确需变更既有ARC，须先修订RGS-REQ-001第10章并走ADR流程，**不得**以在领域文档中新增ARC的方式实质性推翻既有决定。
   - **审查报告类文档**（RGS-REV-nnn）不具位阶，为记录性文档，其结论须经需求文档转化后方产生约束力。

7. **领域文档的治理闭环接入**（依ARC-025）。领域文档须在附件C§7注册域名段、在附件D登记TBD／风险／ADR、在附件C§8登记领域验收标准、挂接阶段计划与试验编号。未完成上述登记的领域文档**不得**基准化——依附件C§1运维规则"本附件未同步更新的需求变更不得批准"。
8. **新增常态运维面的预算约束**（依ARC-026）。任何会产生常态运维负荷的新增项（中间件、定期作业、审计流程、发布通道等），须在附件D§5运维负荷预算台账申领OLU额度；余额不足时**不得**新增，须先回收。相关ADR须记载OLU估算与台账余额，缺少该记载的ADR不得批准。
