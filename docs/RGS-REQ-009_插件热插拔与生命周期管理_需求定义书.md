# 1. 前言

## 1.1 目的

运营期间，策划团队会持续产出限时活动、临时玩法规则、赛季机制等**需要频繁上下线、且上下线节奏与工程发布节奏解耦**的功能单元（以下称"插件"）。若每次活动上线都走完整的RGS-REQ-006挂载流程（新限界上下文、新数据库、新Deployment），将与NFR-OP-010"SRE 2人以内常态运维"的上限冲突——活动的生命周期通常以周为单位，用挂载新App的重量级流程去承载，运维负荷不可持续。

本文档的目的：定义**插件**这一比"新限界上下文"更轻量、但比"纯数值表热更新"（ARC-016）更具行为逻辑能力的功能单元，其热插拔（无需重新部署即可启用/禁用）、生命周期状态机、版本回滚、多节点数据同步的需求，并给出与Rust内存安全模型相容的架构方针（ARC-021），明确**拒绝**通过动态链接库/裸FFI实现"插件"的传统方案。

## 1.2 适用范围

| 范畴 | 说明 | 举例 |
|---|---|---|
| 插件 | 具备一定行为逻辑（非纯数值）、生命周期独立于主干发布节奏、需要频繁启停的功能单元 | 限时活动玩法规则、临时数值倍率活动、节日机制、A/B实验分支 |
| **不适用范围** | 新限界上下文（走RGS-REQ-006挂载流程）；纯数值/配置调整（走既有ARC-016数值表热更新，无需本文档的生命周期机制）；GM后台管控指令（属RGS-REQ-007） |

判定"应做成插件还是应走挂载流程"的原则见§7 ARC-021。

## 1.3 关联文档

| 文档编号 | 文档名 | 与本文档的关系 |
|---|---|---|
| RGS-REQ-001 | 需求定义书 | 本文档延展ARC-014（中间件判定）、ARC-015（版本管理Expand-Contract）、ARC-016（数值表热更新，本文档的插件机制是其超集） |
| RGS-REQ-006／BAS-002 | 功能挂载架构 | 插件与"新限界上下文"的边界判定见ARC-021；插件不触发挂载五要素 |
| RGS-BAS-005 | 插件热插拔与生命周期管理 基本设计书 | 本文档的基本设计展开（本次同步制定） |

# 2. 术语约定

沿用RGS-REQ-002术语表。本文档新增：

| 术语 | 定义 |
|---|---|
| 插件（Plugin） | 本系统内以受控方式实现"行为可热插拔"的功能单元，**不通过**动态链接库加载实现（原因见ARC-021），而通过§7所定义的两种合规机制之一实现 |
| 热插拔（Hot-Plug） | 无需重新部署（滚动更新/重启进程）即可启用（Plug）或禁用（Unplug）插件行为的能力 |
| 插件生命周期 | 插件从注册到移除所经历的状态序列：`已注册`→`已启用`→`已禁用`→`已弃用`→`已移除` |
| 数据同步（本文档语境） | 插件启停状态与插件私有数据在多个运行时/业务服务节点间保持一致的机制，防止同一时刻不同节点对同一插件呈现不同行为 |

# 3. 背景与课题

| 编号 | 课题 |
|---|---|
| P-PLG-001 | 若插件通过传统动态链接库（`.so`/`.dll`）在运行时加载，会引入Rust跨越FFI边界的内存安全风险与ABI不稳定问题，直接威胁ARC-005"权威边界与Single-Writer保证"的正确性——一个有内存错误的插件可能破坏宿主进程的数据完整性 |
| P-PLG-002 | 若插件的启停状态在多个运行时/业务服务节点间不同步，会出现"同一活动在A节点已生效、在B节点未生效"的不一致体验，且可能被利用为跨节点套利（如不同节点对同一活动的奖励倍率不同） |
| P-PLG-003 | 若插件上线无回滚能力，一个有逻辑错误的活动插件可能需要走完整发布流程才能下线，与"活动可能上线数小时后就需紧急下线"的业务节奏不匹配 |
| P-PLG-004 | 若插件私有数据（如某活动的进度数据）与主干数据库耦合过深，插件下线/移除时容易遗留孤儿数据，或误删主干数据 |

# 4. 业务需求

| ID | 需求 | 优先级 |
|---|---|---|
| BR-PLG-001 | 策划团队须能以远快于常规工程发布周期的节奏（分钟级〜小时级）上线/下线活动类插件 | 高 |
| BR-PLG-002 | 插件上线后发现问题，须能在不影响主干业务的前提下快速回滚/紧急下线 | 高 |
| BR-PLG-003 | 插件体系**不得**降低系统既有的内存安全性与数据一致性保证 | 高 |

# 5. 功能需求

## 5.1 插件定义与合规实现方式

| ID | 需求 |
|---|---|
| FR-PLG-001 | 插件**必须**采用§7 ARC-021定义的两种合规实现方式之一（编译期特性开关注册 或 沙箱化脚本引擎），**不得**通过动态链接库/裸FFI加载不受信代码 |
| FR-PLG-002 | 每个插件**必须**在注册时声明：插件ID、所属限界上下文（插件依附于某个既有限界上下文运行，不独立拥有数据库，同ARC-021）、依赖的既有API/事件、私有数据的Schema |

## 5.2 生命周期管理

| ID | 需求 |
|---|---|
| FR-PLG-010 | 插件**必须**遵循状态机：`已注册`→`已启用`↔`已禁用`→`已弃用`→`已移除`，状态迁移须记录审计（复用RGS-BAS-003§7审计设计） |
| FR-PLG-011 | `已启用`↔`已禁用`的切换**必须**支持热插拔（不重启进程），切换延迟目标见§6 |
| FR-PLG-012 | `已移除`**必须**是不可逆操作的最终态，移除前**必须**先经过`已弃用`状态并完成数据归档决定（同RGS-BAS-002§11退场设计的既有理念） |
| FR-PLG-013 | 插件的启用/禁用操作**应当**可由GM后台触发（复用RGS-REQ-007控制平面，作为`AdminService`新增方法，而非独立入口，遵循ARC-019统一入口原则） |

## 5.3 回滚

| ID | 需求 |
|---|---|
| FR-PLG-020 | 插件**必须**支持版本化（`plugin_id`＋`version`），新版本上线时旧版本**必须**保持可立即回退的状态，直至新版本运行稳定期结束 |
| FR-PLG-021 | 回滚操作**必须**能在NFR-PLG-002既定时限内完成，且**不得**要求重新部署或重启进程 |

## 5.4 数据同步

| ID | 需求 |
|---|---|
| FR-PLG-030 | 插件的启停状态**必须**在全部相关节点（运行时/业务服务）间保持强一致或有界最终一致（时限见NFR-PLG-003），**不得**长时间出现节点间行为不一致 |
| FR-PLG-031 | 插件私有数据**必须**归属其所依附限界上下文的既有数据库（新增表，而非新建数据库），遵循该限界上下文既有的一致性机制（OCC/Outbox，同ARC-009） |
| FR-PLG-032 | 插件移除时，其私有数据**必须**按FR-PLG-012的归档决定处理，**不得**遗留无主表且无清理记录 |

# 6. 非功能需求

| ID | 类别 | 内容 | 目标值/判定基准 |
|---|---|---|---|
| NFR-PLG-001 | 效率性 | 从策划提出上线诉求到插件在生产环境启用 | ≤1个工作日（已完成开发测试的插件） |
| NFR-PLG-002 | 可回滚性 | 插件回滚（含紧急禁用）耗时 | p99 < 一次数值表热更新的同等时限（同ARC-016，具体值详细设计确定） |
| NFR-PLG-003 | 一致性 | 插件启停状态跨节点同步延迟 | p99 < 5秒（同ARC-016"tick边界原子切换"的同等量级） |
| NFR-PLG-004 | 安全性 | 插件**不得**引入超越其声明依赖范围的能力（如脚本插件不得访问未声明的API） | 沙箱权限模型验证，见RGS-BAS-005 |

# 7. 架构设计方针 ARC-021

本节为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接RGS-REQ-008新增的ARC-020。**决定事项**，变更须经ADR与审批。

## 7.1 ARC-021：插件热插拔的合规实现方式与生命周期边界（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | 插件**必须**通过以下两种方式之一实现，**不得**使用动态链接库/裸FFI加载不受信代码：①**编译期特性开关插件**——插件代码随主干一同编译，通过配置驱动的特性开关（复用ARC-016数值表热更新的"tick边界原子切换"机制）在运行时启用/禁用，插件的上线/更新走既有CI/CD滚动更新（同ARC-015 Expand-Contract）；②**沙箱化脚本插件**——对于确需比编译期开关更细粒度、更高频热更新能力的场景（如活动规则的具体数值/条件表达式），采用嵌入式沙箱脚本引擎（如受限的Rhai/Lua子集），脚本**仅能**访问显式声明的白名单API，不具备任意内存访问能力 |
| **理由** | Rust的内存安全保证建立在编译期检查之上，跨越FFI边界加载不受信的动态库会完全绕开这层保证，一个插件的内存错误可能破坏整个进程（包括ARC-005权威保证的正确性）。编译期特性开关与沙箱脚本两种方式都不引入跨FFI边界的不受信代码执行，与既有Rust安全模型兼容 |
| **插件与限界上下文的关系** | 插件**不**独立拥有数据库/独立部署单元，**必须**依附于某个既有限界上下文（如活动插件依附于EC或新增的活动限界上下文）运行，若插件逻辑复杂到需要独立数据库/独立扩缩容策略，判定为应走RGS-REQ-006 ARC-018挂载流程而非做成插件 |
| **判定原则（插件 vs 挂载）** | 满足以下**全部**条件时适用插件机制：①生命周期以周/月为单位，短于常规发布节奏②不需要独立数据库③逻辑复杂度可被特性开关或沙箱脚本表达④错误影响面可被§7.2故障隔离设计控制在插件粒度内。否则应走ARC-018挂载流程 |
| **否决方案** | "允许运营/策划直接上传编译后的动态库文件供服务器加载执行"——绕开代码评审与CI/CD质量门禁，且引入FFI内存安全风险，与ARC-005、CON系列既有安全前提直接冲突，已否决 |
| **适用范围** | 全部需要热插拔的功能单元。既有数值表热更新（ARC-016纯数值场景）不强制迁移至本机制，两者共存，插件机制是数值热更新在"具备行为逻辑"场景下的超集 |

# 8. 验收标准

| ID | 验收标准 |
