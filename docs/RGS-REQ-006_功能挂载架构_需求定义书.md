# 1. 前言

## 1.1 目的

RustGameServer（以下称"本系统"）已在RGS-REQ-001／RGS-BAS-001中确立**原子化App群组＋每限界上下文独立DB＋Kubernetes**的整体架构（player_db／economy_db／match_db／social_db／admin_db，各自对应独立的Deployment/StatefulSet）。随项目推进（PH-5〜PH-8），预计将持续新增业务功能（如：邮件系统、公会战、赛季通行证、跨服匹配等）。

若每次新增功能都各自摸索接入方式，会产生：命名不一致、DB边界侵蚀（ARC-008精神被破坏）、事件Schema不兼容、可观测性盲区、上线流程不可重复等问题。**本文档的目的是把"新增一个功能"这件事本身，定义为一个有输入、有输出、可验收、可复用的标准工程流程（以下称"挂载"，Mounting）**，使其在不违反既有ARC-001〜017决定的前提下可重复执行。

## 1.2 适用范围

本文档适用于新增以下任一类型的功能：

| 类型 | 说明 | 示例 |
|---|---|---|
| 新限界上下文（新Atomic App） | 拥有独立数据库、独立Deployment、通过gRPC对外暴露的新业务服务 | 邮件服务、公会服务、赛季通行证服务 |
| 既有限界上下文的功能扩展 | 在player_db／economy_db等既有DB与服务边界**内**新增表/字段/API方法，不新建服务 | 经济服务新增"礼包码兑换"API |
| 横切能力扩展 | 不归属单一限界上下文，影响多个服务的能力 | 新增风控规则引擎、新增A/B实验框架 |

本文档**重点**规定"新限界上下文（新Atomic App）"的挂载流程（第7章ARC-018），因其影响面最大、最容易破坏既有架构边界；对后两类给出简化判定路径（§5.2）。

本文档**不覆盖**：单个服务内部代码的详细设计（属详细设计阶段）、物理DDL（属RGS-DBS-001）、字节级线路格式（属RGS-IFS-001）。

# 2. 术语约定

沿用RGS-REQ-002术语表。本文档新增以下术语：

| 术语 | 定义 |
|---|---|
| 挂载（Mounting） | 将一个新的限界上下文/业务服务，按标准化流程接入本系统既有的Kubernetes集群、服务网格、事件基础设施、可观测性基础设施的过程 |
| 原子化App（Atomic App） | 单一限界上下文对应的独立可部署单元：1个K8s Deployment/StatefulSet + 1个独立数据库(database或独立schema) + 1套gRPC接口 + 1套事件Producer/Consumer配置，边界闭合，不与其他App共享数据库连接 |
| 挂载点（Mount Point） | 新App接入既有系统时必须显式声明的接口集合：gRPC路由、事件Topic、DB连接、可观测性资源标签、网关路由表条目（详见§7 ARC-018） |
| 骨架（Scaffold） | 由标准化模板工具生成的新服务初始代码结构，含CI/CD、Helm chart、健康检查、OTel埋点等"开箱即用"的非业务代码 |
| 退场（Decommission） | 与挂载相对的逆过程：安全地将一个已挂载的App从系统中下线 |

# 3. 背景与课题

| 编号 | 课题 |
|---|---|
| P-MNT-001 | 新功能若自由选择技术栈/部署方式，会导致运维复杂度线性叠加，违反ARC-014"默认不引入新中间件"的精神 |
| P-MNT-002 | 若新功能可自由跨库直接访问其他限界上下文的数据库，会重演ARC-008已否决的"四分方案"跨库Saga问题 |
| P-MNT-003 | 若新功能自行定义事件命名/`partition_key`规则，会破坏ARC-010的顺序保证与消费者的幂等前提 |
| P-MNT-004 | 若新功能上线未接入可观测性基础设施，会重现ARC-017之前"缺乏测定手段"的课题（P-005） |
| P-MNT-005 | 缺少标准化的"从需求到上线"检查清单时，评审依赖个人经验，可追溯性（RGS-REQ-004）容易断裂 |

# 4. 业务需求

| ID | 需求 | 优先级 |
|---|---|---|
| BR-MNT-001 | 业务方新增游戏功能时，工程团队须能在**可预测的周期内**（§6非功能需求给出目标值）完成从需求确定到功能上线 | 高 |
| BR-MNT-002 | 新功能挂载不得影响既有已上线功能的可用性（NFR-AV-*）与数据一致性（DR-*） | 高 |
| BR-MNT-003 | 新功能下线（退场）须为一等公民流程，不得遗留孤儿资源（僵尸DB、失效路由、未清理的事件Topic） | 中 |

# 5. 功能需求

## 5.1 新限界上下文（新Atomic App）挂载

| ID | 需求 |
|---|---|
| FR-MNT-001 | 挂载流程**必须**由标准化脚手架生成初始代码结构（骨架结构见RGS-BAS-002§4），**不得**从零手写CI/CD与K8s manifest |
| FR-MNT-002 | 新App的数据库**必须**是独立的PostgreSQL `database`（或经容量评审后的独立`schema`，判定精神同ARC-008，容量判定原则见BAS-001§5.1），**不得**与既有App共享数据库连接串，**不得**跨库直接`JOIN`或外键引用其他限界上下文的表 |
| FR-MNT-003 | 新App**必须**通过gRPC对外暴露接口；如需被客户端直接访问，须经由API网关路由表登记（不得让客户端直连内部服务） |
| FR-MNT-004 | 新App若需产生/消费事件，**必须**遵循ARC-010既有的Topic命名与`partition_key`规范；新增事件族须登记Schema Registry并标注`schema_version` |
| FR-MNT-005 | 新App**必须**接入既有可观测性基础设施（OTel埋点、统一日志格式、trace贯通），不得使用独立的监控方案 |
| FR-MNT-006 | 新App的K8s部署形态（Deployment或StatefulSet）**必须**按BAS-001§3.2既有判定准则确定：默认无状态Deployment；仅当存在ARC-001同等的"进程内常驻状态且不可迁移"理由时，才可选StatefulSet，并须经架构评审 |
| FR-MNT-007 | 新App挂载**必须**产出挂载记录（Mount Record，见RGS-BAS-002§10），记入RGS-REQ-004可追溯性矩阵 |
| FR-MNT-008 | 涉及跨限界上下文的业务流程（如新功能需要读取经济服务的数据），**必须**通过既有gRPC/事件机制实现，**不得**新增数据库层面的跨库依赖（同ARC-008、ARC-009） |
| FR-MNT-009 | 新App若引入需求定义书ARC-014列举之外的新中间件，**必须**先满足ARC-014判定基准并形成ADR，方可挂载 |

## 5.2 既有限界上下文扩展 / 横切能力扩展（简化路径）

| ID | 需求 |
|---|---|
| FR-MNT-010 | 在既有DB边界内新增表/字段/API方法，**无需**执行§7完整挂载流程，仅需：①数据库迁移脚本走既有CI迁移流水线 ②新增API字段遵循ARC-015后向兼容方针 ③追加/更新对应服务的可观测性埋点 |
| FR-MNT-011 | 横切能力（如风控、实验框架）若以**库/SDK**形式被各App引用，无需独立DB/独立Deployment，但**必须**提供独立的版本发布流程，避免"牵一发动全身"的强耦合升级 |
| FR-MNT-012 | 横切能力若需要独立存储/独立进程运行（如独立风控决策服务），**必须**按§5.1新限界上下文流程执行 |

## 5.3 退场（下线）

| ID | 需求 |
|---|---|
| FR-MNT-013 | 退场**必须**包含：停止新流量路由 → 排空存量请求 → 数据归档/删除决定（须经数据合规评审）→ 撤销K8s资源 → 撤销网关路由 → 撤销事件Topic订阅 → 从可追溯性矩阵标记为"已下线" |
| FR-MNT-014 | 退场**不得**在关联的事件仍有存量消费者的情况下直接停止事件生产（须先完成消费者迁移确认，同ARC-015 Expand-Contract思想） |

# 6. 非功能需求

| ID | 类别 | 内容 | 目标值/判定基准 |
|---|---|---|---|
| NFR-MNT-001 | 效率性 | 从"脚手架生成"到"新App在预发布环境完成首次健康检查"所需时间 | ≤1个工作日（不含业务逻辑开发） |
| NFR-MNT-002 | 可用性 | 新App挂载（含灰度发布）过程中，既有功能的错误率增量 | 增量≤NFR-AV-*既定阈值的10% |
| NFR-MNT-003 | 隔离性 | 新App的数据库故障/过载**不得**影响既有App的数据库连接池与查询延迟 | 独立连接池，独立资源配额（K8s ResourceQuota/LimitRange） |
| NFR-MNT-004 | 可回滚性 | 新App上线后发现问题，**必须**能在不影响既有功能的前提下快速回滚或降级 | 回滚（含灰度权重回退与镜像版本回退）耗时p99<3秒完成切换，参照NFR-PE-007重连恢复时间的同等量级判定 |
| NFR-MNT-005 | 可观测性 | 新App上线时，其黄金指标（延迟/流量/错误/饱和度）**必须**在统一Dashboard中可见 | 上线当日即可见，不得有观测空窗期 |
| NFR-MNT-006 | 一致性 | 挂载模板与既有已上线App的模板**必须**保持同源（同一份Helm chart基座/CI流水线基座） | 模板漂移须走ADR |

# 7. 架构设计方针 ARC-018

本节为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接ARC-017。**决定事项**，变更须经ADR与审批。

## 7.1 ARC-018：新功能挂载规范（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | 任何新限界上下文接入本系统，**必须**遵循"独立DB + 独立部署单元 + gRPC/事件为唯一跨边界通信方式 + 标准化脚手架 + 标准化可观测性接入"的五要素挂载模型，五要素齐备方可视为挂载完成 |
| **理由** | 延续ARC-008"消除不必要的跨库Saga"与ARC-009"禁止双写"的精神；将其从"既有5个限界上下文的静态划分原则"升级为"未来任意新增限界上下文都必须遵循的动态接入规范"，防止系统随功能增多而退化为分布式单体 |
| **与ARC-008的关系** | ARC-008决定的是"道具与货币是否应合并为同一限界上下文"这一具体划分问题；ARC-018决定的是"新划分出的限界上下文应如何接入系统"这一流程问题。新功能是否应与既有上下文合并，或独立成新上下文，仍按ARC-008同等的判定原则（是否存在会产生跨库Saga的强一致性诉求）逐案评审，产出ADR |
| **实现方式** | 由RGS-BAS-002给出脚手架结构、Helm chart模板、DB provisioning流程、网关路由登记、事件Schema登记、可观测性接入的系统级设计 |
| **否决方案** | "新功能自由选择实现方式，事后补齐规范"——事后补齐的实际执行率历史上普遍偏低，且会产生NFR-MNT-003要求的隔离性无法验证的技术债 |
| **适用范围** | 新限界上下文（新Atomic App）。既有上下文内的扩展与横切库/SDK类扩展适用§5.2简化路径 |

# 8. 验收标准

| ID | 验收标准 |
|---|---|
| AC-MNT-001 | 使用标准化脚手架生成的新App，在预发布环境完成部署、健康检查、可观测性Dashboard自动出现，全程无需手工修改CI/CD与Helm chart基座 |
| AC-MNT-002 | 新App数据库故障注入试验（模拟其数据库不可用）不引起既有App错误率上升（对应NFR-MNT-003） |
| AC-MNT-003 | 新App挂载记录（Mount Record）在可追溯性矩阵中可查，包含ARC-018五要素的落实证据 |
| AC-MNT-004 | 一次完整的"挂载→灰度→全量→退场"演练在验证环境中可重复执行，且每一步均有对应的检查清单条目通过 |
