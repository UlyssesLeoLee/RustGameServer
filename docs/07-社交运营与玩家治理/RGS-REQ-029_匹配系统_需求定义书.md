# 1. 前言

## 1.1 目的

RGS-REQ-001§5.3.6（FR-MT-002"匹配队列"，概要"队列投入・撮合・成立通知"）是本系统匹配能力的**声明**，但从未有域文档将其展开为可实现的匹配系统设计。`RGS-BAS-001`§5.5 `match_db`只设计了对局**已经成立之后**的生命周期与结果持久化（`MATCH`/`MATCH_PARTICIPANT`/`MATCH_RESULT`），对局**如何从多个排队玩家匹配成立**这一前置过程完全空白——没有技能评分维度、没有匹配算法（如何在等待时间与匹配质量之间取舍）、没有队列的组队/单排数据模型、没有匹配池在CAP分片架构下的边界判定、没有匹配质量的度量与连败保护、没有排队放弃后的处理。本文档补齐这一整条链路，为FR-MT-002提供可实现的展开设计。

## 1.2 核心设计约束（贯穿全文档，先声明以免读者产生误解）

- 本文档**不**重新设计对局成立后的生命周期管理与结算——该范围已由`RGS-BAS-001`§5.5（`match_db`）与RGS-REQ-001 FR-MT-001/003覆盖，本文档止于"匹配成立、`MATCH`记录创建"这一交接点，交接之后的状态机流转**不变**
- 本文档**不**重新设计排行榜/赛季/段位的展示与结算体系——该范围已由RGS-REQ-017/RGS-BAS-014（GSM域）覆盖，本文档仅在GSM既有维度不足以支撑**对局内技能匹配**用途时，新增一个**匹配专用、非展示性**的评分维度，与GSM展示型排行分离但可选择性联动（见§5.1）
- 本文档**不**重新设计组队合谋/输送检测——该范围属于RGS-REQ-028 ANT域"信号层"的一类具体信号类型，本文档仅定义匹配侧应产出哪些**可被ANT域消费的组队结构信息**（如固定搭档频率），检测逻辑本身**不在本文档展开**（§7.4交叉引用）
- 本文档**不**在CAP分片架构之外另立一套"匹配专属分片模型"——匹配池的跨分片边界判定**必须**套用RGS-REQ-025 FR-CAP-011既定的"逐项列出跨分片共享能力，不默认放开"纪律，本文档的ARC-044正是该纪律在匹配场景下的具体判定结果（而非独立于FR-CAP-011之外的新规则）

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 匹配评分（Match Rating） | 本文档新增的、专供匹配算法内部使用的技能评分维度，非玩家可见的展示型排行分数（区别于RGS-BAS-014既有`ranking_dimension`） |
| 队列条目（Queue Entry） | 一次排队请求的记录单位，可以是单人（单排）或一个既有队伍（组队，复用RGS-REQ-017既有队伍/组队概念） |
| 匹配池（Matchmaking Pool） | 参与同一轮匹配算法撮合的队列条目集合，其范围受§6.2跨分片边界判定约束 |
| 扩圈（Search Radius Expansion） | 匹配算法随等待时间推移逐步放宽匹配评分容差的既定模式，具体设计见RGS-BAS-026 |
| 回填（Backfill） | 对局开始后因玩家提前退出而产生的空位，由匹配系统补充新玩家加入的过程 |

# 3. 背景与课题

## 3.1 现状

- RGS-REQ-001：FR-MT-002"匹配队列"仅一行摘要，从未展开
- RGS-BAS-001§5.5：`match_db`仅覆盖对局成立后的生命周期（`MATCH`状态机、参与者、结果），匹配成立**之前**的过程无任何数据模型或组件设计
- RGS-REQ-025 FR-CAP-010/011：已定义分片间玩家实时状态不共享的原则，以及跨分片共享能力须逐项列出评审的纪律，但清单中未包含"匹配队列成员"这一项，需本文档补充判定
- RGS-BAS-014：GSM域已有`RankingDimension`机制（`player_level`/`season_score`等展示型维度），但均面向玩家可见的排行展示，未覆盖匹配算法所需的、更新频率更高（每局后）且不直接展示的技能评分
- RGS-REQ-028：ANT域已定义"信号层"（服务器权威校验异常＋举报）与"聚合层/处置层"，组队合谋这类欺诈模式本质上是ANT域该处理的一类信号，但ANT域文档制定时匹配系统尚不存在，未预留匹配侧信号接口

## 3.2 课题

- **CH-MM-01**：没有技能评分维度，匹配只能是"先到先得"的随机撮合，无法保证对局双方实力接近，直接影响核心玩法体验
- **CH-MM-02**：没有队列数据模型区分单排与组队，组队玩家的匹配评分如何合成（取平均/取最高/取最低）未定义，且组队规模差异（如3人组匹配单人）如何处理未定义
- **CH-MM-03**：匹配池的范围（单分片内匹配，还是可跨分片撮合）从未按RGS-REQ-025 FR-CAP-011纪律逐项判定，若默认"分片天然隔离"会导致低活跃时段/小分片长时间匹配不到人；若默认"全部跨分片"又可能重新引入FR-CAP-011警告的单点瓶颈
- **CH-MM-04**：等待时间与匹配质量是天然的权衡（越严格匹配质量要求，等待时间越长），当前无任何算法设计取舍这一权衡
- **CH-MM-05**：连续失败（连败）对玩家体验的负面影响未被匹配系统纳入考量，可能导致"越输越匹配到更强对手"的恶性循环（若匹配纯按评分就近撮合而不做连败干预）
- **CH-MM-06**：玩家在排队中途放弃、或对局开始后提前退出产生空位，均无处理设计，可能导致队列状态残留或对局人数不足仍然开始

# 4. 业务需求

| ID | 业务需求 |
|---|---|
| BR-MM-001 | 匹配须基于玩家技能水平进行撮合，而非纯随机或纯先到先得 |
| BR-MM-002 | 匹配须同时支持单人排队与组队排队，且组队与单排的评分/等待时间处理须有明确规则 |
| BR-MM-003 | 匹配池的范围（是否跨分片）须按既有CAP架构的跨分片能力清单纪律逐项判定，不得凭空扩大分片间共享面 |
| BR-MM-004 | 匹配须在等待时间与匹配质量之间提供可运营配置的取舍策略 |
| BR-MM-005 | 连续失败的玩家须获得一定程度的匹配保护，避免体验螺旋恶化 |
| BR-MM-006 | 排队放弃与对局开局空位须有明确处理路径，不产生残留队列状态或人数不足仍开局的情况 |

# 5. 功能需求：技能评分与队列投入

- **FR-MM-001**：系统**必须**为每个可匹配单位（角色）维护一个**匹配评分（Match Rating）**，作为匹配算法撮合依据。**不得**直接复用RGS-BAS-014既有展示型`ranking_dimension`（如`season_score`）作为匹配依据本身——二者更新语义不同（匹配评分每局对局结算后更新，用于算法内部撮合；展示排行分数遵循GSM域自身规则，可能滞后展示、可能赛季重置）。匹配评分的**计算模型**（如ELO/Glicko-2/TrueSkill等具体算法选型）留待RGS-BAS-026详细设计确定
- **FR-MM-002**：匹配评分的对局后结算**必须**复用RGS-BAS-001§4.5.1既有"确定请求"路径（对局结算已是幂等的确定请求场景），**不得**新建一条并行的评分更新管道——匹配评分作为确定请求的一个新增更新字段而非独立事务
- **FR-MM-003**：匹配评分**可以**（非强制）通过既有`RankingSource`事件发布模式（复用RGS-BAS-014§2.3既定的`RankingScoreChanged`事件基础设施）派生出一个只读的展示型排行维度（如"段位分排行榜"），供玩家查看，但该展示视图**必须**遵循GSM域既有的最终一致性与滞后声明（RGS-BAS-014§2.5），**不得**要求匹配评分的每次变更都同步反映到展示视图
- **FR-MM-010**：系统**必须**支持**单人排队**（玩家单独投入队列）与**组队排队**（复用RGS-REQ-017既有队伍概念，队伍作为一个整体投入队列），二者**必须**能够在同一匹配池内被撮合（如组队与单排玩家共同组成一局），**不得**要求两类队列完全隔离
- **FR-MM-011**：组队排队的**合成匹配评分**（用于代表整个队伍参与撮合）**必须**由队伍全体成员的个人匹配评分按既定公式计算（具体公式——取平均/加权/取极值——留待RGS-BAS-026确定），**不得**用队伍中任意单一成员的评分代表整个队伍
- **FR-MM-012**：队伍规模与目标对局编制不匹配时（如3人队伍匹配5v5对局），系统**必须**明确处理规则（如用单排玩家补齐剩余位置，或限制队伍规模不得超过对局编制的既定比例），**不得**产生对局开局人数或阵容不确定的情况
- **FR-MM-013**：玩家在队列中的等待状态（已投入/匹配中/已匹配待确认/已放弃）**必须**可查询，供客户端展示排队进度，查询接口复用既有只读查询模式（同RGS-BAS-003§3.4已确立的低侵入查询原则）

# 6. 功能需求：匹配算法与匹配池边界

- **FR-MM-020**：匹配算法**必须**在匹配评分接近程度与等待时间之间做可配置的取舍——随排队等待时间增长，可接受的评分差容差**应当**逐步放宽（"扩圈"，Search Radius Expansion既定模式，具体扩圈曲线参数留待RGS-BAS-026确定），**不得**采用固定不变的评分容差（会导致偏离平均水平的玩家长时间匹配不到人）
- **FR-MM-021**：匹配池的范围**必须**按RGS-REQ-025 FR-CAP-011既定"逐项列出跨分片共享能力，不默认放开"纪律显式判定：**队列成员归属（尚未进入对局的排队状态）判定为可跨分片共享**，理由见本文档§9 ARC-044；**对局内实时游戏状态（已匹配成立、对局进行中）维持FR-CAP-010既定的单分片、不共享原则不变**——匹配撮合发生在"跨分片可见的队列层"，但撮合成立后玩家实际进入对局所在的分片**必须**是确定的单一分片（复用RGS-REQ-023既有选服路由或撮合时动态指定，具体机制见RGS-BAS-026）
- **FR-MM-022**：跨分片匹配池**必须**复用RGS-REQ-025既定容量分级模型的既有基础设施（不新建独立的跨分片通信机制），队列层的跨分片可见性**必须**遵循与FR-CAP-011同等的独立评审要求，**不得**默认对所有对局模式开放跨分片匹配（如低延迟敏感的模式可配置为仅限单分片内匹配，具体哪些模式启用跨分片留待运营配置）
- **FR-MM-023**：匹配算法的执行**必须**是幂等且可重入的（同一批队列条目在算法执行中途失败后重新执行，**不得**产生重复匹配成立或队列条目丢失），复用ARC-009既有幂等设计原则

# 7. 功能需求：匹配质量、连败保护与放弃处理

- **FR-MM-030**：系统**必须**记录匹配质量度量指标，**至少**包含：匹配成立时的双方/双队平均评分差、玩家从投入队列到匹配成立的等待时长，供运营侧评估匹配算法参数（§6扩圈曲线）是否需要调优
- **FR-MM-031**：系统**必须**提供**连败保护**机制：玩家连续失利达到既定次数后（具体次数留待运营配置，§11 TBD），匹配算法**应当**在后续撮合中适度提高其匹配到实力较弱对手/队友的倾向，**不得**无限制持续施加保护（避免保护机制本身被滥用为"刷分手段"，具体上限与衰减规则留待RGS-BAS-026与运营配置确定）
- **FR-MM-032**：连败保护的调整幅度**必须**有明确上限（不得让保护凌驾于匹配评分本身之上导致长期错配），且**必须**可被运营侧独立开关（复用既有配置/特性开关基础设施，**不得**新建专属配置系统）
- **FR-MM-040**：玩家在匹配成立**之前**主动退出队列（放弃排队），系统**必须**立即将其从匹配池中移除，**不得**保留残留的队列条目参与后续撮合轮次
- **FR-MM-041**：玩家在匹配成立**之后、对局正式开始之前**（如需要双方确认/加载阶段）放弃或超时未确认，系统**必须**将该匹配判定为未成立，**不得**强行以人数不足的阵容开局；已确认的其余玩家**应当**被重新投入队列（保留其原有排队等待时长的合理补偿，具体补偿规则留待RGS-BAS-026确定），**不得**要求已确认玩家重新从零排队
- **FR-MM-042**：对局**已经开始后**因玩家提前退出产生的空位，系统**应当**支持**回填（Backfill）**：从匹配池中撮合新玩家加入进行中的对局，回填的匹配评分容差**应当**参考§6.1扩圈规则但**不要求**与开局时完全一致（进行中对局的回填时效性优先于匹配质量的精确对齐，具体权衡策略留待RGS-BAS-026确定）；不支持回填的对局模式（如强调队伍完整性的模式）**可以**在配置中显式声明关闭回填，**不得**默认全部模式都强制回填
- **FR-MM-043**：对局的实际参与者名单（含回填产生的变更）**必须**准确反映到`RGS-BAS-001`§5.5既有`MATCH_PARTICIPANT`记录，**不得**因回填而破坏该表既有的数据完整性语义
- **FR-MM-044**：系统**必须**产出组队结构信息（如同一批玩家反复固定组队排队匹配的频率统计）供RGS-REQ-028 ANT域信号层消费，作为其"组队合谋/输送"检测的一类信号来源——**本文档不设计该检测逻辑本身**，仅确保数据可用性与可消费性（复用ANT域既有信号接入模式，见RGS-BAS-025§2.1可扩展的信号采集点约定）

# 8. 非功能需求

| ID | 内容 | 等级参考 |
|---|---|---|
| NFR-MM-001 | 匹配算法单轮撮合执行时长**不得**成为玩家等待时间的主要瓶颈（算法本身执行时间应远小于典型排队等待时间量级） | 附件B |
| NFR-MM-002 | 跨分片匹配池的队列成员可见性同步延迟**必须**有明确上限，避免因同步滞后导致同一玩家被重复撮合进多个对局 | 附件B |
| NFR-MM-003 | 匹配质量度量数据（FR-MM-030）的保留期**应当**与既有运营分析类数据同等（供长期趋势分析），具体期限复用既有数据保留策略，不新定义 | 附件B |
| NFR-MM-004 | 匹配成立到对局实际开始的端到端延迟 | p99 目标留待PH-5实测基线确定，同既有NFR-PE-0xx类实时路径指标制定方式 |

# 9. 架构设计方针 ARC-044

**ARC-044：匹配池跨分片边界与技能评分归属原则**

本原则是RGS-REQ-025 FR-CAP-011"跨分片共享能力须逐项列出、不默认放开"纪律在匹配场景下的具体判定结果，包含两条决定：

**决定一：匹配队列成员归属判定为跨分片可共享能力，对局内实时状态维持单分片不共享。**

| 项目 | 内容 |
|---|---|
| 决定 | 玩家投入排队但尚未匹配成立的"队列成员"状态，判定为FR-CAP-011意义下的**跨分片共享能力**；一旦匹配成立、玩家进入对局，该对局的实时游戏状态**必须**归属唯一确定的单一分片，遵循FR-CAP-010既定的分片间零共享原则不变 |
| 理由 | 队列成员本质上是"待撮合的轻量意向数据"（评分、排队时长、队伍构成），不涉及实时tick处理（ARC-001单线程顺序执行约束仅施加于对局进行中的场景Actor，不施加于排队状态），跨分片共享队列成员不违反P-CAP-002"单场景Actor无法无限扩容"的根本约束；反之，若匹配池被人为限制在单分片内，低活跃时段/小分片会出现长时间匹配不到对手的体验问题（CH-MM-03），这正是FR-CAP-011提醒"不得假设分片天然完全隔离而忽略这类跨分片诉求"的典型场景 |
| 否决方案 | （1）匹配池严格限定单分片内——否决，理由如上，会在低活跃时段显著劣化匹配体验，且不被任何既有NFR要求；（2）匹配成立后允许玩家继续保留"跨分片"的对局参与状态（即对局本身跨分片运行）——否决，直接违反FR-CAP-010"分片间玩家实时状态零共享"这条已批准的既有原则，且ARC-001单线程场景Actor模型不支持跨分片tick协同 |
| 适用范围 | 仅适用于"匹配队列成员"这一具体数据类别；不代表其他任何数据类别默认可跨分片共享——其余类别的跨分片诉求须各自独立走FR-CAP-011评审，不得援引本决定类推 |

**决定二：匹配评分是MT域自有的、区别于GSM域展示型排行分数的独立评分维度。**

| 项目 | 内容 |
|---|---|
| 决定 | 匹配评分（Match Rating）归属MT域（对局・匹配子系统）自行维护，**不**并入RGS-BAS-014既有`RankingDimension`模型作为其中一个维度直接复用；GSM域展示型排行分数**可以**（非必须）通过既有事件机制单向派生自匹配评分，但不能反向影响 |
| 理由 | 若直接复用GSM域`RankingDimension`承载匹配评分，会把"每局结算后高频更新、供算法内部消费"的语义与"面向玩家展示、允许滞后、赛季重置"的语义捆细在同一模型上，二者更新频率与一致性要求本质不同（GSM展示视图允许NFR-GSM-002既定滞后，但匹配算法撮合依据若滞后会直接导致撮合质量下降）；分离两个维度使二者可以独立演进（如匹配评分算法迭代不影响展示排行的赛季重置逻辑） |
| 否决方案 | 直接复用`season_score`维度作为匹配依据——否决，理由如上，且`season_score`随赛季重置会导致每赛季初期匹配评分被清零、匹配质量骤降 |
| 适用范围 | 仅适用于本文档定义的匹配评分与GSM展示排行分数的归属划分；不影响GSM域既有维度模型本身 |

具体设计详见 RGS-BAS-026。

# 11. 风险与未决事项

- **本文档待定项**：匹配评分的具体计算模型选型（ELO/Glicko-2/TrueSkill等）留待RGS-BAS-026结合PH-5实测数据确定，本文档仅要求"存在一个匹配专用评分维度"（FR-MM-001），不预先绑定具体算法
- **本文档待定项**：扩圈曲线的具体参数（初始容差、每秒放宽幅度、容差上限）需结合PH-5实测的玩家分布与在线人数基线确定，避免脱离实际玩家规模的空想调优
- **本文档待定项**：连败保护的具体触发阈值（连续失利次数）、调整幅度上限与衰减规则（FR-MM-031/032）需与策划评审确定，不属于纯技术判断
- **本文档待定项**：队伍规模与对局编制不匹配时的具体补齐/限制规则（FR-MM-012）、匹配未成立后重新排队的等待时长补偿具体公式（FR-MM-041）留待详细设计阶段结合具体对局模式确定
- **本文档待定项**：哪些对局模式启用跨分片匹配池、哪些仅限单分片（FR-MM-022）需运营侧按模式的延迟敏感度逐项评审确定，不属于本文档可一次性穷举的清单
- 风险：若跨分片匹配池的队列成员同步机制设计不当，可能重新引入RGS-REQ-025 RSK-CAP-002已警示的"跨分片共享能力抵消分片架构意义"的单点瓶颈——缓解措施为NFR-MM-002明确的同步延迟上限与FR-MM-022要求的逐模式独立评审，具体缓解设计见RGS-BAS-026
- 风险：连败保护机制若被高水平玩家察觉并利用（如刻意输掉对局以换取后续更弱对手，从而"刷"胜率或段位），可能被滥用为一种新的合谋/操纵手段，与RGS-REQ-028 ANT域范围存在重叠——本文档不在此展开检测设计，但FR-MM-044已确保组队结构等信号可供ANT域消费，具体是否需要新增"故意连败"类检测信号留待ANT域后续评估
