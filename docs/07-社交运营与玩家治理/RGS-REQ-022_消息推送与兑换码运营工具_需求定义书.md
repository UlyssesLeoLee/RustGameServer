# 1. 前言

## 1.1 目的与判定原则

移动端离线推送通知（玩家不在游戏内时，通过APNs/FCM等系统通道触达）与RGS-REQ-017定义的站内邮件系统（玩家登录游戏后在收件箱可见）是**两个不同性质的信道**：邮件是游戏内持久化消息，推送是游戏外的即时提醒，二者**不互相替代**。兑换码/礼包码系统此前仅在RGS-REQ-006（功能挂载架构）中作为"挂载模式"的示例一笔带过（"经济服务新增礼包码兑换API"），从未定义防重放、有效期、发放渠道等实际所需的功能需求。

**判定原则**：
- 推送**不新增**独立限界上下文，依附既有玩家（PL）/运营（AD）限界上下文，第三方推送网关（APNs/FCM）视为外部系统（同既有支付服务商的处理方式）
- 兑换码的发放**必须**复用既有FR-EC-003确定请求路径，**不得**新设发放旁路（与本次此前多个模块的一致原则）

## 1.2 关联文档

| 文档 | 关系 |
|---|---|
| RGS-REQ-001 | 复用ARC-006（ACK边界）、FR-EC-003（确定请求路径） |
| RGS-REQ-017 | 邮件系统（信道区分对象），任务/成就配置化触发机制（复用同类配置驱动思想） |
| RGS-REQ-016 | 运营活动（兑换码常见的发放场景之一） |
| RGS-REQ-005附件D | 第三方推送服务的开源许可盘点（若引入自建方案的替代评估） |

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 推送（Push Notification） | 玩家未在线时，经系统级通道（APNs/FCM等）送达的提醒消息 |
| 兑换码 | 一段可被玩家在客户端输入以兑换奖励的字符串，通常由运营批量生成并线下分发（官网/社交媒体/线下活动） |

# 3. 背景与课题

| 课题编号 | 课题 |
|---|---|
| P-OPT-001 | 玩家未在线时，运营活动/邮件到达等信息无法触达，全靠玩家主动打开游戏才能获知，留存与回访效率低 |
| P-OPT-002 | 兑换码若无防重放设计，同一兑换码可能被多次使用或被暴力枚举猜中，造成经济系统的价值发放失控 |
| P-OPT-003 | 推送触达若无用户同意与频率控制机制，容易演变为骚扰式推送，导致玩家关闭通知权限甚至卸载 |

# 5. 功能需求：消息推送

| 编号 | 需求 |
|---|---|
| FR-OPT-001 | 系统**必须**支持向第三方推送网关（APNs/FCM，或自建的开源替代方案，须满足CON-001/CON-002）投递推送消息，第三方网关的选型与密钥管理复用既有RGS-REQ-010 Secrets管理范围 |
| FR-OPT-002 | 推送**必须**分类别（如社交邀请、活动提醒、账号安全），玩家**必须**能按类别自助开关，**不得**只提供"全部开启/全部关闭"的单一粒度 |
| FR-OPT-003 | 推送发送前**必须**校验目标玩家对该类别的同意状态，**不得**向已关闭该类别的玩家发送（违反用户同意边界，ARC-037） |
| FR-OPT-004 | 推送**应当**有频率限制（同一玩家同一类别的推送间隔不得低于可配置阈值），防止运营误操作导致骚扰式轰炸 |
| FR-OPT-005 | 推送发送失败（如设备令牌过期）**必须**被记录且**不得**无限重试，重试策略复用既有ARC-009事件消费者标准模式 |
| FR-OPT-006 | 推送内容**不得**包含玩家账号密文以外的敏感个人信息（复用既有日志脱敏同类原则） |

# 6. 功能需求：兑换码

| 编号 | 需求 |
|---|---|
| FR-OPT-010 | 系统**必须**支持批量生成兑换码，单批次**必须**关联明确的奖励内容、有效期、可兑换次数上限（单个兑换码可为一次性或多次可用，由生成时指定） |
| FR-OPT-011 | 兑换码的字符空间**必须**具备足够的防暴力枚举强度（**不得**使用连续数字或可预测规律），兑换尝试**必须**有速率限制（复用既有NFR-SEC速率限制标准） |
| FR-OPT-012 | 兑换码核销**必须**是幂等操作：同一账号对同一兑换码的重复提交请求**不得**重复发放（复用既有FR-EC-003确定请求路径的幂等保证） |
| FR-OPT-013 | 兑换码核销**必须**校验有效期与剩余可兑换次数，超出范围**必须**明确拒绝并提示原因（区分"已过期""已用完""码不存在"） |
| FR-OPT-014 | 兑换奖励发放**必须**复用既有FR-EC-003确定请求路径，**不得**新设发放旁路 |
| FR-OPT-015 | 运营**必须**能通过GM后台查询兑换码批次的核销进度（复用RGS-BAS-003§3.4只读查询模式） |
| FR-OPT-016 | 兑换码核销记录**必须**留痕（复用RGS-BAS-003§7审计设计），作为经济异常排查的依据 |

# 7. 非功能需求

| 编号 | 分类 | 项目 | 目标 |
|---|---|---|---|
| NFR-OPT-001 | 隐私 | 推送用户同意 | 100%发送前校验同意状态，无绕过路径 |
| NFR-OPT-002 | 安全 | 兑换码防枚举 | 暴力尝试速率限制生效，字符空间强度经安全评审 |

# 8. 架构设计方针 ARC-037

## 8.1 ARC-037：推送的用户同意边界与兑换码的幂等防重放（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | ①推送发送**必须**以玩家分类别的显式同意状态为前置校验，同意状态的判定**集中**在推送发送组件，**不得**由各业务服务各自决定是否推送②兑换码核销**必须**复用既有确定请求路径的幂等机制与FR-EC-003发放路径，**不得**为兑换码单独实现一套发放逻辑 |
| **理由** | ①用户同意判定分散实现容易产生某个业务服务遗漏校验、绕过用户关闭设置的情形，这是推送场景最常见的合规与体验风险来源②兑换码本质是"确定性的一次性/限次奖励发放"，与既有任务奖励、交易结算、赛季奖励是同一类问题（价值发放的原子性与幂等性），复用既有机制避免重复造轮子与行为不一致 |
| **与ARC-018的关系** | 推送与兑换码组件均**依附**既有限界上下文运行，**不新建**独立限界上下文 |

# 9. 验收标准

| 编号 | 内容 |
|---|---|
| AC-OPT-001 | 用户同意边界验证：玩家关闭某类别推送后，该类别推送不再送达 |
| AC-OPT-002 | 兑换码防重放测试：同一账号并发重复提交同一兑换码核销请求，验证仅发放一次 |
| AC-OPT-003 | 兑换码枚举防护测试：模拟暴力枚举兑换码，验证速率限制生效 |
| AC-OPT-004 | 批量生成性能测试：10万量级兑换码批次生成不阻塞GM后台其他操作 |
