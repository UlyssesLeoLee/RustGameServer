# 1. 前言

## 1.1 目的

RGS-REQ-001§5.3.6（FR-AD-004"异常行为检测"）与X-004（"客户端侧反作弊不在本系统范围，以服务器权威+行为检测应对"）构成了本系统反作弊策略的**声明**，但从未有域文档将其**展开为可实现的检测/治理体系**。当前实际状态是：服务器权威校验（ARC-005单一写入者、FR-RT-005移动模拟校验）作为"地基"是完整的，但地基之上完全空白——没有检测信号的系统化采集、没有多个弱信号如何聚合为一个"案件"的机制、没有案件从"疑似"到"确认处置"的审核流程、没有处置动作与既有GM控制平面的对接设计。RGS-REQ-014§3（智能层）自己承认"FR-AD-004只能表达简单阈值规则，无法做多信号组合推理"，但也从未有后续动作去补这个缺口。本文档补齐这一整条链路。

## 1.2 核心设计约束（贯穿全文档，先声明以免读者产生误解）

- 本文档**不**涉及客户端侧反作弊技术（内存篡改检测、驱动级防护等）——该范围由X-004明确排除，**不因本文档而重新纳入**。本文档聚焦**服务端**能做的部分：权威校验的强化、行为信号的采集与分析、案件管理与处置
- 本文档**不**新建反作弊专属的实时判定管线——检测信号的产生复用既有RT/SY的服务器权威校验路径（已存在，只是从未被系统化整理），信号的深度分析复用RGS-REQ-014既有智能层（ARC-027/030确定性闸门），处置复用既有AdminService（ARC-019）与举报系统（RGS-REQ-017 FR-GSM-030〜033），本文档的价值在于把这几个既有能力**串成一条完整链路**，而非发明新组件
- **处置权收口**：任何自动检测结果，无论置信度多高，**均不得**自动执行封禁/惩罚——这是ARC-030确定性闸门原则在反作弊场景的具体应用，处置**必须**经人工审核（复用既有GM控制平面二次确认流程）
- 与RGS-REQ-017 FR-GSM-030（玩家举报）的关系：举报是本体系的**信号来源之一**（另一来源是自动检测），本文档**不重新定义**举报提交机制，只定义举报如何与检测信号一起被聚合进案件

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 检测信号（Detection Signal） | 单次产生的、可疑但不足以单独定案的异常观测（如一次移动速度超限、一次输入频率异常） |
| 案件（Case） | 针对某个`player_id`的多个检测信号（或举报）聚合后形成的、待审核的治理对象 |
| 信号融合（Signal Fusion） | 将多个弱信号组合评估置信度的过程，复用RGS-REQ-014智能层能力 |
| 处置（Disposition） | 案件审核后采取的动作（警告/禁言/封禁/无需处理），必须经既有GM控制平面 |

# 3. 背景与课题

## 3.1 现状

- RGS-BAS-001：服务器权威校验（移动速度、碰撞、输入合法性）已存在，但仅在检测到异常时"丢弃并计入异常计数"，计数之后无任何下游处理
- RGS-REQ-010：明确声明客户端侧反作弊不在范围内，但未定义服务端侧的检测/治理体系应该是什么样
- RGS-REQ-014：智能层设计中提到FR-AD-004能力上限，但反作弊本身既不是智能层的初始四个场景之一（RGS-BAS-011§5A.3），也没有域文档承接
- RGS-REQ-017：FR-GSM-030〜033定义了玩家举报的提交、去重、处置权收口，但举报处置目前是GM人工按案例判断，缺少与自动检测信号的联动

## 3.2 课题

- **CH-ANT-01**：异常计数（现有唯一产出）从未被消费——除了被丢弃的请求本身不生效外，"这个玩家已经异常了很多次"这一信息完全没有沉淀，无法识别惯犯
- **CH-ANT-02**：单个信号（一次速度超限）可能是网络抖动导致的误判，不足以定案；但如果不聚合多个弱信号，反作弊系统永远只能抓最明显、最粗糙的作弊手段，抓不住"轻微但持续"的作弊行为
- **CH-ANT-03**：举报与检测信号是两条独立管道，同一玩家可能同时被举报"作弊"且被自动检测标记异常速度，但两者从未交叉验证，可能重复调查或互相印证的信号被忽略
- **CH-ANT-04**：反作弊处置直接影响玩家账号状态（禁言/封禁），若无审核收口，误判成本极高（正常玩家因网络抖动被封禁）

# 4. 业务需求

| ID | 业务需求 |
|---|---|
| BR-ANT-001 | 服务器权威校验产生的异常事件须被系统化采集，而非仅"丢弃并计数"了事 |
| BR-ANT-002 | 多个弱信号（含举报）须能聚合为一个案件，供人工审核判定，而非逐信号孤立处理 |
| BR-ANT-003 | 案件审核与处置须收口至既有GM控制平面，不存在自动执行的处置路径 |
| BR-ANT-004 | 惯犯（历史案件多、屡教不改）须可被识别，供GM决定升级处置力度 |

# 5. 功能需求：检测信号采集

- **FR-ANT-001**：系统**必须**将既有服务器权威校验产生的异常判定（移动速度超限、碰撞穿透、输入频率异常，复用RGS-BAS-001既有校验逻辑）持久化为**检测信号记录**，字段至少包含`player_id`、信号类型、发生时间、原始数值与阈值、所属场景/对局引用。**不得**继续采用"丢弃后仅递增计数器"的方式，计数器信息不足以支撑后续审核
- **FR-ANT-002**：检测信号的产生**必须**复用既有服务器权威校验路径本身（RT场景Actor校验、SY同步校验），**不得**新增一条并行的反作弊专属实时判定管线——信号只是"把已有校验的判定结果记下来"，校验逻辑本身不因本文档而改变
- **FR-ANT-003**：检测信号的写入**必须**是异步、不阻塞既有实时路径的（复用ARC-013背压原则），信号采集本身故障**不得**影响移动/战斗等业务路径的正常判定（信号记录失败可接受丢失，但**不得**阻塞或拖慢主路径）
- **FR-ANT-004**：除服务器权威校验产生的信号外，系统**必须**接纳玩家举报（复用RGS-REQ-017 FR-GSM-030既有提交机制）作为另一类信号来源，举报记录须可关联至本文档定义的案件（§6）

# 6. 功能需求：案件聚合与信号融合

- **FR-ANT-010**：系统**必须**提供**案件（Case）**聚合机制：针对同一`player_id`在既定时间窗口内的多个检测信号（含举报），**必须**能聚合为一个案件，而非逐信号孤立展示给审核者
- **FR-ANT-011**：案件的置信度评估（多个弱信号组合后是否足以怀疑）**应当**复用RGS-REQ-014既有智能层能力（LangGraph分析图），作为智能层RGS-BAS-011§5A.3初始四场景之外的**新增分析图场景**，须按既有FR-NEURO-044同等评审流程接入（不得绕过分析图生命周期治理直接接入生产），且**必须**满足既有确定性闸门（ARC-030）——分析结果**仅**产出"建议"，不产出任何直接执行的处置动作
- **FR-ANT-012**：低复杂度场景（如同一玩家单一信号类型短时间内重复触发超过既定阈值）**可以**采用简单规则判定生成案件，**不要求**必须经过智能层——本条款明确"简单规则"与"智能层多信号融合"是**互补**关系而非互斥，简单场景不为了"用上智能层"而增加不必要的复杂度（同ARC-014"未证明不引入复杂性"精神）
- **FR-ANT-013**：案件**必须**记录其构成信号的完整引用列表（哪些检测信号/举报被聚合进本案件），供审核者与事后复核追溯依据
- **FR-ANT-014**：同一玩家的历史案件（含已处置与已驳回）**必须**可查询，用于识别惯犯——查询接口复用既有GM控制平面只读查询模式（RGS-BAS-003§3.4）

# 7. 功能需求：处置流程

- **FR-ANT-020**：案件的处置**必须**经由既有GM控制平面（`AdminService`，ARC-019统一入口）人工审核，**不存在**任何自动执行处置动作的路径——无论案件置信度评估结果如何（即使是FR-ANT-011智能层产出的高置信度建议），处置动作的最终触发**必须**是GM的显式操作
- **FR-ANT-021**：处置动作**必须**复用既有GM控制平面高危操作分类与二次确认流程（RGS-BAS-003§8），处置类型（警告/禁言/封禁）**必须**映射至既有`AdminService`方法，**不得**发明新的执行接口
- **FR-ANT-022**：案件审核结果（确认处置/驳回/需要更多信息）**必须**留痕（复用RGS-BAS-003§7审计设计），驳回的案件**不得**物理删除，保留供后续同玩家新案件聚合时参考历史
- **FR-ANT-023**：处置动作执行后，**必须**通知案件所涉及的原始举报者（若案件包含举报来源）处置结果的摘要（不含其他玩家隐私细节），复用既有邮件/通知机制（RGS-REQ-017/RGS-REQ-022既有信道），**不得**要求举报者主动查询才能获知处置结果
- **FR-ANT-024**：误判处置（GM后续判定此前处置有误）**必须**支持撤销/恢复账号状态，撤销操作同样走既有高危操作二次确认与审计留痕，**不得**因"纠错"而降低审计标准

# 9. 架构设计方针 ARC-043

**ARC-043：反作弊信号分层与处置权收口原则**

反作弊体系遵循三层结构，层与层之间职责严格分离：

1. **信号层**：既有服务器权威校验的异常判定 + 玩家举报，二者是唯一的信号来源，**不新增**独立的反作弊专属检测机制
2. **聚合层**：多信号聚合为案件，简单场景走规则判定，复杂场景复用既有智能层（受ARC-030确定性闸门约束，仅产出建议）
3. **处置层**：**唯一**收口至既有GM控制平面，任何自动化程度多高的分析结果都不能跳过人工审核直接执行

三层单向依赖（信号→聚合→处置），**不存在**任何跨层捷径（如信号直接触发处置）。该原则是ARC-030"确定性闸门"与ARC-019"控制平面统一入口"两条既有原则在反作弊这一具体场景下的组合应用，不构成独立于二者之外的新决定。

具体设计详见 RGS-BAS-025。

# 10. 验收标准

| ID | 验收标准 |
|---|---|
| AC-ANT-001 | 故障注入试验：模拟检测信号写入组件不可用，验证RT/SY既有实时路径（移动/战斗判定）不受影响 |
| AC-ANT-002 | 模拟同一玩家在时间窗口内触发5次同类检测信号，验证系统自动聚合为1个案件而非5条孤立记录 |
| AC-ANT-003 | 抽查任一案件的处置记录，验证处置动作的触发者为GM人工操作，不存在系统自动执行的处置记录 |
| AC-ANT-004 | 模拟误判处置后的撤销操作，验证账号状态恢复且撤销本身留有审计记录 |
| AC-ANT-005 | 举报与自动检测信号命中同一玩家时，验证二者被聚合进同一案件而非产生两个独立案件 |

# 11. 风险与未决事项

- **TBD-ANT-001**：案件聚合的具体时间窗口（多久之内的信号算作"同一案件"）与聚合阈值（多少信号触发案件生成）未定义具体数值，需结合PH-4实测的正常玩家网络抖动基线确定，避免阈值过严导致误判率过高
- **TBD-ANT-002**：FR-ANT-011智能层分析图场景的具体图结构（哪些信号特征输入、如何输出置信度）留待详细设计阶段结合RGS-BAS-011既定的LangGraph设计范式确定
- **RSK-ANT-001**：若检测信号的判定阈值设置过严（如移动速度容差过小），可能大量捕获因网络抖动/服务器负载产生的正常玩家误判，反噬玩家体验；若设置过松则漏检——阈值调优本身是持续过程，需纳入常态化运营而非一次性设定
- **RSK-ANT-002**：举报滥用（恶意举报正常玩家"作弊"意图消耗审核资源或诬陷）需要与RGS-REQ-017既有FR-GSM-033去重/滥用检测机制联动，本文档不重新设计举报滥用防护，仅确保案件聚合层不会因大量恶意举报而误判为"高置信度作弊案件"（举报类信号的置信度权重应低于自动检测信号，具体权重留待FR-ANT-011详细设计）
