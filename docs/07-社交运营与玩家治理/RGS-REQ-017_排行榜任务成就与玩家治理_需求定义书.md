# 1. 前言

## 1.1 目的

RGS-REQ-001已确立本系统的核心架构（实时模拟、经济、社交、运营）与九组领域文档已展开其治理、安全、测试等横切关注面。但作为一个**面向运营的游戏服务器**，仍有若干**在几乎全部同类产品中都会出现、此前完全未被设计或仅以一行带过**的功能模块。本文档逐一补齐：

| 模块 | 此前状态 |
|---|---|
| 排行榜（Leaderboard） | 仅在DR-003"临时共享状态・缓存"分类中作为**举例**出现一次，无任何FR、无数据模型、无一致性设计 |
| 任务与成就（Quest & Achievement） | "成就"仅在DR-002示例与FR-GOV-001的永久事实枚举中被提及，**无任务系统本身**（任务的领取/进度/完成/奖励发放）的任何设计 |
| 邮件系统（Mail） | BR-010"邮件・奖励发放"是唯一涉及邮件的条目，仅一行摘要（映射至FR-AD-002批量补偿与FR-EC-003确定请求），**从未设计**邮件作为玩家可见的收件箱（列表、已读/未读、附件领取、过期清理）这一独立能力 |
| 玩家举报与黑名单（Report & Block） | **完全缺失**。既有RGS-REQ-007 FR-GM-012（禁言）是**GM侧**的治理工具；本文档补齐**玩家侧**的自助能力（举报可疑行为、拉黑免打扰），二者不同 |
| 赛季与段位（Season & Ranking） | FR-MT-001〜003（对局生命周期/匹配/结算）已存在，但**赛季重置、段位晋升/保护、跨赛季继承规则**从未设计 |

## 1.2 判定原则（先声明，避免与既有模块混淆）

本文档五个模块**均不新建限界上下文**，全部依附既有限界上下文（EC／GD／MT／AD）运行，遵循RGS-REQ-006 ARC-018既定的挂载判定原则；仅排行榜因引入"派生只读视图与权威数据源之间的一致性边界"这一此前未被讨论过的架构问题，新增ARC-031。其余四个模块**不新增架构方针**，纯为既有ARC-001〜030框架内的功能需求扩展。

# 2. 术语约定

沿用RGS-REQ-002术语表。本文档新增：

| 术语 | 定义 |
|---|---|
| 派生排行视图（Derived Ranking View） | 排行榜对外提供查询的数据形态，由权威数据源（PostgreSQL永久事实）**派生**而来，允许短暂滞后于源数据，但**不得**成为独立的权威 |
| 任务（Quest） | 玩家可领取、追踪进度、完成后获得奖励的目标性活动，状态机涵盖"可领取→已领取→进行中→已完成→已领奖" |
| 成就（Achievement） | 与任务同构但**通常无需主动领取**（被动触发/永久可见）、**不因赛季重置而清空**的里程碑记录 |
| 举报（Report） | 玩家对另一玩家的可疑/违规行为提交的结构化反馈，是FR-AD-004异常检测与GM人工判定之外的**第三类信号来源**（玩家自报） |
| 黑名单（Block List） | 玩家单方面设置的、使被拉黑者无法向自己发起社交行为（私聊/组队邀请）的个人级列表，**不同于**GM侧的系统级禁言 |
| 赛季（Season） | 有明确起止时间的运营周期，段位/排行榜等状态在赛季边界处按既定规则重置或继承 |

# 3. 背景与课题

| 编号 | 课题 |
|---|---|
| P-GSM-001 | 排行榜若直接以PostgreSQL权威表为查询路径（每次查询实时排序），在玩家规模增长后必然成为热点查询瓶颈；若无设计地引入缓存又可能与权威数据脱节，且脱节到什么程度算可接受此前无判定基准 |
| P-GSM-002 | 任务/成就的进度追踪涉及监听大量游戏内事件（击杀数、登录天数、消费金额……），若每个任务条件都单独编写事件订阅逻辑，会随任务数量增长产生大量重复代码，且新增任务类型需要改动核心服务代码而非配置 |
| P-GSM-003 | 邮件系统若与既有补偿发放（FR-AD-002）混为一谈，会让"运营批量补偿"与"玩家可见的常态化收件箱"两种性质不同的诉求耦合在同一套数据模型里，前者是低频运营操作，后者是玩家日常高频查询 |
| P-GSM-004 | 若无玩家自助举报能力，异常行为的发现完全依赖FR-AD-004阈值规则与GM人工巡查，对于规则难以覆盖的"文字/语音骚扰"等场景缺少信号来源 |
| P-GSM-005 | 赛季重置若无明确的架构设计，容易在赛季边界产生数据不一致（如重置过程中玩家仍在完成对局，段位计算基于哪个赛季不明确） |

# 4. 业务需求

| ID | 需求 | 优先级 |
|---|---|---|
| BR-GSM-001 | 玩家须能查看多维度排行榜（等级/战力/赛季积分等），且查询性能不随玩家规模增长而显著劣化 | 高 |
| BR-GSM-002 | 玩家须能通过任务与成就系统获得持续的游玩目标与奖励反馈 | 高 |
| BR-GSM-003 | 玩家须能通过收件箱接收运营批量发放与系统通知，且未及时领取不造成永久损失（在合理保留期内） | 中 |
| BR-GSM-004 | 玩家须能自助举报可疑行为、拉黑不想接触的其他玩家，无需每次都依赖GM人工介入 | 中 |
| BR-GSM-005 | 玩家须能在赛季制玩法中获得公平的段位晋升体验，且赛季重置不产生数据错乱或不当得利 | 高 |

# 5. 功能需求：排行榜

| ID | 需求 |
|---|---|
| FR-GSM-001 | 系统**必须**支持至少以下排行维度：玩家等级、赛季积分、（PH-6+）公会声望，具体维度**应当**可配置扩展而非硬编码有限枚举 |
| FR-GSM-002 | 排行榜查询**必须**从§11 ARC-031定义的派生排行视图读取，**不得**直接对PostgreSQL权威表做实时全表排序查询 |
| FR-GSM-003 | 派生排行视图的更新**必须**为增量式（单次分数变更只触发局部重新排序的必要计算），**不得**采用"每次变更全量重算整个排行榜"的方式 |
| FR-GSM-004 | 排行榜**必须**支持分页查询与"查询指定玩家附近排名"（而非仅前N名），后者是高频的玩家自身定位诉求 |
| FR-GSM-005 | 排行榜数据**必须**允许短暂滞后于权威数据源（同DR-003既定"可容忍，可重建"的缓存属性），但滞后时长**必须**有明确上限并可监控（复用RGS-BAS-004可观测性规范） |
| FR-GSM-006 | 涉及**赛季结算奖励**的排行榜（如"赛季前100名发放专属道具"）在结算时点的名次判定**必须**回落至权威数据源做最终裁定，**不得**仅凭派生视图的滞后快照作为奖励发放依据（避免因视图滞后导致的奖励错发） |

# 6. 功能需求：任务与成就

| ID | 需求 |
|---|---|
| FR-GSM-010 | 任务/成就的**触发条件**（如"击杀100只怪物"、"累计登录7天"）**必须**以声明式配置表达（复用ARC-016数值表热更新机制分发），**不得**为每个任务类型单独编写事件订阅代码 |
| FR-GSM-011 | 任务进度的更新**必须**由既有事件基础设施驱动（订阅ARC-010既定的事件流，如`ItemGranted`／对局结算事件），**不得**要求业务服务为任务系统专门新增同步调用 |
| FR-GSM-012 | 任务状态机**必须**遵循"可领取→已领取→进行中→已完成→已领奖"，非法迁移（如未完成直接领奖）**必须**被拒绝，同RGS-REQ-001第8章既定状态机设计纪律 |
| FR-GSM-013 | 任务奖励发放**必须**复用既有FR-EC-003确定请求路径，**不得**新设发放旁路（同RGS-REQ-013 FR-GOV-001同类原则的应用） |
| FR-GSM-014 | 成就**应当**与任务共享同一套触发条件配置机制与进度追踪基础设施，但**必须**在数据模型上标注"是否随赛季重置清空"（成就默认不清空，任务默认随赛季/周期重置，具体策略可配置） |
| FR-GSM-015 | 任务/成就的进度追踪**不得**成为每次相关事件产生时的同步阻塞路径——进度更新**必须**是异步的（复用ARC-009事件消费幂等机制），事件产生方（如战斗判定）**不得**等待任务进度更新完成才能继续 |

# 7. 功能需求：邮件系统

| ID | 需求 |
|---|---|
| FR-GSM-020 | 邮件系统**必须**提供玩家可见的收件箱：邮件列表、已读/未读状态、附件（道具/货币）领取、邮件删除 |
| FR-GSM-021 | 邮件**必须**区分**系统邮件**（运营批量发放，复用既有FR-AD-002补偿发放机制作为其一种生成来源）与**业务邮件**（如交易失败退还、任务奖励超出背包容量时的兜底发放），两者共享同一套收件箱数据模型与查询接口，**不得**是两套独立系统 |
| FR-GSM-022 | 邮件附件的领取**必须**复用既有FR-EC-003确定请求路径，**不得**新设发放旁路（同FR-GSM-013同类原则） |
| FR-GSM-023 | 邮件**必须**有可配置的保留期，到期未领取的邮件及其附件**应当**被清理（复用RGS-BAS-007§4既定的分区归档标准），清理前**应当**有到期提醒（复用既有通知/告警机制） |
| FR-GSM-024 | 邮件发送**必须**支持批量目标（全服/指定玩家列表/满足特定条件的玩家群体），批量发送**必须**是异步处理（不得阻塞GM操作的即时响应，复用RGS-BAS-003控制平面既有的异步建议/工单处理模式） |

# 8. 功能需求：玩家举报与黑名单

| ID | 需求 |
|---|---|
| FR-GSM-030 | 玩家**必须**能对指定玩家提交举报，包含举报类型（枚举：作弊/骚扰/不当昵称/其他）与可选的上下文引用（如触发举报的具体对局/聊天记录标识） |
| FR-GSM-031 | 举报**必须**产生审计留痕（复用RGS-BAS-003§7审计设计的同类存储原则），且**必须**可被GM后台查询（复用RGS-BAS-003§3.4只读查询模式），作为FR-AD-004阈值检测与GM人工判定之外的第三类信号 |
| FR-GSM-032 | 单个玩家的举报**不得**自动触发任何处罚——举报是**信号**而非**判决**，处罚**必须**经由既有`AdminService`（`BanAccount`／`MuteChat`）由人工或RGS-REQ-014智能层（若已启用）按既有ARC-030确定性闸门流程处理，**不得**为举报开辟自动执行的处罚旁路 |
| FR-GSM-033 | 系统**应当**对短时间内针对同一目标的大量重复举报做去重统计（同一举报者对同一目标的重复举报不重复计数信号强度），防止举报本身被滥用为骚扰手段 |
| FR-GSM-034 | 黑名单**必须**是玩家自助、单方面、即时生效的：被拉黑者**不得**能向拉黑者发起私聊（FR-LBY-011既定私聊路由须查询黑名单状态）、组队邀请，**不得**要求GM介入或审批 |
| FR-GSM-035 | 黑名单**不得**影响拉黑者与被拉黑者在同一公开频道（世界/公会）的可见性——黑名单是**点对点屏蔽**，不是**隐身**，两者语义不同，**不得**混淆实现 |

# 9. 功能需求：赛季与段位

| ID | 需求 |
|---|---|
| FR-GSM-040 | 赛季**必须**有明确的起止时间，赛季切换**必须**在既定边界原子发生（复用ARC-016"tick边界原子切换"同类思想应用于赛季边界，**不得**出现"部分玩家已按新赛季结算、部分仍按旧赛季"的中间态） |
| FR-GSM-041 | 段位**必须**是状态机（同RGS-REQ-001第8章既定纪律），非法迁移（如跳级晋升）**必须**被拒绝 |
| FR-GSM-042 | 赛季重置时，段位/赛季积分的**继承规则**（完全清零／按比例保留／软重置到特定区间）**必须**明确定义且可配置，**不得**由实现阶段临时决定（避免P-GSM-005"重置边界数据错乱"风险的根源——根源正是规则未被提前明确） |
| FR-GSM-043 | 赛季结算（段位定级、赛季奖励发放）**必须**在赛季边界的**权威数据源**上进行（同FR-GSM-006原则的复用：结算不得基于滞后的派生视图），且**必须**具备幂等性（重复触发结算不产生重复奖励） |
| FR-GSM-044 | 赛季切换时正在进行中的对局**必须**有明确归属规则（该局按旧赛季结算，还是不计入任何赛季），**不得**产生"这局到底算不算数"的未定义行为 |

# 10. 非功能需求

| ID | 类别 | 内容 | 目标值/判定基准 |
|---|---|---|---|
| NFR-GSM-001 | 性能 | 排行榜查询（含"附近排名"查询）延迟 | p99 < 100ms，不随玩家总数增长呈超线性劣化 |
| NFR-GSM-002 | 一致性 | 派生排行视图与权威数据源的滞后时长 | p99 < 既定阈值（具体值详细设计确定），超限须告警（复用RGS-BAS-003§6） |
| NFR-GSM-003 | 一致性 | 赛季结算的幂等性与准确性 | 故障注入试验：结算过程中断后重新触发，结果与不中断时一致，无重复/遗漏奖励 |
| NFR-GSM-004 | 可扩展性 | 任务/成就触发条件新增 | 新增一种触发条件类型**不得**要求修改已有任务的代码路径，只需新增配置与对应的事件订阅声明 |
| NFR-GSM-005 | 隐私 | 黑名单列表内容 | 仅拉黑者自己可查询自己的黑名单，**不得**向任何第三方（含被拉黑者）暴露"谁拉黑了谁" |
| NFR-GSM-006 | 存储 | 邮件与举报记录的保留期 | 邮件默认90天（可配置），举报记录同审计日志保留期（复用既有3年，因涉及可能的账号处罚依据） |

# 11. 架构设计方针 ARC-031

本节为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接RGS-REQ-015新增的ARC-028（本文档序号晚于RGS-REQ-016但先于其审批完成，ARC编号依制定顺序连续分配，不影响各文档的独立编号）。**决定事项**，变更须经ADR与审批。

## 11.1 ARC-031：派生排行视图的一致性边界（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | 排行榜**必须**实现为**派生只读视图**：权威数据（玩家等级、赛季积分等）持久化于既有PostgreSQL（各限界上下文既有数据库），排行榜的**排序与查询**由缓存基础设施（复用ARC-012既定的"排行榜"既有缓存边界示例，本条正式将其展开为设计）承载增量更新的有序结构。派生视图**允许**短暂滞后（NFR-GSM-002），但**不得**被任何涉及永久事实发放（赛季奖励、结算）的流程当作权威——此类流程**必须**回落至权威数据源做最终裁定（FR-GSM-006、FR-GSM-043） |
| **理由** | 排行榜的读取模式（高频、大范围排序查询）与权威数据的写入模式（低频、单条更新）在负载特征上截然不同，若用同一套强一致存储同时满足两者，要么读性能不足（P-GSM-001），要么为了读性能牺牲写路径的事务保证。派生视图模式（读写分离，读路径可接受滞后）是解决该矛盾的标准手段，但**必须**明确"哪些操作可以用滞后视图、哪些不能"的边界——否则容易在实现阶段被逐步滥用到不该用的场景（同RGS-REQ-014 RSK-NEURO-004"边界被逐步放宽"同类风险模式） |
| **与ARC-012的关系** | ARC-012已将"排行榜"列为缓存基础设施的既有适用范围示例（"缓存、会话、在线状态、排行榜……"），但未展开其具体的一致性设计。本条是对该既有决定的**具体化**，不改变ARC-012本身 |
| **与ARC-009 Effectively Once的分工** | ARC-009保证的是"业务事务的确定路径不重复/不丢失"，本条保证的是"排行榜这一**派生**视图的更新不需要与源事务同等的强一致性"。两者管辖不同的数据形态（权威事实 vs 派生视图），不冲突 |
| **否决方案1** | "排行榜直接查询权威表并实时`ORDER BY`"——查询性能随数据量增长劣化（P-GSM-001），且排行榜的高频读会与权威表的业务写竞争数据库资源，已否决 |
| **否决方案2** | "赛季结算也直接使用派生视图的当前快照，图省事不回落权威源二次核实"——派生视图的滞后可能导致结算时点的名次与权威数据存在细微偏差，在"前N名发放稀缺奖励"场景下，这种偏差会被玩家察觉并构成公平性质疑，已否决（FR-GSM-006） |
| **适用范围** | 全部排行榜类查询。任务/成就/邮件/举报/黑名单模块不产生排序类高频查询，不适用本条，按既有ARC-008/009/012等既定原则实现即可 |

# 12. 验收标准

| ID | 验收标准 |
|---|---|
| AC-GSM-001 | 排行榜查询延迟满足NFR-GSM-001，负载试验（10万玩家规模）验证不呈超线性劣化 |
| AC-GSM-002 | 赛季结算故障注入试验：结算中途中断后重新触发，验证幂等（无重复/遗漏奖励），且结算结果基于权威数据源而非滞后视图 |
| AC-GSM-003 | 新增一种任务触发条件类型，验证无需修改已有任务代码路径 |
| AC-GSM-004 | 黑名单生效验证：被拉黑者的私聊/组队邀请均被拒绝，但公开频道可见性不受影响；黑名单内容不向第三方泄露 |
| AC-GSM-005 | 举报流程验证：单次举报不触发自动处罚，处罚均经既有`AdminService`人工/闸门流程 |
