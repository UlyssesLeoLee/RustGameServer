# 1. 前言

## 1.1 目的与本文档在文档体系中的位置

RGS-REQ-001第12章已定义试验**分类体系**（TL-1〜8试验级别、VF-001〜016重点验证项目、FT-001〜014故障注入试验、QA-001〜006质量目标），S-008已将"负载试验用模拟客户端"列入系统范围。但**尚未定义**：①模拟客户端/Mock服务的具体架构②TL-6负载试验的工具选型③是否存在、以及如何存在自动化的UAT（用户验收测试）能力。

本文档的目的是把这些**执行手段**补齐，使第12章的试验分类体系具备可执行的落地基础设施。本文档**提前激活**README既有"后续制定文档"表中RGS-TST-001（试验计划书，原计划PH-2制定）的部分范围——具体的**试验用例明细**仍留待RGS-TST-001按§9处置；本文档负责**执行这些用例所需的基础设施**（Mock、性能测试工具、UAT自动化框架）。

## 1.2 关键边界声明（先声明以防误解）

| 边界 | 说明 |
|---|---|
| 不触碰X-001 | 游戏客户端本体由外部团队实现，不属本系统范围。本文档的"模拟客户端"是**协议层的测试替身**（讲IF-001/002协议但不含任何渲染/玩法表现），不是对真实客户端的复刻，也不代替客户端团队的自有测试 |
| 不触碰X-006 | 运营后台UI不属本系统范围，本系统仅提供API（FR-AD-001〜005、RGS-BAS-003）。本文档若涉及Playwright驱动的"GM后台"，其性质是**API契约的参考验证载体**（一个最简UI，仅用于自动化验证`AdminService`的HTTP传输路径行为），**不是**面向运营团队交付的产品级界面 |
| Mock与仿真的区别 | 本文档的Mock服务模拟**外部依赖的接口行为**（如支付渠道IF-006）用于隔离测试，不模拟其业务规则的全部细节；性能测试的"模拟客户端"模拟**协议层的流量特征**用于压测，不模拟游戏内容 |

## 1.3 适用范围

| 范畴 | 说明 |
|---|---|
| Mock服务 | ①协议层模拟客户端（S-008具体化，讲IF-001 QUIC协议，批量并发连接用于负载试验）②外部依赖Mock（IF-006支付渠道等，用于集成/契约测试的隔离）③参考GM后台（用于UAT自动化的最简HTTP/UI载体，非生产交付物） |
| 性能测试 | k6承载TL-6负载试验中**HTTP/gRPC层**（API网关、运营API）的负载生成；协议层（QUIC，IF-001）的负载生成由①的自研模拟客户端承载（k6原生不支持自定义QUIC游戏协议） |
| UAT自动化 | Playwright承载**HTTP层**的端到端场景验证（API网关业务流程、参考GM后台的关键操作路径），**不**承载游戏内实时玩法的UAT（该部分依赖真实客户端，不在本系统范围内，由客户端团队负责） |
| **不适用范围** | 真实游戏客户端的UI自动化测试（X-001范围外）；具体测试用例明细（属RGS-TST-001） |

# 5. 功能需求

## 5.1 协议层模拟客户端（S-008具体化）

| ID | 需求 |
|---|---|
| FR-TST-001 | 模拟客户端**必须**实现IF-001全部消息类型的编解码，**复用**RGS-BAS-008§3核心SDK（`rgs-client-core`）而非独立重新实现协议逻辑——这是ARC-024"核心逻辑单一实现"原则在测试基础设施上的直接复用，避免测试替身与真实客户端行为脱节（"测的不是真实协议实现"这一失效模式由此从架构上排除） |
| FR-TST-002 | 模拟客户端**必须**支持批量并发实例化（单进程模拟数千至数万并发连接），资源占用**必须**可预测（每实例内存/CPU上限可估算，供负载试验的施压端自身容量规划） |
| FR-TST-003 | 模拟客户端的行为**必须**可配置化（移动模式、输入频率、掉线/重连概率），以覆盖NFR-PE-*系列指标要求的多种流量特征，而非仅测试单一理想路径 |
| FR-TST-004 | 模拟客户端**必须**输出可观测性数据（复用RGS-BAS-004埋点规范），使负载试验期间施压端自身的健康状态与被测系统的表现可以区分（避免"性能瓶颈在压测工具本身"这一常见误判） |

## 5.2 外部依赖Mock

| ID | 需求 |
|---|---|
| FR-TST-010 | 外部依赖Mock**必须**至少覆盖IF-006（支付渠道），实现其接口的成功/失败/超时/签名校验失败等多种响应模式，供TL-2/TL-3/VF-006（Saga部分失败与补偿）测试使用 |
| FR-TST-011 | 外部依赖Mock**必须**作为独立的、可在CI流水线中启停的服务提供（复用RGS-BAS-002§4.2既有CI/CD骨架），**不得**要求测试环境访问真实外部服务 |
| FR-TST-012 | 新挂载的限界上下文（RGS-REQ-006 ARC-018）若依赖外部系统，**应当**同步提供对应的Mock，纳入其挂载检查清单（RGS-BAS-002§12.1）的建议项 |

## 5.3 性能测试（k6）

| ID | 需求 |
|---|---|
| FR-TST-020 | k6**必须**承载TL-6负载试验中**HTTP/gRPC层**的负载生成：API网关（IF-002）、运营API（IF-007）的请求速率、延迟分布、错误率测量 |
| FR-TST-021 | 协议层（IF-001 QUIC）的负载生成**必须**由§5.1协议层模拟客户端承载，**不得**试图用k6模拟自定义QUIC游戏协议（k6原生协议支持不含此类场景，勉强适配会产生与真实协议行为偏离的测试替身，重演P-TST-001同类问题） |
| FR-TST-022 | k6测试脚本**必须**产出与RGS-BAS-004§3既定指标命名规范兼容的性能数据，使负载试验结果可直接接入既有可观测性Dashboard，不需要额外的数据转换 |
| FR-TST-023 | 负载试验场景（并发数梯度、持续时间、流量模式）**必须**版本化管理（纳入代码仓库），使PH-4与PH-8两次负载试验（AC-005）使用可比的测试条件 |

## 5.4 UAT自动化（Playwright）

| ID | 需求 |
|---|---|
| FR-TST-030 | Playwright**必须**承载运营API（IF-007，HTTP传输路径）的端到端契约验证：通过驱动§5.5参考GM后台的UI操作，验证从"UI操作"到"`AdminService`方法调用"到"审计记录产生"的完整链路 |
| FR-TST-031 | Playwright**应当**同时提供**纯API模式**（不经UI，直接对HTTP接口发起请求断言）的测试能力，覆盖不便于/不需要通过UI驱动的场景（如批量数据准备），二者共用同一套断言库避免重复维护 |
| FR-TST-032 | Playwright测试**不得**用于测试游戏客户端本体（X-001范围外），也**不得**被误用为游戏客户端的替代实现——本条是边界重申，防止范围蔓延 |

## 5.5 参考GM后台

| ID | 需求 |
|---|---|
| FR-TST-040 | 参考GM后台**必须**覆盖`AdminService`（RGS-BAS-003§3）全部方法各至少一个操作入口，**不要求**生产级的UX设计（无需响应式布局、无障碍支持等生产交付标准） |
| FR-TST-041 | 参考GM后台**必须**明确标注"仅供测试与API契约验证使用，非生产交付物"，避免被误用为实际运营界面（同X-006既有排除范围的重申） |

# 7. 架构设计方针 ARC-028

本节为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接RGS-REQ-014新增的ARC-027。**决定事项**，变更须经ADR与审批。

## 7.1 ARC-028：测试基础设施的分层工具选型与Mock边界（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | 测试基础设施按被测层级分工，**不得**用单一工具覆盖全部层级：①**协议层**（IF-001 QUIC自定义游戏协议）由复用核心SDK的自研模拟客户端承载②**HTTP/gRPC层**（API网关、运营API）由**k6**承载负载生成，由**Playwright**承载UAT自动化③外部依赖由专属Mock服务承载，**不得**要求测试环境访问真实外部系统 |
| **理由** | 协议层是本系统的自定义高频路径（ARC-003/004），通用HTTP压测工具无法正确表达其量化/位打包语义与双路径（Datagram/Stream）特性，勉强适配的测试替身会产生"测试通过但真实协议行为不同"的虚假保证；而HTTP/gRPC层是标准协议，用成熟通用工具（k6、Playwright）复用社区生态、避免自研重复建设（同ARC-014"默认替代方案优先"精神） |
| **模拟客户端必须复用核心SDK** | 复用ARC-024既有决定"核心逻辑单一实现"——模拟客户端若独立实现协议逻辑，会成为该原则此前未曾预见的"第四处协议实现"，重蹈RGS-REQ-012 P-SDK-001已识别的行为漂移风险。因此模拟客户端**不是**独立组件，而是核心SDK的又一适配层（测试专属适配层） |
| **k6/Playwright的技术栈例外说明** | k6（Go）与Playwright（TypeScript/Python均可）均非Rust，需明确其**不违反**CON-003——CON-003约束的是"自研业务服务"，k6/Playwright是**成熟的开源测试工具本体**（同CON-003既有"JVM／Go组件仅限于成熟中间件本体"表述的同类精神，测试工具与中间件本体在"不需要自研、只需配置使用"这一性质上等价），测试脚本本身（配置/断言逻辑）不构成"业务服务"。这与RGS-REQ-014智能层需要CON-003正式例外的情况**不同**——智能层是自研分析逻辑运行于新语言，本条是使用现成工具，两者不应混淆 |
| **否决方案1** | "用k6硬编码模拟QUIC游戏协议"——k6缺乏对自定义UDP/QUIC协议扩展语义（Datagram不可靠通道、量化位打包）的原生支持，勉强实现的插件会成为脱离核心SDK的第二套协议实现，已否决 |
| **否决方案2** | "UAT测试直接针对真实游戏客户端做UI自动化"——直接违反X-001既定范围边界（客户端本体不属本系统），且真实客户端由外部团队按其自有技术栈实现，本系统无法承诺对其UI自动化的可维护性，已否决 |
| **适用范围** | 全部测试基础设施的工具选型。具体测试用例内容不受本条约束，属RGS-TST-001范畴 |
