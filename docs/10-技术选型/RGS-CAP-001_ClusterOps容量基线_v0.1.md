## §1 容量基线

### 1.1 三档容量档位

| 档位 | 单副本承载 | 双副本合计 | 触发条件 | 应对动作 |
|---|---|---|---|---|
| **正常（Nominal）** | 35-50k DAU / 3.5-5k QPS | 70-100k DAU / 7-10k QPS | 日常运营 | 2 副本均摊流量，HPA min replicas = 2 |
| **设计上限（Design Limit）** | **50-70k DAU / 5-7k QPS** | 100-140k DAU / 10-14k QPS | 峰值期 / 营销活动 | 触发 HPA max replicas 扩容（per match manifest max=12）或入口限流 |
| **瞬时上限（Burst Limit）** | 100k DAU / 10k QPS | N/A（单副本独立扛全量）| 另一副本故障切换期间，**最长 30s 不可用窗口** | 另一副本按 §1.3 故障切换缓冲硬扛 |

### 1.2 三档口径定义

- **总容量（Total Capacity）**：系统可服务的最大用户/请求量。per NFR-OP-010 = **100k DAU / 10k QPS**。双副本共享，不是各自承担。
- **单副本设计容量（Per-Replica Design Capacity）**：双副本各自正常承担的设计上限，**留 30% 故障切换缓冲**。**50-70k DAU / 5-7k QPS**。
- **单副本瞬时上限（Per-Replica Burst Limit）**：单副本故障时，另一副本临时扛全量的硬上限。**100k DAU / 10k QPS**（与总容量相等，但属不可持续状态）。
- **故障切换缓冲（Failover Headroom）**：正常运行时预留的"留给故障切换"的余量比例。**30%**。

### 1.3 故障切换缓冲机制

```
正常运行时：
  副本 A ─┐
          ├─ 各承担总容量 50%，即 50k DAU / 5k QPS
  副本 B ─┘

单副本故障时（最坏情况）：
  副本 A 离线（30s 内不可用）
  副本 B 独立扛全量 100k DAU / 10k QPS
  ↑ 这是为什么单副本设计容量必须留 30% 缓冲（50k + 30k 缓冲 = 80k 仍 < 100k 硬扛）
     工程上放宽到 50-70k 是为覆盖 QPS 抖动 ±20% + 临时硬扛 30s 的累计影响
```

**为什么是 30% 不是 50%**：
- 50% 缓冲 = 单副本设计容量 = 25k，过于保守（双副本 50k 总容量，浪费 50%）
- 30% 缓冲 = 单副本设计容量 = 35k（理论值），工程放宽到 50-70k 覆盖 QPS 抖动
- 30s 故障切换窗口内，单副本可临时扛全量 100k（30% 缓冲 + QPS 抖动 20% 都在容忍范围）
- 30s 后仍未恢复 → 触发 §1.4 降级或人工介入

### 1.4 降级路径（与 ADR-0052 v0.2 §5.2.4 联动）

| 持续时间 | 状态 | 应对 |
|---|---|---|
| 0-30s | 故障切换中 | 单副本硬扛全量（瞬时上限 100k/10k）|
| 30-120s | 持续故障 | 触发告警，运维介入；启动 HPA 扩容至 3 副本 |
| 120s-5min | 仍故障 | 触发降级：PFAU 升级流程进入 Paused（per ADR-0052 §2.1）|
| > 5min | 严重故障 | 人工兜底，触发 RGS-INC-NNN 事件，**走 DEC-019 RTO 分级 15min 路径** |

## §2 容量公式

### 2.1 主公式

```
单副本设计容量 = 总容量 × 缓冲系数 / 副本数
              = 总容量 × (1 - 故障切换缓冲) / 副本数
              = 100k × (1 - 0.3) / 2
              = 100k × 0.7 / 2
              = 35k DAU（理论值）
```

### 2.2 缓冲系数

| 缓冲比例 | 缓冲系数 | 单副本设计容量（理论值）| 工程余量（Q-D-06 答复）| 评估 |
|---|---|---|---|---|
| 0% | 1.0 | 50k DAU | 50k DAU | ❌ 无故障切换缓冲，不可用 |
| 20% | 0.8 | 40k DAU | 50-60k DAU | ⚠️ 缓冲不足，故障时硬扛困难 |
| **30%** | **0.7** | **35k DAU** | **50-70k DAU（per Q-D-06）** | **✅ 推荐**（Q-D-06 答复） |
| 50% | 0.5 | 25k DAU | 30-40k DAU | ⚠️ 过于保守，浪费 50% 容量 |

### 2.3 算例（Q-D-06 答复口径）

#### 算例 1：理论值

```
总容量 = 100k DAU
副本数 = 2
故障切换缓冲 = 30%
缓冲系数 = 1 - 0.3 = 0.7
单副本设计容量 = 100k × 0.7 / 2 = 35k DAU
单副本瞬时上限 = 100k DAU（故障切换期间硬扛全量）
```

**问题**：35k 理论值未考虑 QPS 抖动 ±20%，故障切换时 100k × 0.5 + 30% 缓冲 = 65k 实际负载可能超过 35k 设计容量。

#### 算例 2：工程值（Q-D-06 答复）

```
工程上放宽到 50-70k DAU / 5-7k QPS，覆盖：
  - QPS 抖动 ±20%（per ADR-0051 §3 / RGS-TS-001 v0.7 §3 容量抖动分析）
  - 故障切换 30s 窗口内累计影响
  - CRDT 同步 + 分布式锁获取的瞬时延迟
```

**结论**：50-70k DAU / 5-7k QPS = **工程值**（Q-D-06 答复），35k = **理论值**（仅供公式理解，不作为容量承诺）。

#### 算例 3：最坏情况边界验证

```
场景：副本 A 离线，副本 B 独立扛全量 30s
  瞬时负载 = 100k DAU（与总容量相等）
  设计容量 = 50-70k DAU（Q-D-06 答复）
  超载比例 = 100k / 50k = 2.0x（最小）/ 100k / 70k = 1.43x（最大）

评估：
  - 30s 内超载 1.43-2.0x 是可接受的（per match manifest 流量限流 + 入口削峰）
  - 30s 内不可用窗口是 §1.4 降级路径的"第 0 阶段"
  - 若副本 A 持续不可用 → 触发 HPA 扩容（per §1.4 持续 30-120s）
```

### 2.4 QPS / DAU 换算

- NFR-OP-010 假设 DAU/QPS 比 = 100k / 10k = **10:1**（每用户 0.1 QPS）
- 单副本设计容量按同比例换算：50-70k DAU / 5-7k QPS
- QPS 是峰值期数据，DAU 是日活累计，二者不能直接相加，但容量规划按相同缓冲比例处理

## §3 边界条件

### 3.1 单副本临时扛全量

| 维度 | 数值 | 依据 |
|---|---|---|
| 单副本瞬时上限 | 100k DAU / 10k QPS | 等于总容量 |
| 不可用窗口 | 30s（最长）| ADR-0052 v0.2 §5.2.4 fallback RTO 目标 |
| 超载比例 | 1.43-2.0x | 算例 3 |
| 限流策略 | 入口削峰 30% | match manifest `rateLimit` 字段（参考） |
| 持续超载应对 | 30-120s 触发告警 + HPA 扩容 | §1.4 降级路径 |

### 3.2 HPA 配置（per match manifest，参考）

| 配置项 | 数值 | 说明 |
|---|---|---|
| `minReplicas` | 2 | 双副本基线（per ADR-0052 §2.3）|
| `maxReplicas` | 12 | per match manifest，PH-1 阶段上限 |
| `targetCPUUtilizationPercentage` | 70% | 与 30% 故障切换缓冲对齐 |
| `targetMemoryUtilizationPercentage` | 80% | 内存利用率阈值 |
| 扩容触发条件 | CPU > 70% 持续 60s | 标准 HPA 行为 |
| 缩容冷却 | 300s | 避免抖动 |

**注**：HPA max replicas = 12 来自 match manifest 当前配置，PH-1 完成后需实测验证；如不足，扩展上限至 20（per RGS-TS-001 v0.7 §3 容量抖动分析的"理论可扩展性"上限）。

### 3.3 NATS JetStream / Redis 容量

- **NATS JetStream KV**（leader lease + CRDT 同步）：单 leader 写吞吐约 10k QPS（per NATS 官方基准），双副本场景足够（远低于业务 QPS 5-7k）。
- **Redis Redlock**（分布式锁）：单实例约 50k QPS（per Redis 官方基准），双副本场景需主从部署（避免单点）。
- **CRDT 同步流量**：估算约 1k QPS（每副本 100 状态变更/s × 10 副本订阅），远低于 NATS 容量上限。

### 3.4 不适用场景

本容量基线**不适用**于以下场景（需独立评估）：

1. **跨 AZ 部署**：本基线假设单 AZ 双副本；跨 AZ 需增加 AZ 间网络延迟系数（per RGS-TS-001 v0.7 §3 待办）。
2. **跨区域部署**：本基线假设单区域；跨区域需独立评估（per ADR-0050 多区域部署 ADR，PH-2 范围）。
3. **5 域业务面**：本基线仅适用 ClusterOps 控制面；5 域业务面按各自 DTL §5 容量基线（per REV-011 §1 项 1）。
4. **CRDT 状态爆炸**：本基线假设 CRDT 状态量 < 1GB/副本；若超过需独立评估（per PH-2 实测）。

## §4 容量测试方法

### 4.1 工具选型

| 工具 | 用途 | 选型理由 | PH-1 优先级 |
|---|---|---|---|
| **k6** | HTTP/gRPC 负载生成 | 云原生友好，支持 JS 脚本，CI 集成简单 | P0（主用）|
| **vegeta** | HTTP 恒定 QPS 压测 | 简单直接，适合基线测试 | P1（备用）|
| **wrk** | HTTP 高并发压测 | C 实现，资源占用低 | P2（兜底）|
| ghz | gRPC 专项压测 | gRPC 协议原生支持 | P0（如用 gRPC）|

### 4.2 测试目标（per Q-D-06 答复 + §1.1 三档档位）

| 测试场景 | 目标 QPS | 目标 DAU 等价 | 持续时间 | 通过条件 |
|---|---|---|---|---|
| **场景 1：正常档位** | 3.5-5k QPS / 副本 | 35-50k DAU / 副本 | 10min | p99 < 100ms, error rate < 0.1% |
| **场景 2：设计上限** | **5-7k QPS / 副本** | **50-70k DAU / 副本** | 10min | p99 < 200ms, error rate < 0.5% |
| **场景 3：瞬时上限** | 10k QPS / 单副本 | 100k DAU / 单副本 | **30s** | 不崩溃，error rate < 5% |
| **场景 4：双副本独立** | 5k QPS × 2 副本 | 100k DAU 总量 | 30min | 无脑裂，无 CRDT 分歧 |
| **场景 5：leader 切换** | 5k QPS + 副本 A 强制 kill | 同上 | 5min | 切换 RTO < 30s, 无数据丢失 |

### 4.3 测试方法

1. **基线测试**（场景 1-3）：单副本压测，验证单副本设计容量 50-70k DAU / 5-7k QPS 真实可承担。
2. **双副本测试**（场景 4）：双副本同时压测，验证总容量 100k DAU / 10k QPS 真实可承担，CRDT 状态收敛正常。
3. **故障注入测试**（场景 5）：per ADR-0052 §4 测试验证要求，注入"副本 A 强制 kill"故障，验证 §5.2 仲裁机制（leader 切换 / fencing token / CRDT 收敛 / fallback）。
4. **长期稳定性测试**（场景 4 延长）：72h 持续压测，验证内存泄漏 / 连接泄漏 / CRDT 状态膨胀。

### 4.4 报告时点

- **PH-1 编码完成 + RGS-IMPL-053.12 OTel 启用后**（per Q-D-10 答复合并思路）：执行场景 1-3 基线测试。
- **PH-1 集成测试阶段**：执行场景 4-5 故障注入测试。
- **PH-2 上线前**：执行场景 4 长期稳定性测试（72h）。
- **报告归档位置**：`docs/14-测试报告/RGS-CAP-001_容量测试报告_v0.1.md`（待 PH-1 完成后新建）。

- **季度回顾**：每季度由架构师 + 5 域 Lead 复审实际负载 vs 容量基线，必要时调整 §1.1 三档档位。

- **新容量基线升版条件**：实际负载超出设计上限持续 7 天 / 月度负载增长 > 20% / 新增跨域流量。

## §5 与 NFR-OP-010 的关系

### 5.1 NFR-OP-010 假设的口径

NFR-OP-010 假设：
- **DAU 100k / QPS 10k**（单集群、单 AZ）
- 适用于 5 域全开 + 跨域 Saga + all-reachable PFAU 完整生产环境

**本文件澄清**：NFR-OP-010 假设的是 **总容量（系统级）**，不是单 Pod / 单副本容量。

### 5.2 容量口径的层级关系

```
NFR-OP-010（系统级 NFR）
  └─ 总容量：100k DAU / 10k QPS
       └─ RGS-ADR-0052 v0.2 §3.x（架构级 ADR，实例化 NFR）
            └─ 单副本设计容量：50-70k DAU / 5-7k QPS
                 └─ 本文件 RGS-CAP-001 v0.1（容量基线文档，工程级实例化）
                      └─ 三档档位：正常 / 设计上限 / 瞬时上限
                           └─ 5 域 DTL §5 容量基线（域级 DTL，再实例化，per REV-011 §1 项 1）
                                └─ 各域容量分摊（per 域 DTL §5）
```

### 5.3 NFR-OP-010 不修改

- NFR-OP-010 是 **需求层**，不修改
- ADR-0052 v0.2 §3.x + 本文件 RGS-CAP-001 v0.1 是 NFR-OP-010 的 **架构级 + 工程级实例化**
- 单副本 50-70k DAU 是 **工程实例化**（留 30% 故障切换缓冲）
- NFR-OP-010 文本不动；本文件 + ADR-0052 v0.2 在架构 / 工程层补"双副本共享"语义 + 容量公式 + 三档档位。

| 故障切换缓冲 | Failover Headroom | 正常运行时预留的"留给故障切换"的余量比例 |
| 缓冲系数 | Headroom Factor | 1 - 故障切换缓冲 = 0.7 |
| 多主并发 | Multi-Leader | Active-Active 拓扑下双副本各自处理写请求的模式 |
| Leader Lease | Leader Lease | 多主并发下确定"主副本"的租约机制（10s TTL）|
| 分布式锁 | Distributed Lock | 写操作互斥锁（5s lease，per-feature 粒度）|
| CRDT | Conflict-free Replicated Data Type | 无冲突可复制数据类型，状态最终一致 |
| Fallback | Fallback to Single-Leader | 多主不可恢复时降级到单主的机制 |
| Fencing Token | Fencing Token | 单调递增的写入凭证，防止脑裂 |
| HPA | Horizontal Pod Autoscaler | Kubernetes 水平 Pod 自动扩缩 |
