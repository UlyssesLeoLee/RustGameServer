# D5 — Engineering & Delivery（工程交付层）

> **5D Atlas v9.0 · D5/5**
> **目的**: 把 D1-D4 的设计变成**可部署、可监控、可演化、可回滚**的工程产品。
> **失败模式**: 工程层用"先上线再说"完成 —— 没有任何监控与回滚手段,事故后只能靠猜。

## 1. 技术栈选型 (Tech Stack)

### 1.1 选型 ADR 模板

```markdown
# ADR-NNN — <决策>

## 状态
提议 / 通过 / 弃用 / 取代 ADR-NNN

## 上下文
- 想解决: ___
- 约束: ___

## 选项
### 选项 A — ___
- 优势: ___
- 代价: ___

### 选项 B — ___
- 优势: ___
- 代价: ___

## 决策
选 ___ , 因为: ___

## 后果
- 正面: ___
- 负面: ___

## 撤销条件
当 ___ 发生时重审
```

**判据**: 每技术决策都有 ADR;拒绝"老大说用 X 就行"。

### 1.2 选型维度

| 维度 | 必须答 |
|---|---|
| 成熟度 | 维护活跃? LTS? |
| 团队能力 | ≥1 人能 hold |
| 性能 | 是否命中 D5.2 预算 |
| 安全 | CVE 历史 |
| 生态 | 社区 / 文档 / 插件 |
| 成本 | 一次性 / 持续 / 隐性 |

## 2. 性能预算 (Performance Budget)

```markdown
## CWV (Core Web Vitals) 预算
- LCP ≤ 2.5s (75th)
- INP ≤ 200ms (75th)
- CLS ≤ 0.1 (75th)

## 资源预算
- 主页 JS ≤ 200 KB gzip
- 首屏图片 ≤ 150 KB
- CSS ≤ 50 KB gzip
- 字体子集化 ≤ 30 KB per family

## API 预算
- P50 ≤ 200ms
- P95 ≤ 800ms
- P99 ≤ 2000ms
```

**判据**: 预算写入 CI, 任意超 → 阻断合并 (per §5)。

## 3. 可观测性 (Observability)

### 3.1 三支柱

| 支柱 | 用什么 |
|---|---|
| 日志 (Log) | 结构化 (JSON) + trace_id |
| 指标 (Metric) | RED (Rate/Error/Duration) + USE (Utilization/Saturation/Errors) |
| 链路 (Trace) | OpenTelemetry / 厂商方案 |

### 3.2 必须的事件

```markdown
## 用户旅程事件 (per D3 §1)
- enter_<journey>
- step_<journey>_<n>
- complete_<journey>
- error_<journey>_<code>
- abandon_<journey> (heartbeat)

## 系统事件
- boot / ready / shutdown
- config_reload / cert_rotate
- deploy_start / deploy_done
```

### 3.3 告警分级

| 级别 | 含义 | 响应 | Runbook |
|---|---|---|---|
| P0 | 大盘不可用 | 立即值班 | `runbooks/p0-<service>-down.md` |
| P1 | 部分功能挂 | 4h | `runbooks/p1-<symptom>.md` |
| P2 | 体验降级 | 24h | `runbooks/p2-<symptom>.md` |
| P3 | 提示 / 信息 | 周内 | 无 (仅工单) |

**判据**: P0/P1 告警**必须**有 runbook 链接 (per `checklists/D5-checklist.md` §D);
无 runbook 的告警不得升为 P0/P1, 否则值班到现场仍不知怎么修。

### 3.4 ADR 索引

ADR 决策本身写在 `templates/D5-adr.template.md` 生成的独立 ADR 文件中, 但必须有一张总索引:

```markdown
## ADR 索引
| # | 标题 | 状态 | 日期 | 取代 |
|---|---|---|---|---|
| 001 | 选择 X 而非 Y | 通过 | YYYY-MM-DD | — |
| 002 | ___ | 弃用 | YYYY-MM-DD | ADR-001 |
```

**判据**: 索引表必须随代码库维护 (per `checklists/D5-checklist.md` §A);
"弃用" / "取代" 行必须写明被取代的 ADR 编号, 保证决策链可追。

```markdown
## 自动化

- 上线前 5 用户 (含 1 屏读 + 1 色盲 + 1 仅键盘)

## CI 阻断
- 自动 a11y 检查 any fail → 不合并
```

**判据**: a11y 是 CI 卡点,而非"上线前靠人回忆"。

## 5. 测试金字塔 (Testing Pyramid)

```markdown
## 比例 (推荐)
- E2E: 10%
- 集成: 30%
- 单元: 60%

## 必测
- 单元: 状态机转移 (per D3.3) + 纯函数
- 集成: API 契约 + 错误兜底
- E2E: 关键旅程 (D3.1) ≤ 7 条

## 不必测
- 第三方库内部逻辑
- 静态文案
- 已被 e2e 覆盖的 happy path
```

### 5.1 测试配额

```markdown
- 代码变更行 ≤ 500 行 → 必须随 commit 提交测试
- 任何修复 bug → 必须先写复现测试
- 测试名必须描述"做什么",而非"用了什么"
```

## 6. 发布策略 (Release Strategy)

### 6.1 四种发布

| 策略 | 适用 | 回滚 |
|---|---|---|
| 滚动 | 无状态服务 | 自动 |
| 蓝绿 | 数据库迁移类 | 一键切换 |
| 灰度 | 强风险变更 | 渐进放量 |
| Feature Flag | 实验 / 试错 | 旗标回退 |

### 6.2 数据库迁移

```markdown
## 7 条铁律
1. 迁移是后向兼容
2. 大表加字段分批
3. 删除前先孤立 (rename + 观察)
4. 必须有 down 迁移
5. 迁移慢于阈值走异步
6. 迁移与代码可独立回滚
7. 迁移日志必须留
```

### 6.3 回滚预案

```markdown
## 必做
- 每发布都有回滚命令 (`scripts/rollback.sh`)
- 回滚演练每季度一次
- 数据迁移可"前进 / 后退"双向
```

## 7. 安全与凭据 (Security)

```markdown
## 凭据
- 严禁打印 / 入仓 / 日志
- 走环境变量 / 密钥管理 (Vault / SSM)
- 轮换计划: 90 天

## 输入
- 一切外部输入视为不可信
- 白名单校验 (类型 / 长度 / 值域)
- 输出编码 (HTML / SQL / OS)

## 依赖
- 锁版本 + 定期审计 (cargo audit / npm audit)
- SBOM 入库

## 网络
- mTLS 业务级 (per D4 边界)
- 拒绝明文
```

**判据**: 凭据永远不打印,**走 stdin pipe** 形式 (per本仓库 8/27 11:06 JST hard ban)。

### 8.1 API 兼容

- [ ] 任何破坏性变更走 vN → vN+1
- [ ] 旧版有弃用期 (≥ 6 个月)
- [ ] API 文档同步变更

### 8.2 数据迁移

参见 §6.2。

### 8.3 模块边界

```markdown
## 域 (Domain) 划分
- 域 = 一组业务 + 自己的数据 + 自己暴露的 API
- 跨域调用走契约 (gRPC / OpenAPI)
- 域内独立升级, 接口稳定
```
