# D1 — Concept & Strategy（战略层）

> **5D Atlas v9.0 · D1/5**
> **目的**: 在写代码或画线框之前,把"为什么、给谁、怎样算成功"钉死。
> **失败模式**: 战略层缺位会使 D2-D5 全部失焦,后续决策无对齐基准。

---

## 0. 本层回答的核心问题

| # | 问题 | 不回答的后果 |
|---|---|---|
| Q1 | **为什么做这件事**(价值主张/反事实) | D2 决定不了方向,D4 排不了优先级 |
| Q2 | **给谁做**(用户画像/场景切分) | D3 想错对象,D5 性能预算定错口径 |
| Q3 | **不算成功的标准**(北极星 + 反指标) | 上线后无法判断是否拆掉重做 |
| Q4 | **范围与边界**(in/out/next) | 全栈都做,哪层都没做透 |
| Q5 | **依赖与约束**(监管/既有资产/不可动摇项) | 工程层出现"不可能合规"才发现 |
| Q6 | **风险与反向假设**(如何证伪) | 失败归因没有抓手 |

## 1. 价值主张画布 (Value Proposition Canvas)

两栏必须**成对**填写 ——"做给谁"与"解决什么"必须互相印证。

### 1.1 客户侧 (Customer Side)

```markdown
## 客户任务 / Jobs
- 功能性任务: 用户想要完成 ___
- 社会性任务: 用户希望看起来 ___
- 情感性任务: 用户希望感受到 ___

## 痛点 / Pains
- 痛点 1: ___ (严重度 1-5: ___)
- 痛点 2: ___
- 痛点 3: ___

## 收获 / Gains
- 必需收获: ___
- 期望收获: ___
- 意外收获: ___
```

### 1.2 产品侧 (Product Side)

```markdown
## 产品 / 服务
- 提供物 1: ___
- 提供物 2: ___

## 痛点解药 / Pain Relievers
- 解决痛点 1: ___
- 解决痛点 2: ___

## 收获创造 / Gain Creators
- 创造收获 1: ___
- 创造收获 2: ___
```

### 1.3 自检

- [ ] 价值主张是否**只用一句**能讲清(电梯测试)?
- [ ] 用户是否**今天**就能指出"现在用什么替代"?
- [ ] 若明天撤掉,谁**立刻**感到不便?(替代弹性)
- [ ] 有没有任何角色**明确**反对?(反对者签名)

## 2. 用户画像切片 (Persona Slices)

不要写"用户"。**至少 3 个切片**,含 1 个**非目标**。

```markdown
## Persona A — 赶时间的妈妈
- 身份: ___ / 设备: ___ / 时段: ___
- 任务: ___
- 痛点: ___
- 容忍度: 可接受卡顿 ___ 秒; 不可接受 ___
- 关键场景剧本: ___

## Persona B — ___
... (同上结构)

## Persona C — 反转 (非目标用户, 写明是为了防止范围蔓延)
```

**反例**: 用户画像 = "20-35 岁, 喜欢玩游戏" → 没切,等于没写。

## 3. 北极星 + 反指标 (NSM + Anti-Metric)

```markdown
## 北极星指标 (NSM)
- 名称: ___
- 定义: ___
- 计数口径: ___
- 统计周期: 周/月
- 当前基线: ___
- 90 天目标: ___

## 反指标 (NSM 失衡时必爆的 1-3 个)
- 反指标 1: ___ (≤ ___ 时 NSM 才是真信号)
- 反指标 2: ___
- 反指标 3: ___
```

**判据**: NSM 必须能**复合**, 不能纯计数(会被刷量作弊)。

---

## 4. 范围围栏 (Scope Fence)

```markdown
## In-Scope (本期必交付)
1. ___
2. ___
3. ___

## Out-of-Scope (本期明确不做)
1. ___ (理由: ___)
2. ___

## Next-Scope (预留 hook, 本期不实装)
1. ___
2. ___
```

**判据**: 任何"想加就加"的项 → out-of-scope; 任何"必须留接口"的项 → 必须有 hook 名。

---

## 5. 硬约束 (Hard Constraints)

| 类别 | 内容 | 不可动摇 |
|---|---|---|
| 法规 / 合规 | ___ | ☐ |
| 既有资产 / 平台 | ___ | ☐ |
| 上游协议 / 契约 | ___ | ☐ |
| 不可逆决策 | ___ | ☐ |
| 资源上限 | 预算 / 人 / 时 | ☐ |

**判据**: 标 ☐ 项必须引用 **git 实证 / 官方文档 / 合同条款** 之一。
缺证据的"硬约束"是伪约束,会让团队走弯路。

---

## 6. 反向假设 (Reversal Hypotheses)

每个核心假设问一句"**怎么证明它错了?**"

| 假设 | 证伪方式 | 验证成本 | 优先级 |
|---|---|---|---|
| 用户在意 X | 5 人访谈 / 落地页 A-B | 低 | P0 |
| 我们的方案比替代快 30% | 原型 + 计时对照 | 中 | P1 |
| 留存在 D30 ≥ 40% | 灰度 + 队列分析 | 高 | P2 |

**判据**: P0 假设必须在 D1 阶段被验证或证伪,不能拖到 D5 才"测一下"。

---

## 7. D1 出口判据 (Exit Criteria)

未通过即**禁止进入 D2**:

- [ ] 价值主张 1 句话讲清
- [ ] ≥3 个 persona 切片,**含 1 个非目标**
- [ ] 1 个 NSM + ≥3 个反指标
- [ ] In/Out/Next 三栏,每项带理由
- [ ] 硬约束清单每条有证据链接
- [ ] P0 假设列表 + 可执行的证伪方式
- [ ] ≥1 个真人反对者签字 (即使临时代签, 也走审计链)

---

## 8. 已知缺口 (Known Gaps)

> 缺标比错标安全 —— 拿不准显式列"已知缺口",不假装覆盖。

| 缺口 | 影响 | 补足方式 |
|---|---|---|
| 用户访谈样本 < 30 | persona 信度低 | D2 启动前补访 |
| NSM 缺基线 | 90 天目标无法验证 | 上线 2 周后回填 |
| 法规清单只列大类 | 落地需细化 | D5 前由法务/SRE 复审 |
| 反对者签字栏空白 | 出口判据未满足 | Mavis 临代签 + 真人到位追溯 |

## 9. 与其他维度的接口

| 输出物 | 给 D2 | 给 D3 | 给 D5 |
|---|---|---|---|
| 价值主张 | 信息架构主题句 | 关键任务流 | 文案 / 命名风格 |
| Persona | 信息密度 / 层级 | 关键路径 | 性能预算 / 设备分布 |
| 反指标 | 信息架构不要的项 | 反模式清单 | 监控告警 |
| 硬约束 | 不可绕过的导航规则 | 不可绕过的流程 | 不可绕过的工程决策 |
