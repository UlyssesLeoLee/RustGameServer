# 项目: ACP (Arcade Control Panel) — 假设示例

## 电梯版 (≤ 25 字)
> 让街机店主一块屏看完所有机台状态,30 秒内决断。

## 1. 客户侧

### Jobs
- **功能性**: 老板想在任意时间看到所有机台在线 / 故障 / 上分状态
- **社会性**: 老板希望在朋友面前"系统很专业"
- **情感性**: 老板希望"不用再怀疑哪个机台在偷钱"

### Pains
| # | 描述 | 严重度 |
|---|---|---|
| 1 | 巡场不知从哪台看起 | 5 |
| 2 | 发现故障机台时,要先扫码 / 走很近 | 4 |
| 3 | 每天关门前对账耗 1+ 小时 | 5 |

### Gains
- **必需**: 实时看到每台机台故障时间戳
- **期望**: 故障后 5 分钟内收到推送
- **意外**: 自动生成当日各机台营收对比

## 2. 产品侧

### 提供物
- 单屏 dashboard (横屏 PC / 平板)
- 移动端推送
- 每日对账报表

### Pain Relievers
- 解药 1: dashboard 网格按故障优先级排序 (解决痛点 1)
- 解药 2: 推送直达故障机台最近的员工手机 (解决痛点 2)
- 解药 3: 自动汇总每台机台上分/下分 (解决痛点 3)

### Gain Creators
- 实时故障时间戳 (必需收获)
- 推送预警 (期望收获)
- 营收对比 (意外收获)

## 3. Persona 切片

### A — 老板"常驻型"
- 身份: 35-50 岁, 自营 1-3 家街机店
- 设备: 平板 + 手机
- 时段: 全天,但下班后最频繁
- 任务: 远程巡店 / 处理故障
- 痛点: 客户投诉时定位信息慢
- 容忍度: 卡顿 ≤ 3s;不可接受"刷新不出来"

### B — 值班"维修工"
- 身份: 20-35 岁, 员工
- 设备: 手机
- 时段: 班次内
- 任务: 接收推送 → 现场处理
- 痛点: 不知道机台历史故障
- 容忍度: 推送延迟 ≤ 1 min

### C — **非目标** — 街机玩家
- 玩家不直接使用本产品
- 写明以防范围蔓延到"给玩家也开发 app"

## 4. 北极星 + 反指标

- **NSM**: 每周老板**主动查看** dashboard 的活跃天数 (DAU 周活跃天数)
- **90 天目标**: 70% 老板用户周活 ≥ 4 天
- 反指标 1: 推送投诉率 ≤ 5% (过高说明推送过量)
- 反指标 2: 数据延迟 P95 ≤ 60s (过高说明数据链路挂)
- 反指标 3: 误报率 ≤ 2% (过高说明检测规则抖)

## 5. 范围围栏

- In-scope:
  - 中控 dashboard
  - 移动端推送
  - 当日对账
- Out-of-scope:
  - 玩家侧 (留 hook "member_id" 以备未来)
  - 多店连锁管理 (留 hook "tenant_id")
  - AI 故障预测 (本期不做)
- Next-scope (hook):
  - 多店对比报表
  - 玩家偏好推荐 (对老板运营有用)
  - 凭据审计 (合规要求)

## 6. 硬约束

| # | 内容 | 不可动摇 | 证据 |
|---|---|---|---|
| 1 | 不收集玩家个人身份信息 (PII) | ☐ | 假设合规要求的虚构条款 |
| 2 | 移动端推送不依赖第三方推送厂商 | ☐ | (虚构)避免被单一厂商锁定 |
| 3 | dashboard 在 4G 网络下首屏 ≤ 3s | ☐ | 老板容忍度来自 persona A |
| 4 | 数据延迟 ≤ 60s | ☐ | 来自反指标 2 |

## 7. 反向假设

| # | 假设 | 证伪方式 | 优先级 |
|---|---|---|---|
| 1 | 老板愿意每天至少看一次 dashboard | 落地页 A-B + 5 人访谈 | P0 |
| 2 | 故障推送能减少到场维修的次数 | 灰度 + 维修日志对比 | P1 |
| 3 | 街机店都接受在店里长期挂一块屏 | (本期不做) | P2 |
