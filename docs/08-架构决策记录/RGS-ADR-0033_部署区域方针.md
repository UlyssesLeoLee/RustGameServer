## 1. 背景（Context）

TBD-007／ISS-007长期悬置：本系统采用单区域（Multi-AZ）还是多区域（Multi-Region）部署。该问题阻塞了容灾设计（RTO/RPO目标）、数据合规判断（数据驻留）、以及分片架构的地理维度设计，必须先有结论。

关键事实：多区域一旦被写入架构假设，其影响会渗透进数据模型（全局唯一ID、跨区一致性）、部署编排、以及几乎所有涉及延迟的设计；反过来，从单区域**演进**到多区域虽然代价高，但演进路径是清晰的。

## 2. 决定（Decision）

**单区域优先**：以单一区域内的Multi-AZ（多可用区）部署为基准架构，容灾目标按AZ级故障设定，不按区域级故障设定。

多区域**不被永久排除**，但被明确推迟：任何多区域需求须先经RGS-BAS-017§2.3的专项评审，届时另立ADR，不得在其他设计中预先埋入多区域假设。

## 3. 曾考虑并否决的方案（Alternatives Considered）

### 3.1 一开始就做多区域（Active-Active 或 Active-Standby）

区域级容灾能力最强，且能就近服务全球玩家。否决理由：①**成本**——多区域至少翻倍的基础设施与运维负荷，与ARC-026的OLU预算正面冲突；②**一致性代价**——跨区域的强一致不可得，玩家资产类数据（ADR-0007的单事务边界）要么牺牲一致性、要么牺牲延迟，两者对本项目都难以接受；③**当前无需求驱动**——尚无明确的多地域运营计划，为假想需求付出确定成本不符合ARC-014。

### 3.2 单区域单AZ（不做Multi-AZ）

成本最低。否决理由：单AZ故障是真实且并不罕见的事件，一次AZ故障即导致全服不可用且可能丢数据，这一风险等级不可接受。Multi-AZ的增量成本远小于其消除的风险。

### 3.3 保持TBD状态，等业务明确后再定

看似稳妥。否决理由：悬置本身有成本——它同时阻塞了容灾设计与分片设计，且在悬置期间各文档会各自做出不同的隐含假设（本项目已出现过此类分歧）。明确「单区域优先＋演进路径开放」比继续悬置更有价值。

## 4. 结果与代价（Consequences）

**获得**：容灾设计有了明确目标（AZ级），RGS-BAS-017可据此完成拓扑与故障切换设计；分片架构（ARC-040）不必承担地理维度的复杂性。

**付出**：区域级灾难（整个区域不可用）目前无预案，这是**明示接受的风险**，而非疏漏。数据驻留类合规要求若将来出现，须重新评估本决策。

**演进约束**：为保留演进可能，各设计不得引入「假定全系统在同一区域内低延迟可达」的强耦合假设；但也不得为多区域预留未经验证的抽象层（那属于为假想需求付成本）。这一平衡点的把握留给具体设计评审。
