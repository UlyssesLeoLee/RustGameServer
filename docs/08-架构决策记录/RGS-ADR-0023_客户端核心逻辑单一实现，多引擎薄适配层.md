## 1. 背景（Context）

X-001声明本系统交付「协议规范与参考SDK」，目标覆盖Bevy／Unity／UE三引擎。ADR-0002确定的预测/和解模型意味着客户端必须实现相当复杂的逻辑：输入缓冲、本地预测、快照回滚重放、AOI状态维护——这部分逻辑若三引擎各写一遍，三份实现的行为一致性无法保证，而预测/和解**恰恰要求**与服务器逐步一致。

## 2. 决定（Decision）

**核心SDK以Rust单一实现**（编解码、预测/和解、协议版本协商、资源更新校验），三引擎各自只提供**薄适配层**：Bevy直接以crate依赖接入，Unity（C#）与UE（C++）经**C ABI FFI边界**接入。

FFI边界须满足：panic不得跨边界传播（`catch_unwind`）、参数一律校验、内存所有权明确（RGS-DTL-008）。

## 3. 曾考虑并否决的方案（Alternatives Considered）

### 3.1 各引擎独立原生实现（C#写一份、C++写一份）

各引擎生态内最自然，无FFI负担。否决理由：预测/和解逻辑的三份独立实现必然产生行为分歧，而分歧在此处的表现形式是「某引擎的玩家更容易被判定为回滚」——一种极难定位、且直接影响公平性的缺陷。维护成本也是三倍。

### 3.2 以C++写核心、各引擎绑定

C++的引擎生态兼容性最好，UE可直接使用。否决理由：与CON-003（服务端Rust）分裂为两套语言与两套工具链，且协议编解码逻辑无法与服务端共享——而共享编解码正是协议一致性最有力的保证手段。

### 3.3 只提供协议规范文档，不提供SDK实现

交付面最小。否决理由：与X-001既有声明冲突；且预测/和解的实现细节若只靠文档传达，各接入方的实现分歧会以「服务端bug」的形式回流。

## 4. 结果与代价（Consequences）

**获得**：编解码与和解逻辑与服务端同源（同一套Rust代码/同一份协议定义），协议一致性由编译期保证而非文档约定。

**付出**：FFI边界是持续的安全负担——每个导出函数都要处理panic捕获、参数校验、内存归属，RGS-DTL-008为此专门给出可编译级函数原型规范；Unity/UE侧还需绑定生成工具链（TBD-SDK-001，提案cbindgen）。

**遗留风险（RSK-003）**：实时同步细节未定曾导致客户端开发无法启动；ADR-0002已确定路线，但预测缓冲参数仍待实测。
