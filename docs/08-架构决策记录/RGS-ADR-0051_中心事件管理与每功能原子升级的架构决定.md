> **本ADR的写作前提**：本项目此前50项ARC方针中，ARC-018／021／042／019四块已有方针已分别定义"挂载/插件/集群部署/GM后台"四类操作的局部流程，但**没有"以功能（Feature）为统一单元"的整体性决定**。2026-08-19负责人指示「原子化部署的中心事件管理和app集群，以及支持可热插拔的架构需要有专门的管理员可见的运维界面，便于每个功能都可以单独升级，当然，api设计和存储过程要完全适应协调这种架构」。本ADR属**确有取舍**一类：§3列出的替代方案均为真实可选、且选择它会实质改变架构的方案。

---

## 1. 背景（Context）

系统已演进到22+个域、ARC-021插件机制上线、ARC-042集群级部署编排落地，但**集群级操作面**仍存在三个具体缺陷：

1. **升级粒度混乱**：业务方提出"上线X功能"时，工程方需要逐项判定走ARC-018（重挂载）、ARC-021（轻热插拔）、既有App补丁、还是ARC-016配置变更。判定依赖个人经验，无工具辅助，无可视化呈现
2. **事件流不可观测**：现有事件机制是各App自治发布到事件总线，**没有中心注册表**。当事件类型超过百种后，管理员无法在一个统一视图中看到"哪些事件被谁生产、被谁消费、消费延迟多少、是否有死信、是否能重放"
3. **原子性不可视**：插件热插拔（ARC-021）与集群部署（ARC-042）虽各自保证"插件级/集群级"原子性，但**管理员无法在单一界面看到"一个功能从版本A升级到版本B，跨多少节点、跨多少依赖、何时全部生效、何时可回滚"**

RGS-REQ-031已定义ARC-051"集群运营中心（COC）+ 中心事件管理（CEM）+ 每功能原子升级（PFAU）"的统一面。本ADR将该决定落点化：明确"功能"为统一操作单元、CEM的边界、PFAU的原子性边界、API契约与DB侧约束。

## 2. 决定（Decision）

**采纳RGS-REQ-031 ARC-051的完整决定项**，关键点：

1. **统一操作单元 = 功能（Feature）**。Feature的四种形态——①限界上下文型（对应ARC-018）②插件型（对应ARC-021）③补丁型（本文档新增）④配置型（对应ARC-016）——全部走`feature_registry`表的统一元数据
2. **CEM = 集群级事件治理面**。含事件注册表、Schema目录、订阅关系图、消费者健康、死信、可重放历史六部分；通过在事件总线上挂"探针/订阅器"聚合，**不**强制各App改造Publisher SDK
3. **PFAU = "声明→灰度→确认→完成"四步状态机**。"原子"指"全集群目标节点对目标版本已生效达成一致确认"——**不**指"全部节点同时切换"（物理上不可能）
4. **COC UI = GM后台的新增顶级页面**。沿用既有RBAC与AdminService统一入口，**不**另开凭证体系，**不**单独开发前端（复用VIZ域的无限画布渲染能力）
5. **API契约 = 声明式+流式gRPC+`request_id`幂等键**。全部经AdminService转发，**不**让COC UI或第三方直接调用ClusterOpsService
6. **DB侧约束 = 仅Outbox分发、FF应用、版本快照三类协同职责**。**不**跨库、**不**持有长事务、**不**承担业务逻辑（沿用RGS-ADR-0022业务逻辑不入库）

**永久事实声明**：
- 管理员可见的集群运营控制台是本系统的**一等公民**——它的存在不是"可选的可视化增强"，而是"集群运营的可信源"（single source of truth），与ARC-017可观测性基础设施同等地位
- PFAU进行中实例的元数据**必须**持久化于`admin_db`（COC UI仅是视图层，UI自身可被回滚而不影响实例可见性）
- 事件总线**必须**为CEM提供`coc.event_registry_changed`事件（FR-API-010），CEM订阅此事件实时更新注册表，**不得**要求CEM轮询

## 3. 曾考虑并否决的方案（Alternatives Considered）

### 3.1 COC UI作为独立Web应用（不挂GM后台）

**否决理由**：①破坏ARC-019统一入口——COC UI需新开凭证、新开RBAC、新开K8s权限，与NFR-OPS-004冲突；②增加SSO复杂度——运营人员需要在两套系统间切换登录；③爆炸半径失控——COC UI若直接调用K8s API做部署，一次误操作可能影响整个集群。

**采纳路径**：COC UI作为GM后台的**新增顶级页面**（与"账号管控/服务器管控/告警"等并列），沿用既有RBAC（新增`cluster_operator`/`cluster_admin`两个角色），全部写操作经既有AdminService转发。

### 3.2 PFAU自动重试失败节点（无须人工介入）

**否决理由**：①一次失败的升级可能是版本本身的问题，自动重试只会让更多节点进入不一致状态；②自动重试无法区分"网络抖动"（重试可恢复）与"版本不兼容"（重试不可恢复），强制重试可能放大故障；③违反"可追溯的运维"原则——一次无人介入的自动重试无法解释为什么在某个时间点决策重试。

**采纳路径**：任一节点确认失败时，PFAU暂停，由COC UI提供"重试/跳过/回滚"三选一人工操作。**仅**当节点失联（K8s Pod异常退出/节点失联）时自动回滚（FR-PFAU-022），此场景的故障原因可由基础设施层的事件明确解释，与"版本不兼容"场景的故障原因不同。

### 3.3 CEM在每个App的DB中建独立Schema目录表

**否决理由**：①破坏ARC-008独立DB原则——22+个App的DB中各有"事件Schema目录"会增加跨库同步成本；②事件Schema是**集群级**概念，不应被某个App的DB边界切割；③增加新App挂载成本——新App必须先建自己的"事件Schema目录表"才能接入CEM。

**采纳路径**：Schema目录统一存于既有`admin_db`（同ARC-008同库原则），新增`event_schema_registry`表与`event_producer_registry`表，**不**新建独立DB。**不**要求各App改造Publisher SDK——CEM在事件总线上挂"探针/订阅器"聚合即可。

### 3.4 让COC UI直接调用Helm做部署（绕过AdminService）

**否决理由**：①破坏ARC-019"AdminService统一入口"——COC UI将持有K8s凭证，违反NFR-OPS-004；②爆炸半径不可控——COC UI的一次误操作（如错误的namespace、错误的副本数）可能影响整个集群；③脱离既有审计通路（`operation_audit`表）——绕过AdminService的写操作无法被既有审计通路捕获。

**采纳路径**：COC UI的全部写操作经既有`AdminService`（沿用ARC-019），`AdminService`在内部转发至`ClusterOpsService`（COC UI的gRPC后端），`ClusterOpsService`再调用既有GitOps/Helm Release流程（同ARC-042）。**全程不**让COC UI直接接触K8s API。

### 3.5 PFAU的"补丁型Feature"允许上传新动态库

**否决理由**：①直接破坏RGS-ADR-0020"拒绝动态链接库加载"——Rust的内存安全保证建立在编译期检查之上，跨越FFI边界加载不受信的动态库会完全绕开这层保证；②绕过CI/CD质量门禁——一次上传的动态库可绕过代码评审、单元测试、集成测试；③历史教训——曾在PH-3的插件机制评估中明确否决该路径，本ADR无理由重新打开此问题。

**采纳路径**：补丁型Feature上线时**仅**可走两条合规路径（沿用RGS-ADR-0020）：①编译期特性开关插件——补丁代码随主干一同编译，通过FF运行时开关plug/unplug；②沙箱脚本——补丁以Rhai脚本形式承载，沙箱权限模型不允许任意内存访问。**不**允许上传新动态库。

### 3.6 COC UI作为VIZ的子页面

**否决理由**：①RGS-REQ-024 VIZ域的无限画布是**只读**拓扑呈现，**不**含写操作（plug/unplug、灰度、回滚）——COC UI需要的是含写操作的控制台，与VIZ的语义不同；②VIZ的"复用RGS-REQ-008可观测性数据"假设其渲染对象是只读数据，COC UI的写操作无法纳入此假设；③粒度混淆——若COC UI作为VIZ子页面，用户会期望"画布的所有元素都支持点击写操作"，但实际只有"功能矩阵"页面支持写操作，UX上不一致。

**采纳路径**：COC UI作为GM后台的**新增顶级页面**，**复用**VIZ的无限画布渲染能力呈现"依赖图/订阅关系图"（FR-COC-003），**不**作为VIZ的子页面。两者关系是"渲染能力复用"而非"页面归属"。

## 4. 结果与代价（Consequences）

**获得**：
- 管理员获得统一的集群运营面——"功能矩阵首页+事件流+灰度面板+回滚面板"四件套，使"上线/下线/热插拔/回滚"四类操作在COC UI中可见、可控、可追溯
- 事件流获得中心治理面——事件注册表、Schema目录、订阅关系、消费者健康、死信、可重放历史六部分，使"事件无中心治理面"的旧问题得到根治
- 升级获得原子性可视——PFAU的"声明→灰度→确认→完成"四步状态机使"一个功能从版本A升级到版本B"在管理员看来是一个不可分割的、有开始时间与完成时间的操作
- 既有ARC-018/021/042/019四块方针不再各自独立——它们被Feature这棵统一树收束，避免升级粒度混乱

**付出**：
- 新增一个gRPC服务（ClusterOpsService）——需独立维护、版本管理、可观测性接入
- 新增若干`admin_db`表（`feature_registry`/`feature_version_history`/`event_schema_registry`/`event_producer_registry`/`pfa_run_state`等）——增加`admin_db`的存储与维护成本，但避免了新建独立DB
- COC UI的UX设计复杂度——需在"统一操作面"与"避免SRE倾向通过COC UI执行所有操作"之间平衡（见RSK-COC-003）
- 各App的事件Publisher SDK须增加"未注册事件类型fail-fast"实现（FR-CEM-002）——增加少量实现成本

**遗留**：
- TBD-COC-001：无限画布前端选型待定（复用VIZ既有选型还是独立选型）
- TBD-COC-002：PFAU的"补丁型Feature"是否需要"金丝雀测试"作为强制门禁，待PH-7前评估
- RSK-COC-001：CI校验脚本`scripts/check-cem-coverage.sh`需新增，定期扫描Publisher调用点比对`event_registry`
- RSK-COC-002：PFAU超时阈值在PH-7前根据实测调整
- ISS-092：COC UI尚未做OLU运维负荷核算（与ISS-065同类）
