## 1. 背景（Context）

PostgreSQL的存储过程/触发器能把逻辑推到数据库层执行，在某些场景下性能更好、且能强制约束。但数据库中的逻辑不受Rust类型系统保护、不进入常规代码评审与测试覆盖、难以版本管理、且在迁移时极易被遗漏。

## 2. 决定（Decision）

**业务逻辑一律不入库**。存储过程与触发器的允许边界极窄：仅限**一行以内的赋值级约束触发器**（如自动维护`updated_at`），且每一项例外须在对应DTL文档登记（触发器名/所在表/具体逻辑/评审人/ADR编号），并经额外评审。

任何含条件分支（`IF`）、循环、或跨表业务判断的数据库端代码，一律不批准。

## 3. 曾考虑并否决的方案（Alternatives Considered）

### 3.1 允许存储过程承载事务性业务逻辑

能减少应用与数据库往返，某些批量操作性能显著更好。否决理由：本项目的核心业务逻辑（经济结算、状态机迁移）恰恰是最需要类型安全、单元测试与代码评审的部分，把它们放进数据库等于让最关键的代码脱离全部质量保障手段。性能收益可通过批量接口与连接池优化取得，无需牺牲这一点。

### 3.2 完全禁止一切触发器与存储过程（零例外）

规则最清晰，无解释空间。否决理由：`updated_at`这类纯机械的赋值放在应用层需要每个写路径都记得处理，遗漏时产生的是静默的数据质量问题；用触发器强制反而更可靠。ISS-033曾提出收敛为零例外，评估后认为极窄例外的收益大于其风险，但**风险确实存在**——见下方RSK-DBS-001。

## 4. 结果与代价（Consequences）

**获得**：业务逻辑全部在Rust侧，享有类型检查、测试、评审、`cargo audit`的完整保障；数据库迁移不必担心逻辑遗漏。

**付出**：部分批量操作的性能不如数据库端实现；`updated_at`类例外需要逐项登记，有流程成本。

**已登记风险（RSK-DBS-001）**：极窄例外的边界会被逐步放宽——顺手在触发器里加一个`IF`是极自然的演进。缓解手段是登记表＋AC-DBS-004审查，但这依赖人执行；本决策承认该风险未被结构性消除。ISS-033（是否收敛为零例外）保持开放。
