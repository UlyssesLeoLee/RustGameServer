## 1. 背景（Context）

实时游戏服务端必须先确定"并发单元的粒度"，此后的线程模型、状态所有权、锁策略、跨对象交互方式全部由它派生，事后更改代价极高。本项目需要支撑同场景内数十至上百名玩家的高频交互（移动、战斗判定），同时要满足DR-007的乐观并发与ARC-005的Single-Writer保证。

粒度选择直接决定了两件事：一次tick内谁持有可变状态的独占写权限；两个实体交互时是否需要跨并发单元通信。

## 2. 决定（Decision）

以**场景（Scene）为Actor粒度**：每个场景是一个独立Actor，拥有该场景内全部实体状态的独占写权限，串行执行tick循环；玩家、NPC、投射物等在场景内部一律作为**ECS实体**存在，不各自成为Actor。

跨场景交互（如切换场景）通过场景Actor之间的消息传递完成，不共享可变状态。物理落地见RGS-DTL-001§5.1 tick循环伪代码。

## 3. 曾考虑并否决的方案（Alternatives Considered）

### 3.1 每个玩家一个Actor

当时的直接诱因是"玩家是天然的并发边界，且可按玩家水平扩展"。否决理由：同场景玩家之间的交互（碰撞、命中判定、AOI可见性）是**高频且必须一致**的，若每个玩家独立持有状态，一次命中判定就要跨两个Actor往返，且需要额外的一致性协议才能避免"A认为打中、B认为闪避"。这把本可以在单线程内O(1)完成的判定变成了分布式一致性问题，收益（更细的并行度）远小于代价。

### 3.2 单线程全局世界（不划分Actor）

最简单、无并发问题。否决理由：无法利用多核，单进程吞吐被单核性能锁死，与REQ-025的容量分级目标（T2以上）直接冲突。且一个场景的卡顿会拖累全世界。

### 3.3 按空间区域（Region/Grid）划分Actor，跨区域实体迁移

比场景更细的粒度，理论上并行度更高。否决理由：引入了"实体跨边界迁移"这一持续存在的复杂性——迁移中的实体归属、边界处的AOI跨区查询、迁移期间的消息重排，都是长期的正确性负担。而本项目的场景本身已是天然的强隔离边界（玩家不会同时存在于两个场景），场景粒度已能提供足够并行度。ARC-014"未证明必要不引入复杂性"直接适用。

## 4. 结果与代价（Consequences）

**获得**：场景内的一切交互都是单线程串行的，不需要任何锁；`session_epoch`（ARC-005）与tick序号共同提供了清晰的写权限归属；ECS布局（`bevy_ecs`）带来良好的缓存局部性。

**付出**：单个场景的承载上限即为单核性能上限——超大规模同屏（如千人同场景）无法靠本模型解决，须由REQ-025的分片与容量分级在**场景之上**处理，而非在场景之内。这是本决策明确接受的边界，不视为缺陷。

**不可逆性**：高。一旦业务代码建立在"场景内无锁"假设上，改为更细粒度需要重写全部实体交互逻辑。
