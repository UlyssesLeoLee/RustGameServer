## 1. 背景（Context）

本项目由极小团队维护却规划了26个域。运维负荷（部署单元、监控面、备份对象、升级对象、故障处置面）随域数量增长，但团队规模不变。NFR-OP-010原本表述为一个「目标」，而目标在压力下不具约束力——每个域单独看都只增加一点点运维面，累积起来无人负责。

## 2. 决定（Decision）

把NFR-OP-010由**目标**改为**预算**：定义运维负荷单位（OLU），为全系统设定总量上限，每个新增常态运维面须**申领**OLU并记入附件D§5台账；台账余额不足时，新增运维面须先回收既有负荷或经负责人显式加预算，不得默认放行。

配套：涉及新增常态运维面的ADR必须载明ARC-014判定证据与OLU估算及申领后余额，**缺任一项不得批准**（附件D§3.1）。

## 3. 曾考虑并否决的方案（Alternatives Considered）

### 3.1 保持为软性目标，靠架构评审把关

无需建立台账与申领流程。否决理由：软性目标的失效模式已被本项目自身验证——ISS-032记录的预算超支正是在目标状态下累积产生的，且直到建立台账才被发现。评审无量化基准时无法拒绝任何单项申请，因为每一项单独看都合理。

### 3.2 限制域的数量上限（如设定最多15个域）

更简单直接。否决理由：域的数量与运维负荷不成正比——一个纯逻辑域（如PPL前后处理管道，依附既有服务）几乎不增加运维面，而一个自带数据库与独立部署的域增加很多。按域计数会同时错杀轻量域并放行重量域。

## 4. 结果与代价（Consequences）

**获得**：运维负荷从不可见变为可见且可拒绝；Dual-Mode OLU模式（RGS-BAS-010§3.9）进一步把部署即产生的基线负荷与开关开启才产生的增量负荷分开核算，使默认关闭的域能诚实计价。

**付出**：OLU估算本身有主观性，不同人估算同一组件可能差异不小；申领流程增加了新增域的前置工作。

**当前的真实缺口（ISS-065）**：26个域中**13个从未做过OLU核算**。这意味着台账余额（当前+41／开启态+34）是在不完整的分母上算出的——数字本身精确，但覆盖面残缺。本决策的机制成立，但其执行目前只覆盖了一半的域，不应据台账余额认为负荷已受控。
