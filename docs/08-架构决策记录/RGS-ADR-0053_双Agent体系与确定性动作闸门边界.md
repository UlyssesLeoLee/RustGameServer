## 1. 背景与问题陈述

在 `RustGameServer` 的 5 域全开架构下，系统运维复杂度与客服支持压力显著提升：
1. **OLU 预算赤字**：初始测算 SRE 运维负荷达 22 人·天/周，超出 2 SRE 编制上限。
2. **all-reachable 升级卡死痛点（DEC-001）**：单节点瞬时网络抖动容易导致全局 PFAU 升级进入 Paused 停摆。
3. **工单与掉单对账延迟**：玩家充值与资产掉单排查链条长，跨网关/Outbox/Ledger 手工检索耗费海量人力。

---

## 2. 候选决策内容（待审批）

1. **候选：引入双 Agent 协作架构**：
   - **SRE 运维 Agent**：负责告警降噪、拓扑根因分析（RCA）及 PFAU 亚健康节点自动隔离（Quarantine Pool）。
   - **客服 Agent**：负责 7×24h 智能咨询应答、资产对账自动化及小额补偿安全发放。
2. **候选：单向感知与 L0 确定性动作闸门（Action Gate）**：
   - Agent 位于 L3/L4 智能层，**严禁直连生产数据库与底层写接口**。
   - 所有自愈或补偿操作统一封装为结构化 `ActionIntent`，由 Rust 编写的 **L0 确定性闸门**进行签名、防重放、单人/全局配额与黑白名单强校验后原子执行。
3. **候选：Quarantine Pool 机制**：
    - 当某节点因网络抖动超时阻断 PFAU 升级时，当前批次**必须保持 Paused**；SRE Agent 只能提交隔离建议。隔离经 Kubernetes 健康事实、L0 确定性校验、具名人工记录后，至多可作为**新批次**成员快照的输入；`RGS-DTL-031` 必须定义此流程并保留 all-reachable 约束，Agent 不得自动绕过 Paused 条件。

## 3. 代价与收益对比

| 维度 | 收益 | 代价 / 风险 | 缓解措施 |
|---|---|---|---|
| **运维负荷 (OLU)** | 候选缓解措施；不得在证据前宣称由 22 人·天/周降至 ~12 人·天/周 | Agent 自身部署与维护成本待测 | 采用标准化容器编排与轻量化 SLM/LangGraph 模型，并以实际工时复核 |
| **升级可用性** | 候选机制可辅助定位亚健康节点；不得绕过 all-reachable 的暂停语义 | 被隔离节点需事后自动化修复或重建 | 配合 K8s 自动化 Pod 重启流水线闭环，并用故障注入验收 |
| **玩家满意度** | 候选目标为缩短掉单与常见问题处理时间，实际时延待测 | LLM 幻觉可能生成错误回答或过度补偿 | 严格限定小额单人配额，高额争议强制升级人工 |
