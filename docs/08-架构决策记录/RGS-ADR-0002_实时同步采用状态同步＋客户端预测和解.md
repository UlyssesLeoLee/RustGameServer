## 1. 背景（Context）

网络游戏的同步模型是与ADR-0001同级的根决策，决定了协议形态、带宽量级、作弊防护方式、以及客户端SDK的复杂度。两大主流路线——确定性帧同步（Lockstep）与状态同步（State Sync）——在正确性模型上是互斥的，不存在渐进迁移路径。

本项目的约束：需要服务器权威判定（ARC-005/FR-AD-004反作弊前提）、需要容忍玩家网络质量差异、需要支持中途加入与断线重连。

## 2. 决定（Decision）

采用**状态同步**：服务器持有权威状态，按tick广播状态快照（含AOI裁剪与量化压缩，ARC-004）；客户端执行**预测（Prediction）**以掩盖RTT，并在收到权威快照后执行**和解（Reconciliation）**回滚重放本地未确认输入。

客户端预测的存在**不**削弱服务器权威：客户端预测结果与服务器判定不一致时，一律以服务器为准回滚。

## 3. 曾考虑并否决的方案（Alternatives Considered）

### 3.1 确定性帧同步（Lockstep）

带宽极低（只传输入）、天然一致，是RTS与格斗游戏的主流选择。否决理由有三，任一独立成立：①**确定性要求**——全端必须逐位一致的浮点行为，跨Bevy/Unity/UE三引擎（ARC-024）实现这一点代价极高且极脆弱；②**反作弊**——帧同步下客户端持有完整世界状态，透视类作弊无法从协议层防御，与本项目ANT域（ARC-043）依赖"服务器权威校验产生检测信号"的整体设计冲突；③**断线重连与中途加入**——需要完整状态快照机制，等于又实现一遍状态同步。

### 3.2 纯状态同步、不做客户端预测

实现最简单，无和解逻辑，无回滚重放。否决理由：玩家操作到画面反馈之间必然存在一个完整RTT的延迟，在动作类交互中体感不可接受。预测/和解的复杂度是为可玩性付出的必要代价，属于ARC-014意义上"已证明必要"的复杂性。

### 3.3 状态同步 + 服务器回滚（Server-side Rollback / Lag Compensation）

并非与本决策互斥，而是一个**尚未决定**的增量。本ADR不对其表态：是否引入命中判定的服务器侧回退补偿，取决于最终玩法形态（射击类几乎必需，非射击类通常不必），留待玩法确定后另行决策，不在本ADR中预先绑定。

## 4. 结果与代价（Consequences）

**获得**：服务器权威天然成立，为ARC-043反作弊信号采集提供了判定源；客户端网络质量差异被局部化（差网玩家自己回滚更多，不拖累他人）；断线重连与观战只需下发快照。

**付出**：带宽显著高于帧同步，必须靠AOI裁剪（G-003）与量化位打包（ARC-004）压制，这两项因此从"优化"变为"必需"；客户端SDK必须实现预测缓冲与回滚重放，是SDK复杂度的主要来源（ARC-024/RGS-DTL-008）。

**遗留风险**：RSK-003登记的"实时同步方式细节未定导致客户端开发停滞"——本ADR确定了路线，但预测缓冲深度、和解触发阈值等参数仍待实测，见RGS-BAS-001§4.2。
