## 1. 背景（Context）

DDD限界上下文的切分决定了事务边界：同一上下文内可用单库事务保证原子性，跨上下文则必须走Saga（ARC-011）并接受最终一致性与补偿逻辑。

道具与货币在业务上高度耦合——绝大多数经济操作（购买、交易、任务奖励、兑换码）**同时**变更两者，且要求"要么都成、要么都不成"。

## 2. 决定（Decision）

道具与货币归入**同一个限界上下文（EC）、同一个物理数据库（`economy_db`）**，共享事务边界。`wallets`／`inventory_items`／`transaction_ledger`三表同库，`CommitTransaction`在单个数据库事务内完成余额变更、道具变更与流水写入（RGS-DTL-001§3.2）。

## 3. 曾考虑并否决的方案（Alternatives Considered）

### 3.1 道具与货币各自独立限界上下文

更符合"小上下文"的直觉，各自演进自由度更高。否决理由：会把"扣钱发道具"这一**最高频**的核心操作变成跨上下文Saga，即每一次购买都需要补偿逻辑、都存在中间不一致窗口、都要处理补偿失败的升级路径。这是把架构上最不该出问题的路径变成了最脆弱的路径。ARC-011明确Saga应用于"确实跨上下文的长流程"，而非高频原子操作。

### 3.2 统合上下文但分库（同上下文、两个物理DB）

保留逻辑统合、物理隔离。否决理由：PostgreSQL跨库无法做单事务，等于保留了分离方案的全部代价却没有获得独立演进的收益，是两头不讨好。

## 4. 结果与代价（Consequences）

**获得**：经济操作的原子性由数据库事务直接保证，`transaction_ledger.request_id`的UNIQUE约束成为幂等性的物理强制层（RGS-DTL-001§3.1），无需应用层补偿。

**付出**：EC上下文承载了较多业务，是本系统中最"大"的上下文之一；道具系统与货币系统无法独立扩容或独立部署。这一代价被判定为可接受——两者的负载特征本就同源（同一批经济操作驱动）。

**边界声明**：交易系统（ARC-032）、内购（ARC-038）虽涉及经济，但其**流程**跨越EC之外（涉及平台、社交、支付），故仍走Saga；本决策只统合"道具与货币这两类资产本身"的存储与事务边界。
