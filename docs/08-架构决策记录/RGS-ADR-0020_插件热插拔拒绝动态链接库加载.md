## 1. 背景（Context）

运营活动与临时玩法要求「不重启服务即可上线/下线」，这是热插拔需求的来源。Rust生态实现热插拔的直接手段是`dlopen`动态加载`cdylib`，但Rust没有稳定ABI。

## 2. 决定（Decision）

**明确拒绝动态链接库加载**。热插拔通过两种受限形态实现：①**特性开关插件**——逻辑随主程序一同编译，运行时由配置开关控制启停；②**沙箱脚本插件**——在受限脚本引擎内运行（选型见RGS-DTL-005§7：Rhai），仅可调用显式注册的白名单宿主函数。

产生永久事实（道具/货币/购买/交易）的操作，脚本**不得**直接写库，必须经`EconomyService.CommitTransaction`既有路径（RGS-DTL-005§3.2以类型系统强制）。

## 3. 曾考虑并否决的方案（Alternatives Considered）

### 3.1 `dlopen` 加载 cdylib 插件

真正的「任意Rust代码热加载」，能力最强。否决理由有三：①**Rust无稳定ABI**——插件与宿主必须用完全相同的编译器版本与依赖版本构建，否则是未定义行为而非编译错误，这类故障在生产中表现为随机内存损坏，几乎无法排查；②**无隔离**——加载的代码与宿主同进程同权限，一个插件的空指针即导致整个场景进程崩溃，与ARC-021故障隔离要求直接冲突；③**无法真正卸载**——实践中`dlclose`后仍持有静态变量/线程/TLS，所谓热插拔实际只能拔不能卸干净。

### 3.2 WASM沙箱（wasmtime）承载插件

隔离性优于dlopen，且有稳定ABI。否决理由：以本项目当下的插件需求（活动配置、临时玩法规则）而言，WASM引入了完整的工具链与宿主绑定层，属ARC-014意义上未证明必要的复杂性；且WASM与宿主间的数据往返成本高于嵌入式脚本。**本方案未被永久排除**——若将来插件复杂度确实增长到脚本引擎无法承载，WASM是首选升级路径，届时应另立ADR。

### 3.3 完全不做热插拔，一律走发布流程

最简单最安全。否决理由：运营活动的上线节奏与发布窗口不匹配是真实业务约束，一刀切拒绝会把压力转移为绕过流程发布，反而更危险。

## 4. 结果与代价（Consequences）

**获得**：插件能力被限制在可枚举的白名单内，故障面可控；`ScriptCallContext`的`session_epoch`/`request_id_seed`为私有字段，**结构上**不存在脚本覆盖会话世代的通道（RGS-DTL-005§3.2），而非依赖实现者自觉。

**付出**：插件能做的事被显著限制，复杂玩法无法以插件形态交付，仍须走正常发布；白名单函数目录需要随业务持续维护。

**遗留**：TBD-PLG-001（引擎选型）已于RGS-DTL-005§7决定为Rhai；白名单函数完整清单为持续增长项，不在设计阶段一次性确定。
