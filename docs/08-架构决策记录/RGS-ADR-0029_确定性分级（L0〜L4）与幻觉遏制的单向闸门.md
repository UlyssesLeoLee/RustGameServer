## 1. 背景（Context）

一旦系统中存在任何非确定性组件（LLM、启发式模型、外部推荐服务），就出现一个结构性问题：它的输出可能是错的，且错得**看起来合理**。若无强制边界，这类输出会沿着调用链渗透进确定性路径，最终表现为「系统偶尔做出无法解释的决定」。

本项目当下的具体触发点是智能层（ARC-027），但问题本身不限于它。

## 2. 决定（Decision）

建立**确定性分级 L0〜L4**，并规定**单向闸门**：低确定性等级的输出，必须经过部署在**消费者侧**的确定性闸门校验，才可进入高确定性等级的路径；闸门只允许白名单内的枚举值通过，不允许自由文本或未声明的动作类型直接生效。

**闸门必须部署在消费者侧**，不得由生产者自证——生产者侧的自校验在生产者本身出问题时同时失效。

**本决策独立于ADR-0026成立**：即便CR-011不获批、智能层永不开启，本分级体系对未来任何非确定性组件仍然适用。

## 3. 曾考虑并否决的方案（Alternatives Considered）

### 3.1 在生产者侧校验（智能层自己保证输出合法）

实现更简单，闸门只需写一处。否决理由：这是自证清白。若智能层因为bug或模型漂移产出越界内容，其自校验逻辑通常在同一进程、同一代码路径内，往往一并失效。闸门的价值恰恰在于它不信任生产者。

### 3.2 靠人工评审兜底，不做机械闸门

灵活，可处理闸门无法表达的复杂判断。否决理由：人工评审不具备可复现性与可审计性，且在量大时必然退化为橡皮图章。人工审核在本项目中被保留在**处置环节**（ARC-043反作弊须GM确认），但那是「谁来做决定」的问题，与「非确定性输出能否进入确定性路径」是两件事，不能互相替代。

### 3.3 完全禁止任何非确定性组件

最彻底。否决理由：会连带排除许多合理用途（如运营分析中的聚类、异常检测的排序建议）。分级的意义正是允许非确定性存在于低等级、且不让它跨越到高等级。

## 4. 结果与代价（Consequences）

**获得**：反作弊分析图的输出被限制为「标记高优先级／标记低优先级／建议驳回」三类只读分类建议，**不含任何执行类动作**（RGS-BAS-025§4.2）；智能层服务账号不具备`AntiCheatCase.status`写权限（IAM/NetworkPolicy双锁）。

**付出**：每个消费方都要实现自己的闸门，存在重复；白名单枚举的扩展需要走评审，降低了迭代速度——这是有意的摩擦。

**局限**：闸门能挡住「越界的动作类型」，挡不住「白名单内但内容错误的建议」——一个被错误标记为高优先级的案件仍会占用GM注意力。这类错误只能靠下游的人工判断吸收，本决策不声称解决它。
