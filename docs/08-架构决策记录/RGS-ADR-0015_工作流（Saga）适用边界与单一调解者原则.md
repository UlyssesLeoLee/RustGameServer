## 1. 背景（Context）

ADR-0007把高频经济操作收进单一事务边界后，仍存在确实跨限界上下文的长流程：内购（平台↔EC↔PL）、玩家间交易（两个玩家的EC状态＋社交确认）、账号删除编排（跨全部库，FR-GOV-010〜013）。这些流程无法用单库事务完成，必须有明确的一致性方案。

同时需要防止的是另一种失控：Saga被当作"跨服务调用的通用写法"到处使用，使系统退化为难以推理的隐式状态机网络。

## 2. 决定（Decision）

两条规则：

1. **适用边界**——Saga**仅**用于确实跨限界上下文、且中间态可被业务接受的长流程。同上下文内的原子操作一律用数据库事务，不得用Saga。
2. **单一调解者（Orchestration，非Choreography）**——每个Saga必须有唯一一个明确的调解者组件持有流程状态并驱动各步骤，禁止"各服务监听事件各自推进"的编排式实现。

## 3. 曾考虑并否决的方案（Alternatives Considered）

### 3.1 两阶段提交（2PC / XA）

能提供跨库强一致，语义最简单。否决理由：2PC在协调者故障时会持有资源锁进入阻塞态，对本项目的实时路径是不可接受的可用性风险；且要求全部参与方支持XA，与"各限界上下文自主选型存储"的方向冲突。

### 3.2 编排式Saga（Choreography，各服务监听事件自行推进）

无中心组件，耦合度看似更低。否决理由：流程逻辑被打散在N个服务的事件处理器中，**没有任何一处能回答"这笔交易现在处于哪一步"**；补偿路径尤其难以推理——失败发生在第3步时，谁负责触发第1、2步的补偿在编排式下没有明确归属。调试与运维成本远高于其节省的耦合。

### 3.3 允许最终一致但不做补偿（失败即遗留不一致，靠对账修）

实现最省。否决理由：本项目涉及货币与道具，遗留不一致即为资产错误；RGS-BAS-016的支付对账机制是**兜底**而非主路径，不能作为常态依赖。

## 4. 结果与代价（Consequences）

**获得**：每个Saga都有唯一可查询的流程状态与明确的补偿责任方；RGS-DTL-001§10.3给出了购买Saga的补偿路径伪代码，RGS-DTL-015给出交易Saga含补偿失败升级分支的完整实现。

**付出**：调解者是有状态组件，本身需要HA与幂等续跑设计；每新增一个跨上下文流程都要显式设计补偿动作，无法自动获得。

**已知缺口**：补偿动作本身失败时的升级路径目前落到人工介入（RGS-DTL-015），尚无自动化兜底——这是有意接受的，因为补偿失败通常意味着更深的状态异常，自动重试可能放大损害。

## 5. 关联

- 落地设计：RGS-DTL-001§10.3（购买Saga）、RGS-DTL-015（交易Saga与补偿失败升级）、RGS-BAS-009§5.2（账号删除跨库编排）
- 前置决策：ADR-0007（先把高频操作收进单事务，Saga才不至于泛滥）
