# 1. 前言

## 1.1 目的

RGS-REQ-001第10章ARC-017已决定"可观测性自PH-1起必须具备"，并在RGS-BAS-001§4.8给出了trace传播载体与指标采集拓扑的**系统级**设计。但截至目前，**尚未定义**：①具体哪些代码路径必须埋点、埋什么维度②日志的字段级规范（字段名、格式、级别）③指标/span/日志三者的命名规范是否统一④采样策略⑤脱敏规则的具体实现方式。若不统一定义，PH-1起各服务各自摸索埋点方式，会导致：跨服务trace因字段命名不一致而无法联查、日志因未脱敏而违反NFR-SE-012、告警因指标命名混乱而无法配置规则。

本文档的目的：将ARC-017的原则**细化为可执行、可检查的埋点与日志规范**，作为PH-1起全部服务（含RGS-REQ-006/007新增的服务与API）编写埋点代码时的唯一依据。

## 1.2 适用范围

本文档适用于本系统全部组件产生的三类可观测性数据：

| 数据类型 | 说明 |
|---|---|
| Trace（追踪） | span、trace上下文传播，对应NFR-OP-001/002、RGS-BAS-001§4.8.1 |
| Metrics（指标） | 计数器、直方图、仪表，对应NFR-OP-003、RGS-BAS-001§4.8.2 |
| Logs（日志） | 结构化事件日志（不含审计日志——审计日志字段规范已由RGS-REQ-001 FR-AD-005/NFR-SE-010与RGS-BAS-003§7独立定义，本文档不重复，仅在§5.4说明两者关系） |

本文档**不覆盖**：告警规则的具体阈值定义（属运维配置，RGS-BAS-003§6.2已声明不属本系统职责）、可观测性基础设施（OTel Collector/指标存储/日志聚合基础设施）具体选型的物理部署（属详细设计与RGS-OPS-001）。

# 2. 术语约定

沿用RGS-REQ-002术语表。本文档新增：

| 术语 | 定义 |
|---|---|
| 埋点（Instrumentation） | 在代码中插入的、产生trace span或metrics数据点的调用 |
| 关联ID（Correlation ID） | 用于跨组件/跨日志条目关联同一业务操作的标识符集合，即NFR-OP-002所列`trace_id`／`span_id`／`request_id`／`player_id`／`event_id`／`workflow_id` |
| 黄金指标（Golden Signals） | 延迟（Latency）、流量（Traffic）、错误（Errors）、饱和度（Saturation）四类指标，业界通用的服务健康度最小指标集 |
| 结构化日志 | 以固定字段（键值对，通常为JSON）而非自由文本形式输出的日志，便于机器检索与聚合 |
| 脱敏（Masking/Redaction） | 对日志中的个人信息/机密信息做遮蔽、哈希化或移除处理，使日志本身不构成信息泄露面 |
| 采样（Sampling） | 出于成本与存储考虑，仅记录/上报一部分trace或日志的策略，与错误/异常路径的**强制全量**采样相对 |

# 3. 背景与课题

| 编号 | 课题 |
|---|---|
| P-LOG-001 | 若各服务自定义日志字段名（如有的用`playerId`有的用`player_id`），日志聚合基础设施无法按字段联查，NFR-OP-008"15分钟内定位故障子系统"的目标无法达成 |
| P-LOG-002 | 若埋点覆盖范围仅凭开发者个人判断，容易遗漏关键路径（如异常分支、降级路径），故障发生时"最需要观测的地方恰好没有埋点" |
| P-LOG-003 | 若日志中直接输出玩家账号、IP、支付信息等个人信息而不脱敏，违反NFR-SE-012与NFR-SE-009，构成合规风险 |
| P-LOG-004 | 若trace采样率设置不当（全量采集导致存储成本失控，或采样率过低导致低频但重要的错误路径不可见），会与NFR-OP-010"运维负荷上限"冲突 |
| P-LOG-005 | 若不同服务对同一概念使用不同的指标命名（如有的叫`request_duration`有的叫`req_latency`），Dashboard与告警规则的复用性会随服务数量增长而急剧下降，与RGS-BAS-002 NFR-MNT-006"模板一致性"的精神相悖 |

# 5. 功能需求

## 5.1 埋点覆盖范围

| ID | 需求 |
|---|---|
| FR-LOG-001 | 全部对外接口（QUIC消息处理、gRPC方法、HTTP/Webhook端点）的入口与出口**必须**产生span，span命名遵循§7 ARC-020的统一规范 |
| FR-LOG-002 | 全部跨限界上下文调用（gRPC客户端调用、事件发布/消费、数据库访问）**必须**作为子span嵌套在发起该调用的父span之下，实现RGS-BAS-001§4.8.1既定的全路径trace贯通 |
| FR-LOG-003 | 全部错误/异常分支（含降级路径，如ARC-007经济服务不可用时的降级、ARC-013背压触发的拒绝）**必须**埋点记录，且**不得**被采样丢弃（同§5.5采样规则的强制全量例外） |
| FR-LOG-004 | 全部黄金指标（延迟、流量、错误、饱和度）**必须**在每个组件的每个对外接口上采集，具体指标目录见RGS-BAS-004§3 |
| FR-LOG-005 | 场景Actor的tick循环**必须**埋点tick耗时、实体数、mailbox深度（对应ARC-001既有决定与ARC-013背压设置位置），但**不得**在每tick产生span（高频路径用指标而非trace，理由见ARC-020否决方案） |

## 5.2 日志字段规范

| ID | 需求 |
|---|---|
| FR-LOG-010 | 全部日志**必须**为结构化格式（JSON或等价的结构化编码），**不得**输出自由文本拼接的日志行 |
| FR-LOG-011 | 日志**必须**包含统一的基础字段集：时间戳、日志级别、服务名（`service.name`）、关联ID（NFR-OP-002所列全部适用字段，视上下文可得性）、日志消息 |
| FR-LOG-012 | 日志级别**必须**统一采用五级：`TRACE`／`DEBUG`／`INFO`／`WARN`／`ERROR`，各级别的使用场景须有统一定义（见RGS-BAS-004§4.2），**不得**每个服务自定义级别含义 |
| FR-LOG-013 | 日志字段命名**必须**统一采用`snake_case`，且同一概念在全部服务中使用同一字段名（如玩家ID统一为`player_id`，不得混用`playerId`/`pid`等变体） |

## 5.3 脱敏与个人信息保护

| ID | 需求 |
|---|---|
| FR-LOG-020 | 日志与trace属性中**不得**明文输出：账号凭证/密码/Token、支付卡信息、精确地理位置、完整IP地址（**应当**保留网段用于风控分析，精确度由详细设计确定） |
| FR-LOG-021 | 玩家标识符（`player_id`／`character_id`）**可以**明文记录（业务排查刚需），但**不得**同时明文记录可直接反推真实身份的信息（如注册邮箱、手机号），此类字段若必须记录须哈希化 |
| FR-LOG-022 | 脱敏规则**必须**在日志产生的埋点代码层面实施（复用标准化日志库的脱敏中间件/字段标注机制），**不得**依赖"事后从日志聚合基础设施中清洗"作为主要防线（同ARC-020否决方案，防止清洗滞后期间已构成泄露） |

## 5.4 与审计日志的关系

| ID | 需求 |
|---|---|
| FR-LOG-030 | 本文档定义的结构化事件日志与RGS-BAS-003§7审计日志（`admin_db.OPERATION_AUDIT`，仅追加）是**两套独立的数据**，前者面向故障排查与分析（可采样、可轮换删除），后者面向合规与不可否认性（不可采样、不可删除）。**不得**用普通日志替代审计要求，也**不得**将审计记录降级为可清理的普通日志 |

## 5.5 采样

| ID | 需求 |
|---|---|
| FR-LOG-040 | Trace**必须**支持可配置的采样率（对正常成功路径），初始值与调整机制留待PH-4负载试验结果确定（TBD-LOG-001） |
| FR-LOG-041 | 错误路径、高危操作（复用RGS-BAS-003§8高危操作定义）、GM指令（RGS-REQ-007全部FR-GM-*）**必须**强制全量采集，不受采样率影响 |

| ID | 类别 | 内容 | 目标值/判定基准 |
|---|---|---|---|
| NFR-LOG-001 | 一致性 | 全部服务的日志字段命名、日志级别定义、span命名**必须**遵循统一规范（复用RGS-BAS-002标准化脚手架自动生成埋点骨架） | 规范漂移须走ADR，同RGS-REQ-006 NFR-MNT-006同等约束 |

# 7. 架构设计方针 ARC-020

本节为需求定义书RGS-REQ-001第10章架构方针体系的延续，编号紧接RGS-REQ-007新增的ARC-019。**决定事项**，变更须经ADR与审批。

## 7.1 ARC-020：埋点与日志的统一规范（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | 全系统的trace span命名、metrics命名、日志字段，**必须**遵循统一的命名与格式规范（RGS-BAS-004给出具体规范表），且该规范**必须**通过标准化脚手架（RGS-BAS-002§4）自动生成的埋点骨架强制落地，**不得**依赖开发者人工记忆规范手动编写 |
| **理由** | 延续ARC-017"可观测性自PH-1起必须具备"的精神，将其从"要不要做"的原则决定，推进到"如何保证做得一致"的执行层规范决定。跨服务的trace/日志联查能力（NFR-OP-001/002/008）的前提是命名一致，若放任各服务自定义，联查能力会随服务数量增长而线性劣化 |
| **脱敏优先于清洗** | 个人信息脱敏**必须**在埋点/日志产生的源头实施，**不得**采用"先明文记录，后续再从日志聚合基础设施批量清洗"的补救型方案——补救方案在清洗完成前存在泄露窗口，且清洗本身可能遗漏未预见的字段组合 |
| **高频路径不产生span** | 场景Actor每tick循环**不得**逐tick产生独立trace span（否则PH-4负载试验规模下span产生速率将远超NFR-OP-010运维负荷上限），高频路径的可观测性**必须**通过指标（聚合后的耗时分布、计数）而非逐次trace实现，个别慢tick可通过指标阈值触发的诊断快照按需捕获（详细机制留详细设计） |
| **否决方案1** | "各服务自行决定埋点方式，事后统一"——同RGS-REQ-006 ARC-018已否决的"事后补齐规范"模式，历史执行率偏低 |
| **否决方案2** | "日志先明文记录个人信息，依赖日志聚合基础设施的访问控制（RBAC）防止泄露"——访问控制是纵深防御的一层，但不能替代源头脱敏，一旦访问控制配置出错（人为失误），明文个人信息立即暴露，风险不可接受 |
| **适用范围** | 本系统内全部限界上下文，含RGS-REQ-006挂载的新限界上下文与RGS-REQ-007新增的GM管控API |

# 8. 验收标准

| ID | 验收标准 |
|---|---|
| AC-LOG-001 | 任取一条跨越网关→运行时→业务服务→数据库→事件基础设施的调用链路，可通过单一`trace_id`在日志聚合基础设施中检索到全部相关span与日志条目（复用NFR-OP-001既有验收标准，本文档细化后仍须满足） |
| AC-LOG-002 | 对日志聚合基础设施中的样本日志做人工抽查，确认账号凭证、支付卡信息等禁止字段（FR-LOG-020）未以明文出现 |
| AC-LOG-003 | 使用标准化脚手架生成的新服务，无需额外手工编码即可产生符合命名规范的span/metrics/日志（验证ARC-020"脚手架强制落地"要求） |
| AC-LOG-004 | 错误路径与GM指令（FR-LOG-041强制全量采集范围）在采样率<100%的配置下仍100%被记录 |
| AC-LOG-005 | 负载试验环境下，日志与trace的存储/索引成本增长速率不导致NFR-OP-010运维负荷上限被突破（依PH-4实测数据判定） |
