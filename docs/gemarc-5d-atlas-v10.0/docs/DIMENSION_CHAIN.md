# 次元チェーン (Dimension Chain) — 1D→2D→3D→4D→5D

> Universal GemArc 5D Design Atlas v10.0
> なぜこの構成か → [設計判断](#1-なぜ-1-つのバスと-1-つのステージなのか)

---

## 0. 要件

> 「5D建立在4D基础上, 4D建立在3D基础上, 2D建立在1D基础上」

これを満たすには、**各次元が独立した世界を持ってはならない**。
独立した世界は「基础上にある」のではなく「隣に並んでいる」だけになる。

---

## 1. なぜ 1 つのバスと 1 つのステージなのか

### 1.1 バス (`src/core/bus.ts`)

全次元の唯一の接続点。各次元は 2 つの役割だけを持つ:

- **上流から状態を読む** — 自分のスコープ (何を描くか / 何を動かすか) を決める
- **自分の状態を公開する** — 下流がそれを読む

### 1.2 ステージ (`src/core/scene-host.ts`)

3D シーンは「3D 次元の持ち物」ではなく、**プロセス内で 1 個だけ存在する共有リソース**。
3D / 4D / 5D はその**ビュー**に過ぎない。

```
SceneHost  … 3D 形状・カメラ・материал・state 適用・focus 退避・ピッキング
d3.ts      … 12 View / 12 ナビゲーション / ラベルモード UI
d4.ts      … 4D エンジン実行 + タイムライン + ステージへの state 適用
d5.ts      … A/B 因果 + ステージへの branch state 適用 + overlay/split
```

WebGL コンテキストが次元切替のたびに作り直されないよう、**canvas 要素は保持したまま
DOM 上の親だけ差し替える** (`SceneHost.attachTo`)。
検証: `tests/e2e/j04-chain.spec.ts` の C0 が **3D / 4D / 5D で同一の canvas id** を確認する。

## 2. 鎖の定義

```
 1D Prompt  ──promptScope──►  2D 無限キャンバス
 2D 選択    ──selection2d──►  3D 空間ステージ
 3D 焦点    ──focus3d─────►  4D Case 実行
 4D Trace   ──trace────────►  5D A/B 因果実験
 5D 分岐    ──branch───────►  3D ステージ (因果オーバーレイ / 分屏)
```

### 2.1 1D → 2D

1D で Prompt を選ぶと、その `nodeEdgeIds` が `bus.promptScopeNodeIds` に出る。
2D はそれを:

- サイドバーの「上流: 1D Prompt 范围」パネルに表示する
- 「聚焦 1D 范围」で選択とフィットを適用する
- 「仅显示 1D 范围」で `visibleNode()` 过滤器経由で表示を限定する

**意味**: 2D は「全部を描く図」ではなく、**1D が定義したスコープを描く図**になる。

### 2.2 2D → 3D

2D でノード/辺を選ぶと `bus.selection2d` に出る。
3D はそれを購読し、対象ノードへカメラを寄せ、**隣接集合だけを強調**して
それ以外を退避・減光する (spec `focus_retreat`)。

**意味**: 3D は 2D の選択を「3D 空間の位置」に翻訳する。2D のグループ (ドメイン) は
3D のフロア (ドメイン) と同じ粒度で一致する。

### 2.3 3D → 4D

3D でノードを選択すると `bus.focus3d` に隣接集合が出る。
4D はそれを購読し、**そのノードを含む Case に自動切替**して再実行する。

**意味**: 4D は「3D で今見ている場所」の了出来ケースを再生する。

### 2.4 4D → 5D

4D が実行した Trace を `bus.publishTrace()` で公開する。
5D は**それをそのまま基準線 (Branch A)** として使う — 同じ Case・同じ seed・同じエンジン。

**意味**: 5D の「介入前」は 4D が再生したものと**同一**である。比較対象がズレない。

### 2.5 5D → 3D (還流)

5D の分岐結果を `bus.publishBranch()` で公開し、ステージに因果提示を適用する。

| モード | 実描画 |
|---|---|
| `Overlay3D` | 分岐ノードをリング色で強調 (ベースラインは凡例参照) |
| `SplitSynchronized3D` | **1 キャンバスを左右に区切り**、左=ベースライン / 右=分岐を**別々の状態で 2 パス描画** (scissor テスト) |

> 以前は受動的な badge だったが、実描画に変更した。

## 3. 2D のデモツアー (認知負荷低減)

2D は 160 ノード / 14 図種 / 6 レイヤーが一度に出る。最初の一歩が分からない。
`src/dims/demo2d.ts` が **Coach Mark** (呼び出し注記) で順に引导する。

| # | ステップ | 実際の操作 |
|---|---|---|
| 1 | 2D 无尽画布 | — (全景をハイライト) |
| 2 | 1D 的 Prompt 决定画什么 | 1D 范围パネルをハイライト |
| 3 | 图层: 一次只看一层 | ポート層を**実際に閉じる** |
| 4 | 点一个节点 | ノードを**実際にフォーカス** (検査器に証拠が出る) |
| 5 | 14 种专业工程图 | **UML_Class を実際に開く** |
| 6 | 2D → 3D | 3D への導入 |

- 対象は**実 DOM を矩形で囲んで**示す (スクリーンショットや仮画像ではない)
- Esc で即解除、←/→ で移動
- `prefers-reduced-motion` なら paketing 静止
- 破棄時は必ず `stop()` して overlay を残さない

## 5. 設計判断

### 5.1 なぜバスを「状態の总线」にしたのか

次元が互いの状態を**直接参照**すると、2D→3D→4D→5D の間に暗黙の循環参照が生まれる
(4D は 3D -engiene に、3D は 4D の trace に…). バスを通すと:

- 依存は 1 方向に保たれる
- どの次元がどの状態を読んでいるかが**明示的**になる
- 4D → 5D の「同一 trace である」ことが構造的に保証される

### 5.2 なぜ stage をプロセス共有にしたのか

WebGL コンテキストは 1 個のキャンバスに 1 個だけ。4D が自分の SVG 投影を持つと
「4D は 3D の上に立っている」ことにはならず、**別の世界**になる。
共有ステージにすることで:

- 4D の state 適用が 3D の宝石とリングに**直接見える**
- 5D の split が「同じシーンを 2 パスで描く」意味になる
- 認知負荷が下がる (1 つの空間完結)

### 5.3 既知の限界

- 5D の `Overlay3D` / `SplitSynchronized3D` は**同じステージの同じカメラ**を使う。
  独立した 2 カメラ (真の分割) ではない。
- 4D の Case 実行は**明示的なステップ列**駆動であり、グラフ自動走査ではない。
  グラフ改写 (AddInteractiveElement) は**グラフ構造**を変えると計算は正当に
  影響しうるが、Case のステップ列がchanged を参照しないと結果は変わらない。
  これは仕様上の未確定事項であり、BACKLOG に残す。
- 3D ステージは**プロセス内 1 個**。複数タブで開いた場合はそれぞれ独立。
