# 1. 前言

## 1.1 目的与范围边界

RGS-REQ-007（运维与GM后台管控）与RGS-REQ-013（体系治理）定义的是**GM主动发起**的管控能力（封禁、禁言、补偿发放等）。RGS-REQ-017新增的玩家举报（FR-GSM-030〜033）定义的是"信号来源"而非处理流程本身。这些文档均未涉及**玩家主动发起申诉、客服受理并跟进处理**这一完整闭环——即工单从创建、分派、处理到关闭的生命周期。同时，RGS-REQ-016的内购付费（FR-LBY-024〜若干号段）只定义了购买与权益发放，未涉及支付成功后与支付服务商侧记录不一致（掉单、重复扣款、延迟到账）时的对账与补偿机制。本文档补齐这两处空白。

## 1.2 判定原则（先声明，避免与既有模块混淆）

- 工单处理的**处罚执行权**不新增：客服/GM通过工单调查后若需要处罚（封禁/禁言/道具回收），**必须**经由既有`AdminService`（`BanAccount`／`MuteChat`）执行，工单系统本身**不得**成为独立的处罚执行入口（与RGS-REQ-017 FR-GSM-032同类原则的再次应用）
- 支付对账**不新增**支付网关：本文档只处理"本系统内部订单记录"与"支付服务商回调/对账文件"之间的一致性核对，不涉及支付网关本身的选型（那属于RGS-REQ-016§7既有范围）
- 工单与举报的关系：举报（FR-GSM-030）是"针对其他玩家"的信号；工单是"玩家针对自己账号问题（如误封、道具丢失、支付异常）"的申诉入口，两者**共享**同一套客服受理基础设施，但触发场景不同

## 1.3 关联文档

| 文档 | 关系 |
|---|---|
| RGS-REQ-007 | GM后台既有RBAC与操作留痕机制，本文档的工单处理复用其执行通道 |
| RGS-REQ-013 | 复用FR-GOV-001类"无处罚旁路"原则 |
| RGS-REQ-016 | 内购购买与权益发放（FR-LBY相关号段），本文档补齐支付对账 |
| RGS-REQ-017 | 复用RGS-BAS-003§7审计设计、举报信号与工单申诉的边界区分 |

# 2. 术语约定

| 术语 | 定义 |
|---|---|
| 工单（Ticket） | 玩家发起的、针对自身账号问题的申诉记录，具有生命周期状态 |
| 对账（Reconciliation） | 核对系统内部订单记录与支付服务商侧记录是否一致的过程 |
| 掉单 | 玩家已完成支付（支付服务商侧有记录），但系统内部订单未收到对应的成功回调，导致权益未发放 |

# 3. 背景与课题

| 课题编号 | 课题 |
|---|---|
| P-SUP-001 | 玩家账号问题（误封、道具丢失、支付异常）目前只能通过站外渠道（社群/邮件）反馈，缺少系统内的结构化申诉入口，GM后台无法追踪处理进度与SLA |
| P-SUP-002 | 内购支付成功但权益未到账（掉单）时，缺少检测与补偿机制，只能等玩家主动反馈后人工排查，处理时效不可控 |
| P-SUP-003 | 若客服工单被赋予直接执行处罚的能力，会与既有`AdminService`统一入口原则（RGS-REQ-007 ARC-019）产生第二个处罚通道，重演RGS-REQ-013已收口过的"判定权分散"问题（P-GOV-004同类模式） |

# 5. 功能需求：客服工单

| 编号 | 需求 |
|---|---|
| FR-SUP-001 | 玩家**必须**能创建工单，指定问题类型（枚举：账号封禁申诉／道具异常／支付异常／其他），并提供上下文描述与可选证据（如订单号/对局ID） |
| FR-SUP-002 | 工单**必须**有状态机：`待受理→处理中→待玩家补充信息→已解决／已驳回`，非法迁移**必须**被拒绝（同RGS-REQ-001第8章状态机纪律） |
| FR-SUP-003 | 工单**必须**按问题类型分级SLA（如支付异常优先级高于其他类型），超时未受理**应当**触发升级提醒（复用RGS-BAS-003§6告警推送通道） |
| FR-SUP-004 | 客服/GM在工单中做出的处理决定（如判定误封需解封）**必须**通过既有`AdminService`执行，**不得**在工单系统内直接修改账号状态（新设执行旁路） |
| FR-SUP-005 | 工单的全部操作（创建/分派/回复/关闭）**必须**留痕（复用RGS-BAS-003§7审计设计），关闭时须记录处理结论摘要 |
| FR-SUP-006 | 玩家**必须**能查询自己提交的工单列表与当前状态，**不得**要求通过站外渠道才能获知处理进度 |
| FR-SUP-007 | 系统**应当**对同一账号短时间内的重复工单提交做去重/合并提示（复用RGS-REQ-017 FR-GSM-033同类去重思想），防止刷单式骚扰 |

# 6. 功能需求：支付对账

| 编号 | 需求 |
|---|---|
| FR-SUP-010 | 系统**必须**记录每笔内购订单的内部状态（`待支付→已支付→已发货`／`已支付→发货失败→待补偿`），复用RGS-REQ-001第8章状态机纪律 |
| FR-SUP-011 | 系统**必须**定期（可配置周期，默认每小时）与支付服务商侧的交易记录做对账比对，识别"服务商侧已支付但内部订单未到`已发货`终态"的掉单场景 |
| FR-SUP-012 | 掉单被识别后，**必须**自动触发补偿发放流程，补偿发放**必须**复用既有FR-EC-003确定请求路径，**不得**新设发放旁路（同RGS-REQ-017 FR-GSM-013同类原则） |
| FR-SUP-013 | 若自动补偿失败或涉及金额超过阈值（可配置），**必须**转为FR-SUP-001定义的工单流程走人工复核，**不得**无限制自动发放 |
| FR-SUP-014 | 对账记录**必须**留存审计日志（复用RGS-BAS-003§7），供财务/运营核对 |
| FR-SUP-015 | 对账过程**不得**成为支付主路径的同步阻塞点——对账**必须**是异步批处理，玩家支付成功后的即时发货体验不受对账周期影响 |

# 8. 架构设计方针 ARC-033

## 8.1 ARC-033：客服处置权限收口与支付对账的最终裁定源（重要决定）

| 项目 | 内容 |
|---|---|
| **决定** | ①客服工单**不得**成为独立于`AdminService`的第二个处罚/账号状态变更执行通道，全部执行动作**必须**回落至既有`AdminService`（同ARC-019统一入口原则）②支付对账的**最终裁定源**是**支付服务商侧记录**（服务商已确认支付成功即视为权威事实），系统内部订单状态须向其收敛，而非反向要求玩家自证 |
| **理由** | ①与ARC-019"控制平面统一入口"是同一类问题在新场景下的重现，若不明确收口，会重新分裂出判定权分散的问题（同P-GOV-004历史教训）②支付场景下，玩家相对系统处于弱势地位（无法自证"我已支付"），若以内部订单状态为准而非支付服务商记录为准，会产生"明明付款成功却投诉无门"的信任危机，此为对财务风险与玩家信任风险的权衡结果 |
| **超额阈值人工复核** | 自动补偿设置金额上限（FR-SUP-013），超限**必须**转人工，防止对账逻辑缺陷导致大额资金自动流出 |

# 9. 验收标准

| 编号 | 内容 |
|---|---|
| AC-SUP-001 | 工单全生命周期（创建→受理→处理→关闭）在真实环境中可稳定运行，状态机非法迁移被拒绝 |
| AC-SUP-002 | 工单处理决定验证：客服/GM的处理动作均通过`AdminService`执行，工单系统内无独立执行旁路 |
| AC-SUP-003 | 掉单检测与自动补偿故障注入试验：模拟"支付成功但内部订单未发货"场景，验证在NFR-SUP-002时限内自动补偿到账，且不重复补偿 |
| AC-SUP-004 | 超阈值补偿转人工复核验证：模拟超过配置阈值的掉单，验证系统拒绝自动发放并生成待处理工单 |
